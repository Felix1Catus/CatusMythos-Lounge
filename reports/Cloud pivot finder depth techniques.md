# Cloud Pivot Finder — Depth Techniques: Detection Signature Reference

## Overview

This report synthesizes three research-notes files into a single detection-signature reference for the cloud-pivot-finder scanner's metadata-SSRF and subdomain-takeover modules. For each of three topic areas — AWS IMDSv2/ECS metadata, container/orchestrator metadata endpoints, and subdomain-takeover fingerprints — it documents the exact HTTP status code, header, body-string, or DNS signature a defensive scanner should check for, what that signature indicates about the target's configuration, and the CVE or vendor-advisory source backing the claim. Entries are written as "scanner checks for X, which Y documents as indicating Z" rather than as exploitation walkthroughs, consistent with CVE-advisory-style documentation for a developer implementing detection logic. A closing "research gaps" section lists what the underlying notes flagged as unconfirmed, so the implementer knows which checks need empirical verification before being hard-coded as high-confidence findings.

## 1. IMDSv2 and ECS/Fargate metadata

| Signature to detect | What it indicates | Source citation |
|---|---|---|
| Tokenless `GET /latest/meta-data/` returns **200** with metadata body | IMDSv1 reachable, or `HttpTokens=optional` (IMDSv2 not enforced) — immediate credential exposure via SSRF, no token dance needed | Datadog Security Labs: Misconfiguration Spotlight: IMDS; Orca Security cloud-risk pages |
| Tokenless `GET` to a metadata path returns **401 Unauthorized** + response header `X-aws-ec2-metadata-token-required: true` | `HttpTokens=required` (IMDSv2 enforced) — most specific, reliable signal distinguishing "v2 enforced" from "v1/optional"; a bare non-401 status is not sufficient on its own | Synthesized from Datadog Security Labs / Orca Security; corroborated by an Ignition (CoreOS/Fedora) patch comment noting IMDSv2-only probing returns 401 |
| Connection error / non-401 failure (not 200, not 401) | IMDS likely disabled entirely, or the SSRF primitive cannot reach the 169.254.169.254 link-local range at all — should be logged distinctly from "v2-enforced" | Synthesized from search results (not independently verified against a single AWS primary source — treat as moderate confidence) |
| PUT to `/latest/api/token` with `X-Forwarded-For` header present | Rejected by design — IMDSv2 explicitly refuses token-request PUTs carrying `X-Forwarded-For`, specifically to defeat misconfigured reverse-proxy relay | HackTricks (via WebSearch synthesis, corroborated by Datadog) |
| `X-HTTP-Method-Override: PUT` sent on a GET/POST to `/latest/api/token` | Tested negative — IMDS itself returns `405 Method Not Allowed`; this header is only relevant if a WAF/proxy/load-balancer (not the raw IMDS service) parses and rewrites the method | Appsecco: AWS EC2 IMDSv2 versus an esoteric HTTP method |
| Hop-limit / network-mode combination: ECS `bridge` mode + hop-limit 1 | IMDS **blocked** for the task (extra hop through Docker's bridge exceeds the limit) | Latacora: ECS on EC2 — Covering Gaps in IMDS Hardening (Oct 2025) |
| Hop-limit / network-mode combination: ECS `awsvpc` or `host` mode + hop-limit 1 | IMDS **reachable** — these modes are NOT protected by hop-limit 1 despite it being the commonly assumed mitigation | Latacora: ECS on EC2 — Covering Gaps in IMDS Hardening (Oct 2025) |
| `ECS_AWSVPC_BLOCK_IMDS=true` present in `/etc/ecs/ecs.config` (or confirmed via config read) | Documented AWS remediation that actually closes the `awsvpc`-mode gap; absence of this setting on `awsvpc` tasks should be flagged | AWS documentation, via Latacora (Oct 2025); Latacora also found AWS "ECS Managed Instances" sets this to `true` by default |
| Unauthenticated `GET 169.254.170.2<AWS_CONTAINER_CREDENTIALS_RELATIVE_URI>` returns credential JSON | ECS task-role credentials require **no token/PUT step at all** — reachability alone is sufficient; detector logic for this surface should be binary (reachable → exploitable), unlike the two-step EC2 IMDSv2 check | AWS SDK Reference: Container credential provider; Sweet Security: ECScape |
| Host-level IMDS (169.254.169.254) reachable from inside an ECS container, combined with the resulting instance-profile role holding `ecs:DiscoverPollEndpoint` / `ecs:Poll` | "ECScape" technique — a container can impersonate the ECS agent over the ACS WebSocket and receive **every co-located task's** credentials on that host; AWS classified this as a design consideration, not a vulnerability, and assigned no CVE | Sweet Security: ECScape — Understanding IAM Privilege Boundaries in Amazon ECS (disclosed Black Hat USA 2025) |
| DNS answer for an SSRF-target hostname changes between a validation request and the actual connect (TTL=0 rebinding) | TOCTOU bypass of hostname-based SSRF allowlists that re-resolve DNS per request rather than pinning the validated IP | Strobes: SSRF testing; Unveil: SSRF defense in depth; CVE-2026-27127 (Craft CMS, CWE-367) |
| Target framework bypasses an IPv6-literal-only metadata filter via a rebinding domain | **CVE-2026-27127** (Craft CMS, GHSA-gp2f-7wcm-5fhx) — bypass of the earlier fix for CVE-2025-68437, which blocked only IPv6-literal metadata/internal addresses; affected 5.0.0-RC1–5.8.22, fixed in 5.8.23/4.16.19 | Vulert: CVE-2026-27127; OpenCVE; GitLab Advisory DB |
| Lambda function environment has `AWS_CONTAINER_CREDENTIALS_FULL_URI` unset and direct requests to 169.254.169.254/169.254.170.2 fail | Standard Lambda injects credentials via environment variables and does not expose the IMDS/ECS-metadata attack surface by default; SSRF-to-metadata checks should not be applied to plain Lambda | Classmethod hands-on test (single data point, not official AWS doc); DEV Community: AWS credentials for serverless |
| Lambda with **SnapStart** enabled (Java runtime) | Switches to the ECS-style `AWS_CONTAINER_CREDENTIALS_...` variable pattern — this sub-case *should* be probed like ECS task-metadata | AWS re:Post thread on SnapStart credential loading |
| Fargate platform version ≥1.4.0 exposing `ECS_CONTAINER_METADATA_URI_V4` | Same v4 endpoint / same reachability-only gating as ECS-on-EC2 `awsvpc` mode; no token required | AWS ECS Developer Guide: Task metadata endpoint v4 for tasks on Fargate |
| IMDSv2 token flow (PUT+GET) reached and completed in a 2024–2026 disclosed, dated case | **Negative result across all reviewed cases** — no disclosed 2024–2026 case actually defeated the IMDSv2 token mechanism itself (CVE-2025-51591/Pandoc was neutralized by IMDSv2 per Wiz's own statement; the F5/CSO-reported March 2025 campaign targeted IMDSv1, not v2) — detectors should treat direct IMDSv2-token-bypass as lower-priority than adjacent non-token-gated surfaces | Wiz: IMDS Abused — Hunting Rare Behaviors to Uncover Exploits (CVE-2025-51591); CSO Online / F5 Labs (IMDSv1 campaign, ASN 34534, Mar 2025) |

## 2. Container/orchestrator metadata endpoints

| Signature to detect | What it indicates | Source citation |
|---|---|---|
| `GET 169.254.170.2/v2/metadata`, `/v2/metadata/{container-id}`, `/v2/stats` reachable | ECS task metadata endpoint **v2** — AWS states it "is no longer being actively maintained"; enabled by default for Fargate ≥1.1.0 and EC2 `awsvpc` tasks on agent ≥1.17.0 (Linux)/≥1.54.0 (Windows) | AWS: Amazon ECS task metadata endpoint version 2 |
| `${ECS_CONTAINER_METADATA_URI_V4}` base path / `/task` / `/taskWithTags` / `/stats` reachable | Current recommended ECS task metadata endpoint **v4**; on by default on Fargate ≥1.4.0; AWS guarantees field backward-compatibility | AWS: Amazon ECS task metadata endpoint version 4 |
| `GET 169.254.170.2<AWS_CONTAINER_CREDENTIALS_RELATIVE_URI>` succeeds with no `Authorization` header | Plain ECS task-role credential retrieval requires **no bearer-token/Authorization check** — only network-path reachability gates it; architecturally weaker than EKS Pod Identity | AWS SDKs and Tools Reference Guide: Container credential provider |
| Presence of `AWS_CONTAINER_AUTHORIZATION_TOKEN` / `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` env vars | SDK-level bearer-token requirement — set by **EKS Pod Identity** (full-URI + token-file pair) and by Lambda SnapStart, but **not** by plain ECS task roles by default | AWS SDKs and Tools Reference Guide: Container credential provider |
| Unauthenticated `GET` to kubelet port **10255** (`/pods`, `/stats`, `/spec`) returns data | Deprecated unauthenticated read-only kubelet endpoint — CIS Kubernetes Benchmark check 4.2.4 ("`--read-only-port` set to 0") flags this; DISA STIG CNTR-K8-000330/V-242387 calls it deprecated with "no authentication or authorization security control" | Tenable CIS Kubernetes Benchmark audit items; Tenable DISA STIG Kubernetes audit item |
| Repeated container-checkpoint requests against the unauthenticated read-only kubelet endpoint fill node disk | **CVE-2025-0426** — Node DoS via checkpoint-request flood against the unauthenticated kubelet read-only HTTP endpoint; affected kubelet 1.30.0–1.30.9, 1.31.0–1.31.5, 1.32.0–1.32.1 | Red Hat: CVE-2025-0426; NVD: CVE-2025-0426 |
| Authenticated request to kubelet port **10250** succeeds without credentials, or `--anonymous-auth` not set to `false` | kube-apiserver/kubelet `--anonymous-auth` defaults to `true`; CIS Benchmark 1.2.1 flags this as requiring explicit hardening; KEP-4633 (Alpha 1.31 / Beta 1.32 / Stable 1.34) narrows but does not eliminate anonymous access by default | Kubernetes docs: Kubelet authentication/authorization; KEP-4633; Tenable CIS Kubernetes audits |
| `GET` on `nodes/proxy` subresource used to reach a WebSocket-based `exec`/`attach` endpoint | Not actually read-only — some WebSocket endpoints use the `GET` verb to execute commands in containers, so RBAC `get` on `nodes/proxy` is broader than it appears | Kubernetes docs: Kubelet authentication/authorization |
| Node address validation bypass letting an authenticated request directed at a Node proxy reach control-plane-internal secure endpoints | **CVE-2022-3294** — kube-apiserver node-address validation bypass (CWE-20); CVSS 3.1 8.8 High; fixed in Kubernetes 1.22.16, 1.23.14, 1.24.8, 1.25.4+ (pre-2024 but still cited/relevant) | Red Hat: CVE-2022-3294; NVD: CVE-2022-3294 |
| GKE pod reads `kube-env` or VM instance identity token via node metadata | Pod-level metadata concealment (`--workload-metadata=SECURE`) is explicitly labeled **Beta / deprecated** by Google; does not restrict node service-account access and does not cover `hostNetwork: true` pods — Google directs operators to **Workload Identity Federation** instead | Google Cloud: Protecting cluster metadata |
| EKS pod reaches 169.254.169.254 (node IMDS) despite VPC CNI NetworkPolicy in place | NetworkPolicy enforcement on EKS is **not on by default**, requires explicit VPC CNI configuration, and only applies to Amazon Linux nodes (not Fargate/Windows); IMDSv2 hop-limit=1 is the complementary control but only blocks non-host-network pods | AWS EKS: Limit Pod traffic with Kubernetes network policies; AWS Whitepaper: Restrict host networking and block access to IMDS (multi-tenant SaaS on EKS) |
| `GET` to GCP metadata server `v0.1` or `v1beta1` path succeeds | Legacy GCE metadata API — deprecated 2019-09-30, **fully shut down 2020-09-30**; should not succeed against any live GCP metadata server in 2024–2026 | Google Cloud: v0.1 and v1beta1 metadata server endpoints deprecation |
| `GET` to GCP metadata server `v1` path without `Metadata-Flavor: Google` header | Current `v1` API **denies** requests missing this header (CSRF-style protection); legacy `v0.1`/`v1beta1` reportedly did not enforce this check, per third-party scanner docs (not Google first-party) | Google Cloud: View and query VM metadata; Aqua/Trivy misconfiguration docs (secondary source) |
| Docker container (bridge mode, on an AWS EC2 host) + IMDSv2 hop-limit 1 | Blocked from reaching 169.254.169.254 (extra hop via bridge NAT exceeds limit); `host` network mode reaches it directly, sharing the host's namespace | Latacora: ECS on EC2 — Covering Gaps in IMDS Hardening (secondary source for plain-Docker behavior; no first-party Docker doc found) |
| `DOCKER-USER` iptables chain lacks a rule dropping `docker+` → `169.254.169.254/32` | Missing hardening — this rule is the commonly documented explicit mitigation for Docker-to-metadata reachability regardless of network mode | Palo Alto Cortex: Docker network hardening guide |

**Cross-cutting implementation notes carried over from the source notes:**
- Confirmation logic should branch on `nxdomain: true` (Azure, Elastic Beanstalk — confirm via DNS resolution) vs. HTTP-body fingerprint (all other services) per the upstream fingerprints.json schema.
- Negative/suppression fingerprints (Fastly, Zendesk, CloudFront, GCS, Firebase, AWS ELB, Statuspage) must be coded as "match = confirmed NOT vulnerable," reversing a naive "any error body = vulnerable" heuristic.
- The AWS S3 `-an` exclusion regex should be copied verbatim from ProjectDiscovery's maintained template rather than re-derived.
- "Edge case" services require secondary confirmation (e.g., attempting an authorized claim where in-scope) before being reported at high severity — fingerprint match alone is insufficient given these platforms' current TXT/domain-verification account models.

## 4. Research gaps

The following items were explicitly flagged as unconfirmed, low-confidence, or requiring follow-up in the underlying research notes, and should not be hard-coded into detection logic as high-confidence facts without further verification:

- **No bare default hop-limit value** for a newly launched EC2 instance with no AMI/account preference was found in AWS documentation (only precedence rules); should be verified against `aws ec2 describe-instances --query 'Reservations[].Instances[].MetadataOptions'` or `run-instances` API defaults.
- The hacktricks.wiki cloud-SSRF page's `X-Forwarded-For`-rejection claim was corroborated only via WebSearch synthesis, not a direct page read (redirect chain exceeded fetch attempts).
- No 2024–2026 Black Hat/DEF CON/fwd:cloudsec talk specifically on an IMDSv2 token bypass was located (only a 2023, out-of-window fwd:cloudsec talk).
- The alternate-IP-encoding bypass claim (decimal/hex/octal/IPv6-mapped 169.254.169.254) is repeated across secondary SSRF literature but no canonical primary-source example payload was captured.
- No AWS-specific (as opposed to generic cloud-metadata) DNS-rebinding CVE or HackerOne/Bugcrowd report chaining rebinding → IMDSv2 token flow → credential theft was found; CVE-2026-27127 (Craft CMS) is the strongest concrete example but is framework-level, not AWS-IMDSv2-specific.
- Whether EKS's `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` is used by default across modern (2024–2026) EKS Pod Identity deployments, in a way gating access like IMDSv2, was not determined — flagged for dedicated EKS follow-up.
- No primary AWS documentation confirms or denies whether 169.254.169.254 is reachable/blocked inside the standard (non-container-image) Lambda execution environment across all runtimes; the one data point (Classmethod) tested only a container-image Lambda.
- No dedicated 2024–2026 CVE, HackerOne report, or conference talk specifically documents a Lambda/Fargate metadata-retrieval quirk being exploited (this sub-topic rests on documentation/testing inference).
- The Aviatrix 2026 "Proxy Server to Metadata Service Attack" page (citing AWS bulletins "AWS-2025-007"/"AWS-2025-021" by title only) has internal inconsistencies and could not be treated as a confirmed, citable finding — needs verification against AWS's actual bulletin index.
- No official Kubernetes upstream changelog/release-note confirms a specific version number at which `--read-only-port`/10255 was deprecated or removed; only third-party CIS/STIG/vendor mirrors were available. Whether kube-bench's current default profile still checks this port was also not independently confirmed.
- The kube-apiserver `--anonymous-auth` "Default: true" value was not retrieved verbatim from the primary flag-reference page — only via KEP-4633 and CIS-benchmark corroboration.
- No official AKS-specific metadata-blocking documentation was retrieved (the assignment named GKE/EKS/AKS, but only GKE and EKS first-party guidance was found).
- No Google first-party statement confirms that legacy GCP metadata `v0.1`/`v1beta1` endpoints never checked the `Metadata-Flavor` header — this detail is sourced only to third-party scanner docs (Trivy/Aqua).
- Whether a CVE was ultimately issued for "ECScape" after disclosure is unconfirmed (one source said a CVE ID had been requested) — recheck against NVD.
- No EKS-specific (as opposed to generic Kubernetes) CVE for metadata/IMDS exposure, and no AKS-specific metadata-service CVE, were identified.
- No official Docker Inc. documentation directly addresses cloud-metadata-service reachability from containers; all Docker-specific findings are sourced to AWS/third-party hardening guides, not Docker's own docs — flagged as the weakest-sourced section of the container inventory.
- No official changelog/dated commit history confirms exact PR/issue numbers and merge dates for can-i-take-over-xyz status changes since 2023 (e.g., exact commit adding Statuspage's DNS-verification note).
- No primary-source Netlify or Vercel security advisory confirms or denies a platform-wide subdomain-takeover fix; all evidence is indirect (community forums, disputed GitHub issue threads) — requires empirical per-engagement verification rather than trusting vendor posture.
- Firebase's current live fingerprint behavior could not be independently confirmed (the upstream JSON entry has an empty fingerprint string).
- The Silent Push "Danglegeddon" 2026 report could not be fully retrieved (exceeded fetch size limit); findings rely on secondary press coverage (SecurityWeek), not the primary report text, so exact per-service findings from that report could not be extracted.
- No primary source confirms or denies Render.com's post-deletion custom-domain reclaim behavior, or Cloudflare Pages' dangling-CNAME takeover status — both are gaps requiring independent empirical testing (e.g., register/delete/re-register a throwaway service) rather than documentation review.
