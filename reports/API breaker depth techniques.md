# API-breaker's depth pass hardens three fronts

The most effective 2024-2026 technique in each of api-breaker's three target areas turned out to be implementable in pure Python with no new dependencies, and this session's research-and-build passes have already shipped nearly all of them into the skill's four core scripts. For JWT, the highest-leverage additions were `kid`-header SQL-injection, path-traversal, and timing-based-SQLi probing, RFC 7515 `crit`-header non-enforcement testing, RS256↔PS256 relabeling, and `aud`/`iss` claim validation — all now live in `auth_analyzer.py` alongside a 14-entry CVE fingerprint table built from fresh 2024-2026 advisories spanning PyJWT, python-jose, Centrifugo, Rodauth, and nine other libraries, which collectively prove algorithm-confusion and header-injection bugs are still being freshly introduced into actively-maintained code, not a closed chapter. For GraphQL, `schema_builder.py` now runs a five-stage introspection-disabled fallback chain, a depth/complexity DoS probe with fragment-cycle and introspection-naming-bypass sub-probes, a nested-field authorization differential test, a GraphQL CSRF check, an opt-in mutation-BOLA write probe, and engine fingerprinting tied to three real 2024-2026 CVEs — apollo-compiler's CVE-2025-31496, graphql-java's CVE-2024-40094, and Hasura's CVE-2026-54698. For versioning and rate limits, `api_discovery.py` now confirms legacy-version exposure with an actual differential exploit test rather than merely flagging that an old path exists, and `rate_limiter.py` adds a baseline-vs-burst race-condition comparator auto-targeted at financial-impact endpoints plus response-shape-verified path/method/casing mutation testing and a batching/aliasing probe that establishes an unbatched baseline before calling a hit confirmed. One exception was deliberate rather than an oversight: real-key JWKS extraction and `jwk`-header injection were fully designed this session and cryptographically verified end-to-end, then withheld specifically because shipping them would require the `cryptography` package, breaking api-breaker's documented stdlib-only core-pipeline invariant — a dependency-policy call the user made directly when asked. What remains genuinely unbuilt afterward is narrow and almost entirely infrastructure-bound: a true HTTP/2 single-packet race needs raw frame control this skill doesn't carry, a CDN-versus-origin differential test needs a second address this tool cannot infer on its own, and the research itself turned up no industry-standard numeric threshold for a "safe" query depth or alias count — because none exists.

## Header injection beats infrastructure-heavy JWT attacks in 2026

Beyond `alg:none` and placeholder-key RS256→HS256 confusion, the single highest-value technique needs no attacker-controlled infrastructure at all: the `jwk` header lets a token carry its own public key inline, and any verifier that trusts whatever key the token hands it — rather than only ever checking against a pre-pinned server key — will accept a token signed by a key the attacker just generated on the spot. This is not theoretical; **CVE-2026-34240** in the Dart `jose` package shows a real 2026 library doing precisely that, accepting an attacker-embedded `jwk` header with no check against any trusted keystore ([radar.offseq.com](https://radar.offseq.com/threat/cve-2026-34240-cwe-347-improper-verification-of-cr-4aef725b)). The `kid` header carries three independently exploitable sub-attacks: SQL injection when the signing-key lookup is a non-parameterized query ([OWASP WSTG](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/10-Testing_JSON_Web_Tokens)), path traversal when `kid` doubles as a filename — OWASP's documented technique redirects to a known-empty file such as `/dev/null` so the server ends up verifying against an empty-string HMAC secret — and, newly confirmed in 2026, server-side request forgery: **CVE-2026-54430** in OpenIDC's `liboauth2` (used inside AWS ALB's JWT verification) built an unvalidated `kid` value directly into a URL that was fetched *before* signature verification ever ran ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-54430/)). A fourth `kid`-adjacent bug surfaced at the caching layer rather than the header-parsing layer: Centrifugo's **CVE-2026-49998** kept its dynamic JWKS cache keyed only by `kid`, with no issuer or audience component, so a token legitimately issued to one tenant was silently accepted as another tenant's the moment both reused the same key identifier — a direct cross-tenant authentication bypass rated CVSS 8.2 ([OSV GO-2026-5872](https://osv.dev/vulnerability/CVE-2026-49998)). The classic remote-fetch pair, `jku` and `x5u`, remains exploitable wherever the fetch isn't pinned to a real allowlist, and the practical 2026 wrinkle is that `data:` and `file://` URIs can sidestep allowlist logic entirely — a gap confirmed in production by PyJWT's own `PyJWKClient`, which passed JWKS URIs straight into `urllib.request.urlopen()` without restricting the scheme until **CVE-2026-48522** forced a fix in version 2.13.0 ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2026-48522)). Rounding out the header surface, RFC 7515's mandate that a verifier reject any token whose `crit` header names an extension it doesn't enforce turned out to be silently ignored by both PyJWT (**CVE-2026-32597**) and fast-jwt (**CVE-2026-35042**) — so an application that relies on a `crit`-declared extension to enforce something security-relevant, such as a step-up-auth marker, can have that enforcement bypassed simply by omitting the extension from a forged token ([Mondoo](https://mondoo.com/vulnerability-intelligence/vulnerability/GHSA-752w-5fwx-jx9f)). `auth_analyzer.py` now implements the realistic majority of that surface directly: `test_jwt_kid_injection` and `test_jwt_kid_sqli_timing` cover the path-traversal, SQL-injection, and time-based-SQLi variants; `test_jwt_crit_header_bypass` implements the RFC 7515 non-enforcement check; and the 14-entry CVE fingerprint table ties all of it to recoverable version strings across PyJWT, python-jose, panva's `jose`, Dart's `jose`, joserfc, cjwt, PHP's `web-token/jwt-framework`, `liboauth2`, Centrifugo, Rodauth, and fast-jwt.

Beyond header injection, the algorithm-confusion family that RS256→HS256 made famous has grown real siblings. WorkOS documents RS256↔PS256 confusion as a distinct variant — both algorithms share one RSA key, so a verifier that checks only "is this an RSA key" rather than pinning the exact algorithm string can be tricked by a relabeled signature ([WorkOS](https://workos.com/blog/jwt-algorithm-confusion-attacks)), and `test_jwt_rs_ps_relabel` now ships this as a cheap header-relabeling test requiring no new cryptography. Tom Tervoort's Black Hat 2023 research, still the foundational reference for this entire class, showed a validator that trusts a token's declared type can be fooled into treating an RSA-encrypted JWE as a signed JWT whenever the attacker knows the RSA public key, and separately demonstrated a "billion hashes" denial-of-service: a JWE's PBKDF2 iteration count sits in the attacker-controlled `p2c` header, and setting it extremely high forced over four billion SHA-512 operations before the server could even determine the token was invalid, with no valid token needed as a starting point ([Trail of Bits](https://blog.trailofbits.com/2024/03/08/out-of-the-kernel-into-the-tokens/)). Confirmed-affected libraries for that DoS include panva's `jose` (fixed as CVE-2022-36083) and, as recently as a 2026 PT Security advisory, PHP's `web-token/jwt-framework`, which passed `p2c` unbounded into `hash_pbkdf2` until a fix capped it at one million iterations by default ([PT Security](https://dbugs.ptsecurity.com/vulnerability/PT-2026-53178)). A dedicated NDSS 2026 fuzzing paper, "JWTeemo," found **20 additional CVEs** across popular JOSE libraries spanning exactly these categories — signature/encryption confusion, algorithm confusion, format confusion, the billion-hashes attack, and compression-based DoS — which is the clearest evidence available that this bug class is still actively productive rather than solved ([NDSS 2026](https://www.ndss-symposium.org/wp-content/uploads/2026-f697-paper.pdf)). Real-key RS256→HS256 confusion — fetching the server's actual public key from a `/jwks.json` endpoint, or deriving it from two or more valid signatures via the `sig2n` technique when no JWKS is exposed ([PortSwigger](https://portswigger.net/web-security/jwt/algorithm-confusion)) — and `jwk`-header injection were both fully designed this session and verified against a real cryptographic sign/verify round-trip proving a forged token validates. Neither shipped, and that is a scoped decision rather than a gap: both require the `cryptography` package, which would break api-breaker's documented stdlib-only core-pipeline invariant, and the user chose to preserve that invariant when asked directly rather than add the dependency.

Token-lifecycle testing closes the remaining third of this area, and 2026 supplied three independently-confirmed refresh-token failure modes that are all testable with plain HTTP, no cryptography required. Rodauth's refresh route issued new access tokens without confirming the presented token was actually a refresh token (**CVE-2026-82469**); the JWT Auth WordPress plugin and NocoDB both let previously-issued refresh tokens survive a password change or device revocation (**CVE-2026-106466**, **CVE-2026-53928**); and better-auth's OAuth provider had a plain race condition in which two concurrent requests presenting the identical refresh token could both pass the reuse-detection check before either marked it consumed, so one refresh token minted two valid token pairs — the exact failure RFC 9700 §4.14 warns against ([PT Security](https://dbugs.ptsecurity.com/vulnerability/PT-2026-56301)). `analyze_jwt_claims` now flags missing `aud`/`iss` claims outright as a zero-network-cost static check, closing the structural gap that lets a token minted for one service be replayed against any other service sharing the same signing key — precisely the failure behind the Centrifugo cross-tenant bug, and a pattern FastAPI-tenancy's own documentation warns readers about by name ([fastapi-tenancy docs](https://fastapi-tenancy.readthedocs.io/en/latest/guides/resolution/jwt/)).

## Disabling introspection barely slows schema reconstruction down

Turning off the introspection query is the single most common GraphQL hardening step, and it is also the one most thoroughly defeated in practice. PortSwigger documents field-suggestion ("did you mean") error text as an independently sufficient schema-recovery channel, and **Clairvoyance** automates exactly that: a blind wordlist brute force that reconstructs a usable schema purely from suggestion responses, popular enough that Apollo Server disabling introspection by default in production is explicitly cited as the reason the tool exists ([PortSwigger](https://portswigger.net/web-security/graphql); [PyPI: clairvoyance](https://pypi.org/project/clairvoyance)). Even where suggestions are also disabled, a graphql-php maintainer confirms that query validation itself still leaks field existence by nature of accepting or rejecting a query — "the server still leaks information about which fields are available... even if suggestions are turned off" is the documented behavior, not a rare misconfiguration ([GitHub: webonyx/graphql-php#1175](https://www.github.com/webonyx/graphql-php/issues/1175)). Naive blocklists fail just as completely: a regex matching the literal string `__schema{` is defeated by inserting a newline immediately after `__schema`, since GraphQL ignores the whitespace a rigid regex does not ([PortSwigger](https://portswigger.net/web-security/graphql)), and the same query resent as `GET` with the query in the querystring, or as form-encoded `POST`, or against an alternate path like `/graphql/v2`, routinely slips past a filter wired to only one transport shape. `schema_builder.py` now runs all of this as an ordered fallback chain rather than giving up at the first failed introspection call: cheap transport retries first, then regex-evasion retries, then Clairvoyance-style field-suggestion harvesting against a seeded wordlist, then a binary-oracle brute force as the expensive last resort, plus an always-on probe for bare `node`/`nodes` root fields — a structural object-access primitive OWASP calls out independently of whatever else the schema recovery finds.

Once a schema is in hand, two transport-level tricks let a client multiply operations inside limits designed to count HTTP requests. Checkmarx's own demonstration is the clean proof: a target enforcing five requests per second via `429` responses accepted a single batched array of 100 login-mutation attempts — one username against 100 different passwords — as one HTTP request returning `200 OK` with 100 discrete results, and the one correct guess handed back a reusable session token ([Checkmarx](https://checkmarx.com/blog/didnt-notice-your-rate-limiting-graphql-batching-attack/)). Aliasing achieves the identical effect without array batching at all, by repeating one field under different names inside a single query document — PortSwigger's canonical example aliases `isValidDiscount` three times in one request — and OWASP's cheat sheet is explicit that request-count-based limiters "will likely bypass existing rate limits" against either transport, recommending that sensitive operations (passwords, OTPs, session tokens) disable batching outright rather than rely on a cap ([OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)). One caveat tempers both findings: some server implementations deduplicate identical aliased subqueries before execution, so request-shape acceptance alone does not prove the backend actually paid for every copy — real exploitability needs a timing or side-effect check, not just a 200 ([Checkmarx](https://checkmarx.com/blog/alias-and-directive-overloading-in-graphql)). `rate_limiter.py`'s `test_graphql_batching()` now encodes exactly that discipline: it first bursts the unbatched single operation until a `429` appears (or confirms none exists within a budget), records the count at which that happens, then sends a batched or aliased form carrying more copies than that baseline tolerated — so a vulnerability is only flagged when the differential is confirmed, not merely when batching is accepted.

Query depth and cost are unbounded by default in most GraphQL server libraries, per OWASP's own guidance, and this is not purely a design-level risk — it is the direct root cause of at least two 2024-2026 CVEs. **CVE-2025-31496** in `apollo-compiler` re-validated named fragments once per *spread* rather than once per *definition*, with no memoization, so deeply nested or reused fragments drove validation cost up exponentially (CVSS 7.5, no workaround, fixed in 1.27.0) ([Tenable](https://www.tenable.com/cve/CVE-2025-31496)). **CVE-2024-40094** in graphql-java found a specific gap in how the library accounted for alias- and fragment-expanded fields in its own anti-DoS cost model, letting a crafted query evade protection that otherwise existed (CVSS v4.0 8.7 High) ([Tenable](https://www.tenable.com/cve/CVE-2024-40094)). Depth limiting alone also misses a breadth-based variant — an attacker can stay shallow while multiplying expensive field invocations via aliasing, which a pure depth counter never sees ([Wallarm](https://lab.wallarm.com/fundamentals-of-graphql-specific-attacks)) — and even dedicated depth-limiting middleware has been bypassed this way: `@escape.tech/graphql-armor-max-depth` skips introspection-named fields by default, so naming a query or fragment literally `__schema` dodges its depth counter entirely (GHSA-hmfr-rx46-4jx2) ([GitLab Advisory DB](https://advisories.gitlab.com/pkg/npm/@escape.tech/graphql-armor-max-depth/)). `schema_builder.py`'s `test_graphql_depth_complexity_dos()` now escalates nesting against any self-referencing relation it can find (or a fallback list of common patterns like `children`/`parent`), classifies the result by whether a depth error appears, by whether latency grows non-linearly with no error at all, and by outright timeouts, and ships two sub-probes built directly off the CVEs above: a fragment-cycle test that sends two named fragments spreading each other and checks whether the server rejects the cycle, and an introspection-naming-bypass test that retries a confirmed-limited deep query with the operation renamed `__schema` to check for the graphql-armor-style evasion.

The dominant real-world authorization failure in GraphQL is structural rather than a missing check on any one endpoint: a root field like `me` gets gated correctly while a sibling field reaching the identical data by a different path — `user(id)`, or a nested edge like `post(id).author.email` — never re-validates the caller at all. OWASP's API Security Top 10 formalizes the split between whole-object failures (BOLA, API1:2023) and field-level failures (BOPLA, API3:2023), and its own GraphQL guidance states the principle directly: possessing an ID does not imply permission, and both edges and nodes need independent checks, illustrated with a real bug report where edges were checked but nodes were not ([OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)). A fresh, concrete instance of the same pattern at the database layer is **CVE-2026-54698** in Hasura: a `where` clause on a table's computed field — one returning `SETOF some_table` — let a caller infer row-level-permission-protected data that direct table access would have blocked, affecting versions up to 2.49.2 ([Mend.io](https://www.mend.io/vulnerability-database/CVE-2026-54698/)). `schema_builder.py`'s `test_graphql_nested_field_authz()` now runs this as a differential test: call a self field like `me` with a given session and record what it legitimately returns, then call a sibling by-ID field or a nested edge with the identical session against a different object's ID, and flag any field that comes back which the self-field path never exposed. An opt-in `test_graphql_mutation_bola_write()` extends the same logic to writes — calling an `update`/`delete`-style mutation as one user against an object believed to belong to another — gated behind explicit opt-in because a true positive there is a real unauthorized write, and `test_graphql_csrf()` covers the related, independently-documented class of mutations reachable over `GET` or unchecked form-encoded `POST` ([Doyensec](https://blog.doyensec.com/2021/05/20/graphql-csrf.html)). An `fingerprint_graphql_engine()` step now runs ahead of all CVE-specific probing, distinguishing Apollo, graphql-java, and Hasura by response-header and error-shape fingerprints, and feeds a three-entry range-aware CVE table covering exactly the three vulnerabilities named above — every hit is reported as a version-matched hypothesis to verify, not a confirmed exploit, since black-box behavior alone cannot fully confirm a CVE match without a version banner.

## Legacy versions and millisecond race windows outlive rate limiters

Deprecated API versions do not disappear when a newer version ships; they keep running, unpatched, until someone looks for them, and the public breach record for this pattern is unusually concrete for an application-layer bug class. St. Luke's Health System's 2023 breach ran through a deprecated SOAP API for six months after the newer REST services had already been patched, exposing roughly 450,000 patient records; an unnamed US retailer's legacy XML checkout API stayed live after a GraphQL migration and leaked 14 million card records over four months; and Optus's 2022 breach went through an undocumented, leftover endpoint carrying no authentication, no rate limiting, and no monitoring at all, exposing close to 10 million customer records ([instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)). The versioning conventions worth generating candidates against vary by vendor — Stripe's URI-based `/v1/`, Box's date-tokens (`2024.0`, `2025.0`), GitHub's header-based media-type versioning — and the Internet Archive's Wayback/CDX API is the standard programmatic recon tool for surfacing paths and subdomains a target itself forgot it still serves, queried as a CDX search over `<target>/api/*` and re-probed live rather than trusted as archived content ([dataimpulse.com](https://dataimpulse.com/blog/wayback-machine-api/)). Finding that an old path exists is necessary but not sufficient; the step that actually confirms exploitability is a differential test — replaying the exact request already known to trigger a security control on the current version (the same burst count that gets a `429`, the same malformed payload that gets a `422`) against the candidate old version with everything else held constant, and flagging a finding only when the control fires on the current version but not the old one. `api_discovery.py`'s `discover_legacy_versions()` now implements the full pipeline: version/date-token candidate generation, fingerprinting via the `Sunset`, `Deprecation`, and `Link rel="deprecation"` headers (RFC 8594 and RFC 8288), Wayback/CDX enumeration against both the target and wildcard subdomains, and the differential exploit-confirmation test itself rather than stopping at path existence.

Race conditions got a genuine capability jump in 2023-2024 that is worth naming precisely, because it sets the realistic ceiling for what a portable, stdlib-oriented tool can achieve. James Kettle's single-packet attack uses HTTP/2 stream multiplexing to get twenty to thirty fully-formed requests arriving within one TCP packet, collapsing request-arrival jitter from a roughly 4-millisecond median down to under 1 millisecond — tight enough to reliably win race windows that ordinary concurrent requests miss, and fast enough that one real-world case went from a two-hour exploitation time with the older "last-byte sync" technique down to about thirty seconds ([PortSwigger](https://portswigger.net/research/smashing-the-state-machine)). GMO Flatt Security's August 2024 follow-on, "first sequence sync," extended the ceiling further using IP fragmentation and TCP sequence-number reordering to land roughly 10,000 near-simultaneous requests in about 166 milliseconds ([flatt.tech](https://flatt.tech/research/posts/beyond-the-limit-expanding-single-packet-race-condition-with-first-sequence-sync)). The financial stakes this technique exposes are not hypothetical: a HackerOne-disclosed Stripe race condition let a researcher fire roughly 30 parallel "accept offer" requests against a one-time $20,000 fee-discount, and every single one of the 30 redeemed successfully because the accept/redeem check was not atomic — a $600,000 total exposure that paid a $5,000 bounty and needed two separate remediation attempts before Stripe closed it for good ([HackerOne](https://www.hackerone.com/blog/how-business-logic-vulnerability-led-unlimited-discount-redemption)). `rate_limiter.py`'s `test_race_condition()` implements the portable version of Kettle's own detection methodology rather than the raw-frame attack itself: run the identical request sequentially first to record a baseline success count, then fire the same batch through a thread-pool burst, and flag a race-condition bypass whenever the burst produces more successes — or more distinct side effects, like tokens or credits granted — than the sequential baseline allowed; the function auto-targets endpoints whose path or response body matches financial-impact keywords (`coupon`, `discount`, `invite`, `redeem`, `gift_card`, `credit`, `voucher`), mirroring exactly the class of bug Stripe, and the less rigorously sourced but structurally identical Dropbox, Reverb, and Instacart reports, all paid out for. The true single-packet attack itself — precise HEADERS/DATA frame withholding, `TCP_NODELAY` manipulation, and synchronized release — needs raw HTTP/2 frame control that this stdlib-oriented skill deliberately doesn't carry as a dependency; the thread-pool burst is the realistic portable ceiling, and it is explicitly a detection method for the same underlying non-atomic check-then-act flaw, not an imitation of Kettle's packet-timing precision.

Rate limiters and path-based security controls fail just as often from trivial string mismatches as from missing logic, and three 2023-2025 CVEs against actively maintained, non-obscure frameworks confirm the pattern is still being freshly introduced rather than stamped out. Strapi's admin-login rate limiter compared the raw request path as a plain string, so `/admin/Login` (case-varied) and `/admin/login/` (trailing slash) each got their own unlimited counter while `/admin/login` itself correctly hit `429` after 30 attempts — both mutated paths returned `200 OK` with the correct password, a full brute-force-protection bypass via path mutation alone (**CVE-2023-38507**, fixed in 4.12.1) ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2023-38507)). Better Auth's router dependency normalizes `/sign-in/email`, `//sign-in/email`, and `///sign-in/email` to the identical handler, but a path-based rate limit or disabled-paths check matching only the literal configured string let the slash-padded variants through untouched (**CVE-2025-71399**) ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2025-71399)). And Litestar's `RateLimitMiddleware` trusted a client-supplied `X-Forwarded-For` unconditionally as part of its rate-limit cache key, so simply rotating the header value handed every request its own bucket — confirmed by the reporter's own test showing varied `X-Forwarded-For` values all returning `200` where an unheadered third request correctly got `429` (**CVE-2025-59152**) ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2025-59152)). All three share one architectural root cause: the rate-limit key comes from an un-normalized path or an unauthenticated header rather than a canonicalized path plus a server-verified identity signal. `rate_limiter.py`'s `test_path_mutation_bypass()` now re-bursts every endpoint the scanner already confirmed is rate-limited against a mutation set covering trailing-slash toggling, doubled/tripled slashes, per-segment case changes, and method swaps, and verifies the response *body shape* matches a genuine pre-limit success response rather than trusting status code alone — closing off the false-positive risk of a soft-404 page that happens to return 200. `BYPASS_HEADERS` gained `X-Host` and the documented real-world typo `X-Forwared-Host`, both drawn from the same body of practitioner material that confirmed the Litestar-style unconditional-trust flaw is still common.

## Five gaps remain, bounded by infrastructure, not research

What is left unbuilt after three passes is short, and every item has a specific, stated reason rather than being an oversight. A true HTTP/2 single-packet race attack needs raw frame-level control — withholding `END_STREAM`, disabling `TCP_NODELAY`, releasing frames in a single tight loop — that falls outside what this stdlib-oriented skill depends on; the thread-pool burst comparator already shipped is the realistic portable ceiling for detecting the same non-atomic check-then-act flaw, even though it cannot win the sub-millisecond windows Kettle's technique can. Duplicate-header-line injection — sending `X-Forwarded-For` twice in one request, once empty and once populated, rather than rotating a single header's value — is a documented bypass in its own right, but Python's standard `urllib.request` and `http.client` both collapse a header name to one value by construction, so testing it for real needs raw-socket request-line construction rather than anything the existing HTTP layer can be coaxed into doing. A CDN-versus-origin differential test — replaying the identical burst against both an edge-fronted hostname and a direct-to-origin address to catch a gateway rate limit that the backend itself doesn't enforce — is architecturally simple but needs a second origin address as an explicit input; it cannot be derived from path mutation or any other signal already available to the scanner, so it is better wired up as an optional alternate-target flag than attempted automatically. On the GraphQL side, the CVE table covers the single most recent and most relevant Hasura vulnerability, CVE-2026-54698, but four older Hasura CVEs from the 1.3.3 release line — a nested-query DoS, a SQL-injection-based local file read, an SSRF via remote schema injection, and a `run_sql`-based remote code execution rated CVSS 9.8 — remain outside the table; they only matter against a target still running that old release line, and their CVE numbers were themselves only backfilled in late 2025 from aggregator sources rather than primary GHSA/NVD pages, so adding them cleanly would need that primary-source confirmation first. Finally, the research itself settled a question rather than leaving it open: there is no industry-standard numeric threshold for a "safe" GraphQL query depth or alias count. Vendor defaults range from 5-15 aliases per request at the strict end to 50 at the permissive end, and every depth/complexity limit found in practice is implementation- and schema-specific rather than portable, so any single number used for a pass/fail verdict is necessarily the tool's own judgment call, not a sourced standard — which is exactly why the shipped probes report differentials (does a control fire at all, does latency grow non-linearly) rather than comparing against one hardcoded "correct" limit.

These five are distinct in kind from the `jwk`/real-key-JWKS decision described earlier, and the distinction is worth holding onto when prioritizing future work: the JWKS item is fully designed, fully verified, and ready to ship the moment a dependency-policy change allows it, while the five gaps above need either new infrastructure this skill doesn't have a stdlib-compatible path to, an input the scanner cannot generate for itself, or — in the alias/depth-threshold case — do not have a "right answer" waiting to be found at all.

## Conclusion

The throughline across all three domains is that 2024-2026's most dangerous API-security bugs are not exotic — they are old failure patterns (trust the client-supplied key, trust the client-supplied IP header, trust that a counter increments before a second request arrives) reappearing in new, actively-maintained software, which is precisely why a fingerprint-table-plus-differential-test architecture generalizes so well across JWT, GraphQL, and rate-limiting code. The Centrifugo, Litestar, Better Auth, and Hasura CVEs cited here all landed in 2025-2026 against frameworks with no history of neglect, which argues against treating any of these three testing areas as a legacy checklist item that current engineering practice has already solved. The more durable lesson for the skill's own design is the value of the differential-over-acceptance discipline adopted this pass — baselining before bursting, confirming a security control fires on one path before declaring its absence on another, checking response shape rather than status code alone — since nearly every 2024-2026 bypass surfaced here was a bypass of exactly the kind of control a naive single-request test would have falsely credited as present.
