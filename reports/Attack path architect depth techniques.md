# Attack Path Architect — Depth Techniques: MITRE ATT&CK / ATLAS Technique-Classification Reference

Synthesized from two research-notes files for the attack-tree-generator module's technique-reference and finding-class → TTP lookup tables:
- `research_notes/Attack path architect depth techniques/mitre_technique_reference_data.md`
- `research_notes/Attack path architect depth techniques/chain_to_ttp_mapping.md`

This is a defensive documentation reference (technique classification/tagging for a vulnerability scanner's attack-tree generator). It contains no exploitation instructions — only ID-to-name-to-tactic mappings and classification statements.

All ATT&CK data below was pulled live from attack.mitre.org on 2026-11-14. A version-conflict note from the source research: one secondary source states the current ATT&CK release is v20 (13 Oct 2026), another describes it as v19.1; attack.mitre.org pages fetched directly show per-technique "Version" numbers rather than an overall matrix version, so each technique's own page is treated as authoritative rather than any single global version label.

## Section 1 — MITRE ATT&CK technique reference table

> ### ⚠ Callout: ATT&CK v19 tactic restructuring (Defense Evasion → Stealth + Defense Impairment)
> MITRE ATT&CK **v19** (released 28 April 2026) **retired the "Defense Evasion" tactic (TA0005)** and split it into two tactics:
> - **"Stealth"** — *inherits the TA0005 tactic ID* — covering techniques where adversaries hide malicious activity within otherwise-legitimate behavior. Confirmed by direct fetch of `attack.mitre.org/tactics/TA0005/`: page title "Stealth, Tactic TA0005 - Enterprise | MITRE ATT&CK®", description "The adversary is trying to hide and conceal their actions, appearing as normal behavior." ([Source](https://attack.mitre.org/tactics/TA0005/))
> - **"Defense Impairment" (new tactic, ID TA0112)** — covering techniques that disable or undermine security controls.
> - Cited corroboration: "MITRE retired Defense Evasion in ATT&CK v19 and split it into two tactics... Stealth... inherits the TA0005 tactic ID" and "Defense Impairment: This new tactic has ID TA0112" — [D3 Security blog](https://d3security.com/blog/rip-defense-evasion-ta0005/).
>
> **Entries in this table confirmed affected:**
> - **T1078 (Valid Accounts)** and **T1078.004 (Cloud Accounts)** — both now list tactics as **Stealth, Persistence, Privilege Escalation, Initial Access** (not "Defense Evasion") per live fetch of [T1078](https://attack.mitre.org/techniques/T1078/) and [T1078.004](https://attack.mitre.org/techniques/T1078/004/). Note: MITRE's own description *prose* for both pages still uses the phrase "Defense Evasion" even though the tactic field itself now reads "Stealth" — this is stale wording in the narrative text, not a taxonomy error; the table below uses the current tactic-field value.
>
> **Confirmed non-affected counter-example:**
> - **T1548 (Abuse Elevation Control Mechanism)** historically also carried a Defense Evasion tag, but its tactic info box now shows **only Privilege Escalation** — it did **not** retain a Stealth or Defense Impairment mapping as of this check ([Source](https://attack.mitre.org/techniques/T1548/)). This means the restructuring cannot be assumed via a blanket find/replace; each technique's tactic list must be checked individually.
>
> **Research gap:** the source notes did not exhaustively check every technique in this table for a secondary "Defense Impairment (TA0112)" mapping beyond T1078/T1078.004/T1548 — only the tactic info boxes as directly fetched were used.

## Section 2 — Finding-class to TTP classification mapping

Four finding classes from the source notes, two of which (the JWT classes) are documented as a single "JWT depth-technique chains" group (c) with two independently-scored sub-chains (c1, c2). All step descriptions below are phrased as classification/tagging statements ("this step corresponds to / is classified under technique X"), not as instructions. Feasibility/Impact/Stealth are presented strictly as **scanner-severity-scoring metadata** (1–10 scale; feasibility base 4–8, impact base 6–10, stealth reduced when a WAF/CDN or cloud audit-logging layer is present), not as attack guidance.

### (a) ECS-Cape-style cross-task credential exposure

**Pattern label:** ECS-Cape: IMDS-to-Agent-Impersonation Cross-Task Credential Harvest

Source: Sweet Security's own write-up (disclosed Black Hat USA 2025, researcher **Naor Haziz**; AWS treats this as a configuration/design-boundary issue, not a CVE-numbered vulnerability) — [Sweet Security blog](https://www.sweet.security/blog/ecscape-understanding-iam-privilege-boundaries-in-amazon-ecs), corroborated by [CSO Online](https://www.csoonline.com/article/4036655/ecscape-new-aws-ecs-flaw-lets-containers-hijack-iam-roles-without-breaking-out.html) and [The Hacker News](https://thehackernews.com/2025/08/researchers-uncover-ecscape-flaw-in.html).

| Pattern Label | Step Description | ATT&CK / ATLAS ID | Note |
|---|---|---|---|
| ECS-Cape | This step — querying the host's Instance Metadata Service (IMDS, 169.254.169.254) from inside a container to obtain the EC2 instance-profile role's temporary credentials — corresponds to / is classified under **T1552.005** | T1552.005 — Unsecured Credentials: Cloud Instance Metadata API | Direct match: ATT&CK's canonical description is "adversaries with presence on a running VM/container query the Instance Metadata API to identify credentials." ([Source](https://attack.mitre.org/techniques/T1552/005/)) |
| ECS-Cape | This step — calling `DiscoverPollEndpoint` with the stolen instance-role credentials to learn the ECS control-plane endpoint — is classified under **T1528** | T1528 — Steal Application Access Token | Reasonable fit: using one stolen credential set to obtain information enabling acquisition of a further access/credential set; ATT&CK scopes T1528 to Containers/IaaS platforms. ([Source](https://attack.mitre.org/techniques/T1528/)) |
| ECS-Cape | This step — opening a rogue parallel session to the Agent Communication Service (ACS) WebSocket using the stolen instance-role credentials, impersonating the real ECS agent — is classified under **T1550.001 (approximate / imperfect fit, flagged gap)** | T1550.001 — Use Alternate Authentication Material: Application Access Token | No current ATT&CK technique precisely covers "open an unauthorized second session to an internal control-plane protocol by replaying a legitimate agent's authentication path." T1550.001 is the nearest Enterprise fit but does not capture the "impersonate the agent itself" nuance. |
| ECS-Cape | This step — receiving IAM credential payloads for every co-located task on the host via the impersonated session — corresponds to / is classified under the same credential-theft techniques as steps 1–2 | T1552.005 (secondary) + T1528 (secondary) | Direct consequence of the prior step; ATT&CK has no sub-technique for "receive bulk credentials pushed by a legitimate-channel impersonation," so no distinct ID is assigned. |
| ECS-Cape | This step — using the stolen task-role credentials for unauthorized AWS API access as another identity — is classified under **T1078.004** | T1078.004 — Valid Accounts: Cloud Accounts | Standard mapping once stolen cloud credentials are used to authenticate as another identity. ([Source](https://attack.mitre.org/techniques/T1078/004/) — not independently refetched this session, but established as the canonical ID.) |

**Scanner-severity-scoring metadata:**
- **Feasibility: 6/10.** Elevated above the 4–6 floor because the prerequisite (container with host IMDS access + an instance role carrying default `ecs:Poll`/`ecs:DiscoverPollEndpoint`) is the *default* ECS EC2-launch-type configuration per Sweet Security — no custom misconfiguration required beyond "didn't block IMDS from containers." Capped below 7–8 because it requires an existing container compromise (post-initial-access/lateral technique, not remote-unauth) and reverse-engineering an undocumented internal protocol (ACS).
- **Impact: 9/10.** Breaks the assumed per-task credential isolation boundary entirely — a low-privilege task can obtain a high-privilege co-located task's full IAM role with no container breakout. AWS's own framing (instance = sole security boundary) confirms blast radius is "every task on the host."
- **Stealth: 6/10 (reduced from a higher base).** The initial IMDS read is unlogged by CloudTrail (stealthy by default), but subsequent *use* of stolen task-role credentials against AWS APIs is attributed and visible in CloudTrail under the victim task's role identity — a detectable anomaly if monitored. Stealthy at the theft step, more exposed at the use step.

### (b) GraphQL shadow-schema mutation exposure

**Pattern label:** GraphQL Shadow-Schema Mutation Smuggle

Source: [Escape.tech's field-suggestion writeup](https://escape.tech/blog/graphql-verbose-error-suggestions/) and [Escape's vulnerability docs](https://docs.escape.tech/testing/vulnerabilities/information_disclosure/graphql_field_suggestion) ("If introspection is disabled on your target, Field Suggestion still allows users to infer the entire schema"); a `graphql-js` GitHub issue confirming suggestion text lives in the raw `error.message` string independent of the introspection toggle; [PortSwigger's GraphQL material](https://portswigger.net/web-security/graphql) on field-level authorization gaps.

| Pattern Label | Step Description | ATT&CK / ATLAS ID | Note |
|---|---|---|---|
| GraphQL Shadow-Schema | This step — using field-suggestion ("did you mean…?") harvesting / binary-oracle brute-forcing to reconstruct the schema despite introspection being disabled — **has no clean Enterprise ATT&CK fit; explicitly flagged as a gap** | None (approximate analog: T1592/T1595 family) | This is active reconnaissance against an application's own error-handling behavior, not credential-access/execution. ATT&CK's Reconnaissance techniques (T1590–T1596) target pre-engagement OSINT/scanning of an *organization*, not interactive fuzzing of an already-reachable API's error responses. T1595.002 (Active Scanning: Vulnerability Scanning) is the closest analog but scoped to broad known-vuln scanning, not iterative error-oracle schema inference. Recommended table tag: "Reconnaissance (T1592/T1595 family, approximate)" with explicit no-precise-technique annotation. |
| GraphQL Shadow-Schema | This step — using the reconstructed schema to locate a privileged mutation not discoverable via the blocked introspection endpoint — is classified under **T1213 (approximate fit)** | T1213 — Data from Information Repositories | Approximate: using application-internal structural knowledge to find where sensitive operations live is conceptually closer to internal-repository reconnaissance than any closer ID, but T1213 is normally post-access data discovery, not API-surface schema mapping. |
| GraphQL Shadow-Schema | This step — exploiting the nested-field authorization gap to bypass the top-level authorization check — is classified under **T1190 (best available fit)** | T1190 — Exploit Public-Facing Application | ATT&CK defines T1190 broadly as "exploiting a weakness in an internet-facing application" to gain access/effect; a field-level-authorization logic flaw on a public GraphQL endpoint falls within that broad definition, consistent with how BOLA/BFLA findings are commonly mapped to T1190 in third-party practice. |
| GraphQL Shadow-Schema | This step — submitting the unauthorized privileged write via the nested field — is classified under **T1565.001 (conditional)**, or folded into T1190's impact if not itself a data-manipulation write | T1565.001 — Data Manipulation: Stored Data Manipulation | Tag separately only if the write's purpose is data manipulation; an admin-grant-style write is conceptually closer to T1548 (Abuse Elevation Control Mechanism) territory, but no clean Enterprise sub-technique exists specifically for "nested-parameter authorization-check gap" — flagged as approximate/best-effort, same caveat as the prior step. |

**Scanner-severity-scoring metadata:**
- **Feasibility: 5/10.** Introspection-disabled-but-suggestion-enabled is a common misconfiguration (most teams disable introspection but forget to strip suggestion text, per the `graphql-js` issue tracker discussion), so schema reconstruction is realistically achievable, but requires patience (many iterative error-oracle queries) and the nested-field authz gap is implementation-specific, not guaranteed — pulling feasibility toward the middle of the 4–8 band.
- **Impact: 8/10.** End state is an unauthorized privileged write achieved despite introspection being deliberately disabled as a defense — demonstrating that a single surface-level control provided a false sense of security while the deeper authorization-logic flaw remained exploitable.
- **Stealth: 4/10 (reduced from base).** The field-suggestion/binary-oracle harvesting step requires high-volume malformed-query traffic — exactly the noisy, repetitive pattern a WAF or API gateway with anomaly/rate-based detection is positioned to flag, consistent with the convention of lowering stealth when a WAF/CDN sits in front of the target. The final privileged-write request may look like a single legitimate-shaped mutation and be harder to catch at that stage, but the reconnaissance phase dominates the score downward.

### (c) JWT depth-technique chains

#### (c1) JWT key-lookup-injection forgery

**Pattern label:** JWT `kid` Lookup Hijack

Source: [PentesterLab's JWT Kid Injection glossary entry](https://pentesterlab.com/glossary/jwt-kid-injection); corroborating: [HackTricks JWT attacks](https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens), [Invicti](https://invicti.com/blog/web-security/json-web-token-jwt-attacks-vulnerabilities). No MITRE page specifically covering "JWT kid injection" was found; the closest standards references are CWE-22 (Path Traversal) and CWE-89 (SQL Injection) at the weakness level, not technique level.

| Pattern Label | Step Description | ATT&CK / ATLAS ID | Note |
|---|---|---|---|
| JWT `kid` Lookup Hijack | This step — injecting a path-traversal or SQL-injection payload into the `kid` header to redirect the server's key-verification lookup — **has no clean Enterprise ATT&CK technique; explicitly flagged as a gap** | None — cross-reference CWE-22 / CWE-89 instead | ATT&CK has no technique for "parameter injection into a cryptographic key-lookup mechanism." Path traversal and SQL injection are CWE-level weaknesses, not ATT&CK techniques — ATT&CK generally models post-exploitation adversary behavior, not web-input-validation vulnerability classes themselves. Recommendation: leave this step unmapped in the reference table, or cross-reference CWE-22/CWE-89 instead of forcing an ATT&CK ID. |
| JWT `kid` Lookup Hijack | This step — the server resolving the lookup to attacker-known/attacker-supplied key material — is classified under **T1552 (approximate, weak fit)** | T1552 — Unsecured Credentials (general) | Weak fit, included only because the end effect is "the attacker now possesses/controls the credential material used for verification." |
| JWT `kid` Lookup Hijack | This step — forging a validly-signed JWT using the now-known key — is classified under **T1606 (strong fit)** | T1606 — Forge Web Credentials | ATT&CK's T1606 is explicitly "adversaries create their own credentials... to access web resources," including web session tokens, which generalizes cleanly to forging a JWT once the signing material is known or controlled. ([Source](https://attack.mitre.org/techniques/T1606/)) |
| JWT `kid` Lookup Hijack | This step — authenticating / accessing resources using the forged token — is classified under **T1078 (standard mapping)** | T1078 — Valid Accounts | Standard mapping for using a (in this case, forged) credential to authenticate as if legitimate. |

**Scanner-severity-scoring metadata:**
- **Feasibility: 4/10 (base floor).** Requires a specific, increasingly rare implementation flaw (unsanitized `kid` passed directly into a file-path or DB-query construction) that modern JWT libraries' default verification flows have largely closed off; implementation-specific rather than a structural protocol weakness.
- **Impact: 9/10.** Successful exploitation yields full authentication bypass with arbitrary claims (attacker-chosen identity/role), equivalent to full account/privilege takeover.
- **Stealth: 6/10.** Moderate — the injection-probing phase (fuzzing `kid` with traversal/SQLi payloads) can generate anomalous-looking tokens/requests a WAF with JWT-aware inspection or SQLi/path-traversal signatures would likely flag, reducing stealth from a higher base; the final forged-token use, once achieved, looks like a normal authenticated request and is hard to distinguish afterward.

#### (c2) JWT algorithm-family relabeling

**Pattern label:** JWT Algorithm-Family Relabel (RS256→PS256)

Source: [PortSwigger's algorithm confusion attacks page](https://portswigger.net/web-security/jwt/algorithm-confusion), [WorkOS's analysis](https://workos.com/blog/jwt-algorithm-confusion-attacks). Concrete real-world case: **CVE-2026-48523** in PyJWT (2.9.0–2.12.1), where signature verification used the algorithm bound to the PyJWK object rather than the token header's `alg`, allowing an RS256-signed token with its header relabeled to `alg: PS256` to be accepted when the server intended to only accept PS256 — confirmed via [OSV advisory GHSA-jq35-7prp-9v3f](https://osv.dev/GHSA-jq35-7prp-9v3f).

| Pattern Label | Step Description | ATT&CK / ATLAS ID | Note |
|---|---|---|---|
| JWT Algorithm-Family Relabel | This step — relabeling the header `alg` of a validly RS256-signed token to PS256 with zero new signing material created — **has no clean Enterprise ATT&CK technique for the relabeling action itself; explicitly flagged as a gap**, with T1606 as the nearest step-level fit for the overall outcome | T1606 (approximate) — Forge Web Credentials | The relabeling action is better described as *manipulating* an existing valid credential's metadata than *forging* new credential material (no new signature is created) — subtler than T1606 is written to describe. If used in the table, annotate that no cryptographic forgery occurred, only header manipulation. |
| JWT Algorithm-Family Relabel | This step — the server's algorithm-agnostic/mis-pinned verification logic accepting the relabeled token without re-validating signature-to-algorithm consistency — **has no strong Enterprise match; explicitly flagged as a gap** | None strong (T1210 noted as an imperfect conceptual neighbor) | Fundamentally an *implementation flaw in verification logic* (a software defect), which ATT&CK generally doesn't have a precise technique for at this granularity. The closest conceptual parent is still T1606's broader "bypass authentication protection mechanisms" framing, but no dedicated ID exists for "algorithm-pinning failure in signature verification." |
| JWT Algorithm-Family Relabel | This step — the server treating the relabeled token as authenticated and granting access — is classified under **T1078 (standard mapping)** | T1078 — Valid Accounts | Standard mapping once the bypass succeeds and the attacker is treated as authenticated. |

**Scanner-severity-scoring metadata:**
- **Feasibility: 4/10 (lower end of base band).** Lowest-feasibility item among the four classes researched: depends on a narrow, library-specific verification defect (confirmed concretely only in specific cases like the PyJWT CVE, which itself notes the risk "mainly applies where external parties register their own keys") rather than a broadly applicable protocol weakness. WorkOS explicitly notes this variant does not reliably produce a direct exploit the way RS256→HS256 does.
- **Impact: 8/10.** When it does work, impact is high — full authentication bypass using zero new cryptographic material, a particularly severe finding because it requires no key-cracking or secret-guessing.
- **Stealth: 7/10.** Higher stealth than the other JWT sub-chain because the "attack traffic" is a single relabeled token submitted through a normal authentication flow — no fuzzing/brute-forcing footprint, no unusual payload shape beyond one modified header byte sequence, making it very hard for a WAF or anomaly detector to distinguish from a legitimate request. Not raised to 8–10 because the technique still requires the attacker to have captured/possessed a validly RS256-signed token in the first place, which may itself leave a prior access trail.

### (d) Agentic tool-access indirect-injection pattern

**Pattern label:** Agentic Tool-Access Indirect Injection Exfiltration

Three concrete, independently disclosed real-world cases confirm this pattern:
- **EchoLeak (CVE-2025-32711, Microsoft 365 Copilot)** — disclosed by **Aim Labs**, reported to MSRC, CVSS 9.3, publicly disclosed June 11, 2025. Zero-click indirect prompt injection via email content Copilot ingests during normal retrieval, causing the agent to use its own legitimate tool access to exfiltrate information with no user interaction required. NVD's description: "AI command injection in M365 Copilot allows an unauthorized attacker to disclose information over a network." ([Source](https://informationsecuritybuzz.com/zero-click-ai-vulnerability-echoleak-ms-365/); MSRC advisory referenced but not independently fetched this session.)
- **CurXecute (CVE-2025-54135, Cursor IDE)** — disclosed by **AIM Security**. A crafted Slack message, read through an approved/legitimate Slack MCP connector, carried a prompt injection causing Cursor to rewrite its own global MCP configuration file and execute attacker-chosen commands before the user could reject the action. Patched in Cursor 1.3 (merged July 8, 2025; shipped July 29, 2025). ([Cato Networks](https://www.catonetworks.com/blog/curxecute-rce/), [The Hacker News](https://thehackernews.com/2025/08/cursor-ai-code-editor-fixed-flaw.html).)
- **AgentFlayer (Zenity, Black Hat USA 2025)** — zero-click/one-click exploit chains against enterprise AI tools (ChatGPT, Copilot Studio, Salesforce Einstein, Google Gemini, Microsoft Copilot); the common exfiltration pattern (demonstrated against ChatGPT) passed locally-accessible data as URL parameters to exfiltrate via an outbound request the agent's existing tool access permitted. (Secondary coverage; primary Zenity/AIM posts not independently fetched this session.)

| Pattern Label | Step Description | ATT&CK / ATLAS ID | Note |
|---|---|---|---|
| Agentic Indirect Injection | This step (steps 1–2 combined) — the agent ingesting untrusted content (email body, calendar invite, shared document, chat message, or MCP tool description field) that contains a hidden/indirect instruction not authored by the legitimate user — is classified under **AML.T0051.001** | AML.T0051.001 — LLM Prompt Injection: Indirect (**MITRE ATLAS**) | Precise fit — ATLAS explicitly defines indirect prompt injection as "the payload arrives through content the model ingests, such as documents, emails, or web pages." No Enterprise ATT&CK technique covers this AI-specific mechanism, so ATLAS is the correct and necessary choice. |
| Agentic Indirect Injection | This step — the LLM core following the injected instruction instead of/alongside legitimate instructions — is classified under **AML.T0054 (approximate nearest neighbor; recommend not assigning separately)** | AML.T0054 — LLM Jailbreak (**MITRE ATLAS**) | Imperfect fit: ATLAS does not appear (per the source research) to have a dedicated technique purely for "model fails to distinguish injected content from trusted instructions," distinct from the injection delivery itself (AML.T0051) and the subsequent tool misuse. The user did not necessarily jailbreak safety training, just failed instruction-source discrimination. Recommendation: fold this step into AML.T0051.001's outcome rather than forcing AML.T0054. |
| Agentic Indirect Injection | This step — the agent invoking its own legitimately-granted tool(s) to execute the injected instruction — is classified under **AML.T0053** | AML.T0053 — AI Agent Tool Invocation (**MITRE ATLAS**) | Good fit for "agent uses its existing tool access under adversary influence" — the ATLAS-native technique for exactly this behavior; sits under Execution and/or Privilege Escalation per sources. Naming-inconsistency caveat: older secondary material also labels this ID "LLM Plugin Compromise" — verify current canonical name against atlas.mitre.org directly before publishing. |
| Agentic Indirect Injection | This step — data exfiltrated via the agent's legitimate tool access — is classified under **T1567** (Enterprise, preferred for a conventional outbound web/connector request) **or AML.T0024** (ATLAS, only if the channel is specifically the model's own inference-API output) | T1567 — Exfiltration Over Web Service (**ATT&CK**) / AML.T0024 — Exfiltration via AI Inference API (**ATLAS**) | For the EchoLeak/CurXecute/AgentFlayer cases researched, T1567 is the more accurate mapping since exfiltration rode on a conventional web/connector call (e.g., URL-parameter or webhook exfil), not the inference API itself. |
| Agentic Indirect Injection | This step — an unauthorized action taken instead of/in addition to data theft (e.g., the CurXecute MCP config-file rewrite) — is classified under **T1565.001** | T1565.001 — Data Manipulation: Stored Data Manipulation (**ATT&CK**) | Fits the CurXecute case specifically: the agent's legitimate file-write tool access was used, under injected instruction, to rewrite its own MCP configuration file — stored-data manipulation with downstream command-execution consequences. |

**Scanner-severity-scoring metadata:**
- **Feasibility: 7/10.** High end of the base band because this class requires no credential theft, no code-execution vulnerability, and no infrastructure compromise — only (a) a lower-trust content channel the agent already ingests as part of normal operation, and (b) an agent that already has the tool access (both *standard, intended* features of agentic AI deployments, not misconfigurations). Three independent real-world confirmed cases in 2025 (EchoLeak, CurXecute, AgentFlayer) across different vendors (Microsoft, Cursor/Anysphere, multiple AgentFlayer targets) within months of each other indicate a structurally common, repeatable pattern.
- **Impact: 9/10.** High and sometimes zero-click (EchoLeak and CurXecute both achieved zero/low-user-interaction exfiltration or code execution); because the vulnerability is the *combination* of ingestion + tool access rather than either alone, remediation is architecturally harder than patching a single bug — multiple vendors needed dedicated fixes.
- **Stealth: 7/10 (high, but reducible by egress controls — the AI/agent-world analog of a WAF/CDN).** Naturally high because the entire chain uses the agent's own legitimate, pre-authorized tool access — no anomalous authentication event, no new credential, no obviously malicious payload signature in the traditional network sense. Should be **reduced toward 5–6/10** in environments with egress-filtering/DLP on agent tool calls or MCP-call allowlisting (the closest architectural analog to a WAF/CDN for this class), consistent with the scoring convention of lowering stealth when such a control layer is present and monitoring outbound agent tool invocations.

### Unmapped steps note

The following steps were explicitly flagged in the source research as having **no current official MITRE ATT&CK (or ATLAS) technique ID**, and should be rendered in the scanner's table as unmapped/gap rather than forced into a weak match:

1. **GraphQL Shadow-Schema, step 1** — field-suggestion/error-oracle schema reconstruction while introspection is disabled. No ATT&CK technique exists for this; closest analog (T1595.002 / T1592 family) is only approximate.
2. **JWT `kid` Lookup Hijack, step 1** — injecting a path-traversal/SQLi payload into a cryptographic key-lookup parameter. No ATT&CK technique exists; CWE-22 (Path Traversal) and CWE-89 (SQL Injection) are the correct cross-reference instead of an ATT&CK ID.
3. **JWT Algorithm-Family Relabel, step 1** — the header-relabeling action itself (as distinct from its outcome). No clean ATT&CK technique; approximated only to T1606's broader outcome, with an annotation that no cryptographic forgery actually occurred.
4. **JWT Algorithm-Family Relabel, step 2** — the server's algorithm-pinning/verification-logic defect that accepts the relabeled token. No strong Enterprise match; this is an implementation-flaw gap, not a technique ATT&CK models at this granularity.
5. **ECS-Cape, step 3** — the ACS-WebSocket agent-impersonation step (opening a rogue parallel session by replaying a legitimate agent's authentication path). No precise Enterprise technique exists; T1550.001 is used only as an approximate, flagged-imperfect fit.
6. **Agentic Indirect Injection, step 3** — "the model fails to discriminate the injected instruction from legitimate instructions," as a step distinct from injection delivery (AML.T0051.001) and tool misuse (AML.T0053). No dedicated ATLAS ID exists for this specific sub-step; the source research recommends folding it into AML.T0051.001's outcome rather than force-fitting AML.T0054 (LLM Jailbreak).

**Additional sourcing caveat (not an unmapped step, but a naming-accuracy flag):** AML.T0053's canonical name shows a discrepancy across secondary sources — "AI Agent Tool Invocation" vs. an older "LLM Plugin Compromise" label — per [Startup Defense's ATLAS pages](https://www.startupdefense.io/mitre-atlas-techniques/aml-t0051-llm-prompt-injection) and the [D3FEND mirror of AML.T0051](https://d3fend.mitre.org/offensive-technique/attack/AML.T0051/); atlas.mitre.org itself was not independently fetched this session for final confirmation, and the source notes flag that several Enterprise ATT&CK IDs cited for class (d) (T1078.004, T1190, T1550.001, T1565.001, T1567) are likewise stated from established general knowledge/secondary corroboration rather than a fresh primary-source fetch this session.

Also flagged in the source notes: the RS256→PS256 variant (c2) is **narrower and less universally exploitable** than the well-known RS256→HS256 confusion attack — the strongest confirmed real-world instance (PyJWT CVE-2026-48523) is itself caveated by its advisory as applying mainly where external parties register their own JWKs, which should temper how broadly the scanner treats this specific sub-variant versus the more general algorithm-confusion family.
