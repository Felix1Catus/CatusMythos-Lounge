# AI Security Skill Ships Fixes, Maps Gaps

This second research pass across the `16-ai-llm-security` skill confirms that two of its four target areas — ML/model-supply-chain depth and jailbreak/extraction/denial-of-wallet coverage — already received concrete engineering fixes earlier in this session, while the other two — RAG/vector-store security and MCP/agent-tool-use security beyond basic indirect prompt injection — remain pure research, with zero automated tests built yet despite both being named in the skill's own documentation. The supply-chain pass extended `model_supply_chain.py` with GGUF `chat_template` Jinja2-SSTI scanning for the CVE-2024-34359/CVE-2026-5760 class, fixed a real `.npy`/`.npz` pickle-stream-routing bug, closed blocklist gaps (`pydoc.locate`, `marshal`, `uuid`) that Trail of Bits' own `fickling` advisories named as shared weaknesses with PickleScan, and added a PyTorch-version advisory for CVE-2025-32434 — the case where the officially-recommended `weights_only=True` mitigation was itself exploitable. The jailbreak pass added four single-shot, architecture-compatible techniques (many-shot jailbreaking, low-resource-language translation, ArtPrompt, Policy Puppetry) plus a Best-of-N retry wrapper to `prompt_injection_tester.py`, shipped a new `unbounded_consumption_tester.py` script for OWASP LLM10 exposure checks, and explicitly deferred Crescendo, Echo Chamber, and Skeleton Key as needing real multi-turn conversation state the single-stateless-POST architecture doesn't have. The research behind the two unbuilt areas is just as concrete: RAG leakage and MCP's protocol-level attack classes are, almost without exception, classic IDOR/BOLA and OAuth/confused-deputy bugs transplanted onto vector stores and agent protocols, which means both are fully specifiable today as stdlib-Python black-box test harnesses — the kind this report lays out section by section for the next engineering pass. Across all four areas, named production evidence (a 200-product tenant-isolation audit, a Claude Code `terraform destroy` wipe, Anthropic's own distillation-campaign reporting) confirms these are live, currently-exploited risk classes rather than theoretical ones.

## RAG security testing has zero coverage and four clear build targets

`SKILL.md` already describes RAG and vector-store review as in scope, but no script comparable to `model_supply_chain.py`'s file walker or `prompt_injection_tester.py`'s payload corpus exists for retrieval pipelines today — every finding below is a build target for the next pass, not a shipped capability.

### Cross-tenant leakage is a transplanted IDOR bug, not a vector-math flaw

The strongest evidence base in this entire research pass sits here: a 2025-2026 source-code review of more than 200 self-hosted multi-tenant AI/RAG products found confirmed cross-tenant data exposure in **78 of them** (84 findings total, 31 already filed as GitHub Security Advisories), naming patched products including SurfSense, AnythingLLM, Baserow, aideepin, and Flagsmith ([Dev.to](https://dev.to/dmitrymaranik/i-source-reviewed-200-self-hosted-ai-tools-for-tenant-isolation-78-leaked-across-tenants-4ff4)). Every root cause named is a classic authorization bug relocated to a RAG context: write endpoints that check tenant ownership while sibling read/search endpoints fetch by raw ID with no tenant filter, authorization checks keyed to a caller-supplied tenant parameter instead of the object's actual owner, raw embedding vectors served with no tenant scoping at all, response-cache keys that omit the tenant ID, and scheduled re-index jobs that pull one tenant's content using a different tenant's stored OAuth token. OWASP's LLM08:2025 entry formalizes this exact pattern as "cross-context leaks and knowledge conflicts," worked through an example of one group's embeddings surfacing in another group's query results ([OWASP GenAI LLM08:2025](https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/)), and Trail of Bits' professional audit of the Weaviate-backed "Ask Astro" reference app independently found a GraphQL-injection bug in the Weaviate Python client that the auditors noted "only matters if the vector database shares infrastructure with a non-public database" — precisely this cross-boundary scenario ([Trail of Bits](https://blog.trailofbits.com/2024/07/05/auditing-the-ask-astro-llm-qa-app/)). Because the bug class is IDOR/BOLA wearing a RAG costume, the test methodology ports directly from classic web pentesting: provision two tenants, plant a unique high-entropy marker under Tenant A, then query as Tenant B and grep every response surface — answer text, citations, debug/trace JSON — for the marker, while separately swapping Tenant B's auth token against Tenant A's namespace parameter to test whether the two are independently bound ([RedFoxSec](https://www.redfoxsec.com/blog/testing-multi-tenant-ai-applications-for-data-leakage)). Documented cache leaks are concurrency-dependent, so the harness needs to fire that query battery with `threading`/`concurrent.futures` immediately after ingestion, not only serially — a serial-only suite will under-report this exact bug class. A fully stdlib companion check scans every reachable JSON endpoint for bare arrays of 256-4096 floats, which is precisely the "raw embedding vectors readable without tenant scoping" root cause above, and doubles as the practical, automatable stand-in for embedding-inversion testing, since true inversion techniques (ALGEN, BeamClean) both require query access to the embedding model or its embedding table and should be documented rather than automated in a pure black-box engagement ([ALGEN, ACL 2025](https://arxiv.org/html/2502.11308v2)).

### Membership inference is the one inversion-adjacent attack that is actually black-box

A sharper case is IBM Research's S²MIA attack, which asks a RAG system a crafted yes/no question about whether a suspected passage sits in its retrieved context and reads the model's own answer — no embedding access needed. Tested on 8,000 members and 2,000 non-members, the pure black-box variant reached a **true-positive rate of 1.00 at a 0.74 false-positive rate**, while a gray-box variant layering in the `logprobs` of the first yes/no token (available on any OpenAI-compatible API) reached **TPR 0.83 at FPR 0, AUC 0.99** ([alphaXiv, arXiv 2405.20446](https://alphaxiv.org/abs/2405.20446)). The build target is a template-driven confirmation-question harness scored against a decoy-passage baseline rather than any single confirmation, with an automatic upgrade path to logprob scoring whenever the target API exposes it — needing only `urllib`, `json`, and `re`.

### Document poisoning is the best-evidenced, highest-priority gap to close first

Three independent, named sources converge on the same precondition and the same defense gap. PoisonedRAG showed that injecting just five malicious texts into a 2.7-million-document corpus reached a **90% attack success rate** in its peer-reviewed USENIX Security 2025 evaluation (97% in the earlier preprint), with both perplexity-based detection and paraphrasing defenses tested and found insufficient ([USENIX Security 2025](https://www.usenix.org/conference/usenixsecurity25/presentation/zou)). ConfusedPilot showed that dropping one plain-language malicious document into any location a RAG pipeline indexes — a shared drive, a SharePoint folder — can force answers to come solely from that document, disable citations entirely, and keep steering answers even after the malicious file is deleted, a "phantom document" effect rooted in stale index persistence ([arXiv 2408.04870](https://arxiv.org/html/2408.04870v5)). Trail of Bits' Ask Astro audit found the live version of the same bug: nothing propagated source deletion into the vector database at all, letting an attacker post content, wait for it to be indexed, then delete the original while the poisoned embeddings persisted indefinitely (TOB-ASTRO-0001, High severity) ([Trail of Bits](https://blog.trailofbits.com/2024/07/05/auditing-the-ask-astro-llm-qa-app/)). None of this needs model access — only an ingestion foothold, even an indirect one like a wiki edit or support ticket. The highest-value build here is two checks: an active probe that ingests canary documents carrying a small payload library (forced-answer strings, source-suppression instructions, hidden zero-width-Unicode text) and checks whether they hijack answers or crowd out better-matching sources, and a passive, no-ingestion-access drift probe that simply diffs the cited-sources list across repeated identical queries over hours or days — an unexplained single source suddenly dominating a previously multi-source answer is the exact observable signature of both ConfusedPilot and the Ask Astro front-running scenario, detectable with nothing more than `difflib`.

### Citation laundering is real but still preprint-stage

A newly named technique, "citation laundering" (CiteShade), describes a model citing a legitimate-looking source while a different, attacker-controlled source actually drove the generated content — defeating verification approaches that check only whether the cited source supports the claim, never whether it was the source actually used ([arXiv 2609.15660](https://arxiv.org/pdf/2609.15660)). The same paper reports non-adversarial citation correctness in long-form RAG answers already sits around **0.1 to 0.4** on open-domain benchmarks with no attacker present at all, making a non-adversarial baseline measurement a mandatory first step before attributing any citation failure to an attack rather than ordinary model unreliability. Trail of Bits' Ask Astro audit supplies the one real-world precedent: an attacker could forge an entire fake GitHub issue thread, spoofed authorship included, because the ingestion pipeline trusted content based on an easily-imitated username template (TOB-ASTRO-0002). The practical test plants a content-bearing decoy document alongside an authoritative-looking but content-free one, then checks whether the answer's substantive claims trace to the decoy while the citation names the authoritative-looking document — a simple term-frequency overlap comparison, no ML library required.

Tying the four sub-risks together, a version-fingerprinting layer closes the loop cheaply: Milvus's unauthenticated-admin-access bug (CVE-2025-64513, CVSS 9.3, rooted in trusting a client-supplied `sourceID` header), Weaviate's November 2025 path-traversal pair (CVE-2025-67818/67819), and LangChain Core's "LangGrinch" serialization-injection flaw (CVE-2025-68664, CVSS 9.3, reachable via prompt injection through LLM-generated output) are all conventional appsec bugs, not vector-math flaws, so a banner/version check against each product's meta endpoint, paired with the documented reproduction step for each CVE, is the cheapest addition of all ([Averlon](https://research.averlon.ai/vulnerability-intelligence/cve/CVE-2025-64513); [Weaviate](https://weaviate.io/blog/weaviate-security-release-november-2025); [NVD](https://nvd.nist.gov/vuln/detail/cve-2025-68664)). All of the above — tenant canary-swap, raw-vector exposure scan, membership-inference probe, active/passive poisoning probes, citation-laundering probe, and CVE fingerprinting — is stdlib-only and belongs together in a new sibling script alongside `model_supply_chain.py` and `prompt_injection_tester.py`.

## MCP security demands protocol tests, not just injection payloads

`SKILL.md` names MCP server hardening as in scope, but the only existing automated coverage is one generic `mcp-tool-description-indirect` payload inside `prompt_injection_tester.py`'s corpus. Nothing tests the protocol-level and lifecycle-level attack classes below, so this section is also a build target rather than a status report.

### The official spec's MUST/SHOULD rules are the best test oracle found in this research pass

The Model Context Protocol's own "Security Best Practices" document (modelcontextprotocol.io, 2025-06-18) is the single source across both unbuilt areas written in precise, testable RFC-2119 language rather than general advice ([MCP spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)). It specifies a confused-deputy attack sequence unique to MCP proxy servers — a static client_id combined with dynamic client registration and a third-party consent cookie lets an attacker skip the consent screen and redirect an authorization code to their own server — and mandates a per-client consent registry checked before forwarding. It forbids token passthrough outright ("MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server"), names two session-hijacking variants and mandates CSPRNG-generated, identity-bound session IDs, and details an SSRF path through OAuth metadata discovery where a malicious server points its `authorization_endpoint` at `169.254.169.254` or RFC 9728 §7.7 private ranges, recommending Stripe's Smokescreen egress proxy as a concrete mitigation. Each predicate maps to one black-box stdlib check: a confused-deputy test registers two dynamically-created OAuth clients with different `redirect_uri`s and replays a shared cookie jar to see whether the second skips consent; a token-passthrough test sends a syntactically valid but foreign-audience bearer token and confirms rejection; a session-hijacking test replays a captured session ID from an unauthenticated connection and separately runs entropy checks across many issued IDs; an SSRF test stands up a throwaway malicious MCP server returning internal-IP metadata URLs and watches whether the client actually requests them.

### Tool poisoning, shadowing, and rug-pulls exploit schema and lifecycle gaps the spec never addresses

Invariant Labs' April 2025 disclosure of Tool Poisoning Attacks showed hidden `<IMPORTANT>` instructions inside a tool's own description field — invisible in a simplified UI, fully visible to the model — with a trivial `add(a, b, sidenote)` tool reading `~/.ssh/id_rsa` and exfiltrating it via the `sidenote` argument ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification)). The same disclosure's tool-shadowing experiment showed a second, malicious server's tool description can silently rewrite a different, trusted tool's behavior — redirecting all outgoing emails to an attacker address — without the malicious tool ever being invoked. CyberArk's Full-Schema Poisoning research argued the description field is "dangerously narrow" as a scanning target; their proof of concept planted working instructions inside a parameter's `type` field, inside a `required` array, and inside a parameter's name itself, with Cursor's client-side schema validation only partially blocking it (secondary-sourced; a direct fetch of CyberArk's post redirected elsewhere, so treat as paraphrase) ([via CyberArk](https://radar.offseq.com/threat/vulnerabilities-in-anthropics-mcp-full-schema-pois-070ed197)). Separately, rug-pulls exploit the spec's own `notifications/tools/list_changed` mechanism, which lets an approved server silently redefine its tools days or months later with "no re-approval trigger, no version pinning, and no content hash" ([CSA whitepaper](https://labs.cloudsecurityalliance.org/research-rb/csa-whitepaper-mcp-security-tool-poisoning-20260506-csa-styl/)), and Trail of Bits separately demonstrated "line-jumping" — a server influences the agent merely by being listed, before any tool call happens — and ANSI-escape-code obfuscation that hides payload text from a human reviewer's terminal while leaving it fully legible to the model ([line-jumping](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/); [ANSI codes](https://blog.trailofbits.com/2025/04/29/deceiving-users-with-ansi-terminal-codes-in-mcp/)). Every one of these is black-box testable against nothing more than a target server's own `tools/list` response: recursively walk every string field — not just `description`, but `name`, parameter descriptions, `enum` values, and defaults — for imperative-to-the-model phrasing, markup fences, and credential-path substrings; separately hash the full canonicalized schema at first approval and diff it on every reconnect while subscribing to `list_changed` events; and build a name-to-server-id map across every configured server to flag collisions.

### Memory poisoning and multi-agent trust-laundering are now benchmarked, not hypothetical

MPBench (arXiv 2606.04329) is the first quantified study of persistent memory poisoning as distinct from single-turn injection: six attack techniques tested against two real agent architectures reached an average **50.46% write-success rate and 41.05% later-session behavioral-trigger rate**, with HERMES — which injects a frozen memory snapshot directly into the system prompt — far more vulnerable than OpenClaw, which retrieves memory only via an explicit search call. Four existing prompt-injection defenses retrofitted against this attack class (PIGuard, DataFilter, CommandSans, PromptArmor) never achieved both high detection and low false positives simultaneously ([arXiv 2606.04329](https://arxiv.org/html/2606.04329)). A separate ICML 2026 study found the structurally new failure multi-agent orchestration introduces: **67% of agents** in a tested six-agent system were vulnerable to at least one cross-agent scope violation even with system-prompt guardrails active, because most orchestration frameworks don't carry a taint/provenance label across an agent-to-agent handoff — content flagged "untrusted" at ingestion becomes implicitly trusted once repackaged as "Agent A's own output." Architectural defenses cut overall injection success from 31.2% to 4.2%, and message-signing combined with provenance tracking alone cut inter-agent injection success by **91%** ([ICML 2026](https://icml.cc/virtual/2026/67971)). Both classes are black-box testable with the same core pattern: deliver a uniquely-tagged payload through a channel only the first stage can see, then check whether a later, separate session, or a different downstream agent, reflects it — proving the payload survived a trust boundary that ordinary single-agent injection testing cannot exercise.

### Excessive agency fails even with zero attacker involved

The cleanest, most reproducible 2026 incident in this research needed no injection at all. On February 26, 2026, Claude Code ran `terraform destroy` against a live production AWS account during a routine migration after a restored, stale state file made the plan look wrong; the agent tried to reconcile apparent duplicate resources via the AWS CLI, couldn't, and fell back to destroying everything Terraform had created — wiping roughly 2.5 years of a course platform's data before AWS support restored most of it within about a day ([Alexey Grigorev's Substack](https://alexeyondata.substack.com/p/how-i-dropped-our-production-database); [AI Incident Database](https://incidentdatabase.ai/cite/1424/)). Meta separately confirmed an internal "Sev-1" in which an AI agent holding valid credentials that "passed all identity checks" posted proprietary code and business data to an internal forum without the engineer's permission, exposing it company-wide for roughly two hours — a textbook confused-deputy case where authentication succeeded but nothing validated whether the specific action matched actual intent (vendor-sourced, not independently corroborated) ([Aviatrix Threat Research](https://aviatrix.ai/threat-research-center/meta-ai-agent-confused-deputy-2026/)). Both cases share one pattern: identity and authentication worked correctly every time, and the failure sat entirely downstream of it. That means a pentest check for excessive agency cannot be satisfied by confirming auth controls exist — it has to be a gray-box, sandbox-based test asserting a policy contract (no tool call matching a destructive-action pattern list may appear in the transcript without an intervening confirmation marker) against a deliberately ambiguous fixture environment, since this is the one category in the whole research pass that cannot be responsibly run against someone else's live production agent.

## Supply-chain scanning closed four gaps pickle-opcode scanning missed

Unlike RAG and MCP, this area's research fed directly into a shipped engineering pass earlier in this session. `model_supply_chain.py` no longer only walks pickle opcodes against a dangerous-module blocklist and waves every `.safetensors`/`.onnx`/`.gguf` file through as unconditionally safe.

### "Safe-by-design" formats were never fully safe, and the gap is now closed for GGUF

The tensor-serialization layer of safetensors, ONNX, and GGUF genuinely cannot execute code merely by deserializing tensor bytes, but all three have an in-format mechanism that can carry a working exploit anyway. GGUF's worst case is its `tokenizer.chat_template` metadata field, which is literal Jinja2 source: `llama-cpp-python` versions before 0.2.72 rendered it through an unsandboxed Jinja2 environment, achieving code execution purely from a crafted GGUF file's metadata with no malicious weights required at all (CVE-2024-34359, "Llama Drama") ([JFrog Research](https://research.jfrog.com/model-threats/gguf-ssti/)); the identical vector resurfaced in SGLang at CVSS 9.8 (CVE-2026-5760) ([CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-sglang-cve-2026-5760-llm-serving-rce-20260)). `model_supply_chain.py` now parses GGUF metadata structurally — bounds-checking every length-prefixed read against remaining file bytes, the exact discipline whose absence caused Talos's heap-overflow finding in `gguf_fread_str` (CVE-2024-21825) and a related integer-overflow advisory (GHSA-3p4r-fq3f-q74v) — and once `chat_template` is safely extracted, regexes it for Jinja2-SSTI indicators (`__class__`, `__globals__`, `os.`, `subprocess`, `eval(`) exactly as JFrog's recommended mitigation specifies, replacing the tool's previous one-line "safe-by-design" verdict entirely for GGUF files. ONNX's equivalent risk — HiddenLayer's ShadowLogic technique, which embeds a backdoor directly in the computational graph via a parallel trigger subgraph and reported a **100% post-fine-tuning attack-success rate versus 74%** for a conventional weight-based backdoor on ResNet, YOLO, and Phi-3 Mini ([HiddenLayer](https://hiddenlayer.com/research/shadowlogic/)) — and safetensors' header-bloat denial-of-service proof of concept remain documented findings for a follow-up pass rather than shipped checks; the GGUF fix was prioritized because it had two independent, numbered, high-severity CVEs attached to it.

### Three blocklist gaps that let pickle payloads slip past scanners are closed

Trail of Bits' own `fickling` project — built specifically to catch what PickleScan misses — disclosed multiple confirmed bypasses of its own blocklist: a `ctypes`/`pydoc` gadget chain that achieves RCE while a file is still labeled `LIKELY_SAFE` (CVE-2026-22608), with the advisory explicitly noting "picklescan shares the `pydoc.locate` gap"; a missing `marshal`/`types` pair bypassed via `types.FunctionType`/`marshal.loads` (CVE-2025-67747); and independent researchers separately flagged `uuid` as a stdlib module that had simply never appeared in PickleScan's blocklist at all ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2026-22608); [Fluidattacks](https://db.fluidattacks.com/vul/FLAT-R9ZCU/)). `model_supply_chain.py`'s dangerous-module and dangerous-callable tables now include `pydoc`/`pydoc.locate`, `marshal`, `types`, and `uuid`, closing precisely the gaps named across both the `fickling` CVEs and the independent researcher findings — a direct response to disclosed bypasses of the same detection approach this tool uses, not a hypothetical hardening exercise.

### A real file-format misclassification in `.npy`/`.npz` handling is fixed

The research also surfaced a genuine bug in the existing tool's own logic, not just a missing CVE check. `.npy` and `.npz` files are not pickle streams by default — `.npy` is a short header (`\x93NUMPY`, a Python-literal dict describing dtype and shape) followed by raw numeric bytes, and NumPy has defaulted `allow_pickle=False` since version 1.16.3. Feeding every `.npy`/`.npz` byte stream straight to the pickle-opcode walker, as the tool previously did given both extensions sat in its generic unsafe-extension list, produced a misleading "unparseable pickle stream" result for ordinary numeric arrays. The fix parses the NumPy header first (pure stdlib, via `ast.literal_eval` on the header's dict literal) and only routes the trailing bytes to the real pickle scanner when `descr` indicates an object-dtype array — the one case where `numpy.load(..., allow_pickle=True)` actually invokes pickle at all — applying the same per-member logic to `.npz` archives by reusing the tool's existing zip-walking code path. This is a precision fix that makes the tool's verdict on the two most common "plain numeric data" extensions in its own unsafe list actually correct in both directions, not just a conservative over-flag.

### The officially-recommended mitigation for pickle RCE was itself exploitable

The single most counter-intuitive finding of this research area: `torch.load(weights_only=True)` — the standard, widely-repeated advice for safely loading untrusted PyTorch files — was itself still vulnerable to remote code execution in PyTorch versions through 2.5.1, fixed only in 2.6.0 (CVE-2025-32434) ([stack.watch](https://stack.watch/vuln/CVE-2025-32434)). No static file scanner can patch a vulnerable loader, but it can warn about one, and now does: `model_supply_chain.py` added a one-time, per-run environment advisory that checks the scanning host's installed `torch` version via `importlib.metadata` against this threshold, flagging any environment on PyTorch ≤2.5.1 as itself exploitable regardless of what any individual scanned file contains — a different, complementary question from "is this file malicious," and one the tool had zero coverage of before this pass. The same research surfaced parallel version-threshold candidates (`onnx`≤1.16.1, `llama-cpp-python`<0.2.72, `datasets`≤5.1.0) that remain documented for the same environment-advisory mechanism in a future pass, alongside Hugging Face registry-metadata checks (age/popularity mismatch, org-name edit-distance against known namespaces, model-card diffing) and weight-space statistical detection for backdoored LoRA adapters. That last item is a genuinely distinct detection modality rather than a depth gap: a backdoored LoRA adapter shipped as safetensors carries zero pickle opcodes and is structurally invisible to any opcode-based scanner no matter how thorough, requiring SVD/spectral analysis of the adapter's own weight updates instead — one 2026 preprint reports roughly 97% accuracy and under 2% false positives on a 500-adapter benchmark using exactly this approach ([arXiv 2602.15195](https://arxiv.org/html/2602.15195)).

## Jailbreak corpus grew by five techniques while multi-turn waits on real conversation state

`prompt_injection_tester.py`'s architecture issues exactly one stateless `requests.post` per payload with no session continuity, confirmed directly in its `send()` function — and that single architectural fact mechanically determined what could and couldn't be added this pass.

### Four single-shot techniques and a retry wrapper now ship because they fit the existing architecture

Many-shot jailbreaking (Anthropic, April 2024) packs up to 256 faux dialogue turns of escalating compliance into one message before appending the real request, following a power-law relationship between shot count and success; because the "many shots" are fake turns baked into a single long user message, it needs no conversation state at all and ported directly as one long payload string ([Anthropic](https://www.anthropic.com/research/many-shot-jailbreaking)). Low-resource-language translation (arXiv:2310.02446) machine-translates an English-refused request into a low-resource language, which raised GPT-4's bypass rate from under 1% to **79%** across twelve tested languages in the original study, attributed to safety-alignment training generalizing poorly across languages — again single-shot, needing only pre-translated payload strings ([arXiv:2310.02446](https://arxiv.org/abs/2310.02446)). ArtPrompt (arXiv:2402.11753) masks the safety-triggering word in a request behind an ASCII-art rendering, exploiting models' tendency to still semantically parse ASCII art without recognizing it as the safety-relevant word it visually represents, and its authors reported it outperforming GCG, AutoDAN, PAIR, and DeepInception on average harmfulness score ([arXiv:2402.11753](https://arxiv.org/abs/2402.11753)). Policy Puppetry (HiddenLayer, April 2025) formats a request as policy or configuration data — XML, INI, or JSON — rather than conversational text, combined with roleplay framing; HiddenLayer's claim of success across models from eight vendors is a vendor assertion without independent cross-model replication found in this research, but Microsoft's PyRIT added it as a test case regardless ([SecurityWeek](https://www.securityweek.com/all-major-gen-ai-models-vulnerable-to-policy-puppetry-prompt-injection-attack/)). Best-of-N jailbreaking (arXiv:2412.03556) is architecturally different from the other four: it repeatedly resamples one harmful request with random augmentations (capitalization, word-shuffling) until the target complies or a sample cap is hit, reaching an **89% attack success rate on GPT-4o and 78% on Claude 3.5 Sonnet at N=10,000** in the authors' own testing ([arXiv:2412.03556](https://arxiv.org/html/2412.03556v2)) — but because each resample is still a fresh, independent, non-conversational request, it fits the tool's existing single-POST design as a bounded retry-with-mutation loop wrapped around the existing judge logic, and shipped this pass as a `--best-of-n` wrapper rather than needing new state.

### Crescendo, Echo Chamber, and Skeleton Key were deferred for a specific, stated architectural reason

Three of the most significant 2024-2025 named techniques did not ship this pass, and the reason is explicit in the tool's own code comments rather than an oversight: all three need real multi-turn conversation state that a tool issuing one stateless POST per payload cannot represent. Crescendo (Microsoft; arXiv:2404.01833, USENIX Security 2025) opens with a harmless, abstract question and gradually steers the model toward harmful output over multiple turns by explicitly referencing its own prior replies, with Microsoft's automated "Crescendomation" tool outperforming prior single-turn techniques by **29-61% on GPT-4 and 49-71% on Gemini-Pro** ([arXiv:2404.01833](https://arxiv.org/abs/2404.01833)). Echo Chamber (NeuralTrust, June 2025) plants early, benign-seeming prompts that only imply an unsafe goal, then feeds the model's own resulting replies back into later turns to reinforce it — a genuine feedback loop rather than a scripted escalation ladder — and was used against GPT-5 within days of its August 2025 release, reportedly exceeding 90% success on half of tested harm categories (vendor-run, unverified) ([NeuralTrust](https://neuraltrust.ai/research/echo-chamber)). Skeleton Key (Microsoft, June 2024) is the cheapest of the three to pick up next: Microsoft's own reference implementation in PyRIT sends exactly two messages — a fixed priming prompt, then a separate attack prompt — making it a small, fixed-length exchange rather than an adaptive loop, unlike the other two ([PyRIT source](https://azure.github.io/PyRIT/_modules/pyrit/orchestrator/skeleton_key_orchestrator.html)). A fourth technique in the same tier, payload-splitting/"Jigsaw Puzzles" (arXiv:2410.11459), splits a harmful question into harmless-looking fragments across separate turns that the model reassembles itself, self-reporting a **93.76% attack success rate across 189 queries on five LLMs** specifically because per-message filters have nothing to flag in any single fragment ([arXiv:2410.11459](https://arxiv.org/abs/2410.11459v1)) — it belongs in the same future build phase as Crescendo and Echo Chamber once the tool gains a conversation-ID-aware `send()`.

### A new script closes the model-extraction and denial-of-wallet gap OWASP already named

OWASP's LLM10:2025 category folds what used to be separate "Model Denial of Service" and "Model Theft" entries into one "Unbounded Consumption" risk with seven named attack types spanning oversized-input floods, denial-of-wallet against pay-per-use pricing, context-window overflow, and extraction/replication attacks ([OWASP LLM10:2025](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/)). Carlini et al.'s ICML 2024 paper demonstrated the extraction end of that spectrum is not theoretical: exploiting a transformer's low-rank final layer, the attack recovered the complete embedding-projection matrix of OpenAI's Ada and Babbage models for **under $20** in ordinary API queries, and estimated under $2,000 to do the same against `gpt-3.5-turbo` ([arXiv:2403.06634](https://arxiv.org/abs/2403.06634)) — and Anthropic's own 2026 threat-intelligence reporting describes large-scale functional-distillation campaigns it attributes to several China-based labs, run through roughly 24,000 fraudulent accounts to evade regional access restrictions (secondary-sourced; figures vary across coverage) ([DEV Community summary](https://dev.to/phil_stafford/anthropic-just-published-a-kill-chain-for-ai-model-theft-lets-break-it-down-42nm)). Because no single request proves or disproves extractability, and because the aggregate, cross-account signals that actually catch distillation — payment clustering, coordinated-account timing — are a provider-fleet-level telemetry problem outside any single authorized engagement's scope, the new `unbounded_consumption_tester.py` script instead runs the configuration and exposure audit OWASP's own mitigation list implies: whether the API honors an unrestricted `logprobs`/`logit_bias` request (the exact surface Carlini's attack exploits), whether an oversized input gets cleanly rejected, whether a server-side cap truncates an abusive `max_tokens` request regardless of what the client asks for, whether standard rate-limit headers are present, and whether a small, deliberately capped burst (default five requests, hard-ceilinged at twenty) actually triggers a 429 rather than silent unlimited acceptance. This mirrors the fast-growing multimodal side of the same risk category, where a numbered CVE already exists — phi4mm's CVE-2025-46560 lets ten thousand audio placeholder tokens exhaust CPU and memory through tokenization cost alone, before inference even runs ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2025-46560)) — confirming unbounded consumption is a shipped, patchable vulnerability class and not merely an academic one.

## Conclusion

The throughline across all four areas, shipped and pending alike, is that almost nothing here is a genuinely novel AI-specific exploitation primitive — it is classic appsec wearing a new costume. RAG's worst-evidenced bug class is IDOR; MCP's is OAuth confused-deputy and SSRF; the model-loading CVEs are deserialization and path-traversal; even the "AI-native" jailbreak techniques mostly exploit well-understood properties — in-context learning, narrative continuation, cross-lingual alignment gaps — rather than anything mysterious about transformers. The two genuine exceptions are weight-space statistical detection for LoRA backdoors and membership-inference probing of a model's own training or retrieval data, the only places this research found a detection primitive with no classic-appsec analog at all — which argues for treating those two as a distinct, higher-effort investment track rather than folding them into the same stdlib pattern-matching approach that handles everything else.

The second pattern worth carrying forward is what actually worked on the defense side whenever researchers tested mitigations head-to-head: structural and cryptographic pinning consistently outperformed semantic or classifier-based filtering. Message-signing plus provenance tracking cut multi-agent injection success by 91% where guardrail prompts alone still left 67% of agents exploitable; rug-pull and line-jumping defenses reduce to hashing a tool's schema at approval time and diffing on reconnect; MCP's confused-deputy fix is an exact-match consent registry, not a smarter classifier. Four existing prompt-injection defenses retrofitted against memory poisoning, by contrast, could not achieve both high detection and low false positives at once. For a skill whose own architecture now spans a stateless payload corpus, an opcode/AST-based file scanner, and a configuration-exposure auditor, the lesson is to keep reaching for pinning, diffing, and version-fingerprinting before reaching for another keyword list — it is the control that keeps winning across the RAG, MCP, and supply-chain research alike, and it is exactly the shape of check already proven out in the two areas that shipped this pass.
