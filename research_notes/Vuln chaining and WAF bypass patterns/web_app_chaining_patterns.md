# Web Application Vulnerability Chaining Patterns (2023–2026)

Scope: web app / API chains only (cloud/infra chains excluded — covered separately). Goal: a catalog of *transferable chain structures* a correlation engine could encode, not just anecdotes.

## What class of primitive enables what follow-on class?

### Takeaway
Across nearly every writeup researched, the enabling primitive is almost never "high severity" on its own — it's a **boundary-crossing capability** (reach a URL you shouldn't, write a cookie you shouldn't, cache a response you shouldn't, redirect somewhere you shouldn't) that becomes dangerous only when a *second* component trusts that boundary. The through-line: **component A validates/authenticates based on an assumption that component B's behavior silently violates.**

### Cited Findings

**Pattern 1 — Open redirect enables SSRF-filter / allowlist bypass**
- SSRF filters that validate only the *first-hop* URL (hostname allowlist) can be defeated when the allowlisted host itself has an open redirect; the filter never re-validates the final destination after a 3xx. — [PortSwigger lab writeups / bug-bounty guides](https://infosecwriteups.com/from-open-redirect-to-internal-access-my-ssrf-exploit-story-10a736962f98); general pattern described in [Bugcrowd "gadgets" article](https://www.bugcrowd.com/blog/how-to-find-bugs-on-a-hardened-target-using-gadgets/)
- A 2025 writeup describes a server 302 to an internal cloud metadata URL returning a live Azure Management API token, reported to a Bugcrowd program. — [infosecwriteups via search summary](https://infosecwriteups.com/)
- Grafana CVE-2025-4123 ("Grafana Ghost"): client-side path traversal in the front-end router combined with an open redirect in the plugin-install flow let an attacker make the trusted origin load attacker-controlled JavaScript (stored XSS), which was then used for SSRF against the Image Renderer plugin and account takeover. Estimated 36%+ of internet-facing instances still vulnerable mid-2025. — [SonicWall](https://www.sonicwall.com/blog/high-severity-open-redirect-vulnerability-in-grafana-leads-to-account-takeover-cve-2025-4123), [Pentest-Tools CVE record](https://pentest-tools.com/vulnerabilities-exploits/grafana-xss-open-redirect-ssrf-via-client-path-traversal_27130)

**Pattern 2 — Client-side path traversal (CSPT) acts as "client-side SSRF"**
- The Bugcrowd gadgets article explicitly frames CSPT as "SSRF-like but for the client": an ID or path segment is concatenated unsanitized into a client-side fetch path, so `../` sequences redirect the *browser's own authenticated request* to a different, unintended API route — reaching endpoints the UI never links to, bypassing a front-end allowlist. — [Bugcrowd](https://www.bugcrowd.com/blog/how-to-find-bugs-on-a-hardened-target-using-gadgets/)
- Full chain example from that article: CSPT in a dashboard path → reaches an open-redirect endpoint (`/api/util/redirect`) → redirect target is an attacker-hosted JSON file → JSON contains an `<img onerror>` payload rendered unsanitized into the DOM (reflected/DOM XSS) → payload calls a GET-accessible (POST→GET downgrade) email-change endpoint → full account takeover. Four low/informational-grade gadgets chained into ATO. — [Bugcrowd](https://www.bugcrowd.com/blog/how-to-find-bugs-on-a-hardened-target-using-gadgets/)

**Pattern 3 — Pre-auth info leak unlocks custom crypto, which unlocks authenticated primitives**
- WhatsUp Gold chain (Progress Software, 2022, pattern still cited as canonical in 2024-25 retrospectives): (1) an anonymous render endpoint leaked every user's *encrypted* password when fed a user ID (CVE-2022-29847); (2) a separate unauthenticated evaluation page leaked the product serial number (CVE-2022-29846), which turned out to be the salt/key-derivation input for the proprietary encryption; (3) researchers built a decryptor using the product's own routines plus the leaked serial, yielding plaintext creds; (4) authenticated endpoints then allowed path-traversal file reads and a UNC-path trick that captured a Net-NTLMv2 hash (CVE-2022-29845/29848). No single CVE was critical; the vendor's own per-issue CVSS ratings undersold the combined impact. — [S-RM / SL Cyber research](https://www.slcyber.io/research/chaining-vulnerabilities-to-criticality-in-progress-whatsup-gold)

**Pattern 4 — Cookie scoping/"cookie tossing" from a weak subdomain subverts a *different* domain's OAuth/session flow**
- Researchers had JS execution on a sibling subdomain (`*.gitpod.io`) from a prior finding and asked: what can a subdomain-scoped cookie-write primitive do to a *multi-step* flow that re-reads session cookies at each hop? Answer: set a parent-domain-scoped, path-specific cookie (`Domain=gitpod.io; Path=/api/authorize`) that overrides the victim's session cookie *only* for the OAuth authorize/callback paths (cookies with more specific paths are sent first). The victim's normal browsing is untouched; only the OAuth flow silently runs as the attacker's session, so when the victim links their GitHub/Bitbucket account, it gets bound to the attacker's account. SameSite doesn't help because the write originates from a same-site subdomain. — [Snyk/Elliot Ward writeup](https://labs.snyk.io/resources/hijacking-oauth-flows-via-cookie-tossing/), inspired by [Thomas Houhou's cookie-tossing research](https://www.thomashouhou.com/post/cookie-tossing-attacks); ranked #10 in [PortSwigger Top 10 Web Hacking Techniques of 2024](https://portswigger.net/research/top-10-web-hacking-techniques-of-2024)

**Pattern 5 — Edge/CDN vs. origin URL-parsing disagreement ("parser differential") turns a broad cache rule into auth-token theft**
- ChatGPT account takeover (Harel/nokline, Feb 2024, $6,500 bounty, #9 in PortSwigger Top 10 2024): noticed shared chat links staying stale → inferred Cloudflare was caching anything under `/share/*` by *path shape*, not file extension (`Cf-Cache-Status: HIT` on a non-static URL). Hypothesis, informed by the researcher's prior Glassdoor cache-poisoning work: if the CDN and the origin decode/normalize the URL differently, a path-traversal-style payload can make the CDN cache one path while the origin actually serves another. Payload `/share/%2F..%2Fapi/auth/session?cachebuster=123` — Cloudflare treats it as a cacheable `/share/` path (never decodes `%2F..%2F`), origin resolves it to `/api/auth/session` and returns the *victim's* session/auth token into cache; attacker then requests the same URL and reads the cached victim token. — [nokline writeup](https://nokline.github.io/bugbounty/2024/02/04/ChatGPT-ATO.html)

**Pattern 6 — HTTP component "confusion" (ambiguity between front-end/back-end interpretation of the same request) as a generative source of multiple chainable primitives**
- Orange Tsai's "Confusion Attacks" research on Apache HTTP Server (#1, PortSwigger Top 10 2024; first delivered Black Hat USA 2024) treats the web server like "a CTF challenge," per fellow researcher LiveOverflow's framing, hunting for places where Apache's own internal modules (not even separate systems) disagree about how to parse the same request — yielding multiple distinct CVEs/bypasses from one systemic ambiguity rather than one isolated bug. — [Orange Tsai writeup](https://blog.orange.tw/posts/2024-08-confusion-attacks-en/)
- Related/same-family: Request smuggling via `Transfer-Encoding: 0` abuse affected thousands of Google Cloud-fronted sites (#3, 2024) — front end rewrote a chunked body to non-chunked without correcting `Content-Length`, triggered via `OPTIONS`. — [Bugcrowd writeup](https://www.bugcrowd.com/blog/unveiling-te-0-http-request-smuggling-discovering-a-critical-vulnerability-in-thousands-of-google-cloud-websites/)

**Pattern 7 — Weak/limited XSS primitives (self-XSS, POST-only XSS, HTML-injection-without-script-exec) become critical only when chained to a CSRF/method-confusion delivery mechanism**
- Bugcrowd's "gadgets" taxonomy explicitly separates *weak XSS vectors* (self-XSS, POST-only XSS, style-tag-only injection) from *delivery* gadgets: POST→GET method downgrade (an endpoint meant to require POST also accepts GET) turns a POST-only XSS into a one-click/link-deliverable exploit, and CSS-injection can be used to exfiltrate a CSRF token out-of-band, removing the need for same-origin script execution at all. — [Bugcrowd](https://www.bugcrowd.com/blog/how-to-find-bugs-on-a-hardened-target-using-gadgets/)

**Pattern 8 — CORS misconfiguration as a token-exfiltration bridge, chained with reflected auth state**
- Langflow (CVE-2025-34291, CVSS 9.4): a CORS misconfiguration combined with `SameSite=None` cookies on a token-refresh endpoint meant a victim simply visiting a malicious page triggered a cross-site authenticated request *and* let the attacker's origin read the response — authentication bypass leading to full account takeover and RCE, from two misconfigurations that individually look like "missing header hardening." — [Obsidian Security](https://obsidiansecurity.com/blog/cve-2025-34291-critical-account-takeover-and-rce-vulnerability-in-the-langflow-ai-agent-workflow-platform)
- General pattern repeatedly described by independent bounty hunters: `Access-Control-Allow-Origin` reflecting arbitrary/subdomain origins + `Access-Control-Allow-Credentials: true` lets any attacker-controlled origin (including a takeable/wildcard-matched subdomain) read authenticated API responses containing session tokens, converting a "misconfigured header" into direct credential theft. — [00xmora writeup](https://00xmora.github.io/posts/Auth-Token-Theft-via-CORS-Misconfiguration)

**Pattern 9 — Host-header trust (password-reset link construction) chained with a secondary leak/redirect to externalize the reset token**
- Multiple 2025 writeups (mailcow CVE-2025-25198, independent bounty reports) describe the reset-link generator trusting the `Host`/`X-Forwarded-Host` header to build the absolute reset URL; attacker supplies their own host, victim (or an automated system/email-preview bot) "clicks" the link, and the token lands in server logs the attacker can read, or is sent directly to the attacker's server. Chained variants add Host-header injection → XSS (if the host value is reflected unsanitized in an error/email template) → account takeover. — [Exploit-DB / mailcow advisory](https://exploit-db.com/exploits/52485); [chained writeup](https://infosecwriteups.com/how-i-chained-host-header-injection-to-password-reset-link-poisoning-to-xss-and-account-takeover-c5acad3acbb7)

**Pattern 10 — IDOR as a horizontal-privilege primitive chained with a second IDOR/CSRF for vertical escalation**
- Repeated structural pattern across many 2024-2025 writeups: IDOR #1 lets an attacker *add* a victim account to an attacker-controlled group/organization (an action that alone looks like a minor authorization gap in a low-traffic admin feature); IDOR #2 or a CSRF-able action, now reachable because the victim is "inside" the attacker's org/group, lets the attacker reset the victim's password or change their email. Neither IDOR alone reaches a sensitive object; the first one's output (group membership) is the second one's missing precondition. — [r29k Bugcrowd writeup, referenced in search](https://infosecwriteups.com/)

**Pattern 11 — GraphQL introspection as a map that turns scattered IDORs into systematic authorization bypass**
- Introspection (often shrugged off as informational since it "just" discloses schema) hands an attacker the complete list of resolvers/mutations and their argument shapes; several writeups describe using that map purely to *find* which resolvers skip an ownership check on a supplied ID (classic IDOR) far faster than black-box fuzzing, and to discover alias-batching abuse that defeats per-request rate limiting on brute-force ID enumeration. — [financial-platform case study](https://portofolio-dwforsec.pages.dev/case-study/graphql-authorization-bypass-chain); [Speednet HTB writeup](https://teto-o.github.io/blog/speednet-writeup)

### Inferences
- The recurring structural signature is: **Finding A grants a capability** (reach an internal/arbitrary URL, write/overwrite a cookie, populate a cache entry, control a Host header, see a schema, join a group) **that happens to satisfy an unstated precondition of Finding B** (an allowlist check, a trust assumption about which session cookie is "current," a trust assumption that a cached path = a static asset, a trust assumption that whoever controls the Host header is the legitimate deployment, a trust assumption that group membership implies consent). Automated scanners generally only check "does this finding violate its own spec" (e.g., "is this redirect open," "is this cookie `HttpOnly`") and never model what a *downstream* component silently assumes about the thing the first finding controls.
- Low/informational findings cluster into a few reusable "gadget" categories (redirect, CSPT, weak XSS, method confusion, Host-header trust, cookie-scope writes, cache-key/path mismatches, schema disclosure) that recombine across completely unrelated apps — this is why Bugcrowd explicitly markets "gadgets" as LEGO pieces rather than app-specific bugs.
- Researchers describe the trigger moment consistently as *noticing an anomaly outside the vuln class they were hunting* (a stale cache header, a redirect that "just" lands on-domain, a subdomain where they already had JS execution for an unrelated reason) and then asking "what does this let me reach that I couldn't reach before" rather than "is this exploitable in isolation."

## Why would isolation-testing tools miss these chains, and what triggered the researcher's "combine these" insight?

### Takeaway
In every case studied, the researcher's own account describes a shift from "is this a bug" to "what is this weird-but-technically-correct behavior, and what else on the app does it touch" — usually triggered by an observation adjacent to, not inside, their current test (a response header, a timing quirk, a prior unrelated foothold). Isolated scanners miss these because the "missing" piece is never a vulnerability in the component being tested — it's a trust assumption living in a *different* component that the scanner never correlates against.

### Cited Findings
- Bugcrowd's explicit methodology: "take notes on every quirk, including in Repeater, because small oddities may later combine with others"; ask two fixed questions per finding — "What could I do with this?" and "How can I make this gadget stronger?" — and deliberately hold low-severity findings rather than reporting them immediately as informative, specifically so they remain available to combine later. — [Bugcrowd](https://www.bugcrowd.com/blog/how-to-find-bugs-on-a-hardened-target-using-gadgets/)
- ChatGPT ATO researcher's trigger was noticing that shared chat links appeared stale (a *functional* oddity, not a security signal) and only then checking response headers for `Cf-Cache-Status: HIT`; his "what if" question was explicitly informed by *prior, unrelated* cache-poisoning research on a different target (Glassdoor), i.e., pattern recognition transferred across engagements. — [nokline](https://nokline.github.io/bugbounty/2024/02/04/ChatGPT-ATO.html)
- Cookie-tossing/OAuth researchers already held an *unrelated* foothold (JS execution on a sibling subdomain from earlier WebSocket research) and asked "what can this cookie-write primitive do to flows elsewhere on the parent domain" — the insight was to stop treating the subdomain XSS as "low impact because it's just a subdomain" and instead ask which *multi-step, cookie-dependent* flows exist anywhere on the parent domain. — [Snyk/Labs](https://labs.snyk.io/resources/hijacking-oauth-flows-via-cookie-tossing/)
- WhatsUp Gold researchers explicitly describe hitting a dead end (leaked passwords were encrypted, static analysis of a hardcoded-looking salt didn't decrypt anything) and *switching methodology* — from static review to live debugging of the running process — specifically because the chain's economic payoff (unauthenticated → full credential theft) justified the extra effort a single-bug scan would never invest. — [SL Cyber](https://www.slcyber.io/research/chaining-vulnerabilities-to-criticality-in-progress-whatsup-gold)
- Orange Tsai's Apache research is characterized by peers as treating the *server itself* as the target surface for internal logic disagreements ("like a CTF challenge") rather than testing it against a fixed checklist of known vulnerability classes — i.e., hypothesis-driven adversarial reading of the codebase for self-contradiction, not pattern-matching against OWASP categories. — [PortSwigger summary, LiveOverflow's characterization](https://portswigger.net/research/top-10-web-hacking-techniques-of-2024)

### Inferences
- A single-vulnerability-class scanner (XSS scanner, IDOR fuzzer, CORS checker, SSRF prober) by construction evaluates one endpoint/one header/one input against one rule set at a time; it has no persistent "capability ledger" tracking what an *already-confirmed* low-severity finding grants the tester (e.g., "I can now write cookies scoped to `.example.com`," "I can now make the origin server render arbitrary attacker JSON into a trusted sink," "I can now control the absolute URL in a password-reset email"). Every chain above was discovered by a human maintaining exactly that ledger across tools/sessions.
- The "trigger" is consistently *cross-context pattern transfer*: a researcher notices a behavior that looks irrelevant to the vuln class they're currently testing (a cache header while testing functionality, a redirect while testing SSRF allowlists, an existing foothold from a different bug) and re-asks "what precondition does this quietly satisfy elsewhere." This is fundamentally a graph-search operation (capability → precondition matching) rather than a classification operation, which is why classifier-style scanners don't do it natively.

### Gaps
- None of the primary sources reviewed gave a fully quantified "time spent manually chaining" figure, so there's no hard data point for how much more expensive chain-discovery is vs. single-bug discovery (would help prioritize tool investment) — flagged as a gap for the report writer to note as unresolved.

## How could a correlation engine encode detection/chain-discovery rules for these patterns?

### Takeaway
The common encoding shape across all 11 patterns is a **capability/precondition matching rule**: each finding is tagged with (a) what capability it *grants* the tester (a semantic effect, not just a CWE label) and (b) what capability it *requires* as an unmet precondition to escalate; the engine then does a graph join over the current finding set, flagging pairs/sets where one finding's granted-capability set intersects another's required-capability set.

### Cited Findings / Design Notes
*(These are concrete rule sketches derived from the patterns above, not quotes from a source — treat as original synthesis for the report writer, not a cited claim.)*

- **Capability tagging schema.** Tag every finding with structured facts instead of (or in addition to) a CWE/OWASP category, e.g.:
  - `grants: {redirect_to: arbitrary_url, scope: on-domain}` for an open redirect
  - `grants: {write_cookie: true, cookie_domain: parent, path_scope: specific}` for a subdomain XSS/cookie-tossing foothold
  - `grants: {read_response_cross_origin: true, credentials: true}` for a CORS misconfig
  - `grants: {control_header: Host, reflected_in: [email_template, reset_link, error_page]}` for Host-header trust issues
  - `grants: {cache_write: true, cache_key_granularity: path_prefix}` for an over-broad cache rule
  - `grants: {bypass_filter: allowlist_hostname_only}` for an SSRF filter that doesn't re-validate redirect targets
  - `requires: {final_destination_validated: false}` as the SSRF endpoint's own unmet precondition, which the open redirect's `grants.redirect_to` satisfies — **rule: flag SSRF-endpoint finding + open-redirect finding whenever the redirect's target domain is in the SSRF endpoint's allowlist.**
  - `requires: {session_cookie_authoritative: assumed}` as the OAuth-callback endpoint's precondition — **rule: flag any finding granting `write_cookie` on a domain/path that overlaps an OAuth callback/authorize path's cookie-read scope.**
  - `requires: {path_normalization_consistent_with_origin: assumed}` as a cache rule's precondition — **rule: flag whenever a cache rule's matched path prefix is tested against both the edge's and origin's URL-decoding behavior and they diverge (double-decode, encoded traversal sequences, encoded slashes) AND a sensitive same-path-prefix endpoint exists at the origin.**
  - `requires: {redirect_url_absolute_trust: host_header}` — **rule: flag Host-header-reflected-into-absolute-URL findings whenever that URL is subsequently emailed, logged to an externally-readable sink, or rendered unescaped (chain to XSS).**
  - `requires: {resource_owner_check: present}` as every object-access endpoint's nominal precondition — **rule: when GraphQL/REST introspection or schema disclosure yields a resolver/endpoint list, auto-queue each resolver for an automated IDOR probe (swap the ID/owner param for a second test account's ID) rather than treating introspection as a standalone informational finding.**
  - **Sequencing/graph rule:** maintain a directed "capability graph" per target: nodes = findings, edges = `A.grants ⊇ B.requires`. Any path of length ≥2 through the graph is a candidate chain; rank candidates by the severity delta between the weakest node and the strongest downstream node reachable (this captures exactly the "low+low=critical" economics bounty programs reward).
  - **Method-confusion rule:** for any finding tagged `requires: delivery_mechanism` (self-XSS, POST-only XSS), cross-check whether the *same* endpoint, or the vulnerable parameter's sink endpoint, also accepts GET/accepts method override params (`_method`, `X-HTTP-Method-Override`) — if so, upgrade severity and flag as a CSRF-deliverable chain.
  - **Cross-session/cross-engagement memory:** persist the capability tags *per researcher/per tool instance* across targets (not just per-target), since multiple real chains above were found by recognizing a pattern from a *previous, unrelated* engagement (ChatGPT ATO ← Glassdoor cache poisoning). A correlation engine with a long-lived pattern library (rather than a fresh model per scan) would catch repeat structural matches a per-target-only tool cannot.

### Gaps
- None of the primary sources describe an existing automated tool that implements this capability-graph approach for web-app chains specifically (tools like this exist more for binary/cloud IAM graph chaining); this section is original synthesis rather than a reported existing implementation, and should be labeled as such in the final report.
