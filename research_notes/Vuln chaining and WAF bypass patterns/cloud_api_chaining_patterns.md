# Cloud Infrastructure & API/GraphQL Vulnerability Chains (2023-2026)

Scope note: classic client-side web chains (simple XSS/CSRF) are excluded per assignment; this catalog focuses on cloud provider (AWS/Azure/GCP), SaaS/cloud-native, CI/CD, and API/GraphQL chaining patterns. Several of the strongest primary sources found were vendor-appliance and supply-chain chains rather than pure bug-bounty writeups — these are included because they contain the transferable chaining *structure* the correlation engine needs, which is the stated objective.

## What class of primitive commonly enables what class of follow-on primitive in cloud/API contexts?

### Takeaway
Across every chain found, the enabling pattern is the same shape: a primitive that looks like "just information disclosure" or "just a missing check" in isolation turns into credential/code-execution material once it's traced across a trust boundary (project/tenant, pipeline stage, or build layer) that a single-surface scanner never crosses. The most common enabling pairs are: SSRF → cloud metadata/IMDS → IAM credentials → lateral movement; predictable/guessable cloud resource name + missing ownership check → cross-tenant resource hijack → code execution via a trusted deserialization path; CI/CD permission laxity (branch protection / approval bot / environment secrets) → unreviewed code or stolen token → artifact publish/deploy with no gate → production RCE; exposed build artifact (Docker image, git history) → leftover credential in an image layer or git config → registry/package write access → supply-chain poisoning; GraphQL introspection → undocumented/internal mutation name → missing per-field authorization → privilege escalation or mass data exposure; vendor-appliance auth bypass + a second, independently-unremarkable bug (XXE, OOB write, hardcoded default credential) → pre-auth RCE.

### Cited Findings
- SSRF reaching AWS EC2 Instance Metadata Service (IMDS) remains an active exploitation pattern; threat actors have been chaining SSRF with IMDSv1 exposure since mid-March 2025 to steal IAM role credentials, and moving to IMDSv2 is identified as the single most effective control against it even when an app-level SSRF still exists — [cybersecuritynews.com](https://cybersecuritynews.com/hackers-exploiting-ec2-instance-metadata-vulnerability), [resecurity.com](https://www.resecurity.com/blog/article/ssrf-to-aws-metadata-exposure-how-attackers-steal-cloud-credentials).
- CVE-2025-29972, an SSRF in Microsoft Azure's Storage Resource Provider (CWE-918, critical severity, reported as CVSS 9.8–9.9 depending on tracker), was chained ("Cloud-Wide Contamination") by Cyera researcher Vladimir Tokarev into a multi-stage attack that moved from a classic SSRF through token abuse and lateral movement to regenerating a victim's SFTP passwords, crossing four distinct security boundaries (tenant, control-data, service-trust, network) — [CODE BLUE 2025 talk listing](https://codeblue.jp/en/program/time-table/day2-t1-03), [dev.classmethod.jp summary](https://dev.classmethod.jp/articles/codeblue-2025-day2-track1-1040/), [radar.offseq.com CVE detail](https://radar.offseq.com/threat/cve-2025-29972-cwe-918-server-side-request-forgery-ssrf-in-microsoft-azure-storage-resource-provider-srp-aeb9be).
- Varonis's "Shadow Dependency in GCP Dataflow" research chained: (1) Apache Beam's Python SDK deriving a default staging-bucket name deterministically from project ID + region (not secret, hence guessable), (2) the Python SDK (unlike the Java SDK) not checking who owns an existing bucket with that name before reusing it, (3) GCS's global bucket namespace meaning "whoever creates the name first, wins" across tenants, (4) the `--save_main_session` pipeline option pickling the global session state, which every worker unpickles (arbitrary code execution via `__reduce__`), (5) no integrity verification on staged artifacts at the time, and (6) broadly privileged default worker service accounts raising the payoff of code execution — [varonis.com](https://www.varonis.com/blog/shadow-dependency-in-gcp-dataflow-cross-tenant).
- A Lupin & Holmes researcher earned $50,500 by chaining: npm namespace reconnaissance from front-end JS → a public DockerHub image containing proprietary backend source *and* a leftover `.git/config` with a base64 GitHub Actions auth token → a timing/race-condition argument (citing a Unit42 precedent) that the Actions token was likely still valid because the image push happened before the workflow's final steps (staging deploy + Slack notify) completed → a Dockerfile that copied in and later deleted an `.npmrc` with an npm token, which was still recoverable from an earlier, immutable image layer using layer-inspection tools (`dive`, `dlayer`) → write access to a privately-scoped npm package pulled automatically by caret-range (`^4.12.0`) dependencies across developer machines, CI runners, and production — [depi.security (formerly landh.tech)](https://depi.security/blog/20250211-hack-supply-chain-for-50k/).
- A Citadelo CI/CD assessment got a Node.js webshell into an OpenShift (OCP4) production cluster by chaining: (1) an org setting that let the GitHub Actions bot (running as `GITHUB_TOKEN`) count toward required PR approvals despite not being an org member, letting an attacker with PR-write access self-approve a merge into a "protected" branch; (2) no branch protection / no protected environments / no environment-scoped secrets on the application repo, so anyone with write access could read CI secrets, modify the pipeline (e.g., remove SAST steps), or abuse self-hosted runners; (3) Artifactory X-ray flagging the malicious Docker image as critical-vulnerable but nothing gating or requiring review before production deployment — [citadelo.com](https://citadelo.com/en/blog/cicd-security-assessment-255c8).
- "The Trojan PR" describes pipeline poisoning via GitHub Actions achieved by modifying a build wrapper script in a PR to exfiltrate environment variables/secrets during CI execution; the author notes the program initially disputed it as a "trust boundary" issue rather than accepting it outright at high severity, which is a useful signal about how triage underrates pipeline-poisoning reports — [infosecwriteups.com](https://infosecwriteups.com/the-trojan-pr-achieving-code-execution-in-github-actions-via-pipeline-poisoning-a3494bde3f70).
- watchTowr Labs' BMC FootPrints writeup documents four distinct vulnerabilities disclosed together, explicitly built around "our discovery process... and their eventual chaining," including an authentication bypass (WT-2025-0069) chained into remote code execution — [labs.watchtowr.com](https://labs.watchtowr.com/) (BMC FootPrints post referenced via search; URL not independently re-verified in this pass — flagged as a gap below).
- watchTowr Labs' Commvault research (CVE-2025-34028 context) describes two separate pre-auth RCE chains against the same product: one exploitable on any unpatched instance, a second that additionally depends on a common real-world condition (the built-in admin password never having been changed since install) — reported via search summary of labs.watchtowr.com content.
- watchTowr's SysAid On-Premise research chained a pre-authenticated XXE in the `/mdm/checkin` endpoint with a second, separately-rated XXE in `/lshw` (CVE-2025-2775 / CVE-2025-2776, CVSS 9.3) into a pre-auth RCE chain — reported via search summary of labs.watchtowr.com content.
- GraphQL introspection is repeatedly used as the recon step that reveals mutation names; the actual exploitable bug is almost always a missing per-mutation/per-field authorization check rather than introspection itself — e.g., a writeup describing a hidden bulk-transaction mutation reachable without authorization (€900 bounty) and a separate case of a `updateUser(id, isAdmin: true)`-style mutation lacking authz — [undercodetesting.com](https://undercodetesting.com/unmasking-hidden-graphql-endpoints-how-introspection-led-to-a-e900-bounty/), [infosecwriteups.com (0x4bdo)](https://0x4bdo.medium.com/how-i-hacked-a-user-management-system-and-found-3-critical-graphql-vulnerabilities-4362eff1a38f).
- StackHawk's documentation frames the mechanism generally: knowledge of available mutations and subscriptions (via introspection) "provides attackers with specific targets for privilege escalation" — introspection is the map, not the weapon — [docs.stackhawk.com](https://docs.stackhawk.com/vulnerabilities/90054/).

### Inferences
- The recurring structural move is **"trust inherited across a boundary that was never explicitly checked."** In the GCP Dataflow case the boundary is project/tenant ownership of a bucket name; in the CI/CD cases the boundary is "did a human actually review this" vs. "did something that merely looks like review (a bot, an unprotected environment) satisfy the gate"; in SSRF→IMDS the boundary is "the app's own trust zone" vs. "the hypervisor's instance-identity zone"; in GraphQL the boundary is "the schema says this field exists" vs. "the resolver actually checks who's asking."
- Appliance/vendor chains (watchTowr) differ from bug-bounty API chains in that the "primitives" are heterogeneous bug classes (XXE + XXE, auth-bypass + RCE) rather than architectural trust-boundary gaps — but the chaining logic ("bug A removes a guard that bug B needs to be pre-auth/remote") is the same transferable structure a correlation engine should model.
- Supply-chain chains (Lupin & Holmes) show that **artifact immutability is itself an attack-enabling primitive**: Docker's layer model preserves "deleted" secrets, and this is a distinct, specific thing a tool should fingerprint (scan all layers of an image including intermediate ones, not just the final flattened filesystem).

## What made each chain non-obvious to a tool testing each class in isolation, and what was the researcher's actual reasoning process?

### Takeaway
In every case, the "non-obvious" quality comes from the chain requiring either (a) reasoning across two different systems/services that each have their own narrow test surface (SDK vs. storage service vs. compute workers; repo settings vs. CI bot identity vs. artifact registry), or (b) a timing/ordering precondition (a token still valid during a race window, a bucket that must be claimed before the victim's first default job) that stateless, single-pass scanners don't model, or (c) treating a "deleted" or "closed" artifact (an old git object, a docker layer, a conversational introspection response) as still-live data.

### Cited Findings
- Varonis explicitly frames the Dataflow chain as hard for scanners because "each piece looks benign in isolation" (predictable name = naming convention; `--save_main_session` = documented feature; pickle = known tool; missing ownership check = an absence, not a signature) and because it "depends on state and ordering" — the attacker must create the bucket before the victim's first default-bucket job in that region and swap the staged file before workers boot, which per-component tests rarely model — [varonis.com](https://www.varonis.com/blog/shadow-dependency-in-gcp-dataflow-cross-tenant).
- The researcher's traced reasoning sequence in that case: start from the open-source Beam SDK (not the managed Dataflow service) → read how it picks a default staging bucket → notice the name is deterministic and ownership is unchecked in the Python SDK specifically (vs. Java SDK, which does check) → trace what's uploaded to/downloaded from that bucket → recognize the pickled session file is a code-execution artifact, not configuration → connect "attacker-owned bucket at a predictable name" to "delivery channel for code workers will run" → add the timing/ordering precondition — [varonis.com](https://www.varonis.com/blog/shadow-dependency-in-gcp-dataflow-cross-tenant).
- In the Lupin & Holmes chain, the researcher's documented reasoning explicitly targeted a recently-acquired subsidiary on the theory that "newly acquired companies often lag behind the parent's security standards," then followed a cross-system trail: front-end JS → npm namespace → (no public packages, but a claimed namespace implies private ones exist) → GitHub code search (dead end) → plain Google search → DockerHub org → exposed image → `.git/config` → GitHub Actions token → (reasoning about workflow step ordering to argue the token was still live) → Dockerfile `.npmrc` copy-then-delete pattern → extraction from an immutable earlier image layer via `dive`/`dlayer` → recognizing that caret-range (`^`) dependency pinning means a malicious publish propagates silently across dev machines, CI, and prod — [depi.security](https://depi.security/blog/20250211-hack-supply-chain-for-50k/).
- The Citadelo CI/CD chain's non-obviousness comes from each weakness being a *default or absence* rather than an active bug: GitHub Actions bots counting toward PR-approval quorums is an org *setting*, missing branch protection is an absence of a control, and Artifactory X-ray flagging-but-not-blocking is a configured-but-toothless gate. None of these would register on a vulnerability scanner looking for a CVE or injection flaw; the researcher's framing is explicitly "no single flaw was enough on its own... each weakness removed one safeguard" — [citadelo.com](https://citadelo.com/en/blog/cicd-security-assessment-255c8).
- The SSRF→IMDS pattern is non-obvious to isolated testing specifically when IMDSv1 is in play: the SSRF scanner finds "the app will fetch an attacker-supplied URL," but the *impact* (stealing an IAM role's temporary credentials) only exists because of a second, independent configuration choice (IMDSv1 enabled, no required token) at the instance/infra layer that a web-app scanner never inspects — [cybersecuritynews.com](https://cybersecuritynews.com/hackers-exploiting-ec2-instance-metadata-vulnerability), [resecurity.com](https://www.resecurity.com/blog/article/ssrf-to-aws-metadata-exposure-how-attackers-steal-cloud-credentials).
- GraphQL introspection-based chains are non-obvious to field-by-field scanning because the vulnerable condition is *relational* — a mutation exists, a role-check exists on 9 similar mutations but was forgotten on the 10th — and introspection output alone doesn't tell a scanner which specific mutation lacks the check; that requires actually invoking it with a lower-privileged credential and diffing the result against the expected authorization boundary — [docs.stackhawk.com](https://docs.stackhawk.com/vulnerabilities/90054/), [undercodetesting.com](https://undercodetesting.com/unmasking-hidden-graphql-endpoints-how-introspection-led-to-a-e900-bounty/).

### Inferences
- A common thread in researcher reasoning is **"treat a closed/deleted/expired-looking artifact as still potentially live"**: a GitHub Actions token that "should" have expired by workflow end, a `.npmrc` secret "deleted" in a later Docker layer, a `.git/` directory left in a published image. Tools that only inspect the *current* state of a resource (final image filesystem, current token validity at scan time) will systematically miss this class.
- Another common thread is **reasoning about defaults and conventions as attack surface**, not just explicit misconfigurations: GCP Dataflow's deterministic bucket-naming convention, GitHub's default behavior of letting Actions bots count toward approvals, npm's caret-range convention. A correlation engine needs a knowledge base of "known risky default behaviors per platform/SDK," not just a generic misconfiguration scanner.
- The watchTowr-style vendor chains suggest a different but related non-obviousness: individually-patched-looking CVEs (two different XXEs, an auth-bypass CVE and an RCE CVE) are disclosed as a *set* specifically because the vendor/researcher chain-tested them together; a scanner that checks each CVE's patch status independently would conclude the system is "mostly patched" while missing that the remaining unpatched piece combined with a seemingly unrelated low-severity issue still yields full pre-auth RCE.

### Gaps
- None of the fetched sources gave explicit confirmation that any of these researchers used or evaluated automated tooling against the same target before finding the chain manually (i.e., there's no direct "the scanner said X, but I found Y" quote) — the "why tools miss it" analysis above is inferential, built from the structure of each bug, not a direct researcher statement in most cases. This should be flagged to the report writer as inference, not direct testimony, except where explicitly marked as a researcher's own framing (Varonis, Citadelo).

## How should a security-testing tool's correlation engine encode detection/chain-discovery rules for these patterns?

### Takeaway
Each pattern type below maps to a concrete, encodable correlation rule: track primitives as typed facts tagged with the trust-boundary/tenant/pipeline-stage they were observed in, then fire on specific cross-boundary graph edges rather than on single findings.

### Cited Findings / Pattern-to-Rule Mapping
(No new external citations in this section beyond those above; this section synthesizes the preceding findings into actionable rule logic as the objective requires.)

- **Pattern 1 — SSRF → Cloud Metadata → IAM credential → lateral movement.**
  Structure: an SSRF primitive whose target host resolves to `169.254.169.254` (AWS/GCP) or `169.254.169.254`/Azure IMDS endpoint, combined with the instance/function not enforcing IMDSv2 (session-token-required) or not having metadata access blocked at the hypervisor/network layer.
  Rule logic: tag every confirmed SSRF finding with "can reach link-local (169.254.169.254) range: yes/no/untested." If yes, chain-correlate with an infra-layer fact "IMDSv1 enabled on target compute resource" (collected via a separate cloud-config check, e.g., `DescribeInstances` `MetadataOptions.HttpTokens != required` on AWS, or GCP/Azure equivalents). If both facts are true in the same asset, auto-escalate the SSRF finding's severity and auto-generate the next step: attempt metadata credential retrieval, then correlate the retrieved IAM role ARN against the asset inventory's permission graph to flag reachable lateral resources (other buckets, other compute, other secrets-manager entries this role can read).
  Source basis: [cybersecuritynews.com](https://cybersecuritynews.com/hackers-exploiting-ec2-instance-metadata-vulnerability), [resecurity.com](https://www.resecurity.com/blog/article/ssrf-to-aws-metadata-exposure-how-attackers-steal-cloud-credentials).

- **Pattern 2 — Predictable cross-tenant resource name + missing ownership check → trusted-deserialization RCE.**
  Structure: a resource-naming scheme derived deterministically from a non-secret identifier (project ID, account ID, org slug) in a *global* namespace (bucket names, package names, DNS names), where the consuming service does not verify the resource's owner before trusting its contents, AND where the content path leads to code execution (pickle/deserialization, dynamically loaded config, executed script).
  Rule logic: build a rule that (a) flags any SDK/service behavior generating resource names via a documented deterministic formula from non-secret inputs; (b) flags any code path that reads from a "default/implicit" resource location without an explicit ownership/ACL verification step; (c) flags any content-processing step on that resource that uses an unsafe deserialization format (pickle, YAML `unsafe_load`, PHP `unserialize`, etc.). Fire the correlation only when all three co-occur on the same resource-name derivation path — this is a 3-fact AND rule across SDK-behavior docs/code, a missing-check static/dynamic test, and a deserialization-sink match.
  Source basis: [varonis.com](https://www.varonis.com/blog/shadow-dependency-in-gcp-dataflow-cross-tenant).

- **Pattern 3 — CI/CD approval-quorum weakness + unprotected secrets/environment + missing artifact gate → production RCE.**
  Structure: (a) a bot/service identity (e.g., `GITHUB_TOKEN`-driven Actions bot) counts toward a human-approval requirement; (b) the repo/environment has no branch protection or no environment-scoped secrets, so write access implies secret/pipeline access; (c) a security scan (SAST/container scan) result is advisory only, with no enforced block-on-critical gate before deploy.
  Rule logic: model the CI/CD pipeline as a directed graph of (actor-identity → permission → pipeline-stage → deploy-target). Encode three independent boolean checks against the platform's API/config: `approvers_include_non_human_identity == true`, `branch_protection_required_reviews == 0 OR bot_can_satisfy_review == true`, `deploy_gate_blocks_on_scan_result == false`. Any single true is a medium finding; co-occurrence of all three on the same repo→pipeline→prod-deploy path is the chain — auto-generate the finding "PR-write access = production deploy capability, unreviewed."
  Source basis: [citadelo.com](https://citadelo.com/en/blog/cicd-security-assessment-255c8).

- **Pattern 4 — Exposed build artifact (Docker image / public repo) containing a live-build-time secret or a "deleted but still-present-in-history" secret → registry/package write access → supply-chain poisoning.**
  Structure: a publicly reachable Docker image or repository contains (a) VCS metadata (`.git/config`, `.git/HEAD`) with embedded auth tokens from the build environment, and/or (b) a secret file that was copied into an image layer and deleted in a *later* layer, remaining recoverable in an earlier, still-present layer.
  Rule logic: for any publicly accessible container image, run a rule that doesn't just scan the final flattened filesystem but enumerates *every layer* and diffs added-then-removed files, flagging any removed file that matches secret-pattern regexes (npm tokens, AWS keys, `.netrc`/`.npmrc`/`.git-credentials` patterns) found in any earlier layer. Separately, for any `.git/config` found in an exposed image or bucket, extract and classify any embedded `Authorization:`/token header, and flag it as "potentially-still-valid CI token" with a timestamp-based race-window heuristic (token issued at build time X, workflow steps after image-push Y; if Y includes deploy/notify steps, the token's live-window likely extends past the point of public exposure).
  Source basis: [depi.security](https://depi.security/blog/20250211-hack-supply-chain-for-50k/).

- **Pattern 5 — GraphQL introspection → enumerated mutation/field inventory → per-field authorization-check gap → privilege escalation or mass data exposure.**
  Structure: introspection (or a leaked/cached schema, or schema reconstruction via error-based field-guessing when introspection is disabled) yields the full set of mutations/queries; the actual vulnerability is that authorization middleware is applied inconsistently (e.g., applied at the query-root level for 90% of mutations but missing on an admin-style or bulk-action mutation).
  Rule logic: enumerate the full schema (via introspection if enabled, or via a wordlist/diff-based blind schema-reconstruction fallback if disabled). For every mutation/query, execute it twice: once with no/low-privilege credentials, once with the expected-privileged credentials, and diff the authorization-relevant response signals (HTTP status, error message pattern, data returned). Build a baseline "expected-protected" set by clustering mutations with similar naming/argument patterns (e.g., anything matching `set*Role`, `update*Admin`, `*Transfer`, `delete*`) and flag any member of that cluster that returns success/data under low-privilege execution while its siblings correctly reject it — this sibling-inconsistency check is the automatable proxy for "the authz check was forgotten on this one."
  Source basis: [docs.stackhawk.com](https://docs.stackhawk.com/vulnerabilities/90054/), [undercodetesting.com](https://undercodetesting.com/unmasking-hidden-graphql-endpoints-how-introspection-led-to-a-e900-bounty/), [infosecwriteups.com (0x4bdo)](https://0x4bdo.medium.com/how-i-hacked-a-user-management-system-and-found-3-critical-graphql-vulnerabilities-4362eff1a38f).

- **Pattern 6 — Independently-rated vendor CVEs/bugs chained for pre-auth RCE (appliance pattern, generalizable to SaaS multi-component systems).**
  Structure: two or more bugs disclosed/patched as separate CVEs (e.g., an auth-bypass + an RCE, or two XXEs in different endpoints) are only "fully patched" when both are addressed; checking patch-level/CVE-presence independently per component misses that one unpatched low/medium-severity piece plus a seemingly-unrelated already-known issue still composes to full compromise.
  Rule logic: maintain a chain-registry keyed by product+version mapping "CVE-A (e.g., auth-bypass) + CVE-B (e.g., arbitrary-endpoint RCE) = pre-auth-RCE-if-both-unpatched," sourced from vendor/researcher disclosure write-ups (this is inherently a curated-knowledge-base rule, not a dynamically discovered one, since it requires the same prior human disclosure research this report performs). Correlate against asset inventory's per-component patch levels and fire when the *set* of unpatched CVEs on one asset matches a known chain entry, even if no single CVE in the set is itself critical.
  Source basis: watchTowr Labs BMC FootPrints / Commvault / SysAid chain disclosures (search-summary sourced; see Gaps above for verification caveat).

### Inferences
- A unifying implementation principle across all six rule types: the correlation engine needs a **typed fact store with trust-boundary/tenant/pipeline-stage tags on every primitive**, plus a small library of **cross-boundary join rules** (SSRF-reaches-metadata-range AND imdsv1-enabled; bot-counts-as-approver AND no-branch-protection AND no-deploy-gate; sibling-mutation-authz-inconsistency), rather than a single "chain scoring" heuristic. Each pattern above is essentially a multi-table JOIN over facts collected by otherwise-independent single-purpose scanners (SSRF scanner, cloud-config auditor, CI/CD config auditor, container-layer scanner, GraphQL fuzzer, CVE/patch-level tracker).
- The sibling-inconsistency heuristic (Pattern 5) and the layer-diff heuristic (Pattern 4) are the two most concretely automatable rules found in this research — both rely on *differential* testing (compare across siblings, compare across layers/time) rather than single-point signature matching, which matches the broader inference that "chains are relational, not detectable by single-point signatures."

### Gaps
- No source provided pseudocode or an actual implemented detection rule from a named commercial/open-source tool (e.g., no confirmation that Nuclei, Burp, or a named ASM platform already encodes any of these six rules) — the rule logic above is this researcher's synthesis from the chain structure described in the sources, not a reproduction of an existing tool's documented ruleset. This should be treated as a design proposal, not a verified existing implementation, when the report writer incorporates it.
