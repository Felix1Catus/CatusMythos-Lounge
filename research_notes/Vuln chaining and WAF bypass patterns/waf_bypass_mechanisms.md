# WAF / Bot-Detection / Rate-Limit Bypass Mechanisms (2023–2026, weighted 2024–2026)

## Key Question 1: HTTP request smuggling via WAF/origin discrepancies (desync attacks) — what specific parser differences are exploited in 2024–2026 research?

### Takeaway
2024–2026 desync research (led by James Kettle/PortSwigger) moved past classic CL.TE/TE.CL into: (a) HTTP/2-to-HTTP/1.1 downgrade smuggling at CDNs that silently downgrade upstream connections, (b) chunk-extension parsing laxness as a new desync primitive, (c) `Expect: 100-continue`-based 0.CL smuggling, and (d) an emerging "shared-parser confusion" / AI-assisted fuzzing class (HTTP Terminator) that found new desync triggers by exploring ~30,000 candidate vectors. The structural argument (PortSwigger's "HTTP/1.1 Must Die") is that *any* HTTP/1.1 hop between WAF/CDN and origin remains exploitable because front-end and back-end disagree on where one request ends and the next begins — no single patch fixes the class, only end-to-end HTTP/2 does.

### Cited Findings
- **Chunk-extension desync (Imperva, patched on Imperva's own cloud WAF):** Chunked `Transfer-Encoding` chunk-size lines may carry optional `;extension` syntax after the hex size. A bare semicolon with no extension name is RFC-malformed. The front-end tolerates this malformed chunk-extension and treats the whole byte stream as one request; the back-end instead treats the newline right after the semicolon as the end of the chunk-size line, so it parses a *different* message boundary. This lets an attacker append a second, fully independent HTTP request (e.g. `GET /admin`) after what the front-end thinks is still inside the first request's chunked body — the back-end splits it out and processes it as a real, un-inspected request. — [Imperva](https://www.imperva.com/blog/smuggling-requests-with-chunked-extensions-a-new-http-desync-trick/)
- **0.CL via `Expect: 100-continue` (PortSwigger, James Kettle, "HTTP/1.1 Must Die"):** With `Expect: 100-continue`, a client normally sends headers, waits for a `100 Continue`, then sends the body. Some front-ends correctly forward the `Expect` header but get confused when the back-end's *first* response is not `100 Continue` — the front-end "forgets" it still needs to relay a body, so the back-end is left expecting a body (`Content-Length: N`) that never arrives from that logical request; the next request on the reused connection supplies the missing bytes, which get spliced onto the end of the previous request's body as a smuggled prefix (0.CL / CL.0 family). Obfuscated `Expect` values (e.g. `Expect: y 100-continue`, seen on GitLab) exposed far more vulnerable targets than the plain header. WAF regex rules are commonly written against obfuscated `Transfer-Encoding` headers, not `Expect`, so this class evades existing WAF smuggling signatures entirely. — [PortSwigger research](https://portswigger.net/research/http1-must-die)
- **0.CL at Akamai (CVE-2025-32094):** A 0.CL variant discovered by Kettle, presented at Black Hat USA 2025/DEF CON 33, affected Akamai's infrastructure and was assigned CVE-2025-32094. PortSwigger built the new 0.CL detection methodology into Burp Suite Professional/DAST. — [SecurityWeek](https://www.securityweek.com/new-http-request-smuggling-attacks-impacted-cdns-major-orgs-millions-of-websites/), [PortSwigger blog](https://portswigger.net/blog/http-1-1-must-die-dafydd-stuttard-on-what-this-means-for-enterprise-security)
- **Parser-discrepancy taxonomy (V-H / H-V):** PortSwigger's framework classifies smuggling-enabling discrepancies as Visible-Hidden (a masked/obfuscated header, e.g. a mutated `Host`, is seen by the front-end but hidden from the back-end) or Hidden-Visible (reverse). The research explicitly challenges the older assumption ("Lie 2") that "an HTTP/1.1 desync can only be caused by a [Content-Length/Transfer-Encoding] parser discrepancy" — other header/connection-handling disagreements independently cause desync. — [PortSwigger research](https://portswigger.net/research/http1-must-die)
- **Response Queue Poisoning (RQP) reliability problem:** RQP against GitLab worked but is "tricky on low-traffic targets due to an inherent race condition" — the attacker's team needed roughly 27,000 requests to succeed reliably, because the poisoned response has to land exactly between two specific victim requests. — [PortSwigger research](https://portswigger.net/research/http1-must-die)
- **HTTP Terminator (2026, AI-assisted fuzzer by Kettle, open-sourced by PortSwigger):** Explored ~30,000 candidate desync vectors and produced novel desync triggers, including what PortSwigger describes as a "dual-matching Content-Length pattern" and a "dangling-byte" technique engineered specifically to remove the race condition that makes RQP unreliable — it deliberately leaves a smuggled request exactly one byte short so the back-end does not emit its second (poisoned) response until a genuine victim request supplies the missing byte, converting RQP from probabilistic to deterministic. This also surfaced a "shared-parser confusion" class and a human-guided discovery of a desync zero-day in Apache Traffic Server (reported as CVE-2026-63078, **unverified** in CVE.org/NVD as of the source's check). Treat exact terminology/CVE as from a single secondary outlet (The Hacker News) pending the primary PortSwigger write-up. — [The Hacker News via search summary](https://thehackernews.com/2026/08/ai-assisted-http-terminator-finds-novel.html)
- **HTTP/2 downgrade smuggling (H2.TE class):** Apache Traffic Server (CVE-2026-58150, versions 9.0.0–9.2.14 and 10.0.0–10.1.3) fails to strip/reject the `Transfer-Encoding` header when downgrading an incoming HTTP/2 request to HTTP/1.1 for the backend — the classic H2.TE downgrade-smuggling primitive. Mitigation cited is disabling HTTP/2 until patched. Kettle's broader argument: many CDNs advertise HTTP/2 support to clients but silently downgrade to HTTP/1.1 on the backend leg, re-introducing every HTTP/1.1 parser-discrepancy bug even for clients that never spoke HTTP/1.1. — [SentinelOne CVE DB](https://www.sentinelone.com/vulnerability-database/cve-2026-58150/), [PortSwigger research](https://portswigger.net/research/http1-must-die)
- **h2 Python library (CVE-2025-57804):** HTTP/2-to-HTTP/1.1 downgrade smuggling via insufficient validation of header names/values before downgrade — illegal characters in headers survive the translation and are reinterpreted by the HTTP/1.1 parser. — [Red Hat Bugzilla](https://bugzilla.redhat.com/show_bug.cgi?id=2390942), [GitHub Advisory](https://www.cvelogic.com/github-advisories/GHSA-847f-9342-265h)
- **Request tunnelling via keep-alive (Thomas Stacey/Assured):** Distinct from smuggling — abuses persistent/keep-alive connections so that a "tunnelled" request bypasses WAF rules, access controls, and header rewrites applied only to the first request on a connection, because the proxy/WAF applies its inspection logic per-connection-setup rather than per-request. — [Assured](https://www.assured.se/posts/the-single-packet-shovel-desync-powered-request-tunnelling)

### Inferences
- The center of gravity in 2024–2026 desync research has shifted from "find a new CL/TE header combination" to "find any place two layers disagree about message framing" — Expect-header confusion, chunk-extension laxness, and H2-downgrade header stripping are functionally the same bug class (shared framing state across a trusted hop) wearing different syntax.
- WAF vendors' smuggling detection is still substantially signature-based against known obfuscated `Transfer-Encoding`/`Content-Length` patterns; techniques that route around those two headers entirely (Expect-based 0.CL, chunk-extensions) are reported as bypassing WAF rules specifically because the WAF's smuggling ruleset doesn't model them.
- The "dangling-byte" RQP refinement, if confirmed, converts response queue poisoning from a noisy/statistical attack into a reliable, two-request attack — this would materially lower the automated-testing cost for RQP-class findings.

## Key Question 2: Encoding/normalization differences between WAF and backend parsers (JSON/path normalization, Unicode case folding, double-encoding, parameter pollution)

### Takeaway
The dominant 2024–2026 technique here is **content-type/charset parser differentials**: WAFs and backends disagree about multipart boundaries, charset decoding (UTF-16LE vs UTF-8), JSON unescaping order, and comma-joining of duplicate query parameters — each gap lets a blocked keyword be reassembled or hidden from the WAF's view while the backend still executes it. A large-scale academic study (WAFFLED) confirms this is systemic, not a one-off: 1,207 confirmed WAF/backend parsing-discrepancy bypasses across five major WAFs.

### Cited Findings
- **WAFFLED study (arXiv 2503.10846, revised October 2025):** Fuzzed non-malicious-looking parts of requests (headers, body segments) across `application/json`, `multipart/form-data`, and `application/xml` bodies against AWS WAF, Azure WAF, Google Cloud Armor, Cloudflare, and ModSecurity. Found **1,207 confirmed parsing-discrepancy bypasses**. Cites a supporting finding that over 90% of tested websites accept `application/x-www-form-urlencoded` and `multipart/form-data` interchangeably for the same endpoint — meaning a WAF tuned for one content-type's grammar can be routed around by submitting the same data as the other. Proposes "HTTP-Normalizer," a proxy that validates/normalizes requests against RFC grammar before the WAF/app sees them, as mitigation. — [arXiv:2503.10846](https://arxiv.org/abs/2503.10846)
- **Vercel React2Shell challenge — multipart boundary confusion ($170k paid in bypasses):** WAF sits in front of a Next.js backend using the `busboy` multipart parser.
  - *Duplicate boundary parameter*: `Content-Type: multipart/form-data; boundary=y; boundary=x` — the WAF used the **last** boundary value (`x`) and, finding no matching boundary in the body, skipped inspecting the body entirely; busboy used the **first** value (`y`) and parsed the body normally. Net effect: WAF inspects nothing, backend executes everything.
  - *Non-UTF-8 bytes in a header value* (e.g. a raw `0x88` byte inside `a="b<0x88>"`) caused the WAF to error and **fail open** (forward unmodified), while busboy parsed it fine.
  - *charset=utf16le on a form field's Content-Type*: the WAF's signature matching scanned raw bytes, so a UTF-16LE-encoded `:constructor` string didn't match the ASCII signature; busboy decoded the declared charset and reconstructed the ASCII string for execution.
  - *Duplicate `Content-Type` headers on a single multipart part* (first `charset=utf16le`, second `charset=utf8`): WAF read the **second** (harmless-looking) header; busboy used the **first** and decoded the malicious UTF-16LE payload.
  - *Trailing space on the closing boundary marker* (`--y-- ` instead of `--y--`): the WAF accepted the marker as the end of the form and stopped inspecting; busboy rejected the malformed marker and kept parsing subsequent "garbage," which was actually the real attack payload.
  - Vercel's eventual fix abandoned structural parsing for the WAF and instead null-byte-stripped and JSON-unescaped the *raw* body before matching — eliminating differentials at a stated cost of more false positives/performance overhead. — [Hacktron](https://hacktron.ai/blog/react2shell-vercel-waf-bypass)
- **HTTP parameter pollution → stored/reflected JS injection (academic/industry test, via Ethiack):** Root cause is that many frameworks (ASP.NET, classic ASP, Node.js) **comma-join** duplicate query-string parameters of the same name before the application layer sees them (Microsoft's own docs confirm this merge behavior), while the WAF inspects each duplicate parameter **individually** and sees no single malicious value.
  - *Payload 1*: `/?q=1'&q=alert(1)&q='2` → each `q` value looks benign alone; after ASP.NET's comma-join: `1',alert(1),'2`; when interpolated into `var userInput = 'USER_CONTROLLED_DATA';` this becomes `var userInput = '1',alert(1),'2';` — valid JS using the comma operator, executing `alert(1)` as a side effect.
  - *Payload 3 (keyword-splitting variant)*: `q=1'%0aasd=window&q=def="al"+"ert"&q=asd[def](1)+'` — `%0a` starts a fresh JS statement, and the literal string `alert` is split across two parameter values (`"al"+"ert"`) so no single parameter ever contains the blocked keyword; after joining, this reconstructs `window["alert"](1)`.
  - Measured bypass rates: the simple payload bypassed 17.6% of tested WAF configurations; the keyword-split/multi-statement payload bypassed 70.6%. A follow-on automated "hackbot" found an additional Azure WAF bypass via a **backslash-escaping discrepancy** (not parameter pollution itself). — [Ethiack](https://blog.ethiack.com/blog/bypassing-wafs-for-fun-and-js-injection-with-parameter-pollution)
- **Unicode compatibility normalization bypass:** When the backend applies Unicode NFKC/compatibility normalization *after* the WAF has already inspected the raw input, fullwidth or circled Unicode characters that visually/semantically map to ASCII (e.g. fullwidth `．．／` for `../`) pass the WAF's ASCII-pattern signatures but normalize to the dangerous ASCII form (path traversal, SSRF-style IP literals) once the backend normalizes them. — [jlajara.gitlab.io](https://jlajara.gitlab.io/Bypass_WAF_Unicode)

### Inferences
- A recurring structural pattern across all these findings: **the WAF and backend each implement their own, independently-written grammar for the same content-type/encoding**, and any field with more than one legal interpretation (duplicate boundaries, duplicate headers, duplicate query params, ambiguous charset) is a candidate bypass surface — this is a general testing heuristic, not just specific to the cases found.
- "Fail open on parse error" (seen in the non-UTF-8-header case) is an especially dangerous WAF failure mode because it's often *easier* to trigger than a true bypass — simply feeding malformed-but-backend-valid input can disable inspection entirely rather than requiring a crafted evasion of a signature.
- Comma-join-based parameter pollution is JS-interpolation-context-specific (it exploits the JS comma operator); the same mechanism would need a different "join operator" to be useful against SQL or shell-command sinks, so testing should be tailored per sink language.

### Gaps
- Could not retrieve the full WAFFLED paper body (only the abstract was reachable); the exact Content-Length/Transfer-Encoding-specific findings, methodology details, and per-WAF breakdown of the 1,207 bypasses were not available from this fetch — the HTML (arxiv.org/html/2503.10846v4) or PDF should be fetched directly for a complete catalog.

## Key Question 3: Header-based bypasses (X-Forwarded-For / X-Real-IP / Host manipulation for trusted-traffic spoofing or rate-limit bypass)

### Takeaway
Two distinct mechanism classes dominate: (1) **unconditional trust of forwarding headers** by rate-limiting/IP-allowlist logic (spoof the header, get a fresh bucket or pass an allowlist check), and (2) **header-name mutation/smuggling** that exploits a front-end/back-end disagreement about which header is "the real" `X-Forwarded-For`/`Host`, letting an attacker-controlled header reach logic that assumes only the trusted proxy can set it.

### Cited Findings
- **Unconditional XFF trust in rate-limiting middleware (Litestar, CVE-2025-59152):** The framework's rate-limit middleware, when an `X-Forwarded-For` header is present, trusts it unconditionally and uses its value as part of the client identifier/bucket key — so an attacker rotating the header value gets a fresh rate-limit bucket per request regardless of actual source IP. — [Corgea advisory](https://corgea.com/advisories/vulnerabilities/CVE-2025-59152), [OSV](https://osv.dev/vulnerability/GHSA-hm36-ffrh-c77c)
- **Same pattern recurring across products:** MyTube (CVE-2026-23848) and 9router (CVE-2026-55501, classified CWE-290 "authentication bypass by spoofing") both had login-lockout/rate-limit defeated by rotating `X-Forwarded-For`. — [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-23848/), [SecureLayer7](https://securelayer7.net/lab/cve-2026-55501-9router-x-forwarded-for-rate-limit-bypass)
- **Bug-bounty confirmation (Acronis, Nov 2024):** Spoofed `X-Forwarded-For` bypassed the login rate limit on `passport.acronis.work`; the same technique also worked against the OTP endpoint, i.e. it defeated both brute-force throttling and OTP brute-force protection with the same header manipulation. — [Bugboard report](https://bugboard.rsecloud.com/report/2627062)
- **Header-name-mutation smuggling (Intruder.io, "Practical HTTP Header Smuggling"):** Core mechanism — a front-end proxy recognizes and strips/rewrites only the *exact* canonical header name; appending characters after a space in the header name produces a header the front-end does not recognize (and thus passes through unmodified) but the back-end's more lenient parser still binds to the intended header. Concrete mutations: `X-My-Header abcd: test` (generic demo), `X-Forwarded-For abcd: z`, and `X-Forwarded-For:[0x0b]z` (the latter used specifically against **AWS Cognito rate limiting**).
  - *AWS API Gateway IP-allowlist bypass*: a resource policy allowed only `1.2.3.4` and `10.0.0.0/8`; a normal `X-Forwarded-For` header was stripped/rewritten by the front-end, but `X-Forwarded-For abcd: z` was not recognized as the canonical header by the front-end (so passed through raw) and was still read as `X-Forwarded-For` by the policy-evaluation layer, letting the attacker inject an allowed address and pass the IP-based access control. AWS fixed it after disclosure.
  - *Related Host-header smuggling → cache poisoning*: sending both a normal and a mutated `Host` header caused API Gateway to route/respond based on the API named in the mutated header; a cache sitting in front stored that response under the victim's real Host, enabling cache poisoning against other users.
  - *Duplicate Content-Length (CL.CL) detection*: sending two `Content-Length` headers (one mutated) causes front-end and back-end to each bind to a different one, which can desynchronize the connection; the article describes an error-based technique to safely detect this discrepancy without fully exploiting it. — [Intruder.io](https://intruder.io/research/practical-http-header-smuggling)
- **Immunefi finding — WebSocket proxy trusting spoofed forwarded IP:** A reported finding describes a WebSocket proxy that trusts a client-supplied forwarded-IP header for rate-limiting purposes, the same unconditional-trust root cause as the Litestar case but in a WebSocket-proxy context rather than plain HTTP. — [Immunefi report](https://reports.immunefi.com/base/74580-bc-insight-websocket-proxy-trusts-spoofed-forwarded-ip-for-rate-limits)

### Inferences
- The header-mutation-smuggling technique (appending junk after a space in a header name) is structurally identical to the request-smuggling parser-discrepancy pattern in Key Question 1 — it's the *same root cause* (two systems disagree on where a token/name ends) applied to header-name parsing instead of chunk/body framing. Any automated test suite for "header smuggling" should reuse the same differential-request methodology used for desync testing.
- Because XFF-trust bugs are concentrated in application/framework-level rate-limiting code (not the WAF itself), WAF-level IP reputation/rate-limiting can be correct while the origin application's own rate-limiting is still bypassable — testing needs to target both layers independently.

### Gaps
- No CRLF/newline-injection-based header smuggling example was found in the fetched sources (Intruder.io explicitly says it does not cover newline injection); this sub-technique may need a separate, more targeted search.
- Could not find a 2024-2026-specific academic/vendor paper quantifying how common unconditional XFF trust is across popular rate-limiting middleware/libraries beyond the individual CVEs listed.

## Key Question 4: Timing/behavioral evasion against ML/behavioral bot detection — HTTP-layer and request-pattern techniques

### Takeaway
2024–2026 bot-detection evasion research centers on defeating **TLS/HTTP-layer fingerprinting** (JA3/JA4, HTTP/2 SETTINGS/frame-ordering fingerprints) rather than purely behavioral/mouse-movement signals; a peer-reviewed 2025 study found real-world evasion rates against commercial detectors well above 40%, and defenders are responding by cross-referencing TLS fingerprint, HTTP/2 fingerprint, and declared User-Agent for consistency rather than trusting any single signal.

### Cited Findings
- **UC Davis 2025 study (cited via secondary source, IMC 2025):** Tested 20 commercial bot-evasion/scraping services against two leading detection systems and measured average evasion rates of **52.93%** against a leading commercial detection system and **44.56%** against a widely used open detection library. Original paper not independently retrieved in this research pass — flagged as needing primary-source verification. — [via scrapehero.com secondary summary]
- **JA3 → JA4 arms race:** By early 2025, JA4 (and its variants JA4S for server, JA4H for HTTP-client, JA4X for X.509 certs) had shipped in major bot-management products, specifically to counter widely-circulated JA3-spoofing libraries. The mechanism being exploited/defended: JA3 is computed purely from the TLS ClientHello (cipher list, extensions, elliptic curves) in a fixed order, so matching a target JA3 string previously just meant replaying the same ordered list from a non-browser TLS stack; JA4 changes the hashing/field-selection to be harder to trivially replay. — [scrapfly.io / blog.send.win summaries]
- **Cross-signal consistency checking as the countermeasure:** Multiple sources describe modern anti-bot stacks explicitly cross-referencing the HTTP/2 frame SETTINGS values and stream-priority/ordering against the TLS JA3/JA4 hash and the declared `User-Agent` string — i.e., a request can have a "valid-looking" JA4 for Chrome but fail detection because its HTTP/2 SETTINGS frame ordering doesn't match what that Chrome version actually sends, or because the User-Agent claims a browser whose JA4 doesn't match. This is a direct, implementable detection (and thus a direct, implementable evasion target): an automated evasion test must align TLS fingerprint, HTTP/2 fingerprint, and User-Agent simultaneously, not just one of the three. — [scrapfly.io: "how Cloudflare detects bots"]

### Inferences
- Because detection has moved to multi-signal consistency rather than single-signal blocklisting, a bypass technique that only solves one signal (e.g., a JA3-spoofing library with no matching HTTP/2 fingerprint) is increasingly likely to be caught — this raises the bar for automated-test design: a realistic bypass test needs a full matched stack (TLS client + HTTP/2 client + UA), not an isolated header/fingerprint change.
- The specific numeric evasion rates (52.93% / 44.56%) are a single secondary citation of an academic study and should be treated as provisional until the primary IMC 2025 paper is located and confirmed.

### Gaps
- This research pass did not find primary, technically detailed 2024–2026 material purely on *request-pattern-layer* evasion (e.g., specific timing/interval randomization algorithms, request-sequencing against rate-limiters/ML models) distinct from TLS/HTTP fingerprinting — the searches surfaced TLS/HTTP2 fingerprinting content predominantly. A follow-up search specifically for "request pacing," "Akamai Bot Manager sensor data bypass," or "PerimeterX/HUMAN behavioral evasion 2025" would likely be needed to close this gap; not attempted due to the ~15-tool-call budget for this assignment.

## Key Question 5: Novel 2024–2026 technique classes not covered above (CDN-specific, cache-related, gRPC/HTTP3-specific)

### Takeaway
The most concrete, high-impact novel class found is **CDN-architecture bypass via a mistakenly-unprotected internal validation path** (Cloudflare's October 2025 ACME bug), which is structurally different from parser-differential smuggling: it's a *routing/policy-scoping* bug where an entire WAF rule layer is skippable for a specific, predictable path. H2C smuggling (technically from 2021 but still being actively found "in the wild" against modern WAFs through 2024+) is the other major standing novel-ish class: it doesn't exploit a parsing differential at all, but abuses an HTTP/1.1-to-HTTP/2-cleartext upgrade handshake that most WAFs/reverse proxies don't understand, to open a raw, uninspected tunnel straight to the backend.

### Cited Findings
- **Cloudflare ACME-validation-path WAF bypass (reported Oct 9, 2025 by FearsOff; fixed Oct 27, 2025):** Requests targeting a specific certificate-validation (ACME HTTP-01 challenge) path on Cloudflare could completely circumvent **all** customer-configured WAF rules for that path, because the path was scoped as an internal/trusted validation route and account-level WAF rules were not applied to it. This "global WAF bypass" primitive enabled header-based secondary attacks (SSRF, SQLi, cache poisoning) against the origin once WAF inspection was skipped entirely on that path. Mitigation discussed: prefer DNS-01 over HTTP-01 ACME challenges to avoid relying on an HTTP path that must remain unauthenticated/unfiltered. — [SecurityAffairs](https://securityaffairs.com/187156/security/acme-flaw-in-cloudflare-allowed-attackers-to-reach-origin-servers.html), [OffSeq](https://radar.offseq.com/threat/cloudflare-fixes-acme-validation-bug-allowing-waf--2d0bd150)
- **Origin-IP exposure as a WAF-bypass enabler (Zafran "BreakingWAF," published Dec 3, 2024):** Found more than 140,000 domains belonging to Fortune 1000 companies that sit behind a CDN/WAF but whose true origin IP/port is discoverable (via historical DNS, SSL cert SANs, SaaS misconfig, etc.), meaning the WAF can simply be bypassed by connecting directly to the origin — the WAF's protection is contingent entirely on origin-IP secrecy, which the research found is "rarely" reinforced with IP allowlisting or mutual-TLS "Authenticated Origin Pulls." — [Zafran](https://www.zafran.io/resources/breaking-waf-technical-analysis)
- **Shared-CDN-IP-range allowlisting is weak (Certitude):** Even where an origin restricts inbound connections to "Cloudflare's published IP ranges," this is insufficient because *every* Cloudflare customer's traffic originates from those same ranges — any other Cloudflare customer (including an attacker's own free-tier Cloudflare zone proxying to the victim's discovered origin IP) can reach the victim's origin and bypass the victim's WAF entirely ("using Cloudflare to bypass Cloudflare"). The robust fix requires Authenticated Origin Pulls with a custom client certificate, not IP allowlisting alone. — [Certitude](https://certitude.consulting/blog/?p=2274)
- **H2C smuggling still effective against modern WAF/CDN products (originally Jake Miller/Bishop Fox, re-tooled by Assetnote, actively cited through 2024+):** Exploits an obscure legitimate HTTP/1.1 feature — the `Connection: Upgrade, HTTP2-Settings` / `Upgrade: h2c` cleartext-HTTP/2-upgrade handshake. A front-end/reverse-proxy/WAF that is a plain HTTP/1.1 parser and doesn't recognize or strip this upgrade request forwards it to the backend; if the backend *does* support h2c, the connection is "upgraded" to a raw HTTP/2 tunnel between attacker and backend that completely bypasses the front-end's per-request inspection (the front-end now just blindly relays opaque HTTP/2 frames it can't parse). Reported real-world impact: Azure WAF (configured mode) — full WAF bypass as long as the first request isn't itself blocked and an h2c connection can be established; Cloudflare Access — authentication bypass. Google Cloud Platform's load balancer was *not* vulnerable because it strips Upgrade headers. Caveat noted by the researchers: if the h2c upgrade can't be established, the attacker remains bound by all normal reverse-proxy/WAF rules — it's an all-or-nothing bypass, not a partial one. — [PortSwigger Daily Swig](https://portswigger.net/daily-swig/h2c-smuggling-proves-effective-against-azure-cloudflare-access-and-more), [Assetnote](https://assetnote.io/resources/research/h2c-smuggling-in-the-wild)
- **"nowafpls" / body-padding bypass (Shubham Shah/Assetnote):** A distinct, simpler mechanism — many WAFs only inspect the first N bytes of a request body (an inspection-size limit for performance). The `nowafpls` Burp extension automates padding requests with junk past that limit — inserted into XML comments, extra JSON keys/values, or extra URL-encoded parameters — pushing the actual malicious payload beyond the WAF's inspection window while the backend still parses and acts on the full body. — [via search summary of Shubham Shah talk material]

### Inferences
- A pattern across this section: several of the highest-impact "WAF bypasses" in 2024–2026 are not parser-differential bugs at all, but **scope/trust-boundary mistakes** — a path exempted from WAF rules (Cloudflare ACME), a backend reachable by *any* traffic matching an IP range the WAF trusts (shared CDN ranges), or a protocol upgrade that produces a tunnel the WAF never inspects again (h2c). For an automated test suite, these require a different test design than header-fuzzing: enumerate known "special" paths (ACME, health checks, admin), attempt direct-origin connection if the IP is discoverable, and attempt protocol-upgrade handshakes (h2c, WebSocket) through the WAF.
- Inspection-size-limit bypass (nowafpls) suggests a cheap, broadly-applicable automated test: send a payload known to trigger a block near byte 0, then resend with large benign padding (comments/extra params) before the payload, scanning for the byte offset at which the WAF stops inspecting.

## Suggested Automated-Test Implementations (cross-cutting summary for developer handoff)

- **Desync/smuggling differential testing:** For a given target through the WAF/CDN, send the same logical request via N header-combination variants (plain CL, plain TE, CL+TE both present with conflicting values, obfuscated TE e.g. `Transfer-Encoding: chunked\r\nTransfer-Encoding: x`, chunk-size lines with a bare trailing `;`, `Expect: 100-continue` and obfuscated `Expect: y 100-continue`) and diff: (a) whether the WAF blocks/passes each variant differently, and (b) whether the backend's response timing/behavior indicates it consumed a different byte range than the front-end intended (classic CL.TE/TE.CL timing-based detection, extendable to the Expect/chunk-extension variants). Tools: PortSwigger's HTTP Request Smuggler Burp extension and the open-sourced HTTP Terminator are directly reusable here.
- **Multipart/charset/JSON differential testing:** Automatically generate N permutations of a single request body (duplicate `boundary=` parameters with different values, duplicate `Content-Type`/charset headers per-part with different charsets, non-UTF-8 byte injection in header values, trailing-space variants on closing boundary markers, UTF-16LE-encoded keywords) and compare WAF-block decision vs. observed backend behavior (echoed/reflected value, error code, timing) to find cases where the two disagree.
- **Parameter-pollution testing:** For each input sink, send the payload split across N duplicate same-named parameters (first/last/comma-join/array hypotheses) and determine the framework's join behavior empirically, then attempt keyword-splitting (e.g., splitting `alert` into `"al"+"ert"` for JS contexts, or SQL/shell equivalents) across the duplicates while diffing against single-parameter WAF-signature matching.
- **Header-spoofing/XFF-trust testing:** For any rate-limited or IP-restricted endpoint, automate sending the same request N times rotating `X-Forwarded-For`/`X-Real-IP`/`Forwarded` values (including malformed/private-range values) to detect whether the rate-limit bucket or allowlist check follows the header; separately, automate header-name-mutation variants (`X-Forwarded-For abcd: <ip>`, trailing control-byte variants like `X-Forwarded-For:[0x0b]<ip>`) to detect front-end/back-end header-name-parsing disagreement.
- **CDN scope/trust-boundary testing:** Enumerate well-known "exempted" paths (ACME `/.well-known/acme-challenge/*`, health-check endpoints, provider-specific internal paths) and test whether WAF rules that block on other paths are actually applied there; separately, if an origin IP can be discovered (cert SAN history, passive DNS), test direct-to-origin connection bypassing the CDN/WAF entirely, and test connecting via a different, attacker-controlled account on the same CDN to probe shared-IP-range allowlist weaknesses.
- **Protocol-upgrade tunnel testing:** Send an `Upgrade: h2c` / `Connection: Upgrade, HTTP2-Settings` handshake through the WAF/reverse-proxy to detect whether the backend accepts an HTTP/2 cleartext upgrade that would then tunnel all subsequent frames uninspected; similarly test WebSocket upgrade handling for the same uninspected-tunnel pattern.
- **Inspection-size-limit testing:** Send a known-blocked payload at byte offset 0, then resend with increasing amounts of benign padding (via extra JSON keys, XML comments, or extra URL params) before the payload, to binary-search the WAF's inspection byte limit.
- **Bot-detection consistency testing:** For any client claiming a specific browser via User-Agent, verify its TLS ClientHello (JA3/JA4) and HTTP/2 SETTINGS-frame fingerprint actually match what that real browser/version produces; an automated test harness should assemble matched (TLS-stack, HTTP/2-stack, UA) triples and flag any client library/proxy that can only control one of the three, since detectors are increasingly cross-referencing all three.
