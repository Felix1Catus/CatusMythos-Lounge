# GraphQL-Specific Security Testing Techniques (2024-2026)

Scoping note: the existing `api-breaker` scripts (`schema_builder.py`, `api_discovery.py`) only (a) fuzz common GraphQL paths, (b) send one full introspection query and record pass/fail, and (c) if introspection succeeds, walk `__schema.types[].fields[]`. Neither script does anything when introspection is disabled, nor do they touch batching, aliases, depth/complexity DoS, field-level authz, or implementation-specific CVEs. All six key questions below target exactly that gap.

## Introspection-disabled bypass techniques (field-suggestion inference, Clairvoyance-style brute-forcing, regex/transport bypasses)

### Takeaway
Disabling the introspection query alone does not hide a GraphQL schema: field-suggestion ("Did you mean") error text, blind wordlist brute-forcing (the Clairvoyance technique), and naive regex/transport filters around the literal string `__schema` are all independently sufficient to reconstruct most of a schema, and this is treated as settled, mainstream knowledge across OWASP, PortSwigger, and Escape.tech.

### Cited Findings
- PortSwigger's official GraphQL material documents the field-suggestion leak directly, with the example error text `"There is no entry for 'productInfo'. Did you mean 'productInformation' instead?"`, and states Clairvoyance "automates schema recovery from suggestion responses" — [PortSwigger: GraphQL API vulnerabilities](https://portswigger.net/web-security/graphql)
- Clairvoyance (Nikita Stupin) performs "blind introspection," brute-forcing field names from a wordlist to reconstruct a JSON schema compatible with GraphQL Voyager / InQL; basic usage is `pip install clairvoyance` then `clairvoyance <url> -o schema.json` — [PyPI: clairvoyance](https://pypi.org/project/clairvoyance), [PyPI: clairvoyance 2.0.6](https://pypi.org/project/clairvoyance/2.0.6/)
- Apollo Server disables introspection automatically when `NODE_ENV=production`, which is precisely why blind-recovery tooling exists — [PyPI: clairvoyance 2.0.6](https://pypi.org/project/clairvoyance/2.0.6/)
- A curated GraphQL-specific wordlist outperforms generic English wordlists for this brute force; PayloadsAllTheThings independently documents the same approach: "bruteforce known keywords, field and type names using wordlists such as Escape-Technologies/graphql-wordlist when the schema of a GraphQL API is not accessible" — [Escape: GraphQL Wordlist](https://escape.tech/blog/graphql-security-wordlist/), [PayloadsAllTheThings GraphQL Injection](https://git.dotya.ml/wanderer/PayloadsAllTheThings/src/branch/master/GraphQL%20Injection)
- `graphql-path-enum` consumes a recovered (or legitimate) introspection JSON and enumerates every path that reaches a named type, e.g. `graphql-path-enum -i ./test_data/h1_introspection.json -t Skill` — found via aggregated search result describing the tool's CLI usage
- Regex-based introspection blocklists that match the literal substring `__schema{` are bypassed because GraphQL ignores whitespace/newlines/commas that a naive regex does not: PortSwigger's lab technique is to insert a newline (URL-encoded `%0a`) immediately after `__schema` — "the server is configured to exclude queries matching the regex `__schema{`, which the query no longer matches even though it is still a valid introspection query" — [PortSwigger: GraphQL API vulnerabilities](https://portswigger.net/web-security/graphql)
- Other documented transport-level bypasses when a POST-based introspection block is in place: resend the identical query as `GET /graphql?query=...`, resend as `application/x-www-form-urlencoded` POST, or try a secondary/versioned endpoint (e.g. `/graphql/v2`) that the filter wasn't applied to — [PortSwigger: GraphQL API vulnerabilities](https://portswigger.net/web-security/graphql); corroborated independently by aggregated search results
- Even with suggestions disabled, field validation itself still leaks presence/absence of a field: a graphql-php GitHub issue states "even if suggestions are turned off, the server still leaks information about which fields are available by nature of query validation," and a companion write-up stresses not to stop at the introspection error, "it only hides the field list; field validation still talks" — [GitHub: webonyx/graphql-php#1175](https://www.github.com/webonyx/graphql-php/issues/1175), [HackerDNA: The Field the Error Named](https://hackerdna.com/daily-hack/the-field-the-error-named)
- Named defensive countermeasures confirm the attack is real enough to need dedicated tooling: `@escape.tech/graphql-armor-block-field-suggestions`, and Apollo Server 4.11+'s `hideSchemaDetailsFromClientErrors: true` config flag — [npm: graphql-armor-block-field-suggestions](https://npmjs.com/package/@escape.tech/graphql-armor-block-field-suggestions)
- Even depth-limiting defenses built specifically for GraphQL have had introspection-naming bypasses: GHSA-hmfr-rx46-4jx2 against `@escape.tech/graphql-armor-max-depth` states the plugin's depth counter is bypassable because it skips introspection-named fields by default (`ignoreIntrospection: true` is the default), so naming a query/fragment literally `__schema` lets a payload dodge the depth counter entirely — [GitLab Advisory DB](https://advisories.gitlab.com/pkg/npm/@escape.tech/graphql-armor-max-depth/) (cross-relevant to the depth/complexity question below)

### Inferences
- `schema_builder.py`'s `build_graphql_schema()` currently sends exactly one introspection query and, on any failure, sets `introspection_enabled: False` and stops — this whole fallback chain is net-new code, not a tweak:
  1. **Transport retries first (cheap, ~3 requests):** retry the identical introspection query as `GET` with the query URL-encoded in the querystring, and as `POST` with `Content-Type: application/x-www-form-urlencoded` instead of JSON. Success oracle is unchanged (`"__schema"` present in a 200 JSON body).
  2. **Regex-evasion retries (cheap, ~3-5 requests):** resend the introspection query with a newline/comma/comment inserted immediately after the `__schema` token (e.g. `query{__schema\n{queryType{name}}}`), and once more against any alternate GraphQL path already found by `api_discovery.py` (e.g. `/graphql/v2`, `/v2/graphql`). Same success oracle.
  3. **Field-suggestion harvesting (Clairvoyance-style, moderate cost):** if introspection is still blocked, iterate a seed wordlist of plausible field/type names (common REST-style nouns already in `schema_builder.py`'s `PROBE_FIELDS`/`RESOURCE_NAMES`, plus GraphQL-idiomatic names like `viewer`, `me`, `node`, `nodes`, `edges`, `connection`). For each candidate, send a deliberately-almost-right or deliberately-wrong field name as a root selection (`{"query": "{ <candidate>_x1 }"}`) and regex the error array for a suggestion pattern such as `Did you mean "(\w+)"` or `Did you mean one of these types: "([\w", ]+)"`. Every regex match is a confirmed real field/type name — add it to the discovered-schema dict directly; this typically needs only tens of requests against a good seed list, not thousands.
  4. **Binary-oracle brute force (expensive, last resort):** if suggestions are also disabled, fall back to one-request-per-candidate: send `{"query": "{ <candidate> }"}` against the root query type for each wordlist entry and classify by error text — `"Cannot query field \"X\" on type"` (or equivalent "unknown field" phrasing) means reject; any other response (a different validation error, an auth/permission error, or a "must have a selection of subfields" type-mismatch error) means the field exists and should be recorded. Use Escape's public GraphQL wordlist as the candidate source rather than a generic English list.
  5. **Always probe for `node`/`nodes` directly**, regardless of which path above succeeds: a bare `{"query": "{ node(id: \"1\") { __typename } }"}` (or `nodes(ids: [...])`) is a single-request structural check worth running unconditionally, since OWASP calls this out as a common direct-object-access primitive independent of the rest of the schema (see the authorization section below).

### Gaps
- No single primary source documents all of (transport bypass → regex bypass → suggestion harvesting → binary brute force) as one unified pipeline; this ordering is my own synthesis of separately-documented pieces, not a cited end-to-end methodology.
- Current exact maintenance status / latest release of the original `nikitastupin/clairvoyance` repo vs. its forks (`clairvoyancex`, `clairvoyancenext`) was not confirmed — if porting logic rather than shelling out to the tool, this doesn't matter, but it's worth noting the ecosystem is fragmented across forks.

## Batching attacks (array batching used to bypass per-request rate limiting)

### Takeaway
GraphQL's optional "array batching" transport — POSTing a JSON array of independent operations to one HTTP request — is a well-documented, concretely-demonstrated bypass for rate limiters and brute-force lockouts that count HTTP requests rather than GraphQL operations; OWASP's own cheat sheet and a dedicated Checkmarx walkthrough both confirm the exact mechanism and give a reproducible demonstration.

### Cited Findings
- Batched request format: the client POSTs a JSON **array** to a single `POST /graphql`; each array element is an independent `{query, variables}` operation; the server returns a JSON array with one result per operation, each in its own `data` object — [Checkmarx: Didn't Notice Your Rate Limiting — GraphQL Batching Attack](https://checkmarx.com/blog/didnt-notice-your-rate-limiting-graphql-batching-attack/)
- Checkmarx's demonstration: the target enforced 5 requests/second via `RateLimit-*` response headers and returned `429 Too Many Requests` on the 6th single request within a window; a single batch containing 100 login mutations (one username, 100 different password guesses) returned `200 OK` with 100 discrete results in one HTTP request, and the one correct-password result contained a `sessionToken` the attacker could reuse to impersonate the account — [Checkmarx](https://checkmarx.com/blog/didnt-notice-your-rate-limiting-graphql-batching-attack/)
- OWASP's cheat sheet confirms the general class: batched operations "will likely bypass existing rate limits" implemented in proxies/gateways, and recommends (a) code-level rate limiting on the number of distinct objects/calls per client even *inside* one batch, (b) disabling batching outright for sensitive objects (usernames, passwords, OTPs, session tokens) since this "requires a custom solution," and (c) capping the number of batched/concurrently-run operations per request, explicitly noting this cap alone is "not a silver bullet" — [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)
- OWASP explicitly calls out that request-count-based rate limiting (e.g., nginx `limit_req`) is insufficient because it "misses expensive queries and multiple operations per request," and recommends combining business-logic GraphQL-aware rate limits with cost and batching limits — [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)
- Escape.tech ships a dedicated, named DAST check for this exact condition (`graphql_batch_limit`), confirming it is treated as a standard scan target by commercial tooling, not a theoretical edge case — [Escape docs: graphql_batch_limit](https://docs.escape.tech/documentation/platform/vulnerabilities/graphql_batch_limit)

### Inferences
- Add a `test_graphql_batching()` probe alongside the existing GraphQL phase in `api_discovery.py` / `schema_builder.py`:
  1. **Baseline the rate limit first:** send single-operation POSTs of a cheap, side-effect-free query (`{"query": "{__typename}"}`) in a tight loop and record the request count/time at which a `429`, a `RateLimit-*` header threshold, or any other throttling response first appears. If nothing throttles after a reasonable count (e.g. 50), record "no observable per-request rate limiting" as its own finding.
  2. **Batch test:** build a JSON **array** of N copies of the same cheap query (start N=20, escalate to 50/100/500) and POST the array as a single request. Check: (a) HTTP 200, not a 400/405 that would indicate the server rejects array bodies outright (itself worth recording as "array batching not supported" — a negative finding); (b) the response body is a JSON array of length N with one result object per element (confirms the server actually executed all N, not just the first). If both hold and N exceeds whatever per-request threshold step 1 found, without the batch itself being throttled or rejected, that is a confirmed rate-limit bypass via batching — record it unconditionally, since it needs no sensitive payload.
  3. **High-value / sensitive variant (flag as opt-in, requires explicit scope confirmation):** if a prior schema-reconstruction pass found a login/password-reset/OTP-verification mutation (field name containing `login`, `signin`, `auth`, `verify`, `otp`, or `reset`), repeat step 2 using that mutation, varying one credential argument (e.g. `password` or `code`) across the array elements against a bounded candidate list, and scan each element's result for a success marker (a token/session field present, or the absence of the "invalid credentials" error text seen in a known-bad control request). Keep the candidate list short by default and require the caller to pass an explicit flag to run this variant, since a true positive means a real account was just accessed.
  4. Record the finding regardless of whether step 3 was run: `"graphql_batching_bypasses_rate_limit": true/false, "max_batch_size_accepted": N`.

### Gaps
- No CVE or formally-named real-world incident was found for the batching bypass specifically — it is documented as a design-level class (OWASP, vendor blogs, scanner vendors) rather than tied to a single disclosed breach or a CVE ID.
- Found no authoritative numeric "default acceptable batch size" recommendation beyond the general advice to cap it; any concrete default threshold used in the ported script (e.g., "flag at >10") would be the tool author's own choice, not sourced.

## Alias-based abuse (repeating the same query/mutation under different aliases in one request)

### Takeaway
GraphQL aliases let a client request the same field or mutation multiple times with different arguments inside a *single* query document — no array batching required — which defeats per-request rate limiting identically to batching and can independently cause resource-exhaustion ("alias overloading"); this is mainstream enough that at least four separate commercial scanners (Escape, Invicti, Acunetix, StackHawk/Pynt) ship dedicated, named alias-limit checks.

### Cited Findings
- Canonical alias-abuse query shape, from PortSwigger's own GraphQL material:
  ```graphql
  query isValidDiscount($code: Int) {
    isValidDiscount(code:$code){ valid }
    isValidDiscount2:isValidDiscount(code:$code){ valid }
    isValidDiscount3:isValidDiscount(code:$code){ valid }
  }
  ```
  with the explanation "Aliases let one HTTP request contain multiple operations, which can evade limits that count HTTP requests" — [PortSwigger: GraphQL API vulnerabilities](https://portswigger.net/web-security/graphql)
- Checkmarx's writeup confirms aliases such as `user2: user(id: 2)` are run sequentially server-side, with each result returned under its alias key in the response JSON, and explicitly distinguishes aliasing (a GraphQL spec feature) from batching (a server-side transport feature) as two independently-usable bypass routes — [Checkmarx](https://checkmarx.com/blog/didnt-notice-your-rate-limiting-graphql-batching-attack/)
- Vendor-recommended alias-count thresholds vary noticeably: Invicti/Acunetix's "GraphQL Alias Overloading" check suggests capping "typically 5-15 aliases per request," while a different tool's documented default (`max_aliases`) is 50 — [Invicti: GraphQL Alias Overloading](https://www.invicti.com/web-application-vulnerabilities/graphql-alias-overloading-allowed-potential-denial-of-service-vulnerability), [Acunetix: GraphQL Alias Overloading](https://acunetix.com/vulnerabilities/web/graphql-alias-overloading-allowed-potential-denial-of-service-vulnerability)
- Important false-positive caveat from Checkmarx: some server implementations deduplicate/optimize identical aliased subqueries (same field + same arguments) into a single backend call, so observing N aliases in the request body does **not** guarantee N× backend load — actual timing/behavior must still be confirmed, not just the request shape — [Checkmarx: Alias and Directive Overloading in GraphQL](https://checkmarx.com/blog/alias-and-directive-overloading-in-graphql)
- Escape ships `graphql_alias_limit` as a dedicated named DAST test — [Escape docs: graphql_alias_limit](https://docs.escape.tech/documentation/dast/vulnerabilities/api/resource_limitation/graphql_alias_limit)
- A lower-authority, self-published case study describes packing many OTP guesses as aliased mutations inside one request specifically to brute-force a 2FA code without tripping per-request lockouts — flagged here as anecdotal/unverified, but structurally consistent with the PortSwigger/Checkmarx mechanism above — aggregated search result, source quality explicitly noted as low

### Inferences
- Add a `test_graphql_alias_limit()` probe:
  1. Pick a cheap, side-effect-free field from the reconstructed schema (fallback: `__typename`, which works against any schema with no auth required). Build one query document containing K aliases of it (`a0: __typename a1: __typename ... aK: __typename`) for escalating K (e.g. 10, 50, 100, 500, 2000).
  2. Send each K as a single request and record: HTTP status, wall-clock response time, and whether the response JSON contains K top-level keys (confirms the server parsed/executed all K rather than truncating or rejecting the document). No rejection and no disproportionate latency growth up to a few thousand aliases = alias-limit finding (absence of a protective cap).
  3. **Brute-force variant (opt-in, same sensitivity caveat as batching):** if a login/verify-code/discount-code mutation exists in the schema, build an aliased batch of candidate values in ONE query document (`a0: verifyCode(code:"0000") a1: verifyCode(code:"0001") ...`) and scan the single JSON response for a success marker across alias keys. Run this independently of the array-batching variant from the previous section — some servers block one transport (array batching) but not the other (aliasing), so both must be tested separately and both results recorded.
  4. Apply Checkmarx's dedup caveat directly: also compare response latency at K=1 vs K=2000 for a field whose arguments are identical across all aliases vs. a field whose arguments differ per alias (e.g. different `id` per alias). If the identical-argument case is suspiciously flat while the varying-argument case scales linearly, the server is likely deduplicating — note this explicitly in the finding ("no enforced alias cap, but possible dedup optimization reduces real exploitability — confidence: medium") rather than overstating impact.

### Gaps
- No consistent industry-standard "safe" alias-count threshold was found (sources range 5-15 up to 50 as *defensive* defaults); any single number used for a pass/fail verdict in the ported detection script is a judgment call, not a sourced standard.
- Did not find a named CVE specific to alias overloading; it is tracked purely as a scanner-rule / vendor-advisory category (CWE classification referenced by some vendors, not independently confirmed here).

## Nested/circular query DoS (query depth, query complexity, circular-reference abuse)

### Takeaway
Query depth and query cost/complexity are unbounded by default in most GraphQL server libraries per OWASP's own cheat sheet, and schemas with bidirectional relationships let a short query string drive exponential resolver cost; this is not just a design-level risk — it is the direct root cause of at least one 2025 CVE (Apollo's `apollo-compiler`) and has a documented real-world GitLab issue, making it one of the better-evidenced categories in this report.

### Cited Findings
- OWASP: depth and amount "can be unlimited" by default, "which may lead to a DoS"; concrete library recommendations are `graphql-depth-limit` (JS) / `MaxQueryDepthInstrumentation` (graphql-java) for depth, and `graphql-cost-analysis` or `graphql-validation-complexity` (JS) / `MaxQueryComplexityInstrumentation` (graphql-java) for cost; it also recommends application-level timeouts (its Java example uses 10 seconds via `Instrumentation`, its JS example aborts after 10,000 ms) as a backstop independent of any cost model — [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)
- Checkmarx's depth-DoS demonstration nests a self-referencing relation (`Paste → Owner → Pastes → Owner → ...`) and shows response time and payload size growing with each added nesting level, concluding that going "too deep may lead to Denial of Service"; the article frames this as a relationship/structure issue rather than giving a single numeric threshold — [Checkmarx: Exploiting GraphQL Query Depth](https://checkmarx.com/blog/exploiting-graphql-query-depth.md)
- Escape.tech stresses that query-string length/depth alone is a weak signal because short queries can still be computationally expensive — a real cost model needs to weight list-returning fields and pagination arguments, not just count nesting levels — [Escape: GraphQL Query Cost Analysis](https://escape.tech/blog/graphql-query-cost-analysis/)
- Depth limits alone miss a breadth-based variant: an attacker can keep nesting shallow while multiplying the number of expensive field invocations via aliasing, which a pure depth counter does not catch — [Wallarm: Fundamentals of GraphQL-Specific Attacks](https://lab.wallarm.com/fundamentals-of-graphql-specific-attacks)
- A real, tracked circular-relationship DoS: GitLab issue "Nested GraphQL query with circular relationship can cause Denial of Service" — [GitLab #30096](https://gitlab.com/gitlab-org/gitlab/-/issues/30096)
- **CVE-2025-31496** (`apollo-compiler`, the Rust GraphQL-query compiler crate, GHSA-7mpv-9xg6-5r79; CVSS 3.1 7.5 High; CWE-770): named fragments were validated once **per fragment spread** rather than once per fragment **definition**, with no memoization/caching of already-validated fragments, so deeply-nested and reused named fragments caused exponential resource use during validation; no known workaround; fixed in apollo-compiler 1.27.0 — [Tenable: CVE-2025-31496](https://www.tenable.com/cve/CVE-2025-31496)
- **CVE-2024-40094** (graphql-java before 19.11 / 20.9 / 21.5; CVSS v3.1 5.3 Medium, CVSS v4.0 8.7 High): the library "does not properly consider ExecutableNormalizedFields (ENFs) as part of preventing denial of service via introspection queries" — i.e. the library's existing anti-DoS query-cost accounting had a specific gap in how it counted normalized (alias/fragment-expanded) fields, letting a crafted query evade protection that otherwise exists; published 2024-07-30; picked up downstream in IBM's March 2025 advisory for Business Automation Workflow — [Tenable: CVE-2024-40094](https://www.tenable.com/cve/CVE-2024-40094), [cybersecurity-help.cz #98137](https://www.cybersecurity-help.cz/vdb/vulns/98137)
- Same-class, older-release CVE for context: **CVE-2021-47713** (Hasura GraphQL 1.3.3, CVSS 7.5 High) — "Denial of Service via Malicious GraphQL Query" via nested queries; note its CVE number was only assigned/published in the Dec-2025/Jan-2026 backfill window even though the affected release (1.3.3) is years old — aggregated search result citing cvefeed.io
- A defense specifically built for depth-limiting has its own disclosed bypass: GHSA-hmfr-rx46-4jx2 against `@escape.tech/graphql-armor-max-depth` — the depth counter skips introspection-named fields by default, so naming a query/fragment `__schema` evades the depth limit; a second, separately-listed advisory GHSA-224p-v68g-5g8f ("Plugin Bypass via fragment caching") appears to describe a closely related or overlapping issue against the same plugin family, though the source page did not clearly distinguish the two mechanisms — [GitLab Advisory DB](https://advisories.gitlab.com/pkg/npm/@escape.tech/graphql-armor-max-depth/)
- Circular/self-referencing **named fragments** (distinct from circular *schema relationships*) are rejected by some servers at validation time — one aggregated, lower-authority pentest-notes source claims Apollo Server returns an HTTP 500 on a circular-fragment payload (linked by that source to CWE-674) and that graphql-java rejects with a "FragmentCycle not allowed"-style error — flagged explicitly as anecdotal/unverified against primary vendor docs

### Inferences
- Add a `test_graphql_depth_complexity_dos()` probe:
  1. **Find or assume a self-referencing relation.** From a reconstructed schema, look for any type `T` with a field whose return type is `T` or cycles back to `T` (e.g. `User.posts[].author`, `Category.children[]`). If introspection was blind (no full schema), fall back to common self-referential name pairs: `children`/`parent`, `replies`/`parent`, `author`/`posts`, `owner`/`items`, `friends`, `subcategories`.
  2. **Escalate nesting depth programmatically** (N=10, then roughly doubling up to a few hundred or until failure), sending each as its own request with a hard client-side timeout (e.g. 15s) kept distinct from a server-returned error.
  3. **Classify the result:** (a) a validation error mentioning "depth" / "exceeds maximum" at some N confirms depth limiting is present — record the threshold N; (b) response time growing non-linearly (e.g. >3x per added level) with no error confirms cost/complexity limiting is **absent** even if depth limiting exists; (c) a timeout, 500, or dropped connection is an immediate confirmed DoS finding.
  4. **Test the breadth/alias variant too**, reusing the alias-generation logic from the alias-abuse section but pointed at an expensive list-returning field instead of `__typename` — this specifically catches servers with depth limiting but no cost limiting, per the Wallarm/Escape findings above.
  5. **Fragment-cycle probe (direct, cheap, high-signal):** send two named fragments that reference each other (`fragment A on T { ...B } fragment B on T { ...A }`) against any valid type `T` in the schema. A spec-compliant validator should reject this (look for "cycle"/"circular" in the error text); if it is accepted/executed instead, record as a high-severity finding on its own, independent of timing.
  6. **Fragment-reuse cost probe (direct CVE-2025-31496-style probe):** define one named fragment and reference (spread) it N times inside nested selections (non-cyclic, just heavily reused), and time this against a manually-flattened query of equivalent nominal depth that uses no fragments. A dramatically slower fragment-based version at equal nominal depth/field-count indicates a fragment-validation-cost bug in the same class as CVE-2025-31496 — this is directly portable and needs no knowledge of the server's exact version, only a timing differential.
  7. **Introspection-naming depth-bypass probe:** once a depth limiter is confirmed present (step 3a), retry the same deep query with the operation (or a fragment) literally named `__schema` to check for the graphql-armor-style `ignoreIntrospection` bypass — cheap to add given the limiter was already found, and has a confirmed real advisory behind it.

### Gaps
- Checkmarx's depth-vs-performance table (exact numeric timings per depth level) was presented as an image in the source article and was not extractable as text — no concrete depth-to-latency numbers are available from that source, only the qualitative trend.
- Could not independently verify the Apollo-500 / graphql-java "FragmentCycle not allowed" claims against primary vendor documentation; treat as a hypothesis to validate empirically during porting, not a confirmed spec-compliance guarantee.
- No single source gave a cross-implementation-comparable numeric complexity-cost default; thresholds are implementation-specific and would need to be learned empirically per target rather than hardcoded.

## Authorization bypass specific to GraphQL (field-level gaps, mutation-based BOLA/IDOR)

### Takeaway
The dominant real-world pattern is authorization wired to one entry point (a root field like `me`, or "the intended" query) while sibling root fields and nested field resolvers that reach the exact same underlying data have no independent check of their own — OWASP's API Security Top 10 formalizes this split as BOLA (API1:2023, object-level) vs. BOPLA (API3:2023, property/field-level), and GraphQL's graph-shaped schema makes "the same data, reached a different way" structurally common rather than an edge case; mutation-based BOLA (a write that trusts a client-supplied object ID) is the direct write-side analogue, and a July 2026 Hasura CVE is a fresh, concrete instance of the pattern at the database-permission layer.

### Cited Findings
- Concretely-illustrated failure pattern: a schema's `me` query correctly checks the session user, but a sibling `user(id)` root field has no ownership check at all and returns any user record by ID; the `User.privateProfile` and `User.email` field resolvers likewise have no per-field ownership check because they only ever receive the parent `User` object and never re-validate the caller's identity against it. The demonstrated exploit, as an authenticated low-privilege user, is `{ user(id: "2") { victimData: privateProfile { ssn dob } email } }` sent with the attacker's own valid session/JWT — [DEV.to: GraphQL Authorization Bypass — A Real CVE Code Review](https://dev.to/securitystefan/graphql-authorization-bypass-a-real-cve-code-review-10jh) (caveat: the article's cited CVE, CVE-2023-26489/wasmCloud, is per the article's own text a *different* bug class — the vulnerable-code walkthrough is the author's own illustrative Apollo Server example, not that CVE's actual code; the exploit **pattern** is standard and independently well-documented elsewhere, but this specific CVE citation should not be repeated as "the" source for it)
- Terminology: field/property-level authorization failures are classified as BOPLA / OWASP API3:2023 (Broken Object Property Level Authorization); whole-object failures are BOLA / API1:2023; practitioners frequently conflate the two since both are authorization failures operating at different schema layers — [Indusface: OWASP API Top 10 — Broken Object Property Level Authorization](https://www.indusface.com/learning/owasp-api-top-10-broken-object-property-level-authorization/)
- OWASP's own GraphQL cheat sheet: "verify the caller can access each requested object... possessing an ID does not imply permission. Enforce checks on both edges and nodes," citing a real bug report where edges were checked but nodes were not; separately, it flags bare `node`/`nodes` root fields (the Relay-style global-ID lookup pattern) as a direct cross-type object-access path that is easy to forget to re-gate, and gives a `jq` recipe for detecting their presence in a dumped schema JSON — [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)
- OWASP also cites a Detectify-disclosed case where "parameter smuggling bypassed account-level field permissions," i.e. a field-level authz bypass achieved by request-shape manipulation rather than a missing check per se — [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)
- Practitioner-stated (non-OWASP-formal) testing methodology: replay the identical GraphQL operation under two different privilege contexts (low-priv vs. admin token, or user-A's token against user-B's object ID) and diff the responses field-by-field; apply the same differential test to mutations, since `updateUser(id, ...)` must independently verify the caller owns `id` rather than merely being authenticated — aggregated practitioner guidance, consistent across multiple independent write-ups
- **CVE-2026-54698** (Hasura GraphQL Engine, GHSA-r27x-gc74-qmxh, CVSS ~6.0, published 2026-07-07): a row-level-permission bypass where "a user can use a `where` clause on a table computed field (returning `SETOF some_table`) to infer [protected row] data" — i.e. a computed/relationship field provides a side channel around the row-level permission that direct table access enforces; affects versions >=2.46.0 <2.49.2 and >=2.45.0 <2.45.5 — [Mend.io vulnerability database](https://www.mend.io/vulnerability-database/CVE-2026-54698/)
- Related, not-explicitly-requested but directly relevant bonus finding: **GraphQL CSRF**. Endpoints that accept mutations over `GET` or form-encoded `POST` without CSRF-token/content-type enforcement allow cross-site mutation execution — Doyensec's 2021 writeup is the field's canonical reference, and Checkmarx revisited the same class in 2024 ("What's Old Becomes New Again: CSRF Attacks on GraphQL APIs"); a GitLab-tracked real case found that a GET-based mutation-detection check inspected the wrong field first on multiplexed (`_json`) batched requests, leaving some batched mutations unchecked for CSRF even though the single-mutation check worked — [Doyensec: That single GraphQL issue that you keep missing](https://blog.doyensec.com/2021/05/20/graphql-csrf.html), [Checkmarx](https://checkmarx.com/?p=80496), [GitLab work item #324397](https://gitlab.com/gitlab-org/gitlab/-/work_items/324397)

### Inferences
- Add a `test_graphql_nested_field_authz()` probe:
  1. From the reconstructed schema (full or blind-brute-forced), identify candidate pairs: a "self" root field (`me`/`viewer`/`currentUser`, no arguments, returns some type `U`) and a sibling by-ID root field returning the same type `U` (an argument named/typed `id`/`ID!`).
  2. **Control path:** with a given session/token, call the self-field (`{ me { id <every scalar field on U> } }`) and record what it returns — this is the caller's own, presumptively-correctly-gated data.
  3. **Test path:** with the exact same session/token, call the sibling by-ID field with a different ID (`{ user(id: "<other-id>") { <same fields> } }`). Seed candidate IDs from small sequential integers and from any IDs already captured elsewhere in the engagement (REST responses from `api_discovery.py`, other GraphQL responses). If this returns data — especially any field never exposed via the self-field, like another user's email/role/internal flags — record as a confirmed object/field-level authz finding.
  4. **Nested-edge variant:** repeat the differential test by reaching the same sensitive field through an unrelated edge (e.g. `{ post(id: X) { author { email privateProfile { ... } } } }` instead of `user(id)` directly). A pass/fail mismatch between two different graph paths to the identical field is itself the finding, independent of whether either path alone looks suspicious.
  5. **Mutation-BOLA variant:** for any discovered `update*`/`delete*`/`cancel*`/`set*` mutation taking an `id` argument, call it as user A against an object ID believed to belong to user B (same ID-seeding approach as step 3) and check whether it reports success (mutated object returned, or `success: true`) rather than an authorization error. Gate this behind an explicit opt-in/dry-run flag and a pre-agreed test object, since a true positive is a real unauthorized write, not just a read.
  6. **Cheap structural check requiring no live differential testing at all:** grep the reconstructed schema for root fields literally named `node`/`nodes` taking an `ID`/`[ID!]` argument, and flag their mere existence as a finding needing manual/automated per-type authz verification — OWASP singles this out as a generic, schema-wide bypass surface.
  7. As a low-cost add-on given it shares infrastructure with the above: probe the discovered GraphQL endpoint for the CSRF class too — resend a discovered state-changing mutation as `GET` with the query in the querystring, and as form-encoded `POST`, both without any CSRF token/custom header the normal client sends; a `200` with the mutation actually applied on either transport is a CSRF finding.

## Named CVEs / real 2024-2026 GraphQL-implementation vulnerabilities

### Takeaway
Confirmed, citable 2024-2026 CVEs in major GraphQL server libraries cluster tightly around two patterns: validation/complexity-accounting gaps enabling DoS (graphql-java, apollo-compiler), and a fresh (July 2026) Hasura row-level-permission bypass via computed/relationship fields — i.e. nearly every *assigned-CVE* finding in this window is either the depth/complexity DoS class or the field/relationship-authz-bypass class already covered above, not a novel attack category; introspection, batching, and alias abuse remain tracked as vendor advisories (GHSA) and scanner-rule categories rather than assigned CVEs against the big three engines (Apollo, graphql-java, Hasura) in this window.

### Cited Findings
- **CVE-2024-40094** — graphql-java before 19.11 / 20.9 / 21.5: "does not properly consider ExecutableNormalizedFields (ENFs) as part of preventing denial of service via introspection queries"; CVSS v3.1 5.3 Medium, CVSS v4.0 8.7 High (the v4 score reflects full availability impact, the v3.1 score mostly low-integrity impact — sources disagree sharply on severity depending on CVSS version used); published 2024-07-30; fixed in 19.11 / 20.9 / 21.5; propagated downstream into IBM's March 2025 Business Automation Workflow security bulletin — [Tenable: CVE-2024-40094](https://www.tenable.com/cve/CVE-2024-40094), [cybersecurity-help.cz #98137](https://www.cybersecurity-help.cz/vdb/vulns/98137), [IBM Support](https://www.ibm.com/support/pages/node/7174997)
- **CVE-2025-31496** — `apollo-compiler` (Rust crate) before 1.27.0, GHSA-7mpv-9xg6-5r79: named-fragment validation re-processed per fragment *spread* instead of per fragment *definition* with no memoization, causing exponential validation cost for deeply-nested/reused fragments; CVSS 3.1 7.5 High; CWE-770 (resource allocation without limits); no workaround; published 2025-04-07; fixed in 1.27.0 — [Tenable: CVE-2025-31496](https://www.tenable.com/cve/CVE-2025-31496)
- **CVE-2026-54698** — Hasura GraphQL Engine, GHSA-r27x-gc74-qmxh: row-level-permission bypass via a `where` clause on a table computed field returning `SETOF some_table`, letting a caller infer data a direct table-level permission would otherwise block; affects >=2.46.0 <2.49.2 and >=2.45.0 <2.45.5; CVSS reported as 6.0 by one aggregator and 5.9 by another (minor scoring disagreement, not resolved here); published 2026-07-07 — [Mend.io vulnerability database](https://www.mend.io/vulnerability-database/CVE-2026-54698/)
- **CVE-2021-47713 / -47714 / -47715 / CVE-2021-47748** — Hasura GraphQL **1.3.3** (an old release line): nested-query DoS, SQL-injection-based local file read, SSRF via remote schema injection, and `run_sql`/PostgreSQL `COPY FROM PROGRAM`-based RCE, respectively; these received their CVE numbers only in the December 2025 / January 2026 backfill window despite the "2021" identifier and the affected release being years old — only relevant if a target genuinely still runs the 1.3.3 line; CVE-2021-47748 is rated critical, CVSS 9.8, with "no mitigation known" per one aggregator — aggregated search results citing cvefeed.io, radar.offseq.com, vuldb.com (no single primary GHSA/NVD page was fetched directly for this cluster — see Gaps)
- Not a CVE, but a relevant vendor research data point: Escape's "State of GraphQL Security 2024" report states that across 160 public GraphQL services and over 3,800 tested operations, 13% of tested APIs presented GraphQL-specific vulnerabilities — [Escape: The State of GraphQL Security 2024](https://escape.tech/blog/the-state-of-graphql-security-2024/) (title/stat only; full report body was not fetched, see Gaps)
- Not CVEs, but real, dated security advisories against popular GraphQL *hardening* middleware (i.e., bugs in the defenses themselves): GHSA-hmfr-rx46-4jx2 and GHSA-224p-v68g-5g8f against `@escape.tech/graphql-armor-max-depth`, both CVSS 5.3 Medium, covering depth-limit bypass via introspection-field-naming and (separately/overlappingly) fragment caching — [GitLab Advisory DB](https://advisories.gitlab.com/pkg/npm/@escape.tech/graphql-armor-max-depth/)
- Doyensec disclosed a December 2, 2025 upgrade to their internal GraphQL security tool (schema brute-forcer, server-engine fingerprinting, automatic variable generation, performance improvements) — a tooling announcement, not a vulnerability disclosure, but it confirms engine-fingerprinting is considered a first-class, actively-developed capability by a top-tier GraphQL security research firm as of late 2025 — aggregated from a Bluesky mirror of Doyensec's posts; full detail lives at blog.doyensec.com and was not independently fetched
- Academic tooling context: an April 2025 arXiv submission, "GraphQLer," is described as "the first context-aware security testing framework for GraphQL APIs" — [arXiv 2504.13358](https://www.arxiv.org/pdf/2504.13358)

### Inferences
- Because every CVE found here is implementation/version-specific rather than a spec-level flaw, the highest-leverage addition to the ported script is a `fingerprint_graphql_engine()` step that runs **before** any CVE-signature probing: distinguish Apollo (error-object shape, `apollo-require-preflight` header behavior), graphql-java (its distinctive error-extensions shape), and Hasura (presence of `x-hasura-*` response headers, or the `/v1/graphql` + `/v1/version` path convention) from response headers and error-shape alone, and record it as a first-class field (`"engine": "apollo"/"graphql-java"/"hasura"/"unknown"`) in the existing output JSON next to `introspection_enabled`.
- Once fingerprinted, run the matching version-aware probe already described above under the depth/complexity section (the CVE-2025-31496-style fragment-reuse timing probe for Apollo-family servers; an aliased/fragmented introspection-query timing probe for graphql-java) and the matching authz probe under the authorization section (computed-field `where`-clause inference probe for Hasura, directly testing the CVE-2026-54698 pattern) — treat a positive hit as "presumptive CVE-class finding, confirm exact version before reporting," not a confirmed CVE match, since none of these can be fully confirmed by black-box behavior alone without a version banner.
- Given how recent and Hasura-specific CVE-2026-54698 is, and how old-but-newly-numbered the 2021-dated Hasura CVEs are, version/release-age context matters more for Hasura than for the other two engines when deciding how much weight to give a positive probe result.
