# JWT Attack Techniques Beyond alg:none and Basic RS256->HS256 Key Confusion (2024-2026)

**Scope note:** `auth_analyzer.py` (read in full before this research) already implements: `alg:none` bypass (with case variants), RS256->HS256 key confusion (tested only against `""`, `"public_key"`, `"-----BEGIN PUBLIC KEY-----"` — not a real public key extraction), a 42-entry weak-HMAC-secret brute force, and static claim analysis (symmetric-alg warning, missing `exp`, long expiry, sensitive-data-in-payload, privilege-claim detection). It has **no** `jku`/`x5u`/`x5c`/`jwk`/`kid` header testing, no JWKS-fetch/SSRF testing, no `aud`/`iss` validation testing, no refresh-token testing, and no real public-key-based RS256->HS256 confusion (it never tries to fetch/derive the actual server public key). Every technique below targets one of those gaps. Existing code conventions to reuse: `decode_jwt()`, `b64url_encode()`/`b64url_decode()`, `forge_jwt_hs256()`/`forge_jwt_none()`, `http_request(url, headers=...)` returning `(status, headers, body)`, the `findings.append({"type":..., "severity":...})` pattern, and the `log()/success()/warn()/vuln()` helpers.

## JWK/header-injection attacks: jku, x5u/x5c, kid, jwk, crit

### Takeaway
The highest-value, zero-infrastructure header-injection attack is the **`jwk` header** (embedding a full attacker-generated public key directly in the unprotected JWT header) — it needs no SSRF/callback infrastructure at all and should be tried before `jku`/`x5u`. `kid` injection (SQLi, path traversal, and a 2026 SSRF variant) and `jku`/`x5u`/`x5c` URL-fetch injection remain real, documented, and exploitable in 2024-2026 live code, including a named CVE pattern (`crit` header non-enforcement, CVE-2026-32597/CVE-2026-35042) that `auth_analyzer.py` does not test at all.

### Cited Findings
- **`jku` (JWK Set URL) injection**: if the server fetches the key set from the URL named in the token's own `jku` header without validating it against an allowlist, an attacker hosts their own JWKS (containing a key they generated) and signs a forged token with the matching private key, which passes verification — "JWT forgery via unvalidated jku parameter" is a long-standing, still-current class in Acunetix's and PortSwigger-ecosystem vulnerability catalogs. — [Acunetix](https://www.acunetix.com/vulnerabilities/web/jwt-signature-bypass-via-unvalidated-jku-parameter/); [jwt-arsenal jku-injection](https://jwt-arsenal.pages.dev/knowledge-base/jku-injection/)
- The `jku` fetch is itself SSRF: the fetch can be pointed at internal/metadata endpoints, and weak string-based allowlists (checking that a trusted domain appears anywhere in the URL) can be bypassed with userinfo (`https://trusted.com@attacker.com`), subdomain tricks (`https://trusted.com.attacker.com`), or an open redirect hosted on the trusted domain itself. — [Acunetix](https://www.acunetix.com/vulnerabilities/web/jwt-signature-bypass-via-unvalidated-jku-parameter/)
- **`x5u`/`x5c` (X.509 URL / certificate chain) injection**: when a verifier trusts a certificate supplied inside the token rather than one it controls, an attacker embeds a self-signed certificate (and the matching private key signs the token) in `x5c`; `x5u` is the remote variant where the server fetches the attacker-hosted certificate by URL. TrustedSec documents a practical two-step methodology (embed in `x5c`, then host+reference via `x5u`) and recommends pointing `x5u` at an out-of-band collaborator URL first to confirm the server actually dereferences it (blind-SSRF confirmation) before building the full forgery. — [TrustedSec](https://trustedsec.com/blog/attacking-jwt-using-x509-certificates); [Acunetix x5c](https://www.acunetix.com/vulnerabilities/web/jwt-signature-bypass-via-unvalidated-x5c-parameter/); [Tenable plugin 115302](https://www.tenable.com/plugins/was/115302)
- **`kid` (Key ID) SQL injection**: when the server looks up the signing key by `kid` in a database without parameterization, a UNION-based `kid` payload can make the lookup query return an attacker-chosen string, which is then used as the HMAC secret to verify (and thus to forge) the token. OWASP's WSTG documents this explicitly as "Command/SQL Injection" via unsanitized `kid`. — [OWASP WSTG](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/10-Testing_JSON_Web_Tokens); [Invicti kid+SQLi](https://www.invicti.com/es/blog/web-security/json-web-token-jwt-attacks-vulnerabilities)
- **`kid` path traversal**: when `kid` is used as a filename to load the key, directory-traversal sequences can redirect it to a predictable file. OWASP's documented example traverses to `/dev/null` (Linux) or `nul` (Windows) — a known-empty file — so the server ends up verifying/signing with the empty string as the HMAC secret. HackTricks documents a variant using a file with known non-empty contents, `/proc/sys/kernel/randomize_va_space`, whose value is reliably `2`, used directly as the HMAC secret. — [OWASP WSTG](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/10-Testing_JSON_Web_Tokens); [HackTricks](https://book.hacktricks.xyz/pentesting-web/hacking-jwt-json-web-tokens)
- **`kid` as SSRF vector (2026, named CVE)**: **CVE-2026-54430** in OpenIDC's `liboauth2` (used by AWS ALB JWT verification) read the unverified `kid` header value and appended it unencoded into a URL that was fetched **before** signature verification — a direct SSRF primitive reachable purely through the `kid` field, independent of `jku`. Fix was URL-encoding `kid` before use. — [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-54430/); [radar.offseq.com](https://radar.offseq.com/threat/cve-2026-54430-cwe-918-server-side-request-forgery-1fd0b4b8e6f5d982)
- **`kid`-keyed cache collision across tenants (2026, named CVE)**: **CVE-2026-49998** in Centrifugo — the dynamic-JWKS key cache and in-flight-request dedup ("singleflight") were keyed **only** by the JWT's `kid` header, not by the JWKS endpoint/issuer/audience. If two tenants' JWKS documents happen to reuse the same `kid` value, a token legitimately issued for tenant A is accepted as tenant B's once tenant A's key is cached first — a direct cross-tenant authentication bypass (CVSS 8.2, CWE-347). Fix: composite cache key (JWKS endpoint URL + `kid`). — [GHSA-g6vg-wj8f-48cj / OSV GO-2026-5872](https://osv.dev/vulnerability/CVE-2026-49998); [corgea.com](https://corgea.com/advisories/vulnerabilities/CVE-2026-49998)
- No source was found that documents the exact scenario the task asked about verbatim — "`kid` pointing at attacker-controlled cache/log content that gets echoed back as the signing key" — as a separately named technique distinct from the path-traversal and SQLi variants above. Treat it as an unverified extrapolation of the path-traversal pattern (see Inferences) rather than a cited, documented attack.
- **`crit` (critical extension) header non-enforcement — library parsing bug, 2026**: RFC 7515 §4.1.11 mandates that a verifier **reject** any JWT whose `crit` header lists an extension the verifier doesn't understand/enforce. **CVE-2026-32597** (PyJWT <2.12.0, GHSA-752w-5fwx-jx9f, CVSS 7.5) and **CVE-2026-35042** (fast-jwt <=6.1.0, fixed 6.2.0) both silently accepted tokens carrying unrecognized `crit` extensions instead of rejecting them — meaning an app that relies on a `crit`-declared extension to enforce something (e.g., a step-up-auth or MFA marker) can have that enforcement silently bypassed. One advisory also flags cross-library inconsistency: a gateway running `jwcrypto` correctly rejects the same token a PyJWT-based backend accepts — a "split-brain" validation gap in multi-service stacks. — [Mondoo/GHSA-752w-5fwx-jx9f](https://mondoo.com/vulnerability-intelligence/vulnerability/GHSA-752w-5fwx-jx9f); [dev.to CVE-2026-32597](https://dev.to/cverports/cve-2026-32597-cve-2026-32597-critical-header-parameter-validation-bypass-in-pyjwt-20df)
- **Header-merge TOCTOU → algorithm confusion in JSON-serialized JWS (PHP, 2026)**: GHSA-jc38-x7x8-2xc8 in PHP `web-token/jwt-framework` (also `jwt-library`, `jwt-bundle`, `jwt-experimental`) — in the JSON Serialization format, a JWS has a separate integrity-protected "protected" header and a plaintext, **non**-integrity-protected top-level "unprotected" header member. `HeaderCheckerManager` validated `alg` from the *protected* header, but `JWSVerifier` actually used the *merged* header (via PHP's `array_merge()`, where the later array's keys win) for the real cryptographic operation — so an attacker-supplied unprotected-header `alg` (e.g., swapping `RS256`→`HS256`) silently overrides the validated protected one. The same `array_merge()` last-wins bug exists in `JWEDecrypter.php` for `alg`/`enc`. Affected: all versions <3.4.10, 4.0.x<4.0.7, 4.1.x<4.1.7 (CVSS 7.4, CWE-345). — [GitLab advisory mirror](https://advisories.gitlab.com/composer/web-token/jwt-framework/GHSA-jc38-x7x8-2xc8/); [radar.offseq.com](https://radar.offseq.com/threat/ghsa-jc38-x7x8-2xc8-php-jwt-framework-jwsverifier--7c5a7fc22ffde60d)
- A Burp extension pattern (name unverified independently — "JWT_X509_Re-Signer") is referenced by community cheat sheets as automating `x5c` embedding and `x5u` injection; treat as a tooling pointer only, not a primary source. — [TrustedSec](https://trustedsec.com/blog/attacking-jwt-using-x509-certificates)

### Inferences
- **Implementation priority**: test `jwk` header injection first (see below) since it needs zero network infrastructure; then `kid` (SQLi/traversal/SSRF, also no infra needed beyond the target itself); then `jku`/`x5u` (need an attacker-reachable HTTP endpoint or at minimum an out-of-band callback domain to detect blind SSRF).
- **`jwk` header injection — new standalone test function, highest implementation priority.** The `jwk` header parameter lets the token itself carry the full public key to verify against (this is distinct from `jku`, which is a *pointer* to a remote key set). If the verifier trusts whatever key the token hands it instead of only ever using a pre-pinned server key, forgery requires no external infrastructure. Concrete test logic for `auth_analyzer.py`:
  1. Generate a fresh keypair matching the original token's key type (`cryptography.hazmat.primitives.asymmetric.rsa.generate_private_key` for RS*/PS* algs, or `ec.generate_private_key(ec.SECP256R1())` for ES256) — this needs a new dependency (`cryptography`) that the current script doesn't import.
  2. Build the JWK representation of the **public** half (base64url `n`/`e` for RSA, `x`/`y`/`crv` for EC).
  3. Set header `{"alg": original_alg, "typ": "JWT", "jwk": <public JWK dict>, "kid": <same kid as original, or omit>}`, keep/modify the payload, sign with the **private** key you just generated using the same `original_alg`.
  4. Send; status 200/201 with the forged (ideally privilege-escalated) claims reflected = confirmed vulnerability. This slots in as `test_jwt_jwk_injection(decoded_jwt, test_url, ...)` parallel to the existing `test_jwt_hs256_confusion`.
- **`jku`/`x5u` test logic** (needs attacker-controlled HTTP reachability — document this as an operational prerequisite, e.g. an ngrok-style tunnel or a pentest-infra listener):
  1. First send a *minimal* probe: set `jku` (or `x5u`) to an attacker-controlled URL that just logs the hit, with an otherwise-untouched token, to confirm the server actually dereferences the header (blind-SSRF confirmation) before investing in full key generation.
  2. If confirmed, generate a keypair, build/serve a JWKS document (`{"keys":[<public JWK with matching kid>]}`) or a self-signed X.509 cert (`cryptography.x509.CertificateBuilder`) at that URL, sign a forged payload with the private key, set `jku`/`x5c`/`x5u` accordingly, and resend.
  3. Also try `data:` and `file://` URIs as the `jku`/`x5u` value — **this needs no network infra at all**: a `data:application/json;base64,<base64(forged JWKS)>` URI, if the HTTP client behind `jku` doesn't allowlist schemes (see the PyJWT `PyJWKClient` CVE below — a documented real-world instance of exactly this gap), achieves full offline forgery. Test this variant before standing up any listener.
  4. For allowlist-bypass probing, also try a battery of near-miss hostnames against any domain the app is known to trust: `https://trusted.com@ATTACKER`, `https://trusted.com.ATTACKER`, `https://ATTACKER/?trusted.com`, `https://trusted.com%2f@ATTACKER` — differential response status/timing across these reveals a naive substring-based allowlist.
- **`kid` SQLi test logic**: iterate `kid` through a small payload list — `' UNION SELECT 'knownsecret'-- -`, `' OR '1'='1`, plus boolean/time-based probes (`' AND SLEEP(5)-- -` and measure latency delta) — for each UNION-style payload that plausibly returns a *known* string, forge an HS256 token using that string as the HMAC secret (reuse `forge_jwt_hs256`) and test for 200. Even without achieving full forgery, a timing delta on the SLEEP payload vs. a benign `kid` is itself a reportable SQLi finding independent of JWT forgery.
- **`kid` path-traversal test logic**: build a table of `(traversal_path, expected_secret_value)` pairs — `("../../../../dev/null", "")`, `("..\\..\\..\\..\\windows\\system32\\drivers\\etc\\hosts", None)` (non-empty/variable, lower value), `("../../../../proc/sys/kernel/randomize_va_space", "2")` — set `kid` to each path, `forge_jwt_hs256(payload, expected_secret_value)`, send, check 200. This is a direct, cheap extension of the existing `brute_force_jwt_secret` loop structure — same forge/send/check shape, different "secret" source.
- **`kid`-as-URL/SSRF test logic** (CVE-2026-54430 pattern): set `kid` to a full URL pointing at an attacker callback (or to internal-looking targets like `http://169.254.169.254/latest/meta-data/` for a cloud-metadata SSRF probe, and `http://localhost:PORT/` variants for internal port probing) and check for an out-of-band hit, exactly like the `jku` blind-SSRF probe above — `kid` deserves the same SSRF test battery as `jku`, not just filesystem-path and SQLi payloads.
- **`crit` header test logic**: take the original decoded token, add `"crit": ["mythosTestExt"], "mythosTestExt": "x"` into a none-alg or weak-secret-signed forged copy (reuse existing `forge_jwt_none`/`forge_jwt_hs256`), send, and if it's accepted exactly as a copy without the `crit` addition would be, flag `jwt_crit_not_enforced` (severity: medium/info — it's a library-conformance gap, impact depends on whether the app actually uses `crit` for anything security-relevant). This is a cheap, pure-header addition to the none/weak-secret tests already in the script, costing almost no new code.
- **Header-merge/TOCTOU test logic**: only reachable if the target's API accepts JWS **JSON Serialization** (a JSON body like `{"payload":"...","protected":"...","header":{...},"signature":"..."}`) rather than compact serialization (`a.b.c` string) — first probe whether the endpoint accepts that body shape at all (try resending a compact token's three parts reformatted into JSON Serialization). If accepted, construct protected header `{"alg":"RS256"}` (base64url-encoded, matching original) but unprotected `header: {"alg":"HS256"}`, and sign the `protected.payload` signing input with HS256 using a weak/empty secret or the RSA public key as the secret (chain this into the existing `test_jwt_hs256_confusion` key-guessing list). Low priority unless recon confirms JSON Serialization support — most REST APIs use compact form only.

### Gaps
- Could not confirm a documented, named attack matching "`kid` pointing to attacker-controlled cache/log content echoed back as the signing key" as asked in the task brief — the closest real analogues found are the SQLi and path-traversal `kid` variants and the CVE-2026-54430 SSRF-via-`kid` case, plus the Centrifugo cross-tenant cache-key collision (which is a cache-confusion bug but not "attacker writes to a log/cache that becomes the key"). If this exact scenario is a known technique, it wasn't surfaced by the searches run.
- Did not verify the "JWT_X509_Re-Signer" Burp extension's existence/repository independently.

## JWKS endpoint attacks: SSRF/substitution and algorithm-confusion variants beyond RS256->HS256

### Takeaway
Beyond the classic RS256→HS256 confusion (which `auth_analyzer.py` already tests, albeit with placeholder keys rather than a real extracted public key), 2024-2026 produced concrete, named library CVEs for RSA-family confusion (RS256↔PS256 via key-type-only checks), sign/encrypt confusion (JWS vs. JWE dispatch), and a PBES2-iteration-count denial-of-service ("billion hashes") — and a dedicated academic fuzzer (NDSS 2026 "JWTeemo") found 20 new CVEs across popular libraries in exactly these categories, confirming this is an active, still-fruitful bug class, not a solved problem.

### Cited Findings
- **Real public-key extraction is the missing piece in the existing RS256→HS256 test**: `auth_analyzer.py`'s `test_jwt_hs256_confusion` only tries `""`, `"public_key"`, and a bare PEM marker string as the HMAC key — it never obtains the server's actual public key. PortSwigger's two lab variants show both acquisition paths pentesters actually use: (1) **exposed key** — fetch it directly from a `/jwks.json`-style endpoint — and (2) **no exposed key** — derive the RSA public key (modulus `n` and exponent `e`) purely from two or more valid signed tokens using the `sig2n` technique, distributed by PortSwigger as a Docker image (`docker run --rm -it portswigger/sig2n <token1> <token2>`). Both acquired keys must then be reformatted into exact PEM/DER byte sequences before use as the HMAC key, and PortSwigger notes formatting (trailing newline, PEM header exactness) materially affects success. — [PortSwigger algorithm-confusion overview](https://portswigger.net/web-security/jwt/algorithm-confusion); community walkthroughs of both lab variants ([mfkrypt lab 7](https://mfkrypt.gitbook.io/stuff/portswigger-web-academy/jwt/lab-7-jwt-bypass-via-algorithm-confusion), [lab 8](https://mfkrypt.gitbook.io/stuff/portswigger-web-academy/jwt/lab-8-jwt-bypass-via-algorithm-confusion-with-no-exposed-key))
- **JWKS-fetch SSRF / substitution, 2026 CVEs**: CVE-2026-105122 (OpenAM <16.1.3, unvalidated `jwks_uri` → SSRF); CVE-2026-49478 (Sigstore Fulcio — cross-host redirects in the OIDC-discovery HTTP client enable blind SSRF **and** JWKS substitution for cache poisoning); a SurrealDB advisory describing a permitted JWKS host that returns a 3xx redirect, sending the actual fetch to an address the allowlist was meant to block (classic allowlist-then-redirect bypass). — [SentinelOne CVE-2026-105122](https://www.sentinelone.com/vulnerability-database/cve-2026-1180/); [feed.craftedsignal.io](https://feed.craftedsignal.io/tags/jwks/feed.json); [PT Security SurrealDB](https://dbugs.ptsecurity.com/vulnerability/PT-2026-53783)
- **PyJWT `PyJWKClient` missing URL-scheme allowlist, 2026**: **CVE-2026-48522** (GHSA-993g-76c3-p5m4, PYSEC-2026-175) — `PyJWKClient` passes the configured/header-derived JWKS URI straight to `urllib.request.urlopen()`, which by default also dereferences `file://`, `ftp://`, and `data:` schemes, not just `http(s)`. In an app that builds the JWKS URL from attacker-influenced input (e.g., from a `jku` header), this widens the SSRF surface to local-file reads and (per the general `data:`-URI principle in the inferences above) fully offline key-substitution. Affected 2.0.0–2.12.2, fixed in 2.13.0 (adds an `allowed_schemes` parameter defaulting to `("https","http")`). CVSS 4.2 (Medium) — the advisory is explicit that full token-forgery impact needs chaining with another app-level flaw (e.g., attacker write access to a local path), but the scheme-acceptance gap itself is independently testable. — [Corgea CVE-2026-48522](https://corgea.com/advisories/vulnerabilities/CVE-2026-48522)
- **RS256↔PS256 confusion**: because both share the same RSA key material, a verifier that checks only "is this an RSA key" rather than pinning the exact algorithm string can be confused between RS256 and PS256 (RSA-PSS). WorkOS's write-up gives this as a concrete named variant of the general confusion pattern (distinct from RS256→HS256), and the fix is identical in spirit: pin one exact algorithm, never a key-type family. — [WorkOS](https://workos.com/blog/jwt-algorithm-confusion-attacks)
- **ES256/EC curve handling**: Connect2id's Nimbus JOSE+JWT added explicit point-on-curve validation in v4.36 (checking that EC public-key coordinates actually lie on the curve named in the key, both at key construction and at ECDSA-verifier construction) specifically to defend against "invalid curve attacks" — primarily a threat against ECDH-ES key-agreement (can leak private-key bits), described as a less direct threat to plain ES256 signature verification. A GitHub issue against `firebase/php-jwt` (#600, mirror-sourced, not independently verified) separately reports the library accepting P-192-curve keys for tokens whose header declares `ES256` (which RFC 7518 mandates must use P-256) — i.e., a library that checks "is this an EC key" rather than "is this specifically a P-256 key." — [Connect2id](https://connect2id.com/blog/nimbus-jose-jwt-invalid-curve-attack-defence); [RFC 8725 (JWT BCP)](https://rfc-editor.org/rfc/rfc8725.html)
- **Sign/encrypt (JWS vs. JWE) confusion**: Tom Tervoort's Black Hat USA 2023 talk "Three New Attacks Against JSON Web Tokens" showed that a validator which trusts the token header's declared algorithm/type can be tricked into treating an **RSA-encrypted JWE** as if it were a signed JWT, if the attacker knows the RSA public key (trivially obtainable from an exposed JWKS) — letting the attacker forge arbitrary claims. This 2023 research is foundational background for several of the library CVEs below and for the NDSS 2026 paper's "signature/encryption confusion" category. — [Black Hat USA 2023 whitepaper](https://i.blackhat.com/BH-US-23/Presentations/US-23-Tervoort-Three-New-Attacks-Against-JSON-Web-Tokens-whitepaper.pdf)
- **"Billion hashes" PBES2 denial-of-service** (same Tervoort talk): a JWE using password-based encryption (`PBES2-*`) carries its PBKDF2 **iteration count in the attacker-controlled token header** (`p2c`). Setting `p2c` extremely high forces the server to perform billions of hash operations deriving the key *before* it can even determine the token is invalid — Tervoort's example required over 4 billion SHA-512 operations, with **no prior knowledge of a valid token needed**. Confirmed-affected libraries include `jose` (npm, panva) <1.28.1/2.0.5/3.20.3/4.9.1 (CVE-2022-36083) and `jose-jwt` (.NET) <4.1; PHP `web-token/jwt-framework` passed `p2c` unbounded into `hash_pbkdf2` until a 2026 fix capped it at 1,000,000 iterations by default (PT-2026-53178). — [Trail of Bits](https://blog.trailofbits.com/2024/03/08/out-of-the-kernel-into-the-tokens/); [PT Security PT-2026-53178](https://dbugs.ptsecurity.com/vulnerability/PT-2026-53178)
- **NDSS 2026 "JWTeemo" fuzzing paper**: a dedicated JWT/JOSE-library fuzzer found vulnerabilities across five categories — signature/encryption confusion, algorithm confusion, JWT-format confusion, the billion-hashes PBES2 attack, and compression-based DoS — resulting in **20 assigned CVEs**, acknowledged by multiple vendors, all exploitable for either authentication bypass or denial of service. The specific itemized CVE list was not retrieved (only the abstract/summary); see Gaps. — [NDSS 2026 paper PDF](https://www.ndss-symposium.org/wp-content/uploads/2026-f697-paper.pdf)
- **CVE-2024-54150 — concrete 2024 algorithm-confusion library bug (cjwt, C)**: `xmidt-org/cjwt`'s `cjwt_decode()` does not require the caller to pin an expected algorithm, and its HMAC-verification path (`verify_hmac()`) uses whatever key bytes it's given without checking whether those bytes are actually a PEM-encoded RSA/EC public key. An attacker who has the server's RSA public key (commonly public) HMAC-SHA256s the token's `header.payload` using the **raw PEM text** as the HMAC secret, labels the header `HS256`, and the library accepts it as if it were a validly RSA-signed token. Independently reproduced by the researcher via both a Ruby forging script and a C test harness. GHSA-9h24-7qp5-gp82. — [PentesterLab](https://pentesterlab.com/blog/another-jwt-algorithm-confusion-cve-2024-54150)
- **CVE-2024-33663 — python-jose, algorithm confusion via OpenSSH-format keys**: affects python-jose <=3.3.0 (GHSA-6c5p-j8vq-pqhj / PYSEC-2024-232). Root cause: the `algorithms` allowlist parameter to `jwt.decode()` is **not mandatory**, and the library's internal "is this key asymmetric" string-based check in its cryptography backend is insufficient for OpenSSH-format ECDSA public keys, so HMAC verification can proceed using an asymmetric public key as the secret. Explicitly described as the same root-cause family as PyJWT's older CVE-2022-29217. Fixed in 3.4.0. CVSS 6.5 (Medium) per Wiz; GitHub's database-specific severity field rates it Critical — note the discrepancy. — [Vicarius](https://www.vicarius.io/vsociety/posts/algorithm-confusion-in-python-jose-cve-2024-33663); [Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2024-33663)
- **CVE-2024-28176 — `jose` (npm, panva), JWE decompression resource exhaustion**: a specially crafted JWE whose header sets `"zip"` (DEFLATE compression) decompresses to a disproportionately large plaintext, causing resource exhaustion during JWE decryption — a decompression-bomb pattern distinct from the PBES2 iteration-count DoS above but in the same "cheap attacker input → expensive server work before rejection" family. Affects `jose` >=3.0.0 <=4.15.4 and 2.x<=2.0.6; fixed in 4.15.5/2.0.7. GHSA-hhhv-q57g-882q. — [GitHub Advisory](https://github.com/advisories/GHSA-hhhv-q57g-882q); [NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-28176)
- **`jwk`-header forgery as a distinct 2026 library CVE**: CVE-2026-34240 in the **Dart** `jose` package (`appsup-dart`, unrelated to panva's JS `jose`) accepts an attacker-embedded key straight from the JOSE header (the `jwk` parameter) without checking it against any trusted keystore, letting an unauthenticated attacker forge arbitrary JWS/JWT tokens. This is independent confirmation, in a real 2026 library, that the `jwk`-header-injection technique above is not merely theoretical. Fixed in 0.3.5+1. — [radar.offseq.com](https://radar.offseq.com/threat/cve-2026-34240-cwe-347-improper-verification-of-cr-4aef725b)
- **joserfc (Python) base64-padding malleability, 2026**: CVE-2026-62995 — `joserfc` accepts JWT segments with non-canonical base64url padding, a parsing-differential/malleability bug (distinct class from algorithm confusion, but relevant to any signature-based integrity assumption that treats the token string as canonical). — [api.osv.dev](https://api.osv.dev/v1/vulns/CVE-2026-62995)

### Inferences
- **Upgrade the existing RS256→HS256 test to use a real key.** The single highest-value fix to `auth_analyzer.py`'s existing (placeholder-only) key-confusion test is: (1) try fetching `<api_base>/.well-known/jwks.json`, `/jwks.json`, and any `jku` value present in the token header itself, parse the JWKS, and extract the RSA public key's `n`/`e` (base64url-decode, big-endian integer, build an RSA public key via `cryptography.hazmat.primitives.asymmetric.rsa.RSAPublicNumbers(e,n).public_key()`), then PEM-serialize it; (2) if no JWKS is discoverable but **two or more valid tokens are available**, implement the `sig2n` derivation (RSA signature forgery via two known-good RS256 signatures over known messages recovers `n` — this is a several-hundred-line algorithm; pragmatically, shell out to the `portswigger/sig2n` Docker image if Docker is available in the test environment, or port the underlying GCD-based `n`-recovery algorithm directly) to recover the key without ever seeing a JWKS. Use the resulting real PEM bytes as one more candidate in the existing `test_keys` list in `test_jwt_hs256_confusion` — this is a pure data-source change, no control-flow change needed.
- **Add an RS256↔PS256 confusion test** as a near-identical sibling function to `test_jwt_hs256_confusion`: once a real RSA public key is available (same acquisition path as above), also try re-signing the original payload with **PS256** (using `cryptography`'s RSA-PSS signer, which needs the **private** key, so this direction only works if a private key was somehow recovered/leaked) or — more practically for a black-box tool — simply **replay the original RS256 signature bytes but relabel the header `alg` as `PS256`** (or vice versa) and send; some verifiers dispatch purely on the declared `alg` string into a generic "RSA-verify" routine that doesn't check the padding scheme actually used, so a relabeled signature can pass if the library is sloppy. This is cheap (no new crypto, just header relabeling + resend) and should be added as a quick check regardless of whether full PS256 signing is implemented.
- **JWKS-fetch SSRF test**: for any discovered `jku` value or configurable JWKS-URL setting, test with `file://`, `ftp://`, and `data:` URIs in addition to the allowlist-bypass hostname battery described in the previous section — this is the same test code path as the `jku` injection test above; the PyJWT `PyJWKClient` CVE confirms real libraries fail to restrict schemes, so this is not a theoretical edge case.
- **PBES2 "billion hashes" DoS test — implement cautiously, single-shot only**: construct a compact JWE with header `{"alg":"PBES2-HS512+A256KW","enc":"A256GCM","p2c": 2**31, "p2s": <base64url random 16 bytes>}`, an arbitrary (even garbage/undecryptable) encrypted-key segment, IV, ciphertext, and tag — it does not need to decrypt successfully, since the point is that key-derivation happens *before* the ciphertext is even touched. Send it once as the bearer token, measure response latency against a baseline (a normal invalid-token rejection), and flag a finding if latency spikes by orders of magnitude (e.g., >5-10s vs. a sub-100ms baseline rejection). **Do not loop this request** — a single request is sufficient to demonstrate the DoS primitive; looping it would constitute an actual resource-exhaustion attack against the target rather than a test, which exceeds authorized-pentest testing norms even under engagement scope. Only applicable where the target is known/suspected to accept JWE (not plain JWS) tokens.
- **Sign/encrypt confusion test**: once a public key is available (JWKS or `sig2n`), also construct a syntactically valid 5-segment compact JWE (`alg: RSA-OAEP` or `RSA1_5` wrapping a random CEK, `enc: A128CBC-HS256`, encrypting an attacker-chosen plaintext claims blob) using that same public key via `cryptography`'s `rsa.encrypt` / a JWE library, and submit it where the app expects a 3-segment signed JWT. The practically implementable signal here (since full exploitation depends on library-internal dispatch bugs that vary) is a **differential error check**: does the 5-segment JWE produce a distinctly different error (parser exception / 500 / different error body) than a clean "invalid JWT" rejection? A different error class signals the verifier got further into type-specific processing than a rejecting verifier should, and is worth flagging for manual follow-up rather than claiming automatic exploitation.
- **Curve-confusion test for ES256**: generate EC keys on alternate curves (P-192 via `ec.SECP192R1()` if supported by the `cryptography` backend, P-384, secp256k1) and sign the payload with each, labeling the header `alg: ES256` regardless of actual curve used; send each. Any 200/201 (or even a distinctly different error vs. a same-curve-wrong-key control) indicates the verifier isn't enforcing that `ES256` specifically requires a P-256 key, matching the firebase/php-jwt #600 pattern.

## Token-lifecycle issues: refresh-token rotation, missing aud/iss, cross-service/tenant confusion

### Takeaway
2026 produced several concrete, named CVEs showing refresh-token rotation logic breaking in three distinct ways (missing token-type check on the refresh route, stale tokens surviving revocation events, and race conditions in concurrent redemption) — all directly testable via HTTP without any cryptography. Missing `aud`/`iss` validation is extremely common, well-documented as a structural anti-pattern (especially with a signing secret/key shared across multiple services), and is the cheapest possible addition to `auth_analyzer.py` since it needs zero additional HTTP requests — it's a pure claims-analysis check on data already decoded.

### Cited Findings
- **Refresh route accepts the wrong token type / wrong HTTP method (CVE-2026-82469, Rodauth <2.47.0)**: the refresh route issued new access tokens without properly checking that the presented token was actually a refresh token — an access token sent to the refresh route via a non-POST method could still yield a fresh, valid access token. CVSS v4 5.1; fixed in 2.47.0. — [Mend.io](https://mend.io/vulnerability-database/CVE-2026-82469/); [OSV](https://osv.dev/vulnerability/CVE-2026-82469)
- **Stale refresh tokens survive revocation events**: JWT Auth WordPress plugin <=3.0.2 (CVE-2026-106466) kept old refresh tokens valid after a password change or device removal — a stolen token stays usable, with impact rising to administrator. NocoDB (CVE-2026-53928) had the equivalent gap in its forgot-password flow: existing refresh tokens were not revoked, so a previously captured token continued to work after the password reset. — [OpenCVE CVE-2026-106466](https://app.opencve.io/cve/CVE-2026-106466); [Miggo CVE-2026-53928](https://www.miggo.io/vulnerability-database/cve/CVE-2026-53928)
- **Refresh-token rotation race condition (better-auth OAuth provider, PT-2026-56301)**: two concurrent requests presenting the **same** refresh token can both pass the revocation/already-used check before either request marks the token consumed, so both mint valid new token pairs from a single refresh token. The advisory cites RFC 9700 §4.14 (OAuth 2.0 Security BCP) for the expected reuse-detection behavior and recommends an atomic compare-and-swap on the token's parent row as the fix. — [PT Security PT-2026-56301](https://dbugs.ptsecurity.com/vulnerability/PT-2026-56301)
- **Missing audience validation = cross-service replay**: multiple independent sources converge on the same structural finding — a service that validates signature and expiry but skips `aud` will accept a token minted for a *different* service that shares the same issuer/signing key, and the risk scales with how many services share one issuer. The clearest concrete illustration: FastAPI-tenancy's own documentation warns explicitly that several services sharing one JWT secret, without audience checking, lets a token minted for one service be accepted by another. A documented real default-insecure pattern: a Rust crate shipped with `validate_aud = false` as its default, silently accepting tokens issued for *any* service until changed. — [fastapi-tenancy docs](https://fastapi-tenancy.readthedocs.io/en/latest/guides/resolution/jwt/); [nhimg.org](https://nhimg.org/articles/jwt-audience-validation-failures-create-replay-risk-across-services/); [WorkOS aud guidance](https://workos.com/blog/how-to-validate-the-jwt-aud-claim-and-why-it-matters)
- **`iss`/`aud` are different checks doing different jobs**: "`iss` tells you who created the token. `aud` tells you who should accept it." Validating only one leaves a gap even if the other is present and correct. — [WorkOS](https://workos.com/blog/how-to-validate-the-jwt-aud-claim-and-why-it-matters)
- **Cross-tenant confusion via shared key infrastructure** is the same Centrifugo CVE-2026-49998 cited under JWKS attacks above (JWKS cache keyed only by `kid`, not issuer/audience/tenant) — directly on-point for "JWT confusion between different services/tenants sharing signing infrastructure" as asked in the task brief, and the clearest 2024-2026 named example of it. — [OSV GO-2026-5872](https://osv.dev/vulnerability/CVE-2026-49998)
- **PyJWT's own `iss` check had a bug in this exact area**: CVE-2024-53861 — a faulty string-comparison in PyJWT's issuer check accepted substring matches (e.g., a token with `iss: "acb"` could pass a check expecting `"_abc_"`-style values) rather than requiring an exact match. Affects 2.10.0, fixed in 2.10.1. This shows that even *correctly implemented* `iss` checking in application code can be undermined by a library-level comparison bug — worth testing with crafted near-miss `iss`/`aud` values (substrings, case variants) even against apps that claim to validate these claims. — [TuxCare](https://tuxcare.com/cve-tracker/cve/details/cve-2025-45768) (cross-referenced); [Red Hat Bugzilla 2385868](https://bugzilla.redhat.com/show_bug.cgi?id=2385868)

### Inferences
- **`aud`/`iss` presence/enforcement check — add to `analyze_jwt_claims`, zero new HTTP requests.** This is the cheapest win in this entire report: extend the existing static-analysis function (which already checks `exp`, sensitive fields, and privilege claims) with: flag `jwt_no_audience` (severity high) if `aud` is absent from the payload entirely; flag `jwt_no_issuer` (severity medium) if `iss` is absent. No network round-trip needed — this is pure `payload.get("aud")`/`payload.get("iss")` logic alongside the existing `exp` check.
- **Active cross-service/cross-tenant replay test** (needs recon context — a list of sibling endpoints/services, which `api_discovery.py`'s output or user-supplied `--input` may already provide): for each additional base URL/service discovered that is plausibly part of the same deployment (shares a domain suffix, or was explicitly provided), replay the **original, unmodified** token against that service's protected endpoints. A 200/201 response = the sibling service accepts a token not minted for it = direct audience-enforcement failure, reportable with zero forgery required.
- **Tampered-`aud` resubmission test** (requires a working forgery method first — chain behind whichever of `alg:none`, weak-secret, or key-confusion already succeeded in the same run): take the payload, strip or replace `aud` with a decoy value, re-sign using the already-confirmed-working forgery technique, and resubmit **to the original endpoint it came from**. If this still returns 200 where the unmodified token also returns 200, but a legitimately-different-`aud` token from a real different context would be expected to fail, that demonstrates the endpoint isn't actually checking `aud` content (vs. merely not having `aud` present) — a stronger, actively-confirmed version of the static check above. Implement as `test_jwt_audience_enforcement(decoded_jwt, test_url, forge_fn, ...)` taking whichever forge function already proved to work.
- **Refresh-endpoint testing — entirely new test function needed, `auth_analyzer.py` currently has none.** If a refresh endpoint is discoverable (common paths: `/token/refresh`, `/auth/refresh`, `/oauth/token` with `grant_type=refresh_token`, or named explicitly via `--input` recon data), implement four checks modeled directly on the cited CVEs: (1) **method/type confusion** — call the refresh route with the current **access** token (not a refresh token) and also with non-POST verbs (GET/PUT/PATCH), checking whether a fresh access token is still issued (Rodauth-style bug); (2) **reuse-after-rotation** — redeem a refresh token once, capture the new pair, then immediately replay the original (now-superseded) refresh token and check whether it's rejected (RFC 9700 §4.14 compliance) or still honored; (3) **concurrent-redemption race** — fire two near-simultaneous requests (Python `threading` or `asyncio.gather` with two independent sockets/connections) presenting the identical refresh token, and check whether both return distinct valid new token pairs (should be exactly one winner); (4) **post-revocation validity** — if a logout-all/change-password/revoke-sessions action is available and testable, call it, then attempt to use a previously captured refresh/access token afterward.

### Gaps
- No single canonical "JWT rotation bypass" write-up was found; all findings are per-CVE/per-product rather than a generalized technique description, so the four test patterns in Inferences are synthesized from several distinct 2026 incidents rather than quoted from one source — flagging this synthesis clearly as an inference, not a direct citation.
- Did not find a 2024-2026 bug-bounty report (HackerOne/Bugcrowd) specifically illustrating cross-service `aud` bypass end-to-end with disclosed program/bounty details; the structural guidance is well-sourced from vendor/engineering blogs but lacks a concrete "this exact bounty was paid for this exact aud bug" citation.

## PASETO/JWE as JWT alternatives: 2024-2026 insecure-migration research

### Takeaway
No new PASETO protocol-level vulnerability or documented 2024-2026 "insecurely migrated to PASETO" incident was found — the only concrete, dated 2024-2026 JWE-specific issues are the PBES2 "billion hashes" DoS and the panva `jose` JWE-compression DoS (CVE-2024-28176), both already covered above. This is a genuine research gap, not a sign the risk doesn't exist: the one substantive design discussion found (Neil Madden vs. Paragon Initiative on the CFRG mailing list) is about whether PASETO's *specification* fully closes algorithm confusion, and directly implies a realistic implementation-level risk if an app hand-rolls PASETO version/purpose dispatch instead of using a conformant library call.

### Cited Findings
- **No 2024-2026 PASETO protocol CVE found.** The only PASETO-ecosystem security issue surfaced is a **dependency** problem: `rusty-paseto` depends on `ed25519-dalek`, which has RUSTSEC-2022-0093 — an unsafe API for serializing/deserializing 64-byte keypairs (combined private+public bytes) that can expose private-key material if misused; a related vulnerability database entry on private-key extraction was last updated October 2025, rated low severity. This is a supply-chain/dependency issue, not a flaw in the PASETO design or spec. — [vulert.com rusty-paseto](https://vulert.com/vuln-db/crates.io/rusty-paseto)
- **Snyk reports no direct vulnerabilities** for the Python `paseto` package (explicitly noting this doesn't cover the package's own dependencies). — [security.snyk.io](https://security.snyk.io/package/pip/paseto)
- **Design-level critique (predates 2024 but is the only substantive security debate on PASETO's core approach)**: Neil Madden, on the CFRG/IETF mailing list, argued the first PASETO RFC draft did not fully address JWT-style algorithm confusion. Paragon Initiative Enterprises (PASETO's creator) responded that the specification and its test vectors are designed to make *conformant* libraries structurally immune to this class of bug — because a PASETO token's version+purpose (e.g., `v4.public.`) is a fixed literal prefix that determines parsing, not an attacker-adjustable "algorithm" field read out of the token the way JWT's `alg` header is. — [mailarchive.ietf.org](https://mailarchive.ietf.org/arch/msg/cfrg/Yd85GHaPfkUYvCsWAdikByQsiLQ/); [Paragon Initiative response](https://paragonie.com/b/QzOiyPsHA63Ao3Le)
- **JWE-specific 2024-2026 incidents are exactly the two already cited under JWKS/algorithm-confusion findings**: CVE-2024-28176 (panva `jose`, JWE `zip`-compression resource exhaustion) and the PBES2 `p2c` "billion hashes" DoS (Tervoort BH2023, with concrete 2024-2026 library fixes landing later, e.g. PT-2026-53178 for PHP web-token/jwt-framework). No additional JWE-specific attack research beyond these two was found.

### Inferences
- **PASETO version/purpose-confusion test (inference, not a cited documented attack — label clearly as such if ported into the tool)**: if a target has migrated to PASETO, a token splits cleanly on `.` into version, purpose, and payload/footer segments (e.g., `v4.public.<payload>.<footer>`), directly analogous to `decode_jwt`'s three-part split. Test: take a captured token's payload+signature/tag bytes unchanged, but swap the version prefix (`v4`→`v2`, or `v3`→`v4`) or the purpose prefix (`public`→`local`) and resubmit. A spec-conformant library rejects any such mismatch outright since the full `version.purpose.` string is itself part of what's cryptographically bound (for `local`, it's AAD; for `public`, parsing dispatch is fixed before any crypto runs) — but an app that reads the prefix *itself* (e.g., via naive string-splitting before calling into a crypto library per-branch) to decide which verification routine to call, rather than asking a single library entry-point to enforce the expected version+purpose, could re-introduce exactly the confusion PASETO's design is meant to prevent. Any non-clean-rejection response (anything other than an immediate, generic auth failure) is the detection signal and should be flagged for manual follow-up, not treated as confirmed exploitation — there is no cited real-world instance of this succeeding.
- **PASETO footer-as-kid test (inference)**: if the app uses the PASETO footer field for key identification (a common pattern, analogous to JWT's `kid`), apply the exact same SQLi/path-traversal/SSRF test battery developed for `kid` above to the footer value, since the underlying risk (unsanitized attacker-controlled input used to select a key) is identical regardless of token format.
- **JWE "zip"-bomb test** is the one concretely implementable JWE-specific check from this section, already detailed under the JWKS/algorithm-confusion section's Inferences (craft a JWE with `"zip":"DEF"` and a decompression-bomb payload) — note here only because it is JWE's most directly cited 2024-2026 attack-surface item. It is gray-box/conditional: black-box testing generally can't construct a *decryptable* JWE without knowing the key, so this check mostly applies when the tool already holds a valid symmetric key (e.g., recovered via a weak-secret brute force reused for JWE) or in authenticated/gray-box engagements.
