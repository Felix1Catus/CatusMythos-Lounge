# API Versioning Bypass & Rate-Limit Bypass Techniques (2024-2026)

Scope note for the report writer / porter: `skills/api-breaker/scripts/rate_limiter.py` was read in full before this research began. It already implements: IP-spoofing header rotation (`X-Forwarded-For`, `X-Real-IP`, `X-Originating-IP`, `X-Client-IP`, `X-Remote-IP`, `X-Remote-Addr`, `X-Forwarded-Host`, `True-Client-IP`, `CF-Connecting-IP`, `Forwarded`), sequential and `ThreadPoolExecutor`-based concurrent bursts, rate-limit response-header extraction, and GraphQL array/alias batching. It does **not** implement: API-version/legacy-path discovery or differential testing, any true HTTP/2 single-packet or precisely-synchronized race-condition technique, path-casing/trailing-slash/double-slash mutation testing, duplicate-header injection, or CDN-vs-backend/alias-path differential testing. The findings below focus on exactly those gaps.

## Deprecated/legacy API version bypass: discovery and exploitation

### Takeaway
Real incidents and practitioner write-ups consistently describe the same pattern — a deprecated API version/path/protocol stays reachable after a newer version ships and never receives the security backports (rate limiting, CAPTCHA, auth checks) applied to the current version. Discovery is systematic: brute-force common version-path patterns, cross-reference the Wayback Machine/CDX API for historically-crawled paths, fingerprint version-disclosure response headers, and diff live endpoints against documentation/changelogs.

### Cited Findings
- Attackers use automated tools that test version patterns like `/v1/`, `/v2/`, `/api/old/` to find weaker, unpatched entry points — [instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)
- St. Luke's Health System (2023): attackers used a deprecated SOAP API — while the newer REST services had already been patched — to expose roughly 450,000 patient records; the exposure went undetected for six months — [instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)
- An unnamed US retailer's legacy XML-based checkout API remained active after the company migrated to GraphQL, exposing 14 million card records over four months — [instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)
- Optus (2022 breach): nearly 10 million customer records were exposed via an undocumented/leftover endpoint that had no authentication, no rate limits, and no monitoring — [instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)
- Real-world versioning schemes to anticipate when generating candidate paths: Stripe uses URI versioning (`/v1/`); Box used date-based version tokens (e.g. `2024.0`, `2025.0` assigned to all endpoints live at that year's end); GitHub uses header-based versioning via custom media types in the `Accept` header — [instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)
- Industry stat cited (unverified primary source, see Gaps): 84% of organizations reported an API security incident in the past year, but only 13% tested their APIs continuously as of 2024 — [instatunnel.blogspot.com](https://instatunnel.blogspot.com/2025/12/api-versioning-vulnerabilities.html)
- A write-up pattern describes a password-reset OTP endpoint at `/api/v3/changepassword/otp` protected by CAPTCHA and rate limiting, while the same functionality at a `/v1/` endpoint had neither; the researcher reportedly brute-forced the OTP (~10,000 attempts) and reset the victim's password. **Confidence note:** this claim comes from a search-engine synthesis of undercodetesting.com; a direct fetch of that page returned HTTP 403, so the claim is unverified firsthand — [undercodetesting.com](https://undercodetesting.com/bypassing-captcha-and-rate-limits-by-downgrading-api-endpoints/) (fetch blocked, 403)
- General practitioner checklist: burst the same request count against both an old and a current version of the equivalent endpoint; a missing 429 on the old version signals rate limiting was added later and never backported. Related variants named: "patch bypass" (a security fix landed in v2 but not v1) and more permissive old request/response models (the old version accepts extra fields current validation strips, enabling mass assignment) — [ldamoredev.github.io](https://ldamoredev.github.io/cibersecurity-notes/en/cybersecurity/attack-surface-mapping/deprecated-api-versions.html)
- The Internet Archive's Wayback/CDX Server API is the primary programmatic recon tool for this class: it returns the full list of historically-crawled URLs for a domain, which is explicitly used to spot API versions, API docs, and endpoints that were deprecated but never fully decommissioned — [dataimpulse.com](https://dataimpulse.com/blog/wayback-machine-api/)
- Recommended four-step workflow: (1) check availability (single-URL lookup), (2) enumerate captures via the CDX endpoint, (3) retrieve archived content via replay, (4) validate results — [dataimpulse.com](https://dataimpulse.com/blog/wayback-machine-api/)
- Common recon chaining pattern: feed Wayback/CDX output (or tools like `gau`/`waybackurls`) into a live-probing tool such as `httpx` to see which historically-archived URLs still respond on the live target today — [yeswehack.com](https://www.yeswehack.com/learn-bug-bounty/recon-wayback-machine-web-archive)

### Inferences (concrete, implementable test logic)
- **Candidate-path generator:** for every discovered endpoint (e.g. `/api/v2/users/{id}`), programmatically generate siblings by substring-replacing the version token: `v2→v1`, `v2→v0`, `v3` (probe forward too), plus `beta`, `alpha`, `old`, `legacy`, `internal`, `deprecated`, plus date-token variants (`2025.0→2024.0→2023.0`) and alternate placements (`/api/v1/x`, `/v1/api/x`, `/api/x?version=1`, and header-based probes: `Accept: application/vnd.<company>.v1+json`, `X-API-Version: 1`, `Api-Version: 1`).
- **Differential security-control test (the actual exploit-confirmation step):** for each candidate old-version path, replay the *exact* request that is already known to trigger a security control on the current version — e.g. the same 429-triggering burst count, the same malformed/oversized payload that gets a 400/422, the same missing-auth request that gets a 401/403 — with everything else (token, body) held constant. Flag a finding only when the control fires on the current version but not on the candidate (e.g. current version 429s at request #30, candidate old version still returns 200 at request #100+ with equivalent functional data returned).
- **Response-header fingerprinting:** log every response header matching case-insensitive patterns `*version*`, `Sunset`, `Deprecation`, and `Link` with `rel="deprecation"` (the standardized RFC 8594 `Sunset` / HTTP `Deprecation` header / RFC 8288 `Link` deprecation-relation signals) across all discovered endpoints — this both identifies the current version string to decrement from and surfaces servers that self-disclose alternate/older versions.
- **Wayback/CDX enumeration, concretely:** query `http://web.archive.org/cdx/search/cdx?url=<target>/api/*&output=json&collapse=urlkey&fl=original,timestamp` and repeat with a wildcard host (`*.target.com`) to catch legacy subdomains like `api-v1.target.com` or `legacy.target.com`; regex-extract path segments matching `/v\d+/` or date-like tokens; dedupe; then re-probe each extracted path against the **live** host (not the archived snapshot) with a HEAD/GET and keep anything that isn't a generic 404.
- **Changelog/doc cross-reference:** fetch `/swagger.json`, `/openapi.json`, `/v1/swagger.json`, `/.well-known/*`, and any discovered changelog page; diff the version tokens/paths mentioned there against what's actually reachable on the "current" surface — tokens mentioned in docs but absent from the live current-version surface are exactly the deprecated-candidate list to re-test.

### Gaps
- No primary, directly-fetched bug-bounty-platform report was retrievable specifically for the "old API version lacks the security control the current version has" class — the breach examples (Optus, St. Luke's, the retailer) are post-incident write-ups, not bug-bounty disclosures, and the OTP `/v1/` example could not be verified firsthand (source blocked by HTTP 403).
- No specific 2024-2026 CVE number was found for "legacy API version missing rate limiting present in current version" as its own category — this appears to be an application-architecture/business-logic issue that doesn't get CVE numbers assigned the way a shared library flaw would.
- The "84%/13%" statistic's original primary source (likely a vendor State-of-API-Security survey) was not independently located or verified.

## Rate-limit bypass beyond the basics (HTTP/2 multiplexing, race conditions, header bypass, path/method mutation)

### Takeaway
The highest-value 2023-2025 techniques beyond simple IP-header spoofing are: (1) James Kettle's single-packet attack, which uses HTTP/2 multiplexing plus packet-level timing control to collapse concurrent-request jitter from several milliseconds to under 1ms, defeating rate limiters and other logic that check-then-increment a counter non-atomically; and (2) exact-string path/header matching inside rate-limiter middleware, which real, independently-confirmed 2023-2025 CVEs show is broken by trivial case changes, slash mutation, and unconditional trust of client-supplied IP headers.

### Cited Findings

**HTTP/2 multiplexing and the single-packet race-condition technique**
- James Kettle's "Smashing the State Machine" (PortSwigger, 2023) introduced the single-packet attack: using HTTP/2's stream multiplexing to get 20-30 fully-formed requests to arrive within a single TCP packet, cutting request-arrival spread from a ~4ms median / 3ms std-dev (older "last-byte sync" technique) to a ~1ms median / 0.3ms std-dev — [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine)
- Exact mechanism: for bodyless requests, send all HEADERS frames without `END_STREAM`, withholding an empty DATA frame with `END_STREAM` set per stream; for requests with a body, send everything except the final byte. Then: wait ~100ms, disable `TCP_NODELAY` (letting Nagle's algorithm coalesce the final frames into one packet), send a PING to warm/verify the connection, then release all withheld frames back-to-back. Wireshark can confirm the released frames land in a single TCP packet. No custom network stack is required — a standard HTTP/2 library suffices — [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine)
- On one real vulnerability, the single-packet attack succeeded in ~30 seconds where the older last-byte-sync technique took over 2 hours — [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine)
- Reference implementation: Turbo Intruder's `race-single-packet-attack.py` template (Burp Suite extension); Burp Repeater's "Send group in parallel" is a lower-effort manual alternative — [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine)
- GMO Flatt Security (RyotaK, August 2024) extended the technique past its ~20-30-request ceiling using IP-fragmentation and TCP-sequence-number reordering ("first sequence sync"), achieving roughly 10,000 near-simultaneous requests in ~166ms — [flatt.tech](https://flatt.tech/research/posts/beyond-the-limit-expanding-single-packet-race-condition-with-first-sequence-sync)
- Kettle's 2024 follow-up, "Listen to the Whispers" (Black Hat USA 2024 / DEF CON 32, published August 2024), extends the same packet-timing-control ideas to pure timing side-channel attacks (described as SPA v2) — [portswigger.net/research/listen-to-the-whispers](https://portswigger.net/research/listen-to-the-whispers)
- General mechanism description: modern rate limiters frequently count TCP connections (or treat each HTTP/1.1-style request as one event) instead of counting individual HTTP/2 streams; bundling many attempts into concurrently-multiplexed streams on one connection — or into one HTTP request via GraphQL aliases — lets the backend execute every operation while the limiter's counter increments only once. Framed explicitly as a TOCTOU flaw: the limiter checks a counter, processes the request, and only then increments it — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- Concrete curl PoC cited for forcing multiplexed delivery: `curl --http2-prior-knowledge` used to send 100 POSTs to a verify-code endpoint over one multiplexed HTTP/2 connection — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)

**Race-condition bug bounty reports with financial impact**
- **Stripe fee-discount race condition** (primary source: HackerOne's own blog): Stripe Support applied a one-time $20,000 fee-discount offer to the researcher's account. The researcher used Turbo Intruder to fire ~30 parallel "accept offer" requests; the discount was applied successfully on each of the 30 (the accept/redeem check was not atomic), worth $600,000 in fee-free transactions total (researcher estimated Stripe's real cost at ~3% of each discount, i.e. ~$600 per $20,000 redemption). Rated Medium severity; $5,000 bounty paid. Stripe's first fix still had an exploitable race window — the issue was confirmed closed only after a second remediation iteration — [hackerone.com/blog](https://www.hackerone.com/blog/how-business-logic-vulnerability-led-unlimited-discount-redemption)
- **Reverb.com gift-card race condition**, listed in a HackerOne-reports aggregator index as "Race Condition allows to redeem multiple times gift cards which leads to free money," 274 upvotes (bounty field shows $0/unlisted in that index — secondary source, not independently re-verified) — [GitHub: AlittleXYZ/hackerone-reports](https://www.github.com/AlittleXYZ/hackerone-reports/blob/master/tops_by_bug_type/TOPRACECONDITION.md)
- **Dropbox coupon-code double-redemption**, same aggregator index: "Race condition when redeeming coupon codes," 5 upvotes, $216 bounty (secondary source) — [GitHub: AlittleXYZ/hackerone-reports](https://www.github.com/AlittleXYZ/hackerone-reports/blob/master/tops_by_bug_type/TOPRACECONDITION.md)
- **Instacart gift/coupon-code race condition**, referenced as `hackerone.com/reports/157996`, described secondhand as simultaneous redemption of one code multiple times — [kathan19.gitbook.io](https://kathan19.gitbook.io/howtohunt/race-condition/race_conditions) (primary HackerOne report page returned no usable content on direct fetch in this research pass)
- Practitioner-recommended exploitation pattern: fire 10-30 (one cited invite-limit case used 75) identical, concurrent requests at a fresh single-use resource (coupon, invite slot, gift-card balance) and check whether the action succeeded more times than the stated limit allows — [undercodetesting.com](https://undercodetesting.com/race-condition-roulette-how-75-concurrent-requests-can-break-your-invite-limits-a-bug-bounty-deep-dive-video/); [appsecexplained.gitbook.io](https://appsecexplained.gitbook.io/appsecexplained/common-vulns/race-conditions/limit-overrun)
- Kettle's target-prediction methodology (directly reusable for an automated scanner): for each endpoint, ask (1) is the relevant state stored server-side/persistently — client-side state like a JWT usually isn't exploitable; (2) does the action **edit** existing state (collision-prone) or **append/create** (enables limit-overrun specifically); (3) what's the dedup/scope key — two operations only collide if they share one (same session/coupon/user ID) — [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine)
- Detection signal for a successful race (Kettle's methodology): compare a slow sequential benchmark run against the concurrent/single-packet burst and look for (a) more successes than the limit should allow, (b) inconsistent sub-state — e.g. in a cited GitLab invite example, 6 concurrent invite requests produced 1 success + 5 "already taken" responses but **2** emails sent, versus the sequential baseline's exactly 1 success + 1 email — and (c) re-check state after a delay, since some effects surface only after deferred/async processing — [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine)

**Header-based bypass beyond the script's current header list**
- Additional headers/techniques not yet in `rate_limiter.py`'s `BYPASS_HEADERS`: `X-Host`, and the literal misspelling `X-Forwared-Host` (real-world broken-but-still-parsed header names are a documented artifact of this bypass class) — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- A distinct technique from simple header rotation: sending `X-Forwarded-For` **twice** in one request — once empty, once with a value — rather than rotating a single header's value — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- Confirming the whole class is still live against real, named, maintained software in 2025: **CVE-2025-59152** (Litestar, Python ASGI framework) — `RateLimitMiddleware`'s `cache_key_from_request()` trusts a client-supplied `X-Forwarded-For` unconditionally as part of the rate-limit cache key, so rotating the header value gives every request its own bucket. The reporter's test showed exactly this: two unheadered requests got 200, the third got 429, but requests carrying varied `X-Forwarded-For` values all returned 200. Affected: Litestar 2.17.0; fixed: 2.18.0. Recommended fix pattern: default to the raw socket IP, and trust forwarded headers only from an explicitly configured trusted-proxy allowlist — [corgea.com/CVE-2025-59152](https://corgea.com/advisories/vulnerabilities/CVE-2025-59152)
- Varying `User-Agent` and cookies alongside IP headers is recommended so that secondary fingerprinting/tracking (beyond the rate-limit key itself) doesn't correlate the rotated requests back to one client — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)

**Method/path-casing/trailing-slash variations**
- **CVE-2023-38507** (Strapi — `@strapi/admin`, `@strapi/plugin-users-permissions`): the admin-login brute-force rate limiter (`packages/core/admin/server/middlewares/rateLimit.js`) compared the raw request path as a plain string, so `/admin/Login` (case-varied) and `/admin/login/` (trailing slash) were each counted as separate, unlimited endpoints, while `/admin/login` itself hit `429` after 30 failed attempts. Both mutated paths returned `200 OK` with the correct password — full bypass of brute-force protection via trivial path mutation. Fixed in 4.12.1 by normalizing case and stripping trailing slashes before using the path as the rate-limit key — [corgea.com/CVE-2023-38507](https://corgea.com/advisories/vulnerabilities/CVE-2023-38507)
- **CVE-2025-71399** (Better Auth, via its `rou3`/`better-call` router dependency; GitHub advisory GHSA-x732-6j76-qmhm): the router's path normalization strips empty segments, so `/sign-in/email`, `//sign-in/email`, and `///sign-in/email` all route to the identical handler — but if `disabledPaths` or a path-based rate limit matches only the literal configured string, the slash-padded variants reach the handler while evading that check. Only exploitable where nothing upstream (e.g. a non-normalizing proxy) collapses repeated slashes first; the advisory names Vercel/Next.js (default) and Cloudflare (with "normalize URLs to origin" enabled) as examples of environments where it does NOT apply. Affected: better-auth before 1.4.5 (via vulnerable `rou3`, previously pinned at `^0.5.1`); fixed in 1.4.5 — [corgea.com/CVE-2025-71399](https://corgea.com/advisories/vulnerabilities/CVE-2025-71399)
- Adjacent, same root cause, different control: **CVE-2025-3454** (Grafana) — an extra slash in the URL path bypasses authorization checks on the datasource proxy API (authorization bypass rather than rate-limit bypass, but the identical double-slash-normalization mismatch) — noted from search-engine/NVD-listing summary, not independently fetched in full.
- Consolidated bypass-path brute-force list (for mutating a *known-limited* endpoint into unprotected siblings): case permutations, common typos, and version swaps tested together, e.g. against a rate-limited `/api/v3/sign-up`: `/Sing-up`, `/SignUp`, `/singup`, `/api/v1/sign-up`, `/api/sign-up` — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- Parameter-based cache-key confusion: appending a meaningless/junk query parameter (e.g. `/resetpwd?someparam=1`) can make a gateway that keys its rate limit on full path+query treat each request as a distinct endpoint — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- Encoding-based value mutation (same root cause, applied to a rate-limited *value* rather than the path): inserting encoded blank/control characters — `%00`, `%0d%0a`, `%0d`, `%0a`, `%09`, `%0c`, `%20` — e.g. `code=1234%0a` — can make a counter keyed on the literal submitted value treat it as an unbudgeted, fresh attempt — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)

### Inferences (concrete, implementable test logic)
- **HTTP/2 single-packet race testing is the single biggest capability gap in `rate_limiter.py`.** `send_concurrent_requests()` currently dispatches ordinary requests through `http_request()` via a `ThreadPoolExecutor` — almost certainly HTTP/1.1-shaped, with normal connection-pool/OS scheduling jitter (commonly tens of ms over the internet). This will reliably miss narrow (sub-5ms) race windows that the thread-pool-burst style can't synchronize tightly enough to trigger. Concrete fix: add an HTTP/2-capable sender — either `httpx.Client(http2=True)` with all N requests built as coroutine objects dispatched via `asyncio.gather()` (so the underlying socket writes are issued back-to-back without scheduler yield; weaker than true single-packet but far better than a thread pool and fully portable), or a raw `h2`/`hyper-h2`-based sender that explicitly implements Kettle's technique: open one connection, send HEADERS (and all body bytes except the final byte) for every request WITHOUT setting `END_STREAM`, then in one tight loop with zero intervening I/O send the final END_STREAM-bearing frame for every stream consecutively. Optionally disable `TCP_NODELAY` on the raw socket and insert a ~100ms pause before the release loop to encourage the OS to coalesce the final frames into one packet.
- **Response signal confirming a race-condition bypass** (implement as a before/after comparator, mirroring Kettle's benchmark-vs-burst methodology): (1) run the identical request sequentially N times first and record the success count (e.g., exactly 1 success for a single-use coupon, or exactly `limit` successes before an N+1th attempt 429s/409s); (2) fire the same N requests as a tight concurrent/single-packet burst; (3) flag `race_condition_bypass` whenever `successes_in_burst > successes_in_baseline`; (4) use a secondary confirmation signal of side-effect-count mismatch — e.g., count distinct success tokens/emails/credits granted and flag if the burst produced more distinct side effects than the sequential baseline, even if raw status-code counts look similar.
- **Auto-targeting for limited-use/financial-impact endpoints** (the Stripe/Dropbox/Instacart/Reverb class): detect candidate endpoints by scanning discovered paths/params/response bodies for substrings `coupon`, `discount`, `invite`, `redeem`, `gift_card`, `credit`, `balance`, `voucher`, `offer`; for each candidate, identify or provision one single-use resource; fire 10-30 concurrent identical redemption requests at it; count success vs. "already used"/409/400 responses; anything beyond 1 success is a confirmed finding, and impact should be estimated as `(successes - 1) * per-use value` when that value is extractable from the API response (directly mirrors the Stripe report's own impact math).
- **Header-bypass extensions to `BYPASS_HEADERS`:** add `X-Host` and the literal misspelling `X-Forwared-Host` as additional entries. Add a distinct test mode that sends `X-Forwarded-For` twice as separate header lines (empty, then a value) in the same request — note this requires a transport that preserves duplicate header lines (Python's `urllib.request`/`http.client` collapse a dict key to one header by default, so this needs either raw-socket request-line construction or a `requests` call built through a custom transport adapter that accepts a list of `(name, value)` tuples). Response signal: identical to the script's existing `test_rate_limit_bypass()` pattern — a 429 observed at some point, then further 200s once the duplicate/typo header variant is introduced.
- **Path/method/casing mutation test — cheap, high-value, currently entirely missing.** For every URL where the existing scanner already recorded a non-null `rate_limited_at`, generate and re-burst against this mutation set: (1) trailing slash toggled (`/admin/login` ↔ `/admin/login/`); (2) doubled/tripled leading or internal slash (`//admin/login`, `/admin//login`); (3) per-segment case mutation (full-lowercase, full-uppercase, title-case); (4) HTTP method swap where functionally plausible (if POST is limited, try PUT/PATCH, and test the `X-HTTP-Method-Override` header trick); (5) one junk/random query parameter appended per request. Exact response signal: the *original* exact path still returns 429 (re-confirm the baseline first) while a mutated variant returns 200 **and** the response body shape matches the pre-limit success responses (checking status code alone risks false positives from soft-404/error pages that happen to return 200). This whole mutation set is only 6-10 extra requests per already-confirmed-limited endpoint, cheap enough to run unconditionally inside the existing `main()` loop wherever `rate_limited_at` is set.

### Gaps
- The Dropbox/Reverb/Instacart bounty figures rest on a secondary GitHub aggregator index and a gitbook page, not a directly-fetched HackerOne primary report page (`hackerone.com/reports/157996` returned no usable content via automated fetch in this pass, likely requiring JS rendering or authentication) — treat those three bounty amounts/upvote counts as plausible but unverified.
- No CVE was found specifically scoped to "HTTP/2 multiplexing used to defeat a production rate limiter" — the HTTP/2 CVEs found (Rapid Reset / CVE-2023-44487, and 2025's "MadeYouReset") are stream-reset-based denial-of-service issues, not rate-limit-bypass issues; the multiplexing-defeats-rate-limiting technique currently lives in research/practitioner write-ups (PortSwigger, HackTricks-derived pages) rather than as a numbered CVE against a specific product.
- The GMO Flatt Security/RyotaK "first sequence sync" extension was only confirmed at the headline level (10,000 requests in ~166ms); the full technical write-up at flatt.tech was found via search but not fetched in this pass — worth a follow-up fetch if deeper low-level porting (raw IP fragmentation) is ever attempted.

## API gateway / reverse-proxy rate-limit inconsistencies

### Takeaway
This is the thinnest-documented of the research areas. The clearest, most concrete, and most reusable documented case is GraphQL query/alias batching (already partially covered by the target script), where an edge/network-layer rate limiter that only counts HTTP requests is architecturally blind to multiple bundled operations. Equivalent documentation for plain REST bulk/batch endpoints and CDN-vs-backend path-alias bypass is sparse and mostly informal — real, named, platform-disclosed incidents for the non-GraphQL variant were not found in this pass.

### Cited Findings
- Root-cause statement: a network firewall/WAF/CDN sitting in front of an application only sees one HTTP request when a client sends a GraphQL batch or heavily-aliased query, so "traditional HTTP rate limiters are completely blind to the attack" even though the backend executes every bundled operation — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- This is an actively-researched, named technique class as of 2024-2026: Checkmarx published dedicated research titled "Didn't Notice Your Rate Limiting: GraphQL Batching Attack" (full content not fetched in this pass) — [checkmarx.com](https://checkmarx.com/?p=80723) — and PentesterLab's glossary carries "GraphQL batching attack" as its own defined entry — [pentesterlab.com/glossary/graphql-batching-attack](https://pentesterlab.com/glossary/graphql-batching-attack)
- A real, bug-bounty-program-disclosed case (company/program name not given in the summary found): a researcher combined GraphQL alias-based batching with resolver enumeration to defeat both per-query rate limits and authorization checks in one chain; reported through an official bug bounty program and resolved — [case-study write-up](https://portofolio-dwforsec.pages.dev/case-study/graphql-authorization-bypass-chain) (secondary source, program identity not independently corroborated)
- Defensive framing useful for severity-scoring any finding in this class: edge/gateway rate limiting should be treated as defense-in-depth only — limits must also be enforced inside the GraphQL execution layer, per-operation/per-resolver, not solely per-HTTP-request at the edge — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- "Batch or bulk REST endpoints" is listed as its own named bypass category (e.g. a `/v2/batch` endpoint or an array-of-operations body bypassing per-endpoint limits that only guard the singular legacy endpoint), but the source cites no independent real-world incident for this REST-specific variant beyond the GraphQL case — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)
- HTTP/2-specific path-confusion compounding variant: if an edge limiter is configured only for the literal path `/verify` but the backend also serves identical logic at `/api/v2/verify`, combining the unprotected alternate path with HTTP/2 multiplexing stacks both bypass classes — [HackTricks mirror](https://desecurity.github.io/hacktricks/pentesting-web/rate-limit-bypass.html)

### Inferences (concrete, implementable test logic)
- **Direct extension of the script's existing `test_graphql_batching()`:** it currently proves batching is *accepted* but never correlates that against whether the same backend operation is rate-limited in its single-request form. Concrete addition: before sending the 100x-batched/aliased query, first establish a baseline by repeatedly sending the *unbatched* single operation (reuse `send_rapid_requests`) until a 429 is observed (or confirmed absent) — note the count `K` at which it 429s. Then send the batched form containing `K + 50` copies of the identical operation in one HTTP request. If it returns 200 with all `K + 50` executed, that differential is the gateway-blindness bypass; log `severity: high` specifically when the targeted operation is sensitive (login, OTP/code verification, password reset), since that's the case with a directly exploitable outcome (effectively unlimited-rate credential/OTP brute force).
- **Generic alias/bulk-equivalent prober:** for every URL the scanner has already confirmed is rate-limited, try a small, configurable seed list of likely bulk/alias equivalents — `{path}/batch`, `{path}/bulk`, a pluralized/bulk form of the final path segment if a naming convention is detectable (e.g. `/user/{id}` → `/users/batch`), and the GraphQL endpoint on the same host if one exists — requesting the same logical operation repeatedly in one call. Flag a finding whenever the alias accepts a volume of operations in one request that the original singular path would have rate-limited individually. This needs a seed list rather than exhaustive generation, since "the bulk equivalent's name" is API-specific.
- **CDN-vs-origin differential test:** when upstream recon has already identified both an edge/CDN hostname and a direct-to-origin address for the same application (e.g. from `recon-dominator`-style output), replay the identical rate-limit burst test (`send_rapid_requests`) against both the edge-fronted URL and the direct-origin URL for the same path and method. A bypass is confirmed when the edge-fronted URL 429s but the direct-origin URL does not. This specific test needs the origin address as an input — it cannot be derived from path mutation alone — so it should be wired up as an optional `--origin-base` alternate target rather than attempted automatically.

The GraphQL batching variant of this class is well-documented as a technique category; a citable primary incident for the REST-only variant was not found in this pass.
- No vendor-specific (Cloudflare/Akamai/Fastly/AWS WAF) documented case of their rate-limiting rules being defeated by a backend-reachable alias path was found. ## Named CVEs and real 2024-2026 bug-bounty-disclosed reports (consolidated)

### Takeaway
Confirmed, independently-fetched CVEs exist for rate-limiter path-matching flaws (case/slash normalization) and IP-spoofing-header trust flaws in real, actively-maintained open-source frameworks spanning 2023-2025. Genuine bug-bounty-program financial-impact disclosures for race-condition-driven rate-limit/business-logic bypass are real and primary-sourced for Stripe; the Dropbox/Instacart/Reverb examples are widely referenced but rest on secondary aggregators in this research pass.

### Cited Findings
- **CVE-2023-38507** — Strapi (`@strapi/admin`, `@strapi/plugin-users-permissions`): admin-login rate limiter bypassed via path case variation (`/admin/Login`) and trailing slash (`/admin/login/`); fixed in 4.12.1 — [corgea.com](https://corgea.com/advisories/vulnerabilities/CVE-2023-38507)
- **CVE-2025-71399** — Better Auth (via `rou3`/`better-call`): path normalization strips empty segments, so slash-padded paths (`//sign-in/email`) bypass `disabledPaths` and path-based rate limits; fixed in 1.4.5; GitHub advisory GHSA-x732-6j76-qmhm — [corgea.com](https://corgea.com/advisories/vulnerabilities/CVE-2025-71399)
- **CVE-2025-59152** — Litestar: `RateLimitMiddleware` trusts client-supplied `X-Forwarded-For` unconditionally as the rate-limit cache key, letting header rotation create unlimited buckets; affected 2.17.0, fixed 2.18.0 — [corgea.com](https://corgea.com/advisories/vulnerabilities/CVE-2025-59152)
- **CVE-2025-3454** — Grafana: an extra slash in the URL path bypasses authorization checks on the datasource proxy API; same double-slash-normalization root cause as CVE-2025-71399, though this one is an authz bypass rather than a rate-limit bypass — noted from a search-engine/NVD-listing summary, not independently fetched in full in this pass.
- **CVE-2023-44487 ("HTTP/2 Rapid Reset")** and its 2025 successor, publicly dubbed **"MadeYouReset"**: both are HTTP/2 stream-reset-based denial-of-service issues (resource exhaustion from mismatched server/spec stream-reset accounting), not rate-limit-bypass vulnerabilities — included here as background relevant to anyone building HTTP/2-multiplexing test tooling, since a target hardened against Rapid Reset-style DoS may still be fully exposed to ordinary (non-reset-abusing) multiplexed-request-volume rate-limit bypass — [thehackernews.com](https://thehackernews.com/2025/08/new-http2-madeyoureset-vulnerability.html)
- **Stripe fee-discount race condition** (primary source, HackerOne's own blog): race condition in an offer-acceptance flow; $20,000 per-redemption value; ~30 parallel Turbo-Intruder-driven requests all succeeded; $600,000 total exposure; $5,000 bounty paid; Medium severity; required two remediation iterations before being confirmed fixed — [hackerone.com/blog](https://www.hackerone.com/blog/how-business-logic-vulnerability-led-unlimited-discount-redemption)
- **Dropbox coupon-code race condition** — "Race condition when redeeming coupon codes," 5 upvotes, $216 bounty — secondary aggregator source, not independently re-verified against hackerone.com directly — [GitHub: AlittleXYZ/hackerone-reports](https://www.github.com/AlittleXYZ/hackerone-reports/blob/master/tops_by_bug_type/TOPRACECONDITION.md)
- **Reverb.com gift-card race condition** — "redeem multiple times gift cards which leads to free money," 274 upvotes — same secondary aggregator — [GitHub: AlittleXYZ/hackerone-reports](https://www.github.com/AlittleXYZ/hackerone-reports/blob/master/tops_by_bug_type/TOPRACECONDITION.md)
- **Instacart gift/coupon-code race condition**, referenced as `hackerone.com/reports/157996` — [kathan19.gitbook.io](https://kathan19.gitbook.io/howtohunt/race-condition/race_conditions) — primary report page returned no usable content on direct automated fetch in this pass.

### Inferences
- Every confirmed-primary CVE in this list (Strapi, Better Auth, Litestar) shares one architectural mistake: the rate-limiter/access-control layer derives its decision key from either (a) a raw, un-normalized request path, or (b) an unauthenticated, attacker-controlled header — never from a canonicalized path plus a server-verified identity signal (session, authenticated user ID, or a trusted-proxy-validated real IP). This supports building the skill's test logic as a generic three-part regression check runnable against *any* target without needing a target-specific CVE match: (1) path-normalization-bypass test (case + slash mutations), (2) header-trust test (rotate every candidate IP header plus the duplicate-header variant), (3) confirm the *same underlying action* actually occurred, not just a non-429 status code.
- Two of the three primary CVEs (Better Auth, Litestar) are from 2025 and hit actively-maintained frameworks, suggesting this bug class is still being freshly (re)introduced into new libraries rather than being a solved, legacy-only problem — this supports giving the path-normalization and header-trust test classes high priority/default-on status in the skill rather than treating them as rare edge cases.

### Gaps
- Three of the race-condition bug-bounty figures (Dropbox, Reverb, Instacart) rest on a single secondary GitHub aggregator index plus a gitbook page rather than a directly-fetched HackerOne primary report page; HackerOne report pages did not return usable content via WebFetch in this pass (likely JS-rendering or auth-gated), so treat those three bounty amounts/upvote counts as plausible but unverified pending manual confirmation on hackerone.com.
- No CVE was found specifically scoped to "GraphQL/REST batching bypasses an edge rate limiter" (the Key Question 3 core claim) — it currently exists only as research/vendor-blog documentation (Checkmarx, PentesterLab, HackTricks), not as a numbered CVE, consistent with it being an architecture/design-pattern issue rather than a single-library bug.
- This research pass did not have remaining budget to run CVE-database queries filtered specifically to 2026 (vs. 2024-2025) for either the API-versioning or rate-limit-bypass classes. The most recent primary-sourced item found was from August 2025 (MadeYouReset); the Better Auth CVE (2025-71399) had no publication month confirmed in the fetched advisory content. A follow-up targeted search for "CVE 2026 rate limit" / "CVE 2026 API version" could surface newer items this pass's queries did not catch.
