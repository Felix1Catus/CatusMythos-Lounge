# Version-String-to-CVE Matching: False Positive/Negative Failure Modes and Mitigations

Context note (not a web source, included because it grounds every mitigation below in the actual target code): the tool in question, `skills/recon-dominator/scripts/cve_lookup.py`, already implements several non-naive refinements worth knowing before reading the findings — exact (not substring) CPE product-name equality instead of `needle in haystack` (to avoid "elementor" matching both "Elementor Pro" and "Essential Addons for Elementor"), an exact-version-equality path for CPE entries with no range fields (e.g. the vsftpd 2.3.4 backdoor), a `"for "`-precedes-product-name text filter to catch third-party addon CVEs, and a prose-parsed fallback range when NVD has no structured CPE data yet. It has **no** backport-awareness, no fork/rebrand detection, and makes no calls beyond the raw NVD CVE 2.0 API — which is exactly the gap this research addresses.

## Vendor/community forks that preserve the original project's version string

### Takeaway
Real documented cases show forks/rebrands breaking both directions of matching: WordPress vulnerability-intelligence vendors (Wordfence, Patchstack, WPScan) have repeatedly published CVE/advisory records that misattribute a fix to the wrong plugin, to a version number that was never released, or simply copy another vendor's bad data — and these three vendors are not independent checks on each other. NVD's own CPE data is routinely too sparse or too coarse to disambiguate same-named-but-different products. No tooling was found that solves this beyond manual verification and strict exact-match (not substring) product-name comparison.

### Cited Findings
- A WordPress.org plugin developer confirmed, in a support thread, that their plugin was undiscoverable in Wordfence's vulnerability database because it "is indeed an early fork of the plugin available on the WP repository" and had "become substantially different" — a scanner keying off the original slug/product name would either miss the fork entirely or wrongly inherit the parent's CVEs — [WordPress.org support thread](https://remarpro.com/support/topic/vulnerability-reported-for-a-plugin-but-link-is-404-and-the-plugin-is-not-in-db)
- Plugin Vulnerabilities documented a case where Wordfence linked a vulnerability fix to a plugin version ("3.4.1") that had never been released on WordPress.org at all; per the plugin's own developer, "Wordfence had somehow mixed up the plugin with a completely unrelated plugin" — [pluginvulnerabilities.com, 6 Jan 2023](https://www.pluginvulnerabilities.com/?p=19282)
- The same site's 22 Jan 2024 post states that Wordfence (itself a CVE-issuing CNA) "list[s] the wrong versions as vulnerable in those CVE records" for some WordPress plugin CVEs — meaning the error can be embedded directly in the authoritative CVE record, not just a third-party tracker. It also reports that WPScan's database entries are "often just copying their data from yet another source," and that Patchstack's data is "largely the same inaccurate data as Wordfence's," including one case where Patchstack claimed a fix "was addressed in version 4.4.7" when "there had yet to even be an attempt to fix" the bug — [pluginvulnerabilities.com, 22 Jan 2024](https://www.pluginvulnerabilities.com/2024/01/22/many-cve-records-are-listing-the-wrong-versions-of-software-as-being-affected/)
- Automattic forked WP Engine's "Advanced Custom Fields" (ACF) plugin into "Secure Custom Fields" (SCF) and substituted it in place of ACF in the official WordPress.org repository (drawing copyright objections); sites with auto-update enabled were migrated from ACF to the fork, which then received its own separate update stream — a documented real case of a fork being swapped in at the distribution-channel level under circumstances a version-string-only scanner cannot see — [WP Tavern](https://wptavern.com/acf-plugin-forked-to-secure-custom-fields-plugin)
- Red Hat's dependency-tooling ecosystem treats fuzzy/best-available CPE matching as unavoidable: a Dependency-Check maintainer states fuzzy matching and "taking the best available match is the best we can do for now," while acknowledging it "has a chance of surfacing false positives" — the identical substring/fuzzy-match failure mode that causes fork misattribution, stated generally — [Dependency-Check issue #6658](https://www.github.com/jeremylong/DependencyCheck/issues/6658)
- Local code evidence (not a web source, cited for grounding only): `cve_lookup.py`'s own inline comments document a previously-live instance of this exact bug class — an NVD keyword search for "elementor pro" returned CVE-2026-28192 ("Unauthenticated Arbitrary File Upload in Piotnet Addons For Elementor Pro") as a false-positive match against the core Elementor Pro product, because that CVE carried no structured CPE data to contradict the keyword match (`skills/recon-dominator/scripts/cve_lookup.py`, lines 128-176 and 256-268).

### Inferences
- The fork/mislabeling problem is not NVD's alone — it is independently replicated by every major WordPress-specific vulnerability feed, so switching data providers does not escape it; cross-referencing multiple feeds only helps when they disagree, and per Plugin Vulnerabilities' claims they frequently don't disagree because they copy each other's data.
- **Implementable mitigation (stdlib-only):** cve_lookup.py's existing exact-CPE-equality check and `"for "`-precedes-product-name filter are already the single highest-value fixes for this class of bug — extend the latter into a small denylist of fork/addon naming conventions (also reject matches where the normalized description contains the product name preceded by "addon(s) for", "extension for", "plugin for the", or followed by "fork", "clone", "alternative to"). Separately, when `cpe_matched_this_product` is `None` (no structured CPE data at all — the exact gap the Elementor Pro/Piotnet bug exploited) and a hypothesis survives only on the keyword/text gate, tag its `range_source` as a distinct value (e.g. `"keyword-only-unverified"`) rather than folding it into `"description-text-heuristic"`, so the summary output visibly distinguishes "NVD structurally confirmed this" from "nothing structured contradicts this, but nothing confirms it either."

### Gaps
- No source documents a concrete case of a fork that *is* vulnerable but escapes detection because its product name diverges from the CVE's affected-product name (the false-negative direction). Only the false-positive-via-misattribution direction has documented real incidents; the false-negative direction is logically implied by the same name-matching mechanism but unconfirmed by a named incident.
- No tooling or research was found for automatically detecting that product B is "a fork of" product A (via code similarity, shared history, or package metadata) for vulnerability-correlation purposes — this appears to be an open, manually-handled problem industry-wide.

## Backport patches that don't bump the version string

### Takeaway
This is the best-documented failure mode of the five. Red Hat, Debian, Ubuntu, and commercial scanners (Nessus, OpenVAS/GVM) all publish primary-source material confirming backporting is deliberate vendor policy, a named cause of scanner false positives, and that each vendor maintains supplementary signals specifically to compensate: RPM release numbers plus OVAL feeds (Red Hat), changelog/DSA cross-checks (Debian), and distro-suffix-aware banner parsing (Nessus/Tenable).

### Cited Findings
- Red Hat: "Red Hat usually does not rebase packages to entirely new versions. Instead, it backports fixes and new features to an older version of the package it distributes. This can sometimes confuse third-party security tools, as they see what they believe is a vulnerable version of a package without understanding that Red Hat has already backported corrections." Worked example: CVE-2022-24070 affects Subversion; Red Hat "patched Subversion 1.14 and backported the fix to version 1.10" under RHSA-2022:2234, so `subversion-libs-1.10.2` is patched even though third-party trackers cited in the article list "1.10.0 through 1.14.1" as vulnerable "in their entirety." Red Hat's fix: it "increments product release numbers when backporting fixes to identify the newer, patched RPMs" — i.e. the RPM *release* field (the `-N` suffix after the version, e.g. `1.10.2-3.el8`), not the version field, is the real patch signal — [Red Hat: What your security scanner isn't telling you](https://www.redhat.com/en/blog/assessing-red-hat-ansible-automation-platform-vulnerabilities)
- Red Hat states the general principle directly: "just because the newest version of a package in a given channel is affected by a CVE does not mean that older versions of that package are necessarily affected," and that determining vulnerability status "is difficult or perhaps impossible given merely RPM version information." Its recommended remedy is consuming its OVAL definitions or using a scanner certified under the Red Hat Vulnerability Scanner Certification program — [same source]
- Debian's official Security FAQ: "Instead of upgrading to a new release we backport security fixes to the version that was shipped in the stable release," done deliberately to keep changes minimal. It gives two explicit user-facing verification methods: "comparing its exact version number with the version indicated in the Debian Security Advisory," and running `apt-get changelog package-name` to check for the changelog entry announcing the fix — [Debian Security FAQ](https://www.debian.org/security/faq.html)
- Ubuntu example: an HTTP banner reading `Server: Apache/2.4.41 (Ubuntu)` can be fully patched for CVE-2024-39573 — the version string never changes, but Ubuntu's package changelog carries a dedicated entry referencing the CVE ID — [AppCheck NG: Understanding Backporting in Infrastructure Vulnerability Scanning](https://appcheck-ng.com/understanding-backporting-in-infrastructure-vulnerability-scanning/)
- Current, concrete OpenSSH/regreSSHion (CVE-2024-6387) case: a banner reading `OpenSSH_9.2p1 Debian-2+deb12u3` was wrongly flagged for regreSSHion by at least one checker tool despite carrying the fix, because the fix lived in the Debian package revision suffix (`-2+deb12u3`) without the upstream-visible `9.2p1` token changing. The documented fix was to parse and compare the **distro revision suffix** separately from the upstream version token — [happyDomain checker-ssh commit](https://git.nemunai.re/happyDomain/checker-ssh/commit/fb2ae7d9037ae4934714ec952c330935e40a1ffa)
- Tenable/Nessus runs dedicated "Backported Security Patch Detection" informational plugins (e.g. plugin 39519 for FTP, 39520 for SSH) and a shared `backport.inc` code path. Tenable states it previously relied on "a list of known backported banners" with an acknowledged detection lag ("If a delta existed between the release of a backported fix & an update made by Tenable Research, a false positive result may have occurred"), and later updated `backport.inc` itself, which "greatly reduced" false positives — [Tenable Nessus plugin 39519](https://www.tenable.com/plugins/nessus/39519); [Tenable Research Release Highlights forum](https://connect.tenable.com/discussions/tenable-research-release-highlights/modernization-of-openssh-plugin-coverage-background-in-an-/108829)
- Greenbone/OpenVAS staff confirm authenticated scanning with "auto false positive" enabled is the mechanism that suppresses backport-caused findings; unauthenticated banner-based QoD (Quality of Detection) filtering is the fallback that reduces — not eliminates — this noise. A 2009 writeup on OpenVAS already flagged backport-caused false positives as a known class requiring manual verification — [Greenbone forum](https://forum.greenbone.net/t/backported-patches-false-positives/3101); [Linux Pro Magazine, OpenVAS](https://www.linuxpromagazine.com/Issues/2009/109/OpenVAS/(offset)/6)
- AppCheck's four generalized vendor strategies for backport-aware scanning: (1) OS/distro fingerprinting plus a maintained distro patch-history database; (2) vendor-specific backport-awareness data suppressing alerts for fixes known backported on specific platforms; (3) credentialed/authenticated scanning reading actual installed-package metadata instead of trusting network banners; (4) manually curated suppression rules for CVEs a security team has independently verified as patched — [AppCheck NG](https://appcheck-ng.com/understanding-backporting-in-infrastructure-vulnerability-scanning/)
- Horizon3.ai argues the only fully reliable verification is to "re-attempt the exploit" after a patch is applied rather than trust any version-string/changelog signal, and documents a case (Cisco) where some devices in a fleet remained exploitable post-patch while others didn't — showing patch metadata can also produce false negatives (claims "patched" when it isn't), the mirror-image risk — [Horizon3.ai](https://horizon3.ai/intelligence/blogs/the-industry-standard-model-is-the-vulnerability/)

### Inferences
- Every vendor's real mitigation requires data cve_lookup.py structurally cannot obtain (stdlib-only, unauthenticated, NVD-API-only, no shell/package-manager access to the target): Red Hat's RPM release-number/OVAL feed, Debian's changelog, or credentialed package access. For OS-package-level findings specifically, the tool's honest ceiling is "flag as needs-live-verification," not "resolve."
- The regreSSHion/Debian-suffix case generalizes cleanly: **parse and strip the distro revision/package-release suffix from the version string, and treat its mere presence as a strong "vendor may have already backported a fix here" signal, distinct from the semantic version comparison.**
- **Implementable mitigation for cve_lookup.py (stdlib-only, zero new dependencies):**
  1. Add a regex-based "backport suffix" detector (sibling to `_parse_version()`): match known distro-package patterns — Debian/Ubuntu (`\d\.\d+(\.\d+)?(p\d+)?[+-](debian|ubuntu|deb\d+u\d+)`), RPM (`-\d+\.(el|fc)\d+`), or a bare trailing `-\d+` build/release counter after the dotted version — and set a new `"possible_distro_backport": true` flag on the hypothesis.
  2. When that flag is true *and* `version_appears_affected` is also true, downgrade the displayed confidence explicitly in `main()`'s summary print, e.g. `"AFFECTED? (distro build — vendor may have backported a fix; verify via distro changelog/advisory before trusting this)"` instead of a plain `"AFFECTED?"`. This operationalizes Debian's and Red Hat's own stated remediation (check changelog/advisory) by signaling *when* that check is necessary — something the tool currently never does.
  3. This is a confidence annotation only, not a resolution — stdlib Python with no shell access cannot itself run `apt-get changelog` or query RHEL's OVAL feed, so full resolution should be explicitly out of scope and labeled as a follow-up step for a human operator or an authenticated-scan stage.

### Gaps
- No source gave Tenable's `backport.inc` literal internal parsing logic (only its existence, purpose, and changelog-level description of fixes made to it).
- No source confirmed whether OpenVAS/GVM's backport false-positive suppression works unauthenticated at all, versus being strictly an authenticated-scan-only feature; forum evidence suggests the latter but doesn't state it explicitly.

## A known general heuristic beyond "trust the version string"

### Takeaway
The strongest documented alternative to bare version-range comparison is (a) checking whether the vulnerable code path is actually reachable/used (JFrog's container research) and (b) using ecosystem-specific structured advisory data (GHSA/OSV) instead of generic CPE strings (Anchore/Grype's production results). A close parallel for CMS plugins is a vendor-published "patch level" field tracked separately from the main version string, which Patchstack's API demonstrates concretely. A literal "fetch a file/endpoint and check for patched behavior" approach was not found documented as a named general industry technique, but it is a direct generalization of what Go's vulnerability database and JFrog's contextual analysis already do at the function level.

### Cited Findings
- JFrog's container research (methodology: "Xray Container Contextual Analysis" checking whether image code/configuration actually reaches the vulnerable function, run against the top 10 most-frequently-reported CVEs across the 200 most-popular "latest"-tag Docker Hub images) found **78% of those CVE findings were "non-applicable"** under contextual analysis — the naive "vulnerable version string present" check was wrong roughly four times out of five in this sample. JFrog credits the Go Vulnerability Database specifically for listing the actual vulnerable *functions* (not just package versions) in its advisories, which is what makes function-level contextual analysis possible — [InfoWorld / JFrog research](https://www.infoworld.com/article/3677550/most-reported-cves-for-docker-hub-images-are-harmless.html)
- Anchore/Grype's production experience: moving supported ecosystems (Python/PyPI, Ruby/RubyGems, others) from NVD CPE-string matching to GitHub Security Advisory (GHSA) data cut false-positive matches by "2,000+" in their test set (only 11 new false negatives), with "up to an 80% reduction" of false positives for some ecosystems; Anchore Enterprise (v5.26.0+) now disables CPE matching by default for every GHSA-covered ecosystem — [Anchore: Say goodbye to false positives](https://anchore.com/blog/say-goodbye-to-false-positives/); [Anchore docs: Supported package ecosystems](https://oss.anchore.com/docs/guides/vulnerability/ecosystems/)
- Patchstack's Threat Intelligence API models exactly the "vendor-specific patch-level field separate from the main version string" pattern: each record carries an `affected_in` range, a `fixed_in` version, and (for multi-branch products) a `patched_in_ranges` list where each range has its own `from_version`/`to_version`/`fixed_in` triple (e.g. affected "<= 3.6.10", fixed_in "3.6.11"), letting one record express "patched differently across several active release branches" — something a single NVD CPE version-range string cannot express. Patchstack explicitly leaves `fixed_in` blank/"No official patch available" when unpatched rather than guessing — [Patchstack API properties](https://docs.patchstack.com/api-solutions/threat-intelligence-api/api-properties/)
- CPE itself is widely reported as the weak link: a VulCPE arXiv paper states false positives in vulnerability management "predominantly stem from limitations in CPE data used during correlation," while separately noting 93.55% of NVD CVE entries do contain at least one valid CPE string — the data exists almost everywhere, but matching *precision* is the problem, not data absence — [VulCPE, arXiv:2505.13895](https://arxiv.org/html/2505.13895v1)
- NIST explored, then stalled on, a more rigorous identifier standard: NISTIR 8085 proposed deriving CPE names from SWID (Software Identification) tag attributes specifically to improve automated "patch detection" and vulnerability-assessment matching, but NIST's page for it states the draft has been discontinued. Industry commentary separately notes SWID adoption has declined in favor of PURL (package URL) rather than CPE — [NISTIR 8085 (discontinued draft)](https://csrc.nist.gov/publications/detail/nistir/8085/draft); [Endor Labs: What's in a name](https://www.endorlabs.com/learn/whats-in-a-name-a-look-at-the-software-identification-ecosystem)
- Horizon3.ai's documented operational heuristic for pentesters is to treat re-exploitation as ground truth: "the best way to know if a vulnerability was successfully patched is to re-attempt the exploit after patching" — functionally the live-exploit analog of "fetch and check for patched behavior" — [Horizon3.ai](https://horizon3.ai/intelligence/blogs/the-industry-standard-model-is-the-vulnerability/)

### Inferences
- No source used the literal phrase "fetch a file/endpoint and check for patched code as a version-string alternative," but it is a natural extension of two things already proven in production: (a) function-reachability analysis (Go vuln DB/JFrog, code-level) and (b) backport-suffix/changelog checking (metadata-level). The live-HTTP-fetch variant is a natural fit for recon-dominator specifically, since — unlike generic SCA tools — it already has network access to the actual target.
- **Implementable mitigation 1 — "patch-signature" override file (stdlib-only):** add an optional, hand-maintained JSON sidecar (e.g. `patch_signatures.json`) keyed by `cve_id`, each entry specifying a relative URL path to fetch on the target (e.g. a WordPress plugin's own `readme.txt`, or a static JS/CSS asset), plus a string/regex expected only in the patched version and one expected only in the vulnerable version. When an entry exists for a matched CVE, fetch it with the script's existing `_http_get_json`-style `urllib.request` helper and let the result **override** the version-range verdict (since it inspects the real artifact, not a claimed version number). Coverage is only as good as the hand-curated file, so absence of an entry must fall back to the existing version-range logic, clearly labeled lower-confidence.
- **Implementable mitigation 2 — prefer ecosystem advisories over CPE where available (stdlib-only):** for components whose `kind` indicates a language-ecosystem package (not a WordPress plugin/theme), add a plain stdlib HTTPS call to OSV.dev's free, keyless JSON API and prefer its `affected[].ranges`/`affected[].versions` data over NVD's CPE match for that component — a direct, source-grounded generalization of Anchore's documented GHSA-over-CPE substitution (the single highest-leverage fix found in this research), requiring only one additional stdlib HTTP call and no new dependency.

### Gaps
- No source quantified how often a content-based "patch-signature" check (fetch a file/endpoint, check for a specific string/behavior) is used as a named general technique outside code-level SCA tools — it appears to be more of an ad hoc pentester technique than a documented methodology with its own literature.
- No official NVD document was found that is NVD's own published statement of its CPE matching limitations, despite specific searching; all characterization of CPE's weaknesses comes from third parties (Anchore, the VulCPE paper, Dependency-Check maintainers) analyzing NVD's output, not from NVD itself.

## WordPress.org plugin/theme API — signals beyond the raw version number

### Takeaway
The official `api.wordpress.org` plugin-info endpoint does expose a `last_updated` timestamp and a parsed `changelog` section, but both have a documented history of being unreliable (stale/incorrect dates, changelog-section mis-parsing bugs, caching lag), and no source confirms that any tool actually cross-references `last_updated` against a CVE's disclosure date as a patched-vs-vulnerable heuristic — that specific idea is directionally reasonable but currently an untested/undocumented heuristic, not an established practice. Patchstack (a third party, not WordPress.org) provides a more directly useful signal — an explicit `fixed_in` field — but its data quality is independently criticized by the same sources covering the fork/misattribution problem above.

### Cited Findings
- Official plugin metadata lives at `api.wordpress.org/plugins/info/1.0/<slug>.json` (community-maintained OpenAPI specs also document `/plugins/info/1.2/`); a WordPress Core Trac ticket confirms this exact path as the source of `last_updated` data — [Make WordPress Core Trac #22416](https://core.trac.wordpress.org/ticket/22416)
- The `last_updated` field has a documented history of being wrong: a 2013 bug report shows it returning a nonsensical `1969-12-31` date for at least one plugin; a parallel 2013 proposal asked WordPress.org to add a *separate*, more precise last-updated-time field specifically so the existing (buggier) field wouldn't need to change and risk breaking compatibility — [wp-meta mailing list, Oct 2017 thread referencing the ticket](https://lists.wordpress.org/pipermail/wp-meta/2017-October/023525.html); [wp-meta mailing list bug report, Sep 2013](https://lists.wordpress.org/pipermail/wp-meta/2013-September/000591.html)
- The API's changelog parsing has its own bug history: a Trac ticket notes that if a developer titles their section "Change Log" instead of "Changelog," the API silently substitutes the plugin's short description into the changelog field instead (marked fixed) — [Core Trac #11217](https://core.trac.wordpress.org/ticket/11217)
- A WordPress.org support thread confirms API responses can lag the actual released version by "a few days" due to caching — meaning even the core `version` field cannot be assumed to reflect what's live on a plugin's SVN/download at query time — [WordPress.org support thread](https://wordpress.org/support/topic/api-wordpress-org-plugins-info-1-0-slug-json-returns-incorrect-version/)
- Patchstack's API is the clearest real-world example, for this ecosystem, of a patch-level field tracked separately from the version string: records carry `affected_in`, `fixed_in`, and multi-branch `patched_in_ranges`, explicitly leaving `fixed_in` blank/"No official patch available" when unpatched rather than guessing — [Patchstack API properties](https://docs.patchstack.com/api-solutions/threat-intelligence-api/api-properties/)
- The same independent critique covering Key Question 1 applies directly here: Plugin Vulnerabilities alleges Patchstack and Wordfence both publish incorrect `fixed_in`/affected-version data at times (including a claimed fix in a version where "there had yet to even be an attempt to fix" the bug), and that WPScan's database "often" copies another source's data — this supplementary signal is not fully independent of the error modes already documented — [pluginvulnerabilities.com](https://www.pluginvulnerabilities.com/2024/01/22/many-cve-records-are-listing-the-wrong-versions-of-software-as-being-affected/)
- Plugin Vulnerabilities separately documents that WordPress plugin developers sometimes patch a security issue across multiple releases without disclosing it as a security fix in the changelog at all (vague entries like "Added security nonces," or a changelog claiming "Security Fixes" that doesn't fully resolve a reported CSRF issue) — meaning changelog text, even when present and accurately dated, cannot be trusted as a complete signal of what was fixed — [pluginvulnerabilities.com, 13 Dec 2023](https://www.pluginvulnerabilities.com/2023/12/13/wordpress-plugin-developers-continue-to-make-additional-attempts-to-fix-vulnerabilities-without-disclosing-it)

### Inferences
- The disclosure-date-vs-`last_updated` cross-reference idea posed in the research brief is directionally sound (a plugin updated after a CVE's public disclosure date is more likely to include a fix than one untouched since before disclosure) but remains an inference, not a documented, validated practice.
- Given `last_updated`'s documented staleness/bugs and caching lag, this signal should only be used as a coarse, directional prior — strong in one direction ("definitely not patched yet if `last_updated` predates disclosure"), weak in the other ("updated after disclosure" does not prove the update addressed that specific CVE) — never as a binary determination on its own.
- **Implementable mitigation for cve_lookup.py (stdlib-only):** for components where `component_kind` indicates a WordPress plugin/theme, add one additional `urllib` call to `https://api.wordpress.org/plugins/info/1.0/{slug}.json`, then: (1) compare the returned `last_updated` date against the CVE's already-tracked `published` date — if `last_updated` precedes `published`, that corroborates the version-range verdict either way; if `last_updated` follows `published`, set a new field `"vendor_updated_after_disclosure": true` with a note recommending a changelog spot-check, since a hotfix release can keep the same version number (the exact pattern documented in the backport-adjacent WordPress findings above); (2) pull the same response's `changelog` HTML and do a plain substring search for the CVE ID or terms like "security"/"XSS"/"vulnerability" near the installed version — free additive signal from a call the tool doesn't currently make.

### Gaps
- No source gives WPScan's own API field names/schema for fixed-version data (only Patchstack's was confirmed) — this would need a direct, dedicated lookup of WPScan's developer documentation that this research round didn't reach.
- No source confirms whether `api.wordpress.org` exposes a changelog entry's own per-version date (versus one whole-plugin `last_updated` timestamp). If it doesn't, the disclosure-date cross-reference above can only be done at whole-plugin granularity, which materially weakens it for plugins with many releases since the CVE.

## Published false-positive-rate statistics for version-based CVE scanning

### Takeaway
Quantified statistics exist but are almost all vendor-published rather than independently peer-reviewed, and measure adjacent-but-not-identical things (container contextual-reachability, CPE-vs-GHSA ecosystem matching) rather than isolating bare version-range comparison as its own variable. No academic, vendor-neutral study was found that isolates "version-string-vs-CVE-range comparison" as the sole independent variable and reports a false-positive rate for it alone.

### Cited Findings
- JFrog (vendor-published, methodology disclosed): across the 10 most frequently reported CVEs found in the 200 most popular "latest"-tag Docker Hub images, **78% of CVE occurrences were "non-applicable"** under contextual (reachability) analysis — the naive "vulnerable version present" signal was a false positive roughly 78% of the time for this sample/CVE set. Only CVE-2022-30631 exceeded 50% real applicability. JFrog states the figure is conservative (biased toward under-counting false positives) because its tooling "prefer[s] false positives to false negatives" — [InfoWorld / JFrog research](https://www.infoworld.com/article/3677550/most-reported-cves-for-docker-hub-images-are-harmless.html)
- Anchore (vendor-published, production telemetry): moving supported ecosystems from CPE matching to GHSA data reduced false-positive matches by "2,000+" in their dataset, with "up to an 80% reduction" for some ecosystems, at a cost of only 11 new false negatives — a concrete, if vendor-sourced, precision/recall tradeoff specifically for the CPE-vs-structured-advisory substitution — [Anchore blog](https://anchore.com/blog/say-goodbye-to-false-positives/)
- VulCPE (arXiv preprint, not confirmed as peer-reviewed/published venue): reports 93.55% of NVD entries carry at least one valid CPE string, and separately asserts false positives "predominantly stem from" CPE data limitations during correlation — qualitative, not quantitative, on the FP rate itself — [arXiv:2505.13895](https://arxiv.org/html/2505.13895v1)
- Socket.dev reports (unverified against NVD directly in this research) that "only 43.5%" of NVD records have the product-matching data a scanner needs to connect a CVE to installed software — if accurate, this is a data-*completeness* statistic (how often a basis for matching even exists), distinct from a false-positive-*rate* statistic (how often an existing match is wrong) — [Socket.dev NVD glossary entry](https://socket.dev/glossary/national-vulnerability-database-nvd.md), flagged as unverified.
- A vendor benchmark (Pentest-Tools.com, 2024, self-run) compares web-app scanners' false-positive rates generally (e.g. noting ZAP produced 88 SQL-injection false positives in their test), but this measures generic web vulnerability scanning, not CVE version-matching specifically, and was run by a company selling a competing scanner — [Pentest-Tools.com benchmark](https://pentest-tools.com/benchmarks/website-vulnerability-scanners)

### Inferences
- The absence of an independent, peer-reviewed, version-matching-specific false-positive-rate study is itself a notable finding: every quantified number available comes from a commercial vendor measuring the improvement of its own product/methodology (JFrog selling contextual analysis; Anchore open-sourcing Grype with GHSA integration). Treat the percentages above as directional evidence the failure mode is large and real, not as a rigorously generalizable base rate for an arbitrary CVE/product pair.
- The two figures that are least marketing-flavored and most methodologically transparent are JFrog's 78% (explicit sample: top-10 CVEs across 200 images; explicit method: reachability analysis) and Anchore's 2,000+/80%/11-false-negatives (explicit before/after on real ecosystem data) — these are the headline statistics to cite, with the vendor caveat attached both times.
- **Implementable mitigation for cve_lookup.py:** with no external authoritative FP-rate to calibrate against, the defensible move is for the tool to self-report its own precision over time — e.g. an optional operator-supplied `confirmed_outcome` field written back into the saved JSON per hypothesis (there's already a clean slot for this next to the existing `version_appears_affected` boolean) — so the project accumulates its own project-specific, defensible false-positive rate across engagements instead of relying on non-comparable external vendor figures.

### Gaps
- No academic or industry paper was found that isolates "bare version-string range comparison against a CVE's published affected-version range" as the sole independent variable and reports a false-positive/negative rate for that comparison alone, decoupled from broader SCA/container/contextual-analysis methodology. This specific, narrow statistic does not appear to exist in citable published form; every available number measures something adjacent rather than the raw comparison itself.
- No source attempted to quantify false-positive rates specifically for the NVD CVE 2.0 API (the exact data source `cve_lookup.py` queries) as distinct from downstream SCA tools that apply additional cleaning atop raw NVD data.
