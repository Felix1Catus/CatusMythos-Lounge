# ML/Model Supply Chain Security Beyond Pickle-Opcode Scanning (2024–2026)

Scoping note: this research targets gaps in `skills/16-ai-llm-security/scripts/model_supply_chain.py`, which currently (a) walks pickle opcodes (`GLOBAL`/`STACK_GLOBAL`/`REDUCE`/`INST`/`OBJ`/`NEWOBJ*`) against a `DANGEROUS_MODULES`/`DANGEROUS_CALLABLES` blocklist for `.pkl/.pickle/.pt/.pth/.bin/.ckpt/.joblib/.dill/.npy/.npz`, and (b) treats `.safetensors/.onnx/.gguf/.ggml/.json` as unconditionally `"safe"` with no further inspection. Every finding below is framed against that baseline.

## Model registry / hosting-platform attacks: what indicators would a scanner check?

### Takeaway
Hugging Face Hub has a documented, recurring pattern of malicious-model uploads (reverse shells, infostealers, crypto-miners) and a separate, large-scale typosquatting/namespace-squatting problem; both are increasingly measured empirically (hundreds of thousands of models scanned, thousands of squatting candidates found) and both are detectable primarily through **registry metadata** (creation date, author/org identity, download/like ratios, file listing, model-card text similarity) rather than file content — this is a different data source than the model file itself and is entirely missing from the current tool.

### Cited Findings
- JFrog's scanners found roughly 100 PyTorch/TensorFlow-Keras models on Hugging Face in early 2024 with malicious functionality (mostly reverse-shell payloads); JFrog noted some were likely security-research probes rather than live attacks — [JFrog](https://jfrog.com/blog/data-scientists-targeted-by-malicious-hugging-face-ml-models-with-silent-backdoor/)
- ReversingLabs (Feb 2025) found two models using a technique dubbed "NullifAI" that abused pickle deserialization to run code while evading Hugging Face's existing scanning; the models went undetected for over 8 months — [HelpNetSecurity](https://www.helpnetsecurity.com/2025/02/10/malicious-ml-models-found-on-hugging-face-hub/)
- Academic study "MalHug" scanned 705K+ models and 176K+ datasets on Hugging Face and found 91 malicious models and 9 malicious dataset loading scripts — [arXiv:2409.09368](https://arxiv.org/pdf/2409.09368v1)
- JFrog and Hugging Face partnered (announced ~March 2025) to integrate JFrog's malicious-model scanning platform-wide; JFrog reported that **96%+ of models Hugging Face already flagged "unsafe" for pickle issues were false positives**, while JFrog's deeper decompilation/data-flow analysis caught 25 "zero-day" malicious models that existing scanners missed — [JFrog](https://jfrog.com/blog/jfrog-and-hugging-face-join-forces/)
- A secondary (May 2026) Cloud Security Alliance research note claims Protect AI, working with Hugging Face, has scanned 4M+ models and flagged ~352,000 as unsafe/suspicious; this figure could not be verified against a Protect AI/Hugging Face primary source and should be treated as unconfirmed — [CSA Labs](https://labs.cloudsecurityalliance.org/research-rb/csa-research-note-huggingface-model-supply-chain-attack-2026/)
- An Internetware 2025 academic measurement study is described as the first large-scale empirical look at typosquatting on Hugging Face: it flagged **1,574 potentially malicious squatting models**, found **10.4%** exhibited suspicious/harmful characteristics, identified **625 cases of typosquatting**, and found **302 organizations** with squatting patterns enabling supply-chain attacks — [Internetware 2025](https://conf.researchr.org/details/internetware-2025/internetware-2025-research-track/42/Exploring-Typo-Squatting-Threats-in-the-Hugging-Face-Ecosystem)
- Protect AI published research specifically on "name squatting" of organizations on Hugging Face (title: "Unveiling AI/ML Supply Chain Attacks: Name Squatting Organizations on Hugging Face"); the primary URL returned HTTP 404 on fetch during this research and its specific indicator list could not be directly verified — [Protect AI (dead link at research time)](https://protectai.com/blog/unveiling-ai-supply-chain-attacks-on-hugging-face)
- A namespace "Open-OSS/privacy-filter" impersonated OpenAI's genuine "Privacy Filter" model, reportedly copying its model card almost word-for-word and shipping an infostealer; secondary blogs attribute discovery variously, and the attribution to a specific research team could not be confirmed from a primary source during this pass — [SkillSafe blog](https://skillsafe-web-github.pages.dev/blog/open-oss-privacy-filter-huggingface-typosquat/), [InfoSecGE blog](https://infosecge.pages.dev/blog/huggingface-openai-privacy-filter-infostealer-2026)
- Palo Alto Networks Unit 42 described "Model Namespace Reuse" (tracked in MITRE ATLAS as AML.CS0065): model identifiers on public hubs can be reclaimed/abused after an account or org renames/vanishes, letting an attacker register the now-free old name; related "AIJacking" research showed the `ai-forever` org namespace was reclaimed after it was formerly known as `sberbank-ai` — [Startup Defense / MITRE ATLAS case study](https://www.startupdefense.io/mitre-atlas-case-studies/aml-cs0065-model-namespace-reuse-supply-chain-attack), [Legit Security](https://www.legitsecurity.com/blog/tens-of-thousands-of-developers-were-potentially-impacted-by-the-hugging-face-aijacking-attack)
- Pluto Security tracked an active campaign ("Load/Mine") of **31 malicious model repositories across 7 Hugging Face accounts**, using small Qwen2-style test checkpoints where `trust_remote_code=True` executes attacker Python (e.g., files named like `modeling_evil.py`); the attacker kept backup repos to survive takedowns — [Pluto Security](https://pluto.security/blog/hugging-face-malware-campaign-load-mine/), [aicybr](https://aicybr.com/blog/hugging-face-load-mine-malicious-models-trust-remote-code-response)
- The Hugging Face Hub API's expandable `ModelInfo` fields include `createdAt`, `downloads` (rolling 30-day count), `downloadsAllTime` (cumulative since creation), `lastModified`, `author`, `cardData`, `gated`, `safetensors`, and `siblings` (file listing) — reachable via `GET /api/models/{repo_id}` or the `huggingface_hub` Python client's `model_info()`/`HfApi` — [HF Hub API docs](https://huggingface.co/docs/hub/api), [huggingface.js hub module docs](https://huggingface.co/docs/huggingface.js/hub/modules)

### Inferences
- **This entire category requires a network call to the registry's metadata API, not just local file inspection** — a meaningful architectural extension to `model_supply_chain.py`, which today only walks local files. It is still "static" in the sense that it never executes/loads model weights; it is one HTTPS GET + `json.loads`, implementable with `urllib.request` from stdlib (no `huggingface_hub` dependency strictly required, though that library wraps the same endpoint and handles pagination/auth).
- Concrete, stdlib-only checks against `GET https://huggingface.co/api/models/{repo_id}`:
  1. **Age/popularity mismatch**: `createdAt` within the last N days (e.g., 30) combined with disproportionately high `downloads`/`downloadsAllTime` is anomalous — legitimate adoption curves ramp over time; a brand-new repo with huge download counts mirrors npm/PyPI typosquat-then-inflate patterns. Flag as `review`.
  2. **Name-similarity to known orgs**: maintain a short allowlist of well-known org/model namespaces (`openai`, `meta-llama`, `google`, `mistralai`, `Qwen`, `deepseek-ai`, `stabilityai`, `microsoft`, `nvidia`, etc.) and compute edit distance (a ~15-line Levenshtein implementable in pure stdlib, no dependency) between the scanned repo's org/model name and each allowlist entry. Distance ≤2, or a hit on common substitution patterns (`0`/`O`, `l`/`1`, `-`/`_`, inserted/doubled character, e.g. "Matplotltib"-style typos seen in the PyPI case below), where the actual `author` field does *not* match the allowlisted org exactly → flag `review`/`DANGEROUS` depending on download count.
  3. **Model-card similarity**: fetch `cardData`/README text and diff it (stdlib `difflib.SequenceMatcher`) against the README of the real org's equivalent model (if resolvable); near-identical card text under a different, unverified namespace is a strong typosquat signal (matches the Open-OSS/privacy-filter pattern of copying OpenAI's card).
  4. **File-listing anomaly**: `siblings` returns filenames without downloading content — flag repos whose file list mixes model weights with `.py` files referencing `auto_map`/custom code, `.sh`/`.exe`/installer-style files, or files whose names suggest obfuscation. This is a zero-cost check layered on top of a metadata call already being made.
  5. **Maintainer-history clustering**: a second API call (`list_models(author=...)`) against the author/org can reveal "burst" account behavior — many repos created in a tight time window, all with squatting-pattern names (the Pluto "Load/Mine" pattern of 31 repos across 7 accounts). This needs one extra call per flagged author, not per scan, so it's cheap to gate behind the name-similarity check firing first.
  6. **Gated/verified flag cross-check**: `gated` and any "verified organization" indicator should be cross-checked against the allowlist — a repo claiming an identity resembling a verified org without the platform's own verification flag is suspicious.
- All six checks above are purely metadata/API-based, require no model-file download and no execution, and are implementable in stdlib Python (`urllib.request`, `json`, `difflib`, hand-rolled Levenshtein) with zero new third-party dependencies — a natural "Phase 0" network check the tool could add as an opt-in (`--check-registry`) step before the existing local file walk, since it needs outbound network access that a purely offline file scanner currently does not.

- Could not confirm the CSA note's claim of "4M+ models scanned / ~352K unsafe" against a Protect AI or Hugging Face primary publication — treat as unconfirmed secondary reporting.

## Are "safe-by-design" formats (safetensors, ONNX, GGUF) actually fully safe?

### Takeaway
No — the *tensor-serialization* layer of these formats genuinely cannot execute arbitrary code the way pickle can, but **2024–2026 research and CVEs repeatedly show that (a) the surrounding parser/loader code has memory-corruption and resource-exhaustion bugs, (b) GGUF's chat-template metadata field is literal Jinja2 source that gets rendered unsandboxed by consumers, and (c) ONNX's graph format is expressive enough (custom/contrib ops, `If`/`Loop` control flow) to embed a fully-working conditional backdoor without triggering any "unsafe" classification at all.** The "safe-by-design" label in `model_supply_chain.py` is accurate only for "no code executes merely by deserializing the tensor bytes" — it is not accurate for "nothing bad can be embedded in this file," which is the claim a pentest tool needs to make precisely.

### Cited Findings
**safetensors**
- No CVE was found filed against the `safetensors` library's core tensor-deserialization logic itself in this research pass.
- A Hugging Face-hosted PoC repo documents a "Denial of Service via Header Bloating in Safetensors": the format caps the header at 100MB, but an attacker can craft a header with a huge number of tensor entries within that cap, exhausting CPU/memory on parse; this is reported as an unconfirmed PoC, not a confirmed-fixed CVE — [HF PoC repo](https://huggingface.co/Damir2024/Malicious-safetensor-poc)
- Metadata-poisoning CVEs were found in *libraries that consume* safetensors metadata, not in the format: CVE-2026-22584 (Salesforce, High severity, fixed July 31 2025) and CVE-2025-23304 (NVIDIA NeMo, High severity, fixed in NeMo 2.3.2) both stem from passing safetensors metadata into a code-execution path in the surrounding tooling — [The Register](https://www.theregister.com/2026/01/13/ai_python_library_bugs_allow/)

**GGUF / llama.cpp**
- CVE-2024-21825: Cisco Talos documented a heap-based buffer overflow in GGUF string/array parsing (`gguf_fread_str` in `ggml.c`), CWE-190 (integer overflow), reachable via a crafted GGUF file and reportedly capable of enabling code execution — [Talos TALOS-2024-1912](https://talosintelligence.com/vulnerability_reports/TALOS-2024-1912)
- GHSA-3p4r-fq3f-q74v: an integer overflow in `gguf_init_from_file_impl` (`ggml/src/gguf.cpp`) causes an undersized heap allocation, later overflowed by a write; the advisory states the main model-loading path is not affected but other tools (the `llama-gguf` example, `imatrix` loading in `llama-quantize`) are reachable — [GitHub Security Advisory](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-3p4r-fq3f-q74v)
- CVE-2026-33298: a more recent heap buffer overflow via integer overflow in GGUF tensor parsing (details limited in sources found) — [Lutra Security field guide](https://fieldguide.lutrasecurity.com/CVE-2026-33298)
- An out-of-bounds read in Ollama's GGUF processing (CVE-2026-7482 per search synthesis) is a separate, Ollama-specific memory-leak-class bug, not an upstream llama.cpp CVE — [related writeup](https://msuiche.com/posts/bleeding-llama-when-ai-model-files-become-memory-leaks/index.md)
- **CVE-2024-34359 ("Llama Drama")**: `llama-cpp-python` before 0.2.72 renders the GGUF file's `tokenizer.chat_template` metadata field (literal Jinja2 source) through an **unsandboxed** Jinja2 environment, enabling arbitrary code execution purely from a crafted GGUF file's metadata, with no weights needed. Loading the same malicious GGUF into `llama-cpp-python` ≥0.2.72 or into other GGUF-compatible tools (e.g., Ollama) does not trigger code execution, per JFrog — [JFrog Research](https://research.jfrog.com/model-threats/gguf-ssti/)
- **CVE-2026-5760 (SGLang, CVSS 9.8)**: the same chat-template-injection vector reappeared in SGLang — a malicious Jinja2 payload embedded in a GGUF model's chat-template metadata achieves RCE on an SGLang server; the disclosure explicitly ties the attack chain back to the "Llama Drama" pattern — [CSA Labs research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-sglang-cve-2026-5760-llm-serving-rce-20260)
- Separately, chat templates can implant **behavioral** backdoors with no code execution at all: an academic paper shows malicious behavior can be implanted purely by editing a model's chat template while leaving weights untouched; Pillar Security built a PoC on a Phi-4 template that only activates for HTML-related requests, making it hard to catch via casual testing — [arXiv 2602.04653 (via EmergentMind)](https://www.emergentmind.com/papers/2602.04653), [Pillar Security](https://www.pillar.security/blog/llm-backdoors-at-the-inference-level-the-threat-of-poisoned-templates)
- JFrog's and Promptfoo's recommended mitigation is to scan `tokenizer.chat_template` text for suspicious substrings (`__class__`, `os`, `subprocess`, `eval`, `exec`) and render templates only in a sandboxed Jinja2 environment — [JFrog Research](https://research.jfrog.com/model-threats/gguf-ssti/), [Promptfoo vuln DB](https://promptfoo.dev/lm-security-db/vuln/chat-template-hidden-instructions-8fee546c/)

**ONNX**
- **ShadowLogic** (HiddenLayer, Oct 2024): a technique for embedding an attacker-defined backdoor directly in a model's **computational graph** rather than its weights — no training/fine-tuning required. The published method adds a parallel "trigger" subgraph (e.g., detecting a specific pixel-value threshold) whose output is blended into the final output via arithmetic/conditional nodes, leaving the original model logic intact for non-triggered inputs. HiddenLayer states the technique "works for any neural network format that serializes a graph representation," naming TensorFlow, CoreML, and OpenVINO in addition to ONNX, and demonstrated it on ResNet, YOLO, and Phi-3 Mini. HiddenLayer reports the backdoor persists through format conversion and fine-tuning, and in their fine-tuning comparison the ShadowLogic backdoor achieved a 100% attack-success rate versus 74% for a conventional weight-based backdoor — [HiddenLayer primary research](https://hiddenlayer.com/research/shadowlogic/)
- A November 2025 follow-up paper by HiddenLayer researchers (Schulz, Kawasaki, Ring) extends ShadowLogic to white-box LLMs via an "uncensoring vector" injected into the computational graph, demonstrated on Phi-3 and Llama 3.2 with a 60% attack-success rate for eliciting further malicious output — [arXiv:2511.00664](https://arxiv.org/abs/2511.00664)
- CVE-2024-27318: directory traversal in ONNX's `load_external_data_for_tensor` (`external_data_helper.py`) — a tensor's `external_data` field can point outside the model's directory (e.g., `external_data/../../secret`), causing arbitrary file read into the model; this is a **bypass of an earlier fix** for CVE-2022-25882; CVSS 7.5 (network), CWE-22; fixed in ONNX 1.16.0 — [NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-27318), [GitHub Advisory GHSA-whh8-fjgc-qp73](https://github.com/advisories/GHSA-whh8-fjgc-qp73)
- A related HiddenLayer advisory (labeled CVE-2024-27319 in HiddenLayer's own page, though this number could not be cross-confirmed against other sources, which consistently cite 27318 for the same `load_external_data_for_tensor` bypass) covers the same path-sanitization-bypass class — [HiddenLayer advisory](https://hiddenlayer.com/?p=9007)
- CVE-2024-5187 and CVE-2024-7776: path traversal in ONNX's `download_model`/`download_model_with_test_data` functions (versions ≤1.16.0 / ≤1.16.1) allowing arbitrary file overwrite and reportedly RCE when a user downloads a malicious ONNX model archive — [SentinelOne CVE-2024-5187](https://www.sentinelone.com/vulnerability-database/cve-2024-5187/), [SentinelOne CVE-2024-7776](https://www.sentinelone.com/vulnerability-database/cve-2024-7776/)
- An unvetted vulnerability write-up describes a "PyOp" (Python custom operator, `com.microsoft` domain) node type that can execute arbitrary Python when the graph is run; the report states many production ONNX Runtime builds disable this by default, but no CVE number or independent confirmation was found — [HF-hosted PoC writeup](https://huggingface.co/Damir2024/Onnx-poc), [OffSec ML wiki](https://wiki.offsecml.com/Supply+Chain+Attacks/Models/Using+the+ONNX+Runtime)
- CVE-2026-14647: an out-of-bounds read in ONNX Runtime's shape-inference code (outside the 2024 window but shows the parser-bug pattern continuing into 2026) — [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-14647/)

### Inferences
- The accurate claim for a pentest tool to encode is: **"safetensors/GGUF/ONNX do not run arbitrary code merely by deserializing tensor *data*, but all three have (1) documented parser-level memory-safety bugs in specific library versions, and (2) at least one in-format mechanism — GGUF chat templates, ONNX custom ops/control-flow graphs — that can carry a working exploit or backdoor while still being 'valid' files of that format."** `model_supply_chain.py`'s current one-line `"safe-by-design format (no arbitrary code execution on load)"` finding should be replaced with format-specific structural checks, all still fully static:
  1. **safetensors header validation** (pure stdlib — `struct.unpack("<Q", data[:8])` for the header length, `json.loads` for the header itself): reject/flag if the declared header length exceeds the file size or an unreasonable absolute cap; reject/flag if the parsed header contains an implausible number of tensor keys relative to file size (header-bloat DoS); validate every tensor's `dtype` against the known enum (F64/F32/F16/BF16/I64/I32/I16/I8/U8/BOOL/F8_E4M3/F8_E5M2…), and validate `data_offsets` pairs are non-overlapping, monotonically increasing, and fit within `[0, file_size - header_len]`, with `(end-start)` matching `shape`-product × dtype itemsize. This directly operationalizes the header-bloat PoC finding and catches corrupt/adversarial headers without ever materializing tensor data.
  2. **GGUF bounds-checked structural parse** (stdlib `struct`): parse magic/version/`tensor_count`/`metadata_kv_count` per the documented layout, but — unlike a naive "trust the length field" parse (the exact bug class behind CVE-2024-21825 and GHSA-3p4r-fq3f-q74v) — verify every length-prefixed string/array read against *remaining bytes in the file* before reading, flagging/rejecting any declared length that exceeds what's left in the file. This simultaneously (a) detects the malformed-file pattern that previously crashed/overflowed vulnerable loaders, and (b) safely extracts metadata values, including `tokenizer.chat_template`.
  3. **GGUF chat-template scan**: once `tokenizer.chat_template` is extracted as a string, regex/substring-search it for Jinja2-SSTI indicators: `{{`/`{%` co-occurring with `__class__`, `__globals__`, `__mro__`, `__subclasses__`, `__init__`, `os.`, `subprocess`, `eval(`, `exec(`, `popen`, `system(`, `getattr(`, `importlib`. This is the literal JFrog/Promptfoo-recommended check, pure string matching, zero execution — flag as `DANGEROUS` or `review` since benign chat templates have no legitimate reason to reference these tokens.
  4. **ONNX graph structural scan**: ONNX files are protobuf; there is no stdlib protobuf decoder, so this requires the `onnx` (or bare `protobuf`) package as a minimal, justified dependency — but parsing via `onnx.ModelProto().ParseFromString(data)` (or `onnx.load(path, load_external_data=False)`) only deserializes the graph *structure*; it never executes it, so this remains a static check. Concrete checks: (a) enumerate every node's `(domain, op_type)` and flag any non-standard `domain` (anything beyond `""`/`ai.onnx`/`ai.onnx.ml`), since custom-op domains like `com.microsoft` PyOp are precisely where native/Python code execution hooks in; (b) flag `If`/`Loop`/`Scan` control-flow nodes on a path to a declared output, especially when gated by narrow numeric-comparison ops (`Equal`/`Less`/`Greater`/`ReduceMax`/`ReduceMin`) that don't correspond to documented class logic — this is a heuristic "review" signal for ShadowLogic-style trigger subgraphs, not a hard detector (false positives expected on legitimate conditional architectures); (c) validate every `external_data` tensor's `location` field via `os.path.normpath`/containment-check against the model's own directory, rejecting any that contain `..` or resolve outside it — this directly closes the CVE-2024-27318/27319 class; (d) optionally diff the node-count/op-type histogram against a small reference fingerprint database for well-known architectures named in the model card, flagging large deviations as informational (weak signal, needs a maintained reference set).
  5. **Hard boundary — what cannot be done statically**: confirming a ShadowLogic-style conditional subgraph actually changes output behavior requires running inference with and without the suspected trigger pattern (dynamic/behavioral testing — out of scope for a safe static scanner); confirming a Jinja2 template is exploitable in a *specific* consuming framework requires knowing whether that framework sandboxes its template engine (framework-specific, not file-specific — treat as `review`, never a definitive clear); and the scanner's own GGUF/ONNX structural parser must itself be hardened (bounds-checked, resource-limited, ideally run in a subprocess with memory/CPU limits) since it is, by definition, parsing untrusted adversarial input of exactly the kind that has triggered memory-corruption CVEs in other parsers.
  6. **A secondary, concrete bug in the existing tool's `.npy`/`.npz` handling**: these are *not* pickle streams by default — `.npy` is a short ASCII/binary header (`\x93NUMPY`, version, header length, then a Python-literal dict string like `{'descr': '<f4', 'fortran_order': False, 'shape': (...)}, parseable via stdlib `ast.literal_eval`) followed by raw numeric bytes. Feeding a normal `.npy` to `scan_pickle_bytes` (as the current tool does) will typically yield "unparseable pickle stream" — a safe failure, but a mischaracterization. The real risk is narrow and precisely identifiable: object-dtype arrays (`descr == '|O'` or similar) are the *only* case where `numpy.load(..., allow_pickle=True)` invokes pickle on the trailing bytes — and NumPy has defaulted `allow_pickle=False` since 1.16.3 (post CVE-2019-6446). A corrected check: parse the small header first; only hand the remaining bytes to the existing `scan_pickle_bytes` walker when `descr` indicates object dtype (in which case the trailing bytes *are* a genuine pickle stream the existing opcode walker handles correctly); otherwise classify as `safe` numeric data. Apply the same per-member logic to `.npz` (a zip of `.npy` members), reusing the tool's existing zipfile-walking code path. This is a precision fix, fully stdlib, and arguably more correct than the current blanket "unsafe extension" treatment.

### Gaps
- No safetensors-library CVE (as opposed to CVEs in *consumers* of safetensors metadata) was found; it's unclear whether the header-bloat DoS PoC was ever triaged/fixed upstream — only an unconfirmed PoC repo was located.
- The HiddenLayer-labeled "CVE-2024-27319" could not be independently confirmed as a distinct CVE from CVE-2024-27318; sources disagree, and this should be verified directly against cve.org/NVD before being cited as two separate vulnerabilities in the skill's documentation.
- The "PyOp"/custom-Python-operator ONNX Runtime execution path has no confirmed CVE number in sources found; its real-world default-enabled status in current ONNX Runtime releases needs direct verification against Microsoft's own advisories before being treated as a confirmed, currently-exploitable vector.
- No independent replication of HiddenLayer's ShadowLogic persistence/attack-success claims (100% ASR after fine-tuning, 60% ASR for the LLM uncensoring variant) was found; these are the vendor/authors' own reported figures.

## LoRA/adapter-specific backdoors: static vs. behavioral detectability

### Takeaway
A backdoored LoRA adapter is structurally tiny, low-rank, and (when shipped as safetensors) carries **zero executable opcodes** — making it simultaneously easier to localize for weight-space statistical analysis than a full backdoored base model, and completely invisible to any scanner (like the current tool) that only looks for dangerous pickle imports. Confirming a specific trigger phrase generally still requires behavioral/execution-based testing; only coarse anomaly-flagging is achievable statically.

### Cited Findings
- PADBench/PEFTGuard (arXiv:2411.17453) released a benchmark of 13,300 benign and backdoored PEFT/LoRA adapters and a detector (PEFTGuard) reporting near-perfect detection in most tested settings; the authors found "fine-mixing" the most effective mitigation among those tested — [arXiv:2411.17453](https://arxiv.org/abs/2411.17453)
- A "Weight-space Detection of Backdoors in LoRA Adapters" paper (arXiv 2602.15195) proposes a **static** detector operating purely on the LoRA weight update ΔW = B·A via SVD/spectral metrics, with no model execution required; the authors report ~97% accuracy with <2% false positives on a 500-adapter Llama-3.2-3B benchmark, motivated explicitly because behavioral detection needs a known trigger and doesn't scale to screening large adapter hubs — [arXiv 2602.15195](https://arxiv.org/html/2602.15195)
- "Token-Level Generalization in LoRA Adapter Backdoors" (arXiv 2605.30189, May 2026) shows a small number of poisoned fine-tuning examples can implant a LoRA backdoor in a prompt-injection classifier while preserving clean accuracy; the paper reports the weight-level signal **concentrates in MLP projection layers**, and a weight-norm-based statistic separates poisoned from clean adapters on their calibration set — [arXiv:2605.30189](https://arxiv.org/pdf/2605.30189)
- These are preprints (arXiv, 2025–2026) without found independent peer-reviewed replication; result figures are each paper's own benchmark performance and may not transfer to adapters/triggers outside their test distribution.

### Inferences
- **What is checkable statically (file-structure/metadata only, no execution)**:
  1. Parse `adapter_config.json` (plain JSON, stdlib) and flag unusual `target_modules` (e.g., unnecessarily including embedding/`lm_head` layers — a known cheap way to implant token-trigger-level behavior) or an unusually high rank `r` relative to typical fine-tunes of the stated base model (high/near-full rank narrows the gap between "LoRA" and "full backdoored fine-tune" and is a prioritization signal, not proof).
  2. Load *only* the tensor bytes via the safetensors header's declared offsets (this reads floats into memory — e.g. via `numpy.frombuffer` — but never executes code, since safetensors has no executable primitive by design) and compute per-layer singular-value spectra of each `lora_B @ lora_A` product (requires `numpy`, a minimal and justified dependency — no `torch` needed for safetensors-origin LoRAs). Flag anomalous concentration of singular-value energy or outlier Frobenius norm in specific layers — per arXiv 2605.30189, MLP `up_proj`/`down_proj` tensors are a reported hot spot — relative to a small reference population of known-clean adapters for the same base model/rank. This mirrors the arXiv 2602.15195 approach and should be exposed as a `review`-level anomaly score, never a hard `DANGEROUS` verdict, since no public, independently replicated ground truth threshold was found.
  3. Tensor-naming-convention check: confirm LoRA tensor names match the expected `*.lora_A.weight` / `*.lora_B.weight` convention for the declared `target_modules`; mismatches (extra tensors, unexpected shapes not matching `r`) are a basic structural red flag separate from any backdoor-specific statistic.
- **What requires execution (explicitly out of scope for a safe static scanner)**: actually identifying *which input* triggers the backdoored behavior requires merging the adapter with its base model and running forward passes — either against a curated trigger-phrase test suite (cheap, but only catches known/common triggers) or via gradient-based/optimization trigger search (the research-grade approach behind PEFTGuard/PADBench). Both require loading model weights into an inference framework and executing them, which is categorically the dynamic/behavioral-testing step this static scanner must explicitly flag as **not performed** and hand off to a separate behavioral-redteaming workflow (e.g., this repo's `llm-redteam` agent) rather than attempt itself.
- **The key contrast to state explicitly in the skill's documentation**: a backdoored *base model* usually needs either a code-execution primitive (pickle/`.bin`) to plant a persistent payload — exactly what the existing opcode scanner catches — or a distributed statistical poisoning across the model's full (huge) parameter set, which is hard to localize. A backdoored *LoRA adapter* is the opposite on both axes: it is trivial to localize (a handful of small, conventionally-named, low-rank tensors) but, if shipped as safetensors, carries **no opcodes at all**, so it is structurally invisible to the current tool regardless of how thorough the pickle-opcode walk is. This is a detection-modality gap, not a depth gap — it needs weight-space statistics or behavioral probing, a capability the tool has zero coverage for today.

### Gaps
- No confirmed, independently-replicated accuracy/false-positive numbers for weight-space LoRA-backdoor detection exist outside each paper's own benchmark; real-world generalization across arbitrary base models, ranks, and trigger designs is unverified.
- No documented real-world (non-academic) incident of a backdoored LoRA adapter distributed via a public hub was found in this research pass — all cited LoRA-backdoor material is academic/research-benchmark work, not an observed in-the-wild campaign. This should be stated plainly: the *technique* is demonstrated and published, but a confirmed in-the-wild case (comparable to the Hugging Face pickle-malware incidents) was not found.

## Supply-chain attacks via the ML tooling itself

### Takeaway
2024–2026 incidents show the dominant *tooling-level* attack surface is `trust_remote_code`/custom modeling code (repeatedly bypassed even when developers believe they've disabled it), malicious dataset loading scripts (a mechanism Hugging Face has now largely removed), and compromised PyPI packages in the ML ecosystem, including a cascading 2026 campaign (TeamPCP) that compromised CI/CD tooling to backdoor widely-used ML-adjacent packages like `litellm`. Nearly all of this is detectable via static AST/text analysis of Python source and config files — a different scan target than the model weight file itself.

### Cited Findings
**trust_remote_code bypasses**
- Diffusers "FaceHugger": three vulnerabilities let a malicious Hub repo execute code even when the caller explicitly sets `trust_remote_code=False`, because the trust check lived in `DiffusionPipeline.download()` rather than at the actual dynamic-module-loading site; one variant (CVE-2026-44827) is CVSS 8.8; fixed in Diffusers 0.38.0 — [CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-huggingface-diffusers-facehugger-rce-20260/), [Zafran](https://www.zafran.io/resources/facehugger-vulnerabilities-in-hugging-face-diffusers-open-door-to-supply-chain-attacks-on-enterprise-ai)
- Transformers CVE-2026-4372: a crafted `config.json` can point to a Hub repo whose Python then runs, bypassing the intended protection of `trust_remote_code`; disclosed by Pluto Security (June 2026), reportedly affecting versions 4.56.0 through 5.2.x — [SecurityBrief UK](https://securitybrief.co.uk/story/hugging-face-transformers-flaw-enabled-remote-code), [TechRepublic](https://techrepublic.com/article/news-hugging-face-transformers-rce-flaw/)
- The same `trust_remote_code=True` hardcoding pattern was separately reported in LMDeploy (CVE-2026-46432) and InstructLab (CVE-2026-6859), with a related issue in vLLM (CVE-2026-22807) — pattern repeats across the downstream ecosystem, per secondary reporting found alongside the Transformers disclosure.
- Pluto's "Load/Mine" campaign (also cited above): 31 malicious repos across 7 HF accounts shipping Python (e.g. `modeling_evil.py`-style files) referenced via `auto_map`, executed when `trust_remote_code=True` — [Pluto Security](https://pluto.security/blog/hugging-face-malware-campaign-load-mine/)

**Malicious dataset loading scripts**
- MalHug (cited above) found 9 malicious dataset loading scripts among 176K+ scanned datasets — [arXiv:2409.09368](https://arxiv.org/pdf/2409.09368v1)
- The `datasets` library historically let a dataset repo ship a Python loading script that `load_dataset()` would execute; this was progressively gated behind an explicit `trust_remote_code` decision and reportedly removed entirely in `datasets` 4.0.0 (July 2025) — found in one secondary blog without independent confirmation of the exact version/date — [via search synthesis, primary confirmation not found]
- CVE-2026-57845: Hugging Face `datasets` through 5.1.0 has an insecure-deserialization vulnerability allowing arbitrary Python code execution via a crafted pickle file loaded through the **deprecated pandas packaged builder**; CVSS 3.1 score 8.8; no patched version confirmed in sources found — [Mend.io vulnerability DB](https://www.mend.io/vulnerability-database/CVE-2026-57845/), [CodeAnt](https://codeant.ai/vulnerability-database/cve-2026-57845)
- Hugging Face disclosed a server-side breach where a malicious dataset chained a remote-code dataset loader with a template-injection flaw in a dataset configuration file; the resulting code ran on an HF processing worker, escalated to node-level access, collected cloud/Kubernetes credentials, and moved laterally into internal clusters over a weekend; Hugging Face stated it found no evidence of tampering with public-facing models, datasets, or Spaces; some secondary reporting attributes the attack to an "autonomous AI agent," an attribution not independently confirmed here — [trackr.live](https://www.trackr.live/?p=1320)

**Compromised PyPI packages (real incidents)**
- Mend.io detected 100+ malicious packages on PyPI on March 28, 2024, typosquatting popular ML libraries (PyTorch, Matplotlib, Selenium) with misspellings like "Matplotltib," "selennim," "PyToich"; payloads used Fernet encryption and attempted persistence via the startup path — [Mend.io](https://www.mend.io/blog/over-100-malicious-packages-target-popular-ml-pypi-libraries/)
- Positive Technologies found PyPI packages impersonating DeepSeek carrying infostealers (exact publication date not confirmed in sources found) — [Dark Reading](https://darkreading.com/application-security/ai-malware-deepseek-packages-pypi)
- An `aiocpa` PyPI package was engineered as a cryptocurrency-wallet stealer without classic typosquatting (not ML-specific, but illustrates the same registry-trust-abuse pattern) — [infostealers.com](https://infostealers.com/?p=4481)
- **TeamPCP campaign (2026)**: a cascading supply-chain compromise that hit the Trivy security-scanner GitHub Action, two Checkmarx IDE extensions, the `litellm` PyPI package (~97M monthly downloads), and the `telnyx` SDK; the CSA note frames this as a structural shift from opportunistic typosquatting to deliberate compromise of trusted, high-download packages — [CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-pypi-supply-chain-campaign-20260329-csa/)
- `litellm` was compromised **twice** in 2026: (1) March 24, 2026 — malicious versions 1.82.7/1.82.8 were live ~40 minutes before PyPI quarantined them; attackers used stolen maintainer credentials obtained by leaking the PyPI publishing token through a compromised Trivy GitHub Action in CI/CD; payload was credential-stealing code; versions ≤1.82.6 considered safe — [NetSPI](https://www.netspi.com/blog/executive-blog/ai-ml-pentesting/litellm-supply-chain-compromise/), [JFrog](https://research.jfrog.com/post/litellm-compromised-teampcp/); (2) October 21, 2026 — a second compromise published malicious version 1.107.0 to both PyPI and Docker via LiteLLM's own release pipeline — [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-docker.md), [Konfirmity](https://www.konfirmity.com/advisories/litellm-1-107-0-supply-chain-compromise)

**Fickling/PickleScan bypasses (directly relevant to the existing tool's threat model)**
- Trail of Bits' `fickling` had multiple confirmed blocklist-bypass CVEs: CVE-2026-22608 (ctypes/pydoc gadget chain achieves RCE while the file is still labeled `LIKELY_SAFE`; fixed in 0.1.7; the advisory notes **picklescan shares the `pydoc.locate` gap**), a `pty`-module bypass (fixed in 0.1.6), and CVE-2025-67747 (missing `marshal`/`types` entries, bypassed via `types.FunctionType`/`marshal.loads`, fixed in 0.1.6) — [Wiz vulnerability DB](https://www.wiz.io/vulnerability-database/cve/cve-2026-22608)
- JFrog separately disclosed three zero-day PickleScan bypass CVEs (CVE-2025-10155/10156/10157), and Sonatype reported four more (CVE-2025-1716/1889/1944/1945) — [Infosecurity Magazine](https://www.infosecurity-magazine.com/news/picklescan-flaws-expose-ai-supply), [JFrog](https://jfrog.com/blog/unveiling-3-zero-day-vulnerabilities-in-picklescan/)
- A Fluidattacks entry and a Positive Technologies entry both independently list stdlib modules (e.g. `uuid`) as never having been present in PickleScan's unsafe-globals blocklist — [Fluidattacks](https://db.fluidattacks.com/vul/FLAT-R9ZCU/), [PT Security](https://dbugs.ptsecurity.com/vulnerability/PT-2026-25456)
- PickleScan's efficacy depends on interpreting a pickle file exactly as PyTorch's real unpickler would; any divergence between PickleScan's parser and PyTorch's actual loading behavior can let a payload bypass detection; PickleScan also uses Python's `zipfile` module and can **fail entirely** (fail-open) on a ZIP with CRC mismatches; Hugging Face's own documentation states the tool "is not 100% foolproof" and that checking safety remains the user's responsibility — [Hugging Face Hub docs](https://huggingface.co/docs/hub/en/security-jfrog), [CyberScoop](https://cyberscoop.com/hugging-face-platform-continues-to-be-plagued-by-vulnerable-pickles/)

**huntr / Protect AI bug-bounty findings (broader ML tooling, suggested source)**
- `huntr` (now under Protect AI, which was later acquired by Palo Alto Networks) is described as the first AI/ML-focused open-source bug-bounty program, with 15,000+ community members; disclosed critical findings include path-traversal bugs in ZenML, lollms, and AnythingLLM (read/delete/overwrite of application database/config files), plus findings in H2O-3, MLflow, Ray, Setuptools, Lunary, and Netaddr; typical vendor disclosure window cited as 45 days — [SC World](https://scworld.com/news/ai-bug-bounty-program-yields-34-flaws-in-open-source-tools), [SecurityWeek](https://www.securityweek.com/over-a-dozen-exploitable-vulnerabilities-found-in-ai-ml-tools/), [huntr blog](https://blog.huntr.com/?p=72)
- A huntr-reported Hugging Face Transformers finding (CVE-2023-6730, CVSS 9.0) earned a $1,500 bounty, illustrating the program's scope includes core ML-framework code, not just peripheral tools — [huntr blog](https://blog.huntr.com/?p=72)

### Inferences
- **All of the above is static/file-based and achievable without executing the scanned repo's code** — the key technique is applying the *same opcode/AST-style static analysis `model_supply_chain.py` already does for pickle* to **Python source files** instead:
  1. Enumerate every `.py` file in a model/dataset repo (from the Hub API `siblings` list, or a local `os.walk`), and for each, parse it with stdlib `ast.parse()` (never `exec`/`import`) and walk the AST for `Import`/`ImportFrom` nodes naming modules like `os`, `subprocess`, `socket`, `ctypes`, `shutil`; `Call` nodes targeting `eval`, `exec`, `__import__`, `getattr`/`setattr` with dynamic string arguments; and base64-decode-then-exec idioms. This is a direct reuse of the existing `DANGEROUS_MODULES`/`DANGEROUS_CALLABLES` concept, just applied to source text via `ast` instead of to pickle opcodes via `pickletools`.
  2. Independently of what the AST walk finds, flag the **mere presence** of an `auto_map` key in `config.json` (the mechanism `trust_remote_code=True` acts on) as a finding on its own — e.g. `"repo requires executing author-supplied Python to load (trust_remote_code path) — same risk class as pickle, independent of weight-file format, and historically bypassed even when the caller sets trust_remote_code=False (CVE-2026-44827, CVE-2026-4372)"`. This directly operationalizes the FaceHugger/Pluto findings as a standing check, not just a historical note.
  3. For dataset repos, flag any top-level `<name>.py` loading script at all as a red flag given the `datasets` library's move away from this mechanism — its mere presence (especially paired with an older pinned `datasets` version) indicates either a stale/legacy repo or an attempt to exploit callers who haven't upgraded.
  4. Add a small, explicitly-dated **known-bad-version denylist** check (pure string/version comparison against `requirements.txt`/`pyproject.toml`/lockfiles, or against the *scanning environment's own* installed packages via stdlib `importlib.metadata.version(...)`) for packages directly implicated in confirmed incidents: `litellm==1.82.7`, `==1.82.8`, `==1.107.0`; `fickling<0.1.7`; `picklescan` pre-fix versions tied to CVE-2025-1716/1889/1944/1945/CVE-2025-10155/10156/10157; `datasets<=5.1.0` (CVE-2026-57845 path); `onnx<=1.16.1` (CVE-2024-5187/7776/27318); `torch<2.6.0` (CVE-2025-32434, see next section); `llama-cpp-python<0.2.72` (CVE-2024-34359). This reframes several CVEs as an **environment-hygiene** check the tool can run once per invocation (not per scanned file) and is entirely stdlib.
- **The hard boundary to state explicitly**: AST-parsing Python source to look for dangerous *patterns* is safe and static — it never imports or runs the code. Actually importing/running a `modeling_*.py` file (what `trust_remote_code=True` does) is precisely the dangerous action this tool exists to warn against, so the scanner must never execute discovered custom code itself, even in a "just checking" sandbox-lite way, without explicit, separately-scoped sandboxing infrastructure that is out of scope for a lightweight static scanner.

### Gaps
- The exact version/date that `datasets` removed Python loading-script support entirely (stated as "4.0.0, July 2025" in one secondary source) was not independently confirmed against Hugging Face's own changelog/release notes.
- Could not verify current (as of this research) default-enabled status of any residual loading-script compatibility shim in recent `datasets` versions.
- The downstream CVE identifiers for LMDeploy (CVE-2026-46432), InstructLab (CVE-2026-6859), and vLLM (CVE-2026-22807) trust_remote_code-pattern issues came from secondary-source synthesis alongside the Transformers CVE-2026-4372 disclosure, not from direct primary-advisory confirmation; verify directly against each project's own security advisories before citing as confirmed in skill documentation.

## 2024–2026 CVEs specifically in model-loading code paths

### Takeaway
Across PyTorch, Transformers, ONNX/ONNX Runtime, and llama.cpp/GGUF, the recurring vulnerability classes are (1) deserialization/RCE in loading functions — including a case where the *documented mitigation itself* (`torch.load(..., weights_only=True)`) was still exploitable until a 2025 fix — (2) path traversal via attacker-controlled file paths embedded in model metadata, and (3) integer-overflow-driven heap corruption in binary metadata parsers (GGUF). A static file scanner cannot patch these, but it can and should warn when the *environment that will load the file* is running a known-vulnerable library version.

### Cited Findings
- **CVE-2025-32434 (PyTorch)**: `torch.load()` with `weights_only=True` — the officially recommended mitigation against pickle RCE — was itself still vulnerable to remote code execution in PyTorch ≤2.5.1 (CWE-502, deserialization of untrusted data); fixed in PyTorch 2.6.0 (GHSA-53q9-r3pm-6pq6); severity ratings vary across trackers (one cites CVSS 4.0 of 9.3, another rates it "Moderate Risk" with EPSS 0.43%) — [stack.watch](https://stack.watch/vuln/CVE-2025-32434)
- Downstream of the same pattern: `lmdeploy` calls `torch.load()` without `weights_only=True` at all (GHSA-9pf3-7rrr-x5jh); vLLM's CVE-2025-24357 is also rooted in `torch.load` deserialization — [Wiz vulnerability DB (CVE-2025-24357)](https://wiz.io/vulnerability-database/cve/cve-2025-24357)
- **CVE-2025-14924 (Transformers)**: RCE in `megatron_gpt2` checkpoint conversion, allowing arbitrary code execution via a malicious checkpoint; vendor guidance explicitly recommends using safetensors-format weights where available since the format "does not execute code during deserialization" — [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-14924/)
- **CVE-2026-4372 (Transformers)** and the Diffusers **FaceHugger** CVEs (incl. CVE-2026-44827) — covered in detail in the prior section — are also, functionally, model-*loading*-path CVEs: the vulnerable code runs during `from_pretrained()`/pipeline loading, not during explicit user action.
- **ONNX / ONNX Runtime**: CVE-2024-27318 (external_data path traversal, fixed 1.16.0), CVE-2024-5187 and CVE-2024-7776 (path traversal in `download_model`/`download_model_with_test_data`, enabling arbitrary file overwrite/RCE), and CVE-2026-14647 (out-of-bounds read in ONNX Runtime shape inference) — all detailed with sources in the prior section.
- **llama.cpp / GGUF**: CVE-2024-21825 (heap overflow in `gguf_fread_str`, Talos), GHSA-3p4r-fq3f-q74v (integer overflow in `gguf_init_from_file_impl`), CVE-2026-33298 (heap buffer overflow via integer overflow in GGUF tensor parsing), and the chat-template RCE class (CVE-2024-34359 "Llama Drama" in `llama-cpp-python`, CVE-2026-5760 in SGLang) — all detailed with sources in the prior section.
- **Datasets**: CVE-2026-57845 (pickle RCE via deprecated pandas packaged builder, `datasets`≤5.1.0) — detailed in the prior section.
- **InvokeAI**: CVE-2024-12029, in the model-install endpoint, fixed in 5.4.3+ — [OffSec](https://www.offsec.com/blog/cve-2024-12029/)

### Inferences
- The single highest-value, most counter-intuitive finding for the skill to surface prominently: **"use `weights_only=True`" was the standard, widely-repeated mitigation advice for `torch.load()` and it was still exploitable (CVE-2025-32434) until PyTorch 2.6.0** — any pentest guidance or detection logic that treats `weights_only=True` as a sufficient control for untrusted `.pt`/`.pth`/`.bin` files is itself outdated unless it also checks the loading environment's PyTorch version.
- **Concrete, stdlib-only addition to the tool**: a one-time, per-run "environment advisory" step (not per-file) using `importlib.metadata.version("torch")`, `importlib.metadata.version("transformers")`, `importlib.metadata.version("onnx")`, `importlib.metadata.version("onnxruntime")`, `importlib.metadata.version("llama-cpp-python")` (wrapped in try/except for packages not installed), compared against a small hardcoded table of first-fixed-version thresholds derived from the CVEs above (`torch<2.6.0`→CVE-2025-32434; `onnx<=1.16.1`→CVE-2024-5187/7776/27318; `llama-cpp-python<0.2.72`→CVE-2024-34359). This is a capability the tool has **zero** coverage for today (it has no awareness of installed library versions at all) and is a cheap, high-signal addition distinct from per-file scanning — it answers "is the thing that's about to load this file itself exploitable," which is a different and complementary question from "is this specific file malicious."
- A static file scanner fundamentally **cannot** detect whether the *target* environment (which may not be the scanning environment at all — e.g., a CI pipeline scanning a model destined for a different production container) runs a vulnerable loader version; the environment check above only covers the case where scan-time and load-time environments coincide. This should be stated as an explicit limitation in the skill's output (e.g., "environment advisory reflects the scanning host's installed versions, not necessarily the deployment target's").

### Gaps
- No single, authoritative, continuously-updated feed enumerating all "model-loading-path" CVEs across these four projects was found; the table compiled here is a manual aggregation from vendor blogs and third-party CVE trackers (SentinelOne, Wiz, stack.watch, OffSec, etc.) rather than a direct NVD/MITRE query, so version-range and severity details should be re-verified against cve.org/NVD directly before being hardcoded into detection logic, especially for the 2026-dated CVEs (many of this research's 2026 sources are themselves recent and could have follow-up corrections).
- Could not confirm a patched version for CVE-2026-57845 (`datasets` pickle RCE) in any source found.
