# Cloud Container/Orchestrator Metadata-Service Endpoints (AWS ECS, Kubernetes/GKE/EKS/AKS, Docker) — Defensive Reference, 2024-2026

## What are AWS's documented ECS task metadata endpoint versions (v2, v3, v4) and the AWS_CONTAINER_CREDENTIALS_RELATIVE_URI credential mechanism? What authentication does it require, and has AWS added AWS_CONTAINER_AUTHORIZATION_TOKEN?

### Takeaway
AWS documents three still-referenced ECS task metadata endpoint generations (v2 = legacy/unmaintained, v3 = superseded, v4 = current) all served from the link-local address `169.254.170.2`, plus a separate task-role credentials endpoint reached via the `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` env var. The credentials endpoint is documented as requiring no network-level auth beyond reachability (it is a plain GET to a link-local/private address), while the newer `AWS_CONTAINER_AUTHORIZATION_TOKEN`/`AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` mechanism is an **AWS SDK/EKS Pod Identity feature**, not something ECS itself sets by default — EKS Pod Identity uses the token-file variant; plain ECS task-role credential retrieval via `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` is not documented as requiring that token.

### Cited Findings
- ECS task metadata endpoint **v2**: served at `169.254.170.2/v2/metadata`, `/v2/metadata/{container-id}`, `/v2/metadata/taskWithTags`, `/v2/stats`, `/v2/stats/{container-id}`; enabled by default for Fargate platform ≥1.1.0 and EC2 `awsvpc` tasks on agent ≥1.17.0 (Linux) / ≥1.54.0 (Windows). AWS's own page states: "The task metadata version 2 endpoint is no longer being actively maintained. We recommend that you update the task metadata version 4 endpoint." — [AWS: Amazon ECS task metadata endpoint version 2](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v2.html)
- ECS task metadata endpoint **v4**: exposed via the `${ECS_CONTAINER_METADATA_URI_V4}` env var; base path returns per-container metadata, `/task` returns task-level metadata (container IDs/names), `/taskWithTags` adds resource tags (via `ListTagsForResource`, noting frequent calls can cause API throttling), `/stats` and `/task/stats` return Docker stats. On Fargate it is on by default for platform version ≥1.4.0; AWS states existing field names/metadata will not be removed (backward-compat guarantee). — [AWS: Amazon ECS task metadata endpoint version 4](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v4.html)
- Task **IAM role credentials** are retrieved by SDKs via `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, which ECS sets automatically when a task IAM role is configured; the value is appended to the fixed ECS credentials host `169.254.170.2`. AWS states: "If you use Amazon ECS, we recommend you use a task IAM Role... When configured, Amazon ECS sets the AWS_CONTAINER_CREDENTIALS_RELATIVE_URI environment variable that the SDKs and tools use to obtain credentials." — [AWS SDKs and Tools Reference Guide: Container credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html)
- `AWS_CONTAINER_AUTHORIZATION_TOKEN` (plain-text token) and `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` (file path to a token) are documented as SDK-level settings: "If this variable is set, the SDK will set the Authorization header on the HTTP request with the environment variable's value." The token-file form takes precedence over the plain-text form if both are set. — [AWS SDKs and Tools Reference Guide: Container credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html)
- Per the same AWS doc, it is **Amazon EKS** (not plain ECS) that sets the full-URI + token-file pair by default: "When configured, Amazon EKS sets the AWS_CONTAINER_CREDENTIALS_FULL_URI and AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE environment variables" as part of **EKS Pod Identity**, which AWS recommends over ECS task roles' older mechanism for "improved credential isolation, least privilege, auditability." — [AWS SDKs and Tools Reference Guide: Container credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html)
- Some AWS SDK versions (Java, .NET, Python/Boto3, when Lambda SnapStart is activated) automatically use `AWS_CONTAINER_CREDENTIALS_FULL_URI` + `AWS_CONTAINER_AUTHORIZATION_TOKEN` for authentication — this is a Lambda SnapStart-specific behavior documented in the SDK compatibility table, not a core ECS agent feature. — [AWS SDKs and Tools Reference Guide: Container credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html)

### Inferences
- The plain ECS-on-EC2 task-role credential retrieval path (`169.254.170.2` + `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`) relies on network-path restriction (only containers on the host can reach the link-local proxy address) rather than a bearer-token/Authorization-header check — this is architecturally weaker than the EKS Pod Identity / token-file model, and is consistent with the ECScape finding below (any process that can reach `169.254.170.2` on a shared EC2 instance can potentially retrieve another task's credentials via the internal ACS protocol, not just its own via the documented relative-URI endpoint).
- AWS has not (as of the documentation reviewed) retrofitted a mandatory `AWS_CONTAINER_AUTHORIZATION_TOKEN` requirement onto the base ECS-on-EC2 task-role credential endpoint; the token mechanism exists at the SDK level and is used by EKS Pod Identity and Lambda SnapStart, but plain ECS task roles continue to be documented without it.

### Gaps
- Could not confirm from official docs whether any specific "recent ECS agent version" release note explicitly added an authorization-token requirement to the classic ECS v2/v3/v4 metadata or credentials endpoints; search results surfaced only the SDK-side feature description, not an ECS-agent changelog entry mandating it. Flagged as a gap rather than asserted.
- Did not independently fetch the v3 endpoint doc page (only v2 and v4 were fetched); v3 behavior is inferred from v2/v4 docs' mutual references (AWS v4 docs describe v4 as functioning "like the v3 endpoint" with added network metadata).

## What does Kubernetes documentation say about the deprecated read-only kubelet port 10255 vs. the authenticated port 10250 — when was 10255 deprecated/removed, and what do security scanners (kube-bench, CIS Benchmark) flag?

### Takeaway
Kubernetes's own kubelet authentication/authorization documentation does not mention port 10255 by number at all in its current form — it describes the authenticated/authorized HTTPS kubelet API generically — while CIS Kubernetes Benchmark checks (mirrored by Tenable/kube-bench-style tooling) consistently flag `--read-only-port`/`readOnlyPort` (10255) as something to set to `0` because it is unauthenticated. No official Kubernetes upstream release note confirming a specific version number that *removed* 10255 was found; it remains a configurable (defaults vary by distro) rather than a hard-removed feature as of the sources reviewed.

### Cited Findings
- The official Kubernetes "Kubelet authentication/authorization" page describes only the secure, authenticated/authorized HTTPS kubelet API: unauthenticated requests are treated as anonymous (`system:anonymous` / group `system:unauthenticated`) unless `--anonymous-auth=false` is set, which causes the kubelet to respond `401 Unauthorized` to such requests; it does not reference port 10255 or 10250 by number. — [Kubernetes docs: Kubelet authentication/authorization](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-authn-authz/)
- The same page documents kubelet **authorization**: default mode is `AlwaysAllow` (permits all requests, authenticated or anonymous); restricting access requires `--authorization-mode=Webhook` so the kubelet calls `SubjectAccessReview` against the API server. It also warns that RBAC `get` on the `nodes/proxy` subresource is not actually read-only because some WebSocket-based endpoints use the `GET` verb to execute commands in containers. — [Kubernetes docs: Kubelet authentication/authorization](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-authn-authz/)
- CIS-benchmark-derived checks (mirrored via Tenable audits across many CIS Kubernetes Benchmark versions, e.g. v1.8.0–v1.20) consistently include "4.2.4 Verify that the --read-only-port argument is set to 0," noting the CIS default assumption is 10255/TCP on the command line, but that kubelet config-file defaults set `readOnlyPort` to 0 (disabled) when a config file is used. — [Tenable CIS Kubernetes v1.20/v1.0.0 Level 1 Worker audit item](https://www.tenable.com/audits/items/CIS_Kubernetes_v1.20_v1.0.0_Level_1_Worker.audit:6422cfe5737a36a4467f65be5809683a)
- A DISA STIG control (CNTR-K8-000330 / related V-242387 findings, mirrored across multiple STIG revisions) states the read-only port provides "no authentication or authorization security control" and calls it deprecated, recommending it be disabled. — [Tenable: DISA STIG Kubernetes audit item](https://tenable.com/audits/items/DISA_STIG_Kubernetes_v2r2.audit:b12a4d742dc626b20d3c582e14755594)
- Managed-Kubernetes vendor behavior: Alibaba Cloud's ACK documentation states it "no longer opens the read-only port 10255 for the kubelet by default" in ACK clusters running Kubernetes 1.26 or later — a vendor default change, not an upstream Kubernetes removal. — [Alibaba Cloud ACK: Replace the monitoring port with the authentication port](https://www.alibabacloud.com/help/en/ack/product-overview/product-updates-replace-the-monitoring-port-with-authentication-port-in-ack-clusters-of-earlier-versions)
- A February 2025 CVE (CVE-2025-0426) specifically targets "the unauthenticated kubelet read-only HTTP endpoint" (i.e., port 10255/the read-only port), where a flood of container checkpoint requests can fill a Node's disk, causing node-level denial of service. Affected kubelet versions per the CVE record: 1.32.0–1.32.1, 1.31.0–1.31.5, 1.30.0–1.30.9 (fixed in later patch releases). — [Red Hat CVE-2025-0426](https://access.redhat.com/security/cve/CVE-2025-0426); [NVD CVE-2025-0426](https://nvd.nist.gov/vuln/detail/CVE-2025-0426)

### Inferences
- The lack of any 10255 reference on the current upstream kubelet-authn-authz doc page suggests Kubernetes' own documentation has moved to describing the authenticated kubelet API generically rather than contrasting it with the legacy read-only port — the read-only port is treated by upstream docs as a kubelet config option (`readOnlyPort: 0` to disable) rather than a deprecated/removed feature with a formal sunset date.
- The persistence of CVE-2025-0426 against the *unauthenticated read-only endpoint* in 2025 (affecting kubelet versions as late as 1.32.1) confirms the port/feature is still present and exploitable in current (2024-2025) kubelet releases when enabled — it has not been removed outright, only recommended-disabled by hardening guidance.

### Gaps
- No official Kubernetes upstream changelog/release-notes entry was found confirming a specific version number where `--read-only-port`/10255 was deprecated or removed as a kubelet flag; only third-party CIS/STIG/vendor mirrors were available in search results. This should be verified directly against kubernetes/kubernetes GitHub changelogs if a precise version number is required.
- Whether kube-bench's current (2024-2026) default profile still includes a check number for the read-only port was not independently confirmed from kube-bench's own GitHub docs — only CIS Benchmark PDF/Tenable mirrors were reviewed.

## What does Kubernetes documentation say about the anonymous-auth API server flag and its current (2024-2026) default state?

### Takeaway
`--anonymous-auth` (kube-apiserver and kubelet) defaults to `true` as of the sources reviewed, and this had **not changed** through 2024; Kubernetes is in the process (via KEP-4633) of adding finer-grained control (restricting anonymous auth to specific endpoints like health checks) rather than flipping the overall default to `false`.

### Cited Findings
- KEP-4633 ("Only allow anonymous auth for configured endpoints") explicitly states anonymous-auth is `true` by default, and that the KEP's structured `AuthenticationConfiguration` mechanism "does not change kubernetes default behavior around anonymous authentication" — it only adds a way to scope anonymous access to specific endpoints (e.g., `/healthz`, `/livez`, `/readyz`) while still defaulting to broad anonymous access otherwise. Milestones: Alpha v1.31, Beta v1.32, Stable v1.34. — [Kubernetes Enhancements: KEP-4633](https://www.kubernetes.dev/resources/keps/4633/)
- On the kubelet side, the official kubelet-authn-authz doc confirms unauthenticated requests are treated as anonymous (`system:anonymous`/`system:unauthenticated`) unless explicitly disabled with `--anonymous-auth=false`, implying `true` is the operative default absent explicit configuration. — [Kubernetes docs: Kubelet authentication/authorization](https://kubernetes.io/docs/reference/access-authn-authz/kubelet-authn-authz/)
- CIS Benchmark checks (mirrored across versions v1.1.0 through v1.8.0+) have long included "1.2.1 Ensure that the --anonymous-auth argument is set to false" for the kube-apiserver, implying the CIS auditors' own assumption that the shipped/common default is `true` (enabled) and must be explicitly hardened. — [Tenable CIS Kubernetes audits](https://tenable.com/audits/items/CIS_Kubernetes_v1.8.0_Level_1_Master.audit:d7c0c468c30e7c412883d0ccaed0a1ad)
- A related MetalK8s GitHub pull request notes that the new per-endpoint anonymous-auth mechanism depends on the `AnonymousAuthConfigurableEndpoints` and `StructuredAuthenticationConfiguration` feature gates, both beta and **on by default in Kubernetes 1.32** — indicating the finer-grained control became usable by default starting 1.32, though the overall anonymous-auth default itself remains `true`. — [MetalK8s PR #4900](https://github.2158297754.workers.dev/scality/metalk8s/pull/4900)

### Inferences
- As of 2024-2026, Kubernetes has not changed the historical insecure-by-default posture of `--anonymous-auth=true`; it has instead built tooling (KEP-4633) to let cluster operators narrow anonymous access to health-check-style endpoints without disabling it cluster-wide, meaning operators must still explicitly set `--anonymous-auth=false` (or configure `authentication.anonymous.enabled: false` with endpoint carve-outs) to harden a cluster — this remains an active, current finding for a security scanner to flag.

### Gaps
- Could not retrieve the primary kube-apiserver command-line reference page's explicit "Default: true" field text directly (only secondary/CIS-mirror confirmation); recommend the report writer treat the `true` default as well-supported by KEP-4633 and CIS checks but not quoted verbatim from the kube-apiserver flag reference page itself.

## What do GKE and EKS's own security docs recommend regarding blocking node-level cloud metadata access from pods?

### Takeaway
GKE's current official guidance is that **metadata concealment is a deprecated/beta stopgap** and the vendor now directs all users toward **Workload Identity Federation for GKE** as the actual fix; GKE does not document a network-level (firewall/NetworkPolicy) control for this in its "Protecting cluster metadata" page. EKS's documented mitigations for blocking pod access to the EC2 Instance Metadata Service (IMDS) center on **VPC CNI network policies** (which must be explicitly enabled) and the **IMDSv2 hop-limit** control, per AWS's EKS and whitepaper guidance.

### Cited Findings
- GKE "Protecting cluster metadata" doc: metadata concealment (`--workload-metadata=SECURE`) is explicitly labeled **Beta and uses a deprecated option**; it blocks user Pods from reading `kube-env` (kubelet credentials) and the VM instance identity token, but "doesn't restrict access to the node's service account," doesn't cover legacy metadata APIs, and does not apply to Pods using `hostNetwork: true`. — [Google Cloud: Protecting cluster metadata](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/protecting-cluster-metadata)
- Quote: Google's documentation states operators "should use Workload Identity Federation for GKE instead of metadata concealment in all situations," and that Workload Identity Federation "replaces the need to use metadata concealment" since it protects the same sensitive metadata; the two approaches are documented as incompatible with each other. — [Google Cloud: Protecting cluster metadata](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/protecting-cluster-metadata)
- The same GKE page recommends, as a complementary control, using a **least-privilege node service account** instead of the Compute Engine default service account, specifically warning against granting roles/permissions like `compute.instances.get` or Compute Instance Admin that would let an attacker read instance metadata via the Compute Engine API even if pod-level metadata access is blocked. — [Google Cloud: Protecting cluster metadata](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/protecting-cluster-metadata)
- GKE's legacy metadata endpoints (`v0.1`, `v1beta1`) were shut down by Google; the same GKE doc confirms these should be avoided/are no longer functional. (See also the dedicated v0.1/v1beta1 deprecation finding below.)
- For EKS, AWS's "Limit Pod traffic with Kubernetes network policies" documentation states Kubernetes network policy enforcement is **not on by default** — the VPC CNI add-on must be explicitly configured/updated to a recent version to enforce it; enforcement applies only to Amazon Linux nodes (not Fargate or Windows nodes), and standalone pods without a controller may not be reliably enforced. — [AWS EKS: Limit Pod traffic with Kubernetes network policies](https://docs.aws.amazon.com/eks/latest/userguide/cni-network-policy.html)
- The AWS "Security practices for multi-tenant SaaS applications on EKS" whitepaper documents two concrete mitigations to block pod access to IMDS: (1) a network policy (enforced via VPC CNI or Calico) that blocks the `169.254.0.0/16` link-local range, and (2) requiring **IMDSv2 with a hop limit of 1**, which causes requests from containers (an extra network hop beyond the host) to be rejected unless the pod uses host networking. — [AWS Whitepaper: Restrict host networking and block access to instance metadata service](https://docs.aws.amazon.com/whitepapers/latest/security-practices-multi-tenant-saas-applications-eks/restrict-the-use-of-host-networking-and-block-access-to-instance-metadata-service.html)
- The same AWS network-policy documentation notes pods authenticating via IAM Roles for Service Accounts (IRSA) or EKS Pod Identity do not need to reach IMDS at all, while pods relying on the node's own instance role may need an explicit allow-rule carved out of any IMDS-blocking policy. — [AWS EKS: Limit Pod traffic with Kubernetes network policies](https://docs.aws.amazon.com/eks/latest/userguide/cni-network-policy.html)

### Inferences
- GKE's framing ("deprecated option," "should use... in all situations") signals Workload Identity is the only control Google is actively maintaining for this risk class; a scanner should treat metadata concealment as legacy/insufficient and flag clusters relying on it alone.
- EKS's mitigation story is more fragmented than GKE's: there is no single "flip this one setting" fix documented by AWS — it's either (a) move workloads off node IAM roles entirely (IRSA/Pod Identity), (b) enforce VPC CNI/Calico NetworkPolicy against the metadata CIDR, or (c) rely on IMDSv2 hop-limit=1, each with coverage gaps (NetworkPolicy enforcement gaps for non-Amazon-Linux nodes/standalone pods; hop-limit only blocks non-host-network pods).

### Gaps
- Did not locate a page explicitly titled "EKS Best Practices Guide" with first-party text on this exact topic in search results (only the EKS user-guide NetworkPolicy page and a general security whitepaper were retrieved) — recommend treating the whitepaper and network-policy doc as representative of current (2024-2026) AWS first-party guidance, but note the EKS Best Practices Guide itself was not directly fetched.
- Azure AKS was named in the assignment's provider list (GKE/EKS/AKS) but no official AKS-specific metadata-blocking documentation was retrieved in this research pass — this is a gap; AKS's IMDS-blocking guidance (if any, likely also network-policy/hop-limit based, analogous to EKS, since AKS nodes also expose Azure IMDS at 169.254.169.254) should be separately verified.

## What does GCP's metadata server documentation say about the legacy v1beta1 API and the Metadata-Flavor header requirement?

### Takeaway
Google's metadata server legacy `v0.1` and `v1beta1` endpoints were deprecated September 30, 2019 and fully shut down September 30, 2020; they are documented as not having required the `Metadata-Flavor: Google` header, whereas the current `v1` API requires that header on every request and denies requests without it.

### Cited Findings
- Google's Compute Engine deprecation reference page lists `v0.1` and `v1beta1` metadata server endpoints as deprecated effective 2019-09-30 and shut down (no longer functioning) as of 2020-09-30. — [Google Cloud: v0.1 and v1beta1 metadata server endpoints deprecation](https://docs.cloud.google.com/compute/docs/deprecations/v0.1-v1beta1-metadata-server)
- Google's current metadata query documentation states that, on the `v1` API, a request without the `Metadata-Flavor: Google` header is denied by the metadata server. — [Google Cloud: View and query VM metadata](https://docs.cloud.google.cn/compute/docs/metadata/querying-metadata)
- Third-party/scanner documentation (Aqua's Trivy/avd misconfiguration docs) characterizes the legacy `v0.1`/`v1beta1` endpoints as not enforcing the metadata-flavor header check that `v1` enforces, which is why SSRF-style requests against legacy endpoints historically bypassed the header-based CSRF-style protection — however, this specific no-header-check characterization is sourced to third-party scanner documentation, not a Google first-party statement, in the results reviewed.

### Inferences
- Because the legacy endpoints are fully shut down (since Sept 2020), a defensive scanner checking live GCP metadata servers in 2024-2026 should not expect `v0.1`/`v1beta1` requests to succeed at all; any residual code/scripts targeting those paths are checking for a already-closed attack surface on GCP's actual metadata service, though they may remain relevant for documentation/training purposes or for other API surfaces that mimic the old GCE metadata format.

### Gaps
- Did not find a Google first-party statement explicitly confirming legacy endpoints never checked the Metadata-Flavor header (this detail is sourced only to third-party scanner docs/Trivy); flagged as secondary-sourced rather than primary-confirmed.

## CVE IDs (2023-2026) associated with kubelet unauthenticated access, ECS metadata/credential exposure, or GKE metadata server

### Takeaway
Two concrete, numbered CVEs were confirmed via official/near-official records (CVE-2025-0426 for the kubelet read-only endpoint, and CVE-2022-3294 for a kube-apiserver node-proxy validation bypass that predates the 2023-2026 window but remains relevant/still-cited); the high-profile "ECScape" ECS flaw (2025) was explicitly **not** assigned a CVE by AWS, which classified it as a design/configuration consideration rather than a vulnerability. No dedicated CVE for "GKE metadata server" exposure itself was found — that risk is treated by Google and scanners as a configuration/architecture issue (addressed via Workload Identity), not a patched CVE.

### Cited Findings
- **CVE-2025-0426** — Kubernetes kubelet: "a large number of container checkpoint requests made to the unauthenticated kubelet read-only HTTP endpoint may cause a Node Denial of Service by filling the Node's disk." Published to NVD 2025-02-13; affected kubelet version ranges 1.30.0–1.30.9, 1.31.0–1.31.5, 1.32.0–1.32.1 (fixed in subsequent patch releases); Red Hat's mirrored description matches in substance. CVSS scores differ by source (Red Hat CVSSv3 ≈6.2; Tenable CVSSv2 4.9/Medium); NVD's analysis status is noted as deferred/awaiting-analysis in some mirrors. — [Red Hat: CVE-2025-0426](https://access.redhat.com/security/cve/CVE-2025-0426); [NVD: CVE-2025-0426](https://nvd.nist.gov/vuln/detail/CVE-2025-0426)
- **CVE-2022-3294** — Kubernetes kube-apiserver: node address validation bypass allowing authenticated requests directed at Nodes to reach otherwise-private/secure endpoints in the control-plane network (Red Hat phrasing: "users may have access to secure endpoints in the control plane network"); classified by the Kubernetes advisory as an improper-authentication issue, CWE-20 (Improper Input Validation) per NVD. CVSS 3.1 base score 8.8 (High) per Aqua's NVD mirror. Published 2023-03-01; fixed in Kubernetes 1.22.16, 1.23.14, 1.24.8, 1.25.4+. Exploitability requires an untrusted actor able to modify Node objects and issue proxy requests to them. — [Red Hat: CVE-2022-3294](https://access.redhat.com/security/cve/CVE-2022-3294); [NVD: CVE-2022-3294](https://nvd.nist.gov/vuln/detail/CVE-2022-3294)
- **"ECScape" (Amazon ECS, disclosed August 2025 at Black Hat USA by Sweet Security researcher)** — not a numbered CVE per the sources reviewed. A container on an EC2-backed ECS task can read the host's IMDS-provided EC2 instance-role credentials, then use them to impersonate the ECS agent on an undocumented internal WebSocket channel (the "Agent Communication Service," ACS) and obtain other co-located tasks' IAM application-role and execution-role credentials — without a container-escape. Fargate is not affected (no instance co-tenancy). AWS reviewed the finding through its coordinated-disclosure program and **classified it as a design consideration/configuration risk rather than a vulnerability**, and did not assign a CVE; AWS's guidance in response includes moving to Fargate, least-privilege task-role policies, restricting IMDS access, and CloudTrail monitoring. — [TheHackerNews: Researchers Uncover ECScape Flaw in Amazon ECS](https://thehackernews.com/2025/08/researchers-uncover-ecscape-flaw-in.html); [CSOonline: ECScape new AWS ECS flaw](https://www.csoonline.com/article/4036655/ecscape-new-aws-ecs-flaw-lets-containers-hijack-iam-roles-without-breaking-out.html)
- No GKE-metadata-server-specific CVE number was found in the sources reviewed. Related risk (legacy node metadata exposing kubelet credentials/instance identity tokens to pods, exploitable via a separate SSRF bug in application code, as in the 2018 Shopify bug-bounty case referenced in community talks) is documented by Google and scanners (Tenable, Aqua/tfsec, Checkov `CKV_GCP_67`, Datadog) as a **misconfiguration to detect**, not a vendor-patched CVE. — [Orca Security: Cloud Risk Encyclopedia – GKE legacy metadata APIs](https://orca.security/resources/cloud-risk-encyclopedia/gke-nodepool-with-legacy-compute-engine-instance-metadata-apis)

### Inferences
- The pattern across all three vendor responses (AWS/ECScape, Google/GKE legacy metadata, and to an extent Kubernetes/CVE-2025-0426 scored only Medium) suggests these metadata-service designs are generally treated by vendors as "insecure-by-default architecture requiring explicit hardening" rather than as patchable vulnerabilities — meaning a defensive scanner's primary value is in **configuration detection** (is the read-only port open? is metadata concealment/Workload Identity enabled? is IMDSv2 hop-limit set? is the ECS task on EC2 vs. Fargate?) rather than in CVE-signature matching.

### Gaps
- Could not confirm whether a CVE identifier was ultimately issued for ECScape after the disclosure (one source said "a CVE ID has been requested"); this should be re-checked against NVD closer to publication, as status may have changed since the August 2025 disclosure.
- No EKS-specific (as opposed to generic Kubernetes) CVE for metadata/IMDS exposure was identified in this research pass.
- No AKS-specific metadata-service CVE was identified; this is a gap for the Azure portion of the assignment's scope.

## Docker (standalone, non-orchestrated) metadata-service exposure — supplementary note

### Takeaway
Docker does not run its own "metadata service"; the relevant risk is a plain Docker container on a cloud VM (EC2/GCE/Azure VM) reaching that **cloud provider's** instance metadata service at `169.254.169.254`. Whether this succeeds depends on Docker's network mode and, for AWS, the IMDSv2 hop-limit setting — this is cloud-vendor and container-runtime interaction behavior rather than a Docker-documented feature, so no single "Docker's own doc page" authoritatively covers it; findings below are best-effort from AWS/vendor and reputable secondary sources since no single primary doc was found.

### Cited Findings
- A container using Docker's default **bridge** network mode is, per community/vendor guidance, blocked from reaching the instance metadata service once IMDSv2's default hop limit is set to 1 (the extra network hop through the bridge exceeds the limit); containers using **host** network mode share the host's network namespace and can reach it directly. AWS's own Latacora-reported testing (cited secondarily) found bridge-mode ECS tasks could not reach IMDS with hop-limit=1, while `awsvpc` and host-network tasks could. — [Latacora: ECS on EC2 — Covering Gaps in IMDS Hardening](https://www.latacora.com/blog/2025/10/02/ecs-on-ec2-covering-gaps-in-imds-hardening/) (secondary source; no single Docker-first-party doc confirms this behavior directly)
- Defensive hardening pattern: adding an iptables rule in the `DOCKER-USER` chain to block container traffic to `169.254.169.254` is a commonly documented technique (e.g., Palo Alto Cortex Cloud's Docker network-hardening guide) for explicitly denying metadata access regardless of network mode. — [Palo Alto Cortex: Docker network hardening guide](https://cortex-docs.paloaltonetworks.com/cortex-cloud-runtime-security/cases-and-issues/investigation-and-response/automation/engines/install-an-engine/docker/docker-hardening-guide/docker-network-hardening.md)

### Inferences
- For a defensive scanner's purposes, "Docker" metadata risk should be modeled as a function of (a) which cloud VM the Docker host runs on, (b) the container's network mode (bridge vs. host vs. custom), and (c) that cloud's IMDS version/hop-limit configuration — not as a distinct Docker-specific endpoint inventory item.

### Gaps
- No official Docker Inc. documentation page was found that directly addresses cloud-metadata-service reachability from containers; all findings here are sourced to AWS whitepapers/blog posts and third-party hardening guides, not Docker's own docs. This should be flagged to the report writer as the weakest-sourced section of this inventory.
