# Current (2024-2026) State of Subdomain-Takeover-Vulnerable Service Fingerprints

## Q1: What is the current status of EdOverflow's can-i-take-over-xyz repo, and which services changed status via recent PRs/issues since 2023?

### Takeaway
The repo is still the de-facto canonical fingerprint source and is still loosely maintained (fingerprints.json is machine-readable and consumed by subzy/subjack/subtake), but its own CI/CD verification is failing for the large majority of entries (only 16 of 76 show a passing automated check), and at least one entry (Bitbucket) has an open, unresolved issue questioning whether its "Vulnerable" status is stale. Netlify, Vercel, Heroku, Shopify, GitHub, Tumblr, Webflow, Wix, Intercom, Frontify, Landingi, Mashery, Smartling, and Tilda are all marked the ambiguous **"Edge case"** status rather than a clean Vulnerable/Not-vulnerable, meaning exploitability is conditional and a tool must not treat these as unconditional positives.

### Cited Findings
- The current README table (76 entries) lists per-service status as one of Vulnerable / Not vulnerable / Edge case, with a CI/CD-verification column; only entries marked 🟩 (16 of 76: AWS/Elastic Beanstalk, AWS/S3, Airee.ru, Anima, Bitbucket, Discourse, HatenaBlog, Help Juice, Help Scout, Helprace, Microsoft Azure, SmartJobBoard, Strikingly, Surge.sh, SurveySparrow, Uberflip, Wordpress, Worksites) currently pass automated fingerprint verification — [can-i-take-over-xyz README](https://github.com/EdOverflow/can-i-take-over-xyz)
- Statuspage is explicitly annotated in the current table as having "Added DNS verification to prevent malicious takeovers," and its status is Not vulnerable with an empty fingerprint — [can-i-take-over-xyz README](https://github.com/EdOverflow/can-i-take-over-xyz)
- Open issue #97 on the repo asks whether Bitbucket still supports CNAME-based custom domains at all ("it appears that bitbucket doesn't support this anymore"); the suggested resolution is to re-verify against current Bitbucket docs and deprecate the entry if CNAME support was dropped, but this had not been resolved at last check — [goodfirstissue.org mirror of issue #97](https://www.goodfirstissue.org/EdOverflow/can-i-take-over-xyz/issues/97)
- Despite that open doubt, the live `fingerprints.json` still lists Bitbucket as `"status": "Vulnerable"`, `"cname": ["bitbucket.io"]`, `"fingerprint": "Repository not found"` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- A January 2024 commenter on the repo's Vercel-tracking discussion argued Vercel is "no longer vulnerable" because a TXT verification record is now required to attach a custom domain, but another commenter disputed this and a June 2024 commenter asked why the status had not been updated; the table still lists Vercel as "Edge case," not "Not vulnerable," reflecting this unresolved dispute — [github.meowingcats01.workers.dev mirror of issue #183](https://github.meowingcats01.workers.dev/EdOverflow/can-i-take-over-xyz/issues/183)
- Multiple third-party forks/mirrors of the project exist (bradparks, samhaxr, dsopas, acealchemycyberblaze, vsec7), indicating community interest in keeping copies current, but none were confirmed as an actively-maintained "successor" with its own independent updates beyond mirroring upstream — [awesome.ecosyste.ms listing](https://awesome.ecosyste.ms/projects/github.com%2FEdOverflow%2Fcan-i-take-over-xyz)

### Inferences
- The "Edge case" status should be treated by a detection tool as **"requires additional confirmation beyond CNAME+fingerprint match"** (e.g., checking whether a sibling/parent domain is already claimed in the target's account), not as a binary vulnerable/not-vulnerable flag — shipping these as hard positives will generate false positives on Netlify, Vercel, Heroku, Shopify, GitHub Pages, Tumblr, Webflow, Wix, and Intercom.
- Because CI/CD verification is failing (🟥) for the large majority of "Vulnerable" entries, the repo's automated checker itself cannot currently confirm most of its own claims live — this is a maintenance/signal-quality gap a tool builder should flag, not blindly trust.

### Gaps
- No official changelog or dated commit history was retrieved confirming exact PR/issue numbers and merge dates for status changes since 2023 (e.g., when Statuspage's DNS-verification note was added, or the exact commit that changed any entry's status). Repo activity snapshots found (via secondary directory sites) show a last push around 2025-02-08, but this could not be independently verified against the live GitHub commit log in this session.
- Could not confirm whether a community fork has diverged with materially different/updated content from upstream (only mirror listings were found, not diffed content).

## Q2: Current exploitability of AWS S3, CloudFront, Azure, GCP (Storage/App Engine/Firebase), Heroku, GitHub Pages, Fastly, Shopify, Zendesk, Netlify, Vercel — have any been patched since 2023?

### Takeaway
Fastly, Zendesk, CloudFront, Google Cloud Storage, Firebase, and AWS ELB are all currently listed **Not vulnerable** with concrete negative fingerprints. AWS S3 and Azure remain **Vulnerable** by the canonical list, but AWS S3 now has a 2025-2026 opt-in mitigation (account-regional "-an" buckets) that is excluded from the nuclei detection regex — meaning the classic takeover is still live for ordinary global-namespace buckets. Netlify, Vercel, Heroku, Shopify, and GitHub Pages remain in the ambiguous "Edge case" bucket — real-world claims of being "fixed" from Netlify/Vercel are **not substantiated by an official security advisory**; what exists is account/domain-verification (TXT record) friction that raises the bar but does not categorically eliminate takeover on all paths.

### Cited Findings
- **AWS/S3**: status "Vulnerable", `cname: ["s3.amazonaws.com"]`, fingerprint `"The specified bucket does not exist"`, `nxdomain: false` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- AWS shipped **account-regional namespaces** for S3 (bucket names scoped to account+region, suffixed `-an`) in 2026; these account-regional bucket names "can never be re-created by another account, even after deletion," but this is opt-in and only applies to newly created buckets — existing global-namespace buckets are unaffected and cannot be migrated/renamed into the new namespace — [CloudSecurityAlliance Labs: Cloud Namespace Hijacking](https://labs.cloudsecurityalliance.org/research/cloud-security-global-namespace-hijacking-systemic-risk-v1-c/); [InfoQ: S3 account regional namespaces](https://www.infoq.com/news/2026/03/s3-account-regional-namespaces)
- ProjectDiscovery's current `aws-bucket-takeover.yaml` nuclei template explicitly **excludes** hosts matching the new account-regional naming convention via a negative regex: `^[a-z0-9][a-z0-9-]+-[0-9]{12}-[a-z0-9-]+-an\.s3\.[a-z0-9-]+\.amazonaws\.com` — confirming that the maintained detection tooling itself treats only non-"-an" buckets as exploitable, and still matches on the body strings `"The specified bucket does not exist"` and `"BucketName"` — [nuclei-templates/http/takeovers/aws-bucket-takeover.yaml](https://raw.githubusercontent.com/projectdiscovery/nuclei-templates/main/http/takeovers/aws-bucket-takeover.yaml)
- The "Bucket Monopoly"-style predictable-bucket-name risk (e.g., CloudFormation `cf-templates-{hash}-{region}`, Elastic Beanstalk `elasticbeanstalk-{region}-{accountid}`) persists for service-auto-created buckets regardless of the new namespace feature — [DEV.to: S3 bucket names global nightmare, AWS fixed it](https://dev.to/nikita_purohit/s3-bucket-names-were-a-global-nightmare-aws-finally-fixed-it-4dce); [Cloud Security Alliance Labs](https://labs.cloudsecurityalliance.org/research/cloud-security-global-namespace-hijacking-systemic-risk-v1-c/)
- **AWS/Elastic Beanstalk**: status "Vulnerable", `cname: ["elasticbeanstalk.com"]`, fingerprint `"NXDOMAIN"`, `nxdomain: true` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **AWS/ELB**: status "Not vulnerable", `cname: ["elb.amazonaws.com"]`, `nxdomain: true` but marked not vulnerable (NXDOMAIN on ELB names is not independently claimable) — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **CloudFront**: status "Not vulnerable", fingerprint `"ViewerCertificateException"` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **Microsoft Azure**: status "Vulnerable" (one of the few 🟩 CI-verified entries), with a long list of vulnerable CNAME suffixes: `cloudapp.net`, `cloudapp.azure.com`, `azurewebsites.net`, `blob.core.windows.net`, `azure-api.net`, `azurehdinsight.net`, `azureedge.net`, `azurecontainer.io`, `database.windows.net`, `azuredatalakestore.net`, `search.windows.net`, `azurecr.io`, `redis.cache.windows.net`, `servicebus.windows.net`, `visualstudio.com`; fingerprint is simply `"NXDOMAIN"` (`nxdomain: true`) — i.e., confirmation is via NXDOMAIN resolution of the CNAME target, not an HTTP body — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json); Microsoft's own docs independently describe this exact dangling-DNS/deprovisioned-resource pattern as a live risk class for Azure resources — [Microsoft Learn: Subdomain takeover](https://learn.microsoft.com/azure/security/fundamentals/subdomain-takeover)
- **Google Cloud Storage**: status "Not vulnerable", fingerprint is the literal XML error body `<?xml version='1.0' encoding='UTF-8'?><Error><Code>NoSuchBucket</Code><Message>The specified bucket does not exist.</Message></Error>` — listed Not vulnerable despite returning this error, implying GCS bucket names are not as freely re-claimable as S3's in the current assessment — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **Firebase**: status "Not vulnerable", fingerprint empty string — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json). Separately, Firebase changed default Cloud Storage bucket naming (new projects since 2024-10-30 use `PROJECT_ID.firebasestorage.app` instead of `PROJECT_ID.appspot.com`), and from 2026-02-02 non-Blaze-plan projects lose read/write access to the legacy `appspot.com` default bucket — this is a billing/access change, not a documented anti-takeover fix, but could incidentally reduce dangling-bucket exposure for the legacy naming scheme — [Firebase: FAQ storage changes announced Sept 2024](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)
- **Fastly**: status "Not vulnerable", fingerprint `"Fastly error: unknown domain:"` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **Zendesk**: status "Not vulnerable", fingerprint `"Help Center Closed"` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **Heroku**: status "Edge case", fingerprint `"No such app"` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **Shopify**: status "Edge case", fingerprint `"Sorry, this shop is currently unavailable."` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json)
- **GitHub (Pages)**: status "Edge case", fingerprint `"There isn't a GitHub Pages site here."`; the maintained nuclei template also matches alternate bodies `"For root URLs (like http://example.com/) you must provide an index.html file"`, `"The site configured at this address does not contain the requested file."`, and explicitly excludes hosts containing `githubapp.com`, `github.com`, `github.io` from being flagged (to avoid matching GitHub's own domains) — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json); [nuclei-templates/github-takeover.yaml](https://raw.githubusercontent.com/projectdiscovery/nuclei-templates/main/http/takeovers/github-takeover.yaml). GitHub does offer optional domain verification (TXT record at `_github-challenge.<domain>`) as a defensive measure for repo owners, but this is opt-in per-account, not a platform-wide fix, and critics note the underlying wildcard/dangling-CNAME claim mechanism is unchanged — [GitHub Docs: Verifying your custom domain for GitHub Pages](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/verifying-your-custom-domain-for-github-pages)
- **Netlify**: status "Edge case", fingerprint `"Not Found - Request ID:"` — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json). No official Netlify advisory/changelog documenting a platform-side anti-takeover fix was found; in practice Netlify requires a TXT record (`verified-for-netlify`) to resolve "domain already managed by another team" conflicts, and active real-world takeover reports against Netlify-hosted domains continued to surface in community forums (e.g., a reported takeover of `developer.reserve.org` pointing to Netlify) — [Netlify Community: Unauthorised Netlify project has taken over my subdomain](https://answers.netlify.com/t/unauthorised-netlify-project-has-taken-over-my-subdomain/168458); [Canny: Security Report — Subdomain Takeover pointing to Netlify](https://reserve.canny.io/defi-surfaces-bug-reporting/p/security-report-subdomain-takeover-of-http-wwwdeveloperreserveorg-pointing-to-ne)
- **Vercel**: status "Edge case", fingerprint `"DEPLOYMENT_NOT_FOUND."` (note: `cname` field in the current fingerprints.json is malformed/placeholder — `["https://nonexistent-example.vercel.com/"]` rather than a real CNAME suffix like `vercel.app` or `cname.vercel-dns.com`; a detection tool should not use this field verbatim and should instead match on `vercel.app`/`vercel-dns.com` CNAME suffixes with the `DEPLOYMENT_NOT_FOUND` body) — [fingerprints.json](https://raw.githubusercontent.com/EdOverflow/can-i-take-over-xyz/master/fingerprints.json). Vercel's 2024 "more secure deployment protection" changelog entry extended Standard Deployment Protection to auto-generated domains, but this is about access control to deployments, not a fix for dangling custom-domain CNAMEs — [Vercel Changelog: More secure deployment protection](https://vercel.com/changelog/more-secure-deployment-protection). A live bug-bounty report (`proxies.sifchain.finance` pointing to Vercel) and ongoing Vercel Community threads about "subdomain already used by another team after project deletion" indicate the underlying claim/reassignment behavior is still exploitable in some configurations as of 2024-2025 — [bugboard.rsecloud.com report](https://bugboard.rsecloud.com/report/1487793); [Vercel Community: subdomain already used by another team](https://community.vercel.com/t/vercel-subdomain-already-used-by-another-team-after-project-deletion/36016)

### Inferences
- Treat **Netlify and Vercel's public "we fixed it" posture as unproven at the platform level**: both now require some form of domain/TXT ownership verification before a custom domain becomes "active" within an account, which blocks the simplest "just add the same custom domain to my new free account" claim path for domains that were already verified-bound to an owner. However, neither company has published a dedicated security advisory stating dangling-CNAME takeover is categorically impossible, and both still show live community reports of exactly this failure mode in 2024-2025. A detection tool should keep Netlify/Vercel fingerprints as **"Edge case — confirm manually before reporting,"** not silent-drop them, and not report them as auto-confirmed high severity either.
- AWS S3 should be flagged in any 2024-2026 tool as: **vulnerable only for buckets not already following the new `-an` account-regional naming scheme**; the regex exclusion used by ProjectDiscovery's own maintained template is the right model to copy.
- GCP (Cloud Storage, Firebase) and Fastly/Zendesk/CloudFront should be treated as **negative/suppressed fingerprints** in 2024-2026 tooling — matching their error strings should NOT be scored as exploitable; they exist in fingerprint lists only to avoid false positives (i.e., "if you see this string, it is NOT exploitable").

### Gaps
- No primary-source Netlify or Vercel security advisory/blog post was found explicitly confirming or denying a platform-wide subdomain-takeover fix; all evidence is indirect (community forum behavior, third-party commentary, one disputed GitHub issue thread). This should be called out to the report writer as an open question requiring the pentest tool to verify empirically per-engagement rather than trust vendor claims.
- Could not independently confirm Firebase's current live fingerprint behavior (the JSON entry has an empty fingerprint string, suggesting the upstream project itself lacks a concrete confirmed string for Firebase).

### Inferences
- A 2024-2026 takeover-detection module should pull its fingerprint corpus primarily from **ProjectDiscovery's nuclei-templates `http/takeovers/` directory** (actively maintained, template-per-service, each with explicit matchers/negative-matchers) rather than solely from the static `fingerprints.json`, since nuclei's templates include dozens of newer niche SaaS services (Wasabi, AfterShip, AnnounceKit, Aha!, GitBook, Framer, Clever, Flexbe, GoHire, GreatPages, JazzHR, Proposify, Redirect.Pizza, Simplebooklet, Softr, Sprintful, Squadcast, Tave, Teamwork, Vend, Wishpond, Wufoo) not present in the original 2017-era table, and because nuclei templates often encode negative/exclusion matchers (e.g., the AWS `-an` namespace exclusion, the GitHub `github.com`/`github.io`/`githubapp.com` self-domain exclusion) that materially reduce false positives compared to a flat string-match approach.
- Render, Railway, and Cloudflare Pages should be treated as **unconfirmed/no-current-evidence** for dangling-CNAME takeover rather than being added to a "confirmed vulnerable" list; a tool could still probe their default domains for generic 404/"not found" patterns as a heuristic, but should mark results as low-confidence pending a primary-source bug bounty or vendor disclosure.

### Gaps
- Could not fully retrieve the Silent Push Danglegeddon 2026 PDF directly (exceeded fetch size limit); findings above rely on secondary press coverage (SecurityWeek, EMA) rather than the primary report text, so exact service-by-service findings from that report (if any) could not be extracted.
- No primary source was found specifically confirming or denying Render.com's post-deletion custom-domain reclaim behavior — this is a real gap for the target service list and should be independently tested empirically (e.g., register a throwaway Render service, bind a custom domain, delete the service, and attempt to re-register the same subdomain under a second account) rather than inferred from documentation.
- Cloudflare Pages takeover status is likewise unconfirmed either way from any source found; Cloudflare's own custom-domain verification flow was not directly examined in this session.

## Implementation Notes for the Detection Module (cross-cutting, not tied to a single key question)

- **Confirmation logic should branch on `nxdomain` vs HTTP-body fingerprint**, matching the upstream schema: services like Azure (`"NXDOMAIN"`, `nxdomain: true`) and AWS Elastic Beanstalk (`"NXDOMAIN"`, `nxdomain: true`) are confirmed by resolving the CNAME target and observing NXDOMAIN, not by an HTTP request/response at all — attempting an HTTP fetch against a CNAME target that doesn't even resolve will simply fail/timeout and should not be conflated with an HTTP-fingerprint miss. All other listed services use an HTTP status/body string fingerprint.
- **Negative/suppression fingerprints matter as much as positive ones.** Current data for Fastly (`"Fastly error: unknown domain:"`), Zendesk (`"Help Center Closed"`), CloudFront (`"ViewerCertificateException"`), Google Cloud Storage (the `NoSuchBucket` XML body), Firebase, GCP services generally, AWS ELB, and Statuspage should all be coded as **non-exploitable fingerprints** (match = confirmed NOT vulnerable) in the 2024-2026 ruleset, reversing what a naive 2018-era "any error body = vulnerable" heuristic would conclude.
- **AWS S3 exclusion regex to copy verbatim** (from the live nuclei template) to avoid false-positiving on the new protected bucket namespace: a host matching `^[a-z0-9][a-z0-9-]+-[0-9]{12}-[a-z0-9-]+-an\.s3\.[a-z0-9-]+\.amazonaws\.com` should be excluded from an S3-takeover-vulnerable verdict even if it returns `"The specified bucket does not exist"` — [nuclei-templates/aws-bucket-takeover.yaml](https://raw.githubusercontent.com/projectdiscovery/nuclei-templates/main/http/takeovers/aws-bucket-takeover.yaml)
- **"Edge case" services (Netlify, Vercel, Heroku, Shopify, GitHub Pages, Tumblr, Webflow, Wix, Intercom, Frontify, Landingi, Mashery, Smartling, Tilda) require secondary confirmation** beyond fingerprint match — e.g., actually attempting to register/claim the subdomain on the provider (where permitted and in-scope/authorized) before reporting high severity, since the provider's error page alone does not guarantee an unclaimed/claimable namespace in the current (TXT/domain-verification-hardened) account models these platforms now use.
