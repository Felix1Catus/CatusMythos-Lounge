# AWS IMDSv2 Bypass Edge Cases and SSRF Techniques (2024-2026)

## What is the exact mechanism behind the "misconfigured proxy adds a hop" bypass, and what hop-limit values are realistic defaults vs hardened configs?

### Takeaway
The hop-limit protection only constrains the TTL on the IP packet carrying the IMDSv2 token response, not the HTTP method/header capability of an SSRF — and AWS's own hop-limit semantics mean several ECS networking modes (awsvpc, host) are **not** protected even at hop limit 1, while only `bridge` mode actually adds the extra hop that hop-limit-1 is meant to stop. The "proxy adds a hop" framing is most concretely demonstrated by Latacora's 2025 ECS-on-EC2 research, which is a first-party technical measurement, not speculation.

### Cited Findings
- AWS's own docs define the hop limit as "the number of network hops that the PUT response is allowed to make," configurable from 1 to 64, settable at account, AMI, or instance level with a documented precedence order (instance launch config > account default > AMI default) — [AWS EC2 UserGuide: Configure Instance Metadata options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html)
- When an AMI is registered/modified with `imds-support=v2.0`, AWS automatically sets hop limit to **2** for that AMI's default (this is the documented AWS mechanism for "raise the limit to 2 for containers") — [AWS EC2 UserGuide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html)
- Account-level default hop limit can be set per-region; in AWS's own worked example, an account-level `HttpPutResponseHopLimit` of **1** overrides the AMI's attempt to set 2, because account-level precedence is higher than AMI-level — [AWS EC2 UserGuide](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html)
- Amazon Linux 2023 AMI ships with hop limit **2** by default specifically to allow containers to access IMDS — [Datadog Security Labs: Misconfiguration Spotlight: IMDS](https://securitylabs.datadoghq.com/articles/misconfiguration-spotlight-imds/)
- In the default IMDSv2 configuration, the TCP packet carrying the session token has TTL **1**, "so misconfigured firewalls, NAT devices, and routers won't forward it" — [Datadog Security Labs: Misconfiguration Spotlight: IMDS](https://securitylabs.datadoghq.com/articles/misconfiguration-spotlight-imds/)
- **Exact ECS networking-mode mechanism (Latacora, Oct 2025):** with IMDSv2 required and hop limit 1:
  - `bridge` network mode: IMDS is **blocked** for tasks, because the task's network interface sits behind Docker's virtual bridge network — "the networking interface comes under second hop from the IMDS endpoint."
  - `awsvpc` network mode: IMDS is **reachable** — the task's own ENI is only one hop from 169.254.169.254, so hop limit 1 does not block it.
  - `host` network mode: IMDS is **reachable** — tasks share the host's network namespace directly, so it is also one hop.
  — [Latacora: ECS on EC2: Covering Gaps in IMDS Hardening (Oct 2025)](https://www.latacora.com/blog/2025/10/02/ecs-on-ec2-covering-gaps-in-imds-hardening/)
- Remediations found to actually close the gap, per the same source: for `awsvpc` mode, set `ECS_AWSVPC_BLOCK_IMDS=true` in `/etc/ecs/ecs.config` (AWS-documented); for `bridge` mode, add an iptables rule in the `DOCKER-USER` chain dropping traffic from `docker+` interfaces to `169.254.169.254/32`; for `host` mode, there is **no setting that blocks IMDS while leaving IAM task roles functional** — the only mitigation is a runtime/per-process firewall rule. Latacora also found (via their own testing, not officially documented by AWS) that AWS "ECS Managed Instances" sets `ECS_AWSVPC_BLOCK_IMDS` to `true` by default for `awsvpc` mode — [Latacora](https://www.latacora.com/blog/2025/10/02/ecs-on-ec2-covering-gaps-in-imds-hardening/)
- Security groups and NACLs **cannot** block IMDS access at all, because 169.254.169.254 is a link-local address not subject to VPC routing/ACL enforcement — [Latacora](https://www.latacora.com/blog/2025/10/02/ecs-on-ec2-covering-gaps-in-imds-hardening/)
- IMDSv2 explicitly rejects token-request (PUT) calls that carry an `X-Forwarded-For` header, specifically to defeat misconfigured reverse proxies that would otherwise relay the PUT — [HackTricks via search summary](https://book.hacktricks.xyz/pentesting-web/ssrf-server-side-request-forgery/cloud-ssrf) (page itself could not be fetched directly due to redirects; this claim is corroborated independently by the WebSearch engine's own summary of multiple sources including Datadog's article, which states the same X-Forwarded-For block)
- A tested, negative result: appending `X-HTTP-Method-Override: PUT` to a GET or POST request against `http://169.254.169.254/latest/api/token` does **not** work — both tests returned `405 Method Not Allowed`. Conclusion: IMDSv2's token endpoint does not honor XHMO; this "bypass" only matters if a WAF/reverse-proxy/load-balancer itself parses XHMO and rewrites the method before forwarding — the raw IMDS service does not implement it — [Appsecco: AWS EC2 IMDSv2 versus an esoteric HTTP method](https://appsecco.com/blog/aws-ec2-imdsv2-versus-an-esoteric-http-method)
- A live CTF-style writeup ("Perimeter Leak," Wiz Cloud Security Challenge style) demonstrated a Spring Boot application exposing a generic proxy endpoint that forwarded arbitrary methods/URLs without restriction; because the proxy could issue the PUT with custom headers, the full IMDSv2 token-then-GET flow could be driven through it end-to-end, yielding instance role credentials — [kabinet gitbook: Perimeter Leak writeup](https://kabinet.gitbook.io/ctf-writeup/2026/wiz-cloud-security-challenge/perimeter-leak); mirrored at [writeups-arbaazjamadar-com.pages.dev/perimeterleak](https://writeups-arbaazjamadar-com.pages.dev/perimeterleak)
- Acunetix describes a related "SNI proxy misconfiguration" SSRF class, noting that exploitation through a proxy still requires the proxy to pass through the necessary HTTP method and custom headers — i.e., the proxy must not strip the PUT method or the `X-aws-ec2-metadata-token*` headers for the attack to work — [Acunetix: SNI proxy misconfiguration SSRF vulnerabilities](https://www.acunetix.com/blog/web-security-zone/sni-proxy-misconfiguration-ssrf-vulnerabilities/)
- A lower-confidence secondary source (Aviatrix threat research page, dated 2026) describes a broader campaign of SSRF against "misconfigured proxy servers" reaching 169.254.169.254, citing filter-evasion via "IPv4-mapped IPv6 addresses and long unsigned integer forms" of the metadata IP, and referencing AWS internal bulletins "AWS-2025-007" and "AWS-2025-021" by title only. **This source has internal inconsistencies** (executive summary says proxy servers were attacked; the attack-path narrative describes a web app on EC2 instead) and marks its own Impact assessment as "inferred." Treat as unconfirmed/low-quality until corroborated by the primary AWS bulletins or SANS ISC diary it cites — [Aviatrix: Proxy Server to Metadata Service Attack (2026)](https://aviatrix.ai/threat-research-center/proxy-server-metadata-service-attack-2026/)

### Inferences
- The "proxy adds a hop" bypass is best understood as two distinct failure modes that get conflated in blog writing: (1) a **network-layer** hop addition (e.g., Docker bridge NAT, or a L3 proxy/load balancer sitting between the vulnerable process and the metadata endpoint) that genuinely exceeds a restrictive hop-limit-1 TTL and silently drops the PUT response — this is a reliability/availability failure for the token flow, not something an attacker directly weaponizes by itself; and (2) an **application-layer** SSRF-through-proxy where the proxy is itself the attacker's confused deputy, faithfully relaying the full PUT+headers+GET sequence the attacker crafts — in this case hop limit is irrelevant because the proxy process *is* the one hop away from IMDS and is one hop within whatever limit is configured. A detector should check both: (a) whether the target's hop-limit/network-mode combination structurally permits a token round-trip from the position the SSRF lands in (per the ECS table above), and (b) whether the discovered SSRF primitive allows arbitrary method + arbitrary custom headers to be relayed (if so, hop limit provides no protection regardless of its numeric value).
- Given AWS's documented precedence rules, a detector cannot assume hop limit "2" or "1" from AMI identity alone — the account-level region default can silently override an AMI's setting, and the actual runtime value must be queried (e.g., via `DescribeInstances`/`MetadataOptions` if the pentest has that visibility, or inferred empirically by testing whether a request relayed through N hops succeeds).

### Gaps
- No source gave a single authoritative "default hop limit for a newly launched EC2 instance with no AMI/account preference set" as a bare number — AWS's documentation frames it entirely in terms of precedence (instance > account > AMI) rather than stating an unconditional default. This should be verified directly against `aws ec2 describe-instances --query 'Reservations[].Instances[].MetadataOptions'` behavior or the `run-instances` API default if the pentest tool needs a hard-coded assumption.
- Could not independently verify the hacktricks.wiki cloud-ssrf page's content directly (two redirect hops — book.hacktricks.xyz → hacktricks.wiki → tollbit.hacktricks.wiki — exceeded available fetch attempts); claims attributed to it above are corroborated via the WebSearch tool's own synthesis rather than a direct page read, so confidence is moderate, not high.
- No current (2024-2026) Black Hat/DEF CON/fwd:cloudsec talk specifically on an IMDSv2 hop-limit bypass was found; the closest located talk is fwd:cloudsec **2023**'s "IMDS: The Gatekeeper to Your Cloud Castles (And How to Keep the Dragons Out)" by Liv Matan and Lior Zatlavi, which is background, not a 2024-2026 finding — [Ermetic/fwd:cloudsec 2023](https://ermetic.com/resources/videos/imds-the-gatekeeper-to-your-cloud-castles-and-how-to-keep-the-dragons-out/). No fwd:cloudsec 2024/2025 schedule pages were checked directly (budget-limited); a follow-up researcher should check pretalx.com/fwd-cloudsec-2024 and -2025 directly.

## What is the DNS-rebinding angle against the 169.254.169.254 literal — can a hostname's DNS answer be rebound to the metadata IP after an initial SSRF-filter check passes?

### Takeaway
Yes — this is a well-established, currently-exploited class (TOCTOU between hostname-validation and the actual outbound connection), with a concrete, dated 2026 real-world CVE (Craft CMS, CVE-2026-27127) demonstrating exactly this pattern against cloud metadata services generically (not AWS-specific, but directly applicable). The fix pattern is universally: resolve once, pin the IP, connect to the pinned IP — never re-resolve between check and connect.

### Cited Findings
- The general mechanism: an attacker-controlled domain's DNS answer first returns a public/allowed IP so an SSRF allowlist check passes, then the resolver returns 169.254.169.254 (or another blocked address) on the actual connection — a time-of-check-to-time-of-use (TOCTOU) gap between validation and the real HTTP connection — [Strobes: SSRF testing](https://strobes.co/blog/ssrf-server-side-request-forgery-testing); [Unveil: SSRF defense in depth](https://unveilscan.unveiltech.com/blog/ssrf-defense.html)
- A concrete real-world mechanism example: a rebinding domain configured with DNS TTL of **0**, which resolves to `127.0.0.1` or `169.254.169.254` at actual connect time, defeating a blacklist guard that resolved-and-checked the hostname earlier — cited from a Budibase SSRF advisory summary indexed in a CVE database entry — [Miggo CVE database summary referencing Budibase](https://www.miggo.io/vulnerability-database/cve/CVE-2026-27127)
- **CVE-2026-27127 (Craft CMS, GHSA-gp2f-7wcm-5fhx):** a GraphQL Asset mutation's SSRF protection resolves the hostname separately from the actual HTTP request, creating exactly this TOCTOU race (classified CWE-367, Time-of-check Time-of-use Race Condition). It is explicitly described as a **bypass of an earlier, incomplete fix** (for CVE-2025-68437) that had only blocked IPv6-literal metadata/internal addresses — the rebinding technique reaches "any internal host or cloud metadata service" regardless of address family. Affected versions 5.0.0-RC1 through 5.8.22; fixed in 5.8.23 and 4.16.19. CVSS scores are reported inconsistently across trackers (one source: 7.0; NVD: 6.3/Medium) — [Vulert: CVE-2026-27127](https://vulert.com/vuln-db/CVE-2026-27127); [OpenCVE](https://app.opencve.io/cve/CVE-2026-27127); [GitLab Advisory DB](https://advisories.gitlab.com/composer/craftcms/cms/CVE-2026-27127/)
- Recommended mitigation pattern across sources: resolve the hostname once, validate that single resolved IP, then connect using that pinned IP address directly (never issue a second DNS lookup for the connection) — [Strobes](https://strobes.co/blog/ssrf-server-side-request-forgery-testing); corroborated by the Craft CMS advisory's framing of the root cause as "separate" resolution and request steps.
- Naive IP-literal filters (blocking only the string `169.254.169.254`) are reported as easily evaded using alternate encodings of the same address — decimal, hex, octal, or IPv6-mapped forms — per multiple SSRF testing writeups, though no single canonical example request was captured from a primary source in this research pass — [Strobes](https://strobes.co/blog/ssrf-server-side-request-forgery-testing) (general claim); this specific encoding-evasion claim is widely repeated across SSRF literature but was not verified against a primary AWS-specific advisory in this pass.

### Inferences
- Since IMDSv2's token PUT and the credential GET are two *separate* HTTP round-trips (potentially over two separate TCP connections, each triggering its own DNS resolution if the attacker-controlled SSRF target is a hostname rather than a literal IP), an SSRF-rebinding chain against AWS IMDSv2 specifically does not even need to defeat a single check-then-connect gap — it only needs the *victim application's* outbound HTTP client to re-resolve DNS per-request (the common case for most HTTP clients that don't pin connections), while an attacker's authoritative DNS server flips the answer between the validation-triggering request and the credential-fetching request. A detector/automated check should specifically test: does the target's SSRF sink re-resolve DNS for every outbound request (vs. caching within a single logical operation), and does any allowlist check happen against the hostname rather than the connected socket's peer address?
- Because IMDSv2 itself requires attacker control of the PUT method and two custom headers (TTL header and later the token header) in addition to the destination address, DNS rebinding alone is not sufficient against EC2 IMDSv2 unless the underlying SSRF primitive already grants that level of request control (arbitrary method + arbitrary headers) — rebinding defeats *destination-based* filtering, not IMDSv2's *protocol-based* token requirement. It is far more directly impactful against IMDSv1 (no token, so destination-reachability is the only control an attacker needs) and against non-token-gated services like ECS task-role credentials (see next section) or any other internal service that trusts unauthenticated access from the "it looks like a safe public IP" first-resolution check.

### Gaps
- No AWS-specific (EC2 IMDS literal, as opposed to generic "cloud metadata service") DNS-rebinding CVE or disclosed HackerOne/Bugcrowd report was found in this research pass specifically chaining rebinding → IMDSv2 token flow → credential theft. The Craft CMS case is the strongest concrete 2026 example found but is framework-level/generic-cloud-metadata, not an AWS-IMDSv2-specific case study.
- Could not verify the "alternate IP encoding" bypass claim (decimal/hex/octal/IPv6-mapped 169.254.169.254) against a primary source within budget; it is repeated across secondary SSRF literature but no canonical example payload was captured.

## Does ECS task role metadata require any IMDSv2-style token? What gates access?

### Takeaway
ECS task-role credentials (both the legacy `/v2/credentials/<GUID>` and the current v3/v4 endpoints at 169.254.170.2) require **no IMDSv2-style PUT-for-token flow at all** — a single unauthenticated GET to the correct URI returns full temporary credentials. The only gating mechanism is network-path-based: knowledge of the task-specific credentials-relative-URI path (treated as a secret-ish GUID) combined with being able to reach 169.254.170.2 from the right network position (the task's own network namespace in awsvpc mode, or the shared host network namespace in bridge/host mode).

### Cited Findings
- SDKs locate ECS task-role credentials via the `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` environment variable (ECS) or `AWS_CONTAINER_CREDENTIALS_FULL_URI` (EKS), and fetch them from 169.254.170.2 at that path — there is no documented token-acquisition step analogous to IMDSv2's `/latest/api/token` PUT — [AWS SDK Reference: Container credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html)
- Per Sweet Security's ECScape research: "Amazon ECS tasks retrieve credentials via a local metadata service (169.254.170.2) with a unique credentials endpoint for each task," and the article describes no token or authentication step for these GET requests — [Sweet Security: ECScape — Understanding IAM Privilege Boundaries in Amazon ECS](https://www.sweet.security/blog/ecscape-understanding-iam-privilege-boundaries-in-amazon-ecs)
- Gating mechanism, per the same source: the ECS control plane (not the local agent) calls STS to assume the task role and task execution role, then delivers the resulting credentials to the ECS agent over an authenticated ACS WebSocket; the agent caches them and serves them per-task based on the container's network identity (its unique IP address lets the agent determine which task is asking) — [Sweet Security](https://www.sweet.security/blog/ecscape-understanding-iam-privilege-boundaries-in-amazon-ecs)
- There is a related but distinct value, `AWS_CONTAINER_AUTHORIZATION_TOKEN`/`AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`, used by some SDK container-credential-provider implementations (notably relevant to EKS Pod Identity / some ECS configurations) as a bearer value sent *to* the metadata endpoint; SDK source comments warn this token is itself a bearer credential and must not be sent to a non-local/non-HTTPS host — but this is an EKS/host-validation feature, not a universal ECS requirement, and plain ECS task-role GETs on 169.254.170.2 work without it — [AWS SDK Reference](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html); corroborated by a Medium deep-dive — [Security Nuances of the AWS Metadata Service in Container Workloads](https://medium.com/simply-cloudsec/security-nuances-of-the-aws-metadata-service-in-container-workloads-680be43b63e)
- **ECScape privilege-escalation chain (named technique, no CVE assigned):** (1) a container with unblocked IMDS access queries 169.254.169.254 and gets the *host's EC2 instance-profile* credentials; (2) using those, it calls `ecs:DiscoverPollEndpoint`; (3) it gathers the cluster ARN from task metadata and the container-instance ARN from the agent's introspection API (reachable from inside the container); (4) it opens a SigV4-signed WebSocket to the discovered ACS endpoint using the instance role's `ecs:Poll` permission with `sendCredentials=true`, impersonating the real ECS agent; (5) the ECS control plane then pushes **every** task's credentials on that host — including other tenants' task-role and execution-role credentials — to the impersonating container. AWS reviewed this as a "design consideration," not a vulnerability, assigned **no CVE**, but updated documentation and credited the researchers — [Sweet Security: ECScape](https://www.sweet.security/blog/ecscape-understanding-iam-privilege-boundaries-in-amazon-ecs)
- The v2 task metadata endpoint is deprecated/no-longer-actively-maintained; AWS recommends v4 (`ECS_CONTAINER_METADATA_URI_V4`) going forward — [AWS ECS Developer Guide: Task metadata endpoint v2](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v2.html)
- The ECS Local Container Endpoints project documentation notes the v2 metadata/credentials endpoints require that 169.254.170.2 be made reachable to the container (i.e., it is a network-namespace/routing exposure problem, not an auth problem) — [awslabs/amazon-ecs-local-container-endpoints docs](https://github-redirect.dependabot.com/awslabs/amazon-ecs-local-container-endpoints/blob/mainline/docs/setup-networking.md)

### Inferences
- For an automated SSRF-to-credential-theft detector: once SSRF (or any arbitrary-outbound-request primitive from inside an ECS task) can reach `169.254.170.2<task's AWS_CONTAINER_CREDENTIALS_RELATIVE_URI path>`, a **single unauthenticated GET** is sufficient — there is no PUT/token prerequisite to simulate, unlike EC2 IMDSv2. The detector's check for "is this ECS metadata reachable and exploitable" should therefore be binary (reachable → exploitable), whereas the EC2 IMDSv2 check needs the two-step token dance.
- Treat ECScape as the most significant 2024-2026 finding for ECS specifically: it shows that even with IMDSv2 fully hardened on the underlying EC2 instance, an unrelated SSRF-reachable container with any outbound IMDS access becomes a path to *every other tenant task's* credentials on that host, via the ECS control-plane trust model rather than via the metadata endpoint's auth. This should be encoded as a distinct check from plain IMDS/task-credential SSRF: "can this task reach 169.254.169.254 (host IMDS) at all, and if so what IAM permissions does the resulting instance-profile role have (specifically `ecs:DiscoverPollEndpoint` and `ecs:Poll`)?"

### Gaps
- No official AWS documentation statement was found explicitly confirming "ECS task credential endpoints never require a token" as a blanket policy statement (the absence of token-flow documentation is treated here as strong circumstantial evidence, corroborated by multiple independent research write-ups, but not an explicit AWS security-bulletin confirmation).
- Could not determine within budget whether EKS's `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` mechanism is used by default in modern (2024-2026) EKS Pod Identity deployments in a way that would gate access similarly to IMDSv2 — flagged as an area needing a dedicated EKS-focused follow-up, since this task's scope was EC2/ECS/Lambda per the assignment.

## Lambda/Fargate metadata-retrieval quirks vs standard EC2 IMDSv2

### Takeaway
Standard AWS Lambda functions do not rely on IMDS or the ECS container-credentials endpoint at all under normal operation — credentials are injected directly as environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`) at initialization, making classic "SSRF-to-169.254.169.254" attacks against Lambda largely ineffective by default; this changes under Lambda SnapStart, which switches the Java runtime to the container-credential-variable pattern instead. Fargate (ECS launch type) uses the same 169.254.170.2 task-credentials mechanism described above, gated only by network-namespace reachability, with AWS's official guidance to use the v4 endpoint (`ECS_CONTAINER_METADATA_URI_V4`) for Fargate platform version 1.4.0+.

### Cited Findings
- Lambda's execution-role credentials are injected into the function's environment at initialization, and environment variables are a high-priority credential source in the SDK credential-resolution chain — [DEV Community: AWS credentials for serverless](https://dev.to/aws-builders/aws-credentials-for-serverless-2f24)
- A hands-on test of a Lambda container-image function found `AWS_CONTAINER_CREDENTIALS_FULL_URI` was **not set**, and direct curl requests to both 169.254.170.2 and 169.254.169.254 from inside the Lambda execution environment **failed** — concluding that assumptions carried over from ECS containers (that these metadata addresses are reachable) do not hold for standard Lambda — [Classmethod (dev.classmethod.jp): Lambda container image environment variables check](https://dev.classmethod.jp/articles/container-image-lambda-environment-variables/) (single hands-on test, not official AWS documentation — treat as a useful data point, not a guarantee across all Lambda runtime/configuration combinations)
- With AWS Lambda **SnapStart** enabled, the Java runtime switches to using the container-credential environment variables (`AWS_CONTAINER_CREDENTIALS_...`) instead of the standard access-key environment variables used otherwise — [AWS re:Post thread](https://repost.aws/questions/QU1HDpHlmVRH2sWxa-5MCGKg/unable-to-load-credentials-from-system-settings-lambda-with-snapstartp-enabled)
- For Fargate (ECS launch type), AWS's official guidance for platform version 1.4.0 and later is to use the v4 task metadata endpoint via the `ECS_CONTAINER_METADATA_URI_V4` environment variable — same mechanism and same lack of token requirement as ECS-on-EC2 — [AWS ECS Developer Guide: Task metadata endpoint v4 for tasks on Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v4-fargate.html)

### Inferences
- An automated detector targeting "Lambda SSRF → credential theft" should **not** assume the IMDS/ECS-metadata attack surface applies by default; it should instead check whether the compromised/SSRF-reachable process can read process environment variables directly (a different vulnerability class — e.g., arbitrary file read of `/proc/self/environ`, log/error-message leakage of env vars, or a deserialization/RCE bug) since that is where Lambda credentials actually live in the common case. The detector should flag SnapStart-enabled Java Lambdas as a distinct sub-case where the ECS-style container-credentials URI *does* become relevant and worth probing.
- Fargate should be treated identically to ECS-on-EC2's `awsvpc` mode for detection purposes (same v4 endpoint, same reachability-only gating, no token) — Latacora's awsvpc findings likely transfer directly, though this was not independently confirmed for Fargate specifically within this research pass.

### Gaps
- No primary AWS documentation was found explicitly stating whether 169.254.169.254 (EC2-style IMDS) is reachable or blocked at the network level inside the standard (non-container-image) Lambda execution environment for all runtimes — the one data point found (Classmethod) tested only a container-image Lambda and found it unreachable; this has not been confirmed as AWS's documented/guaranteed behavior across the Lambda fleet, zip-based Lambdas, or Lambda@Edge.
- Could not find a dedicated 2024-2026 CVE, HackerOne report, or conference talk specifically about a Lambda or Fargate metadata-retrieval quirk being exploited; this sub-topic rests on documentation/testing inference rather than a disclosed real-world case.

## Specific 2024-2026 CVEs, disclosed writeups, or conference talks demonstrating a live IMDSv2 bypass (excluding the 2019 Capital One IMDSv1 case)

### Takeaway
No disclosed case found in this research actually bypassed EC2 IMDSv2's token mechanism itself in 2024-2026 — every concrete, dated incident or research finding either (a) targeted IMDSv1-only targets, (b) routed around IMDSv2 entirely via a non-token-gated metadata surface (ECS task roles via ECScape), (c) exploited DNS-rebinding/TOCTOU against a generic cloud-metadata-reaching application control (Craft CMS), or (d) is a negative result confirming IMDSv2 held (the Pandoc CVE-2025-51591 case, where Wiz explicitly states IMDSv2 neutralized the attack). This is itself a notable finding: IMDSv2's token requirement appears to have held up against disclosed real-world attempts in this window; attackers instead route around it via adjacent surfaces.

### Cited Findings
- **CVE-2025-51591 (Pandoc SSRF, exploited in the wild, reported by Wiz):** Pandoc renders `<iframe>` tags during HTML-to-PDF conversion; an attacker-controlled iframe `src` pointing at 169.254.169.254 could reach metadata paths (`/latest/meta-data/iam/info`, `/latest/meta-data/iam`) when the calling application omitted Pandoc's recommended `raw_html`/`sandbox` protections. Wiz states explicitly: **"the attack was neutralized by the mandatory enforcement of IMDSv2"** — the iframe's stateless GET could not supply the required session token, so the attacker could reach other internal hosts but not steal credentials from an IMDSv2-enforced instance; Wiz notes IMDSv1 would likely have led to compromise — [Wiz: IMDS Abused — Hunting Rare Behaviors to Uncover Exploits](https://www.wiz.io/blog/imds-anomaly-hunting-zero-day)
- **ECScape (Sweet Security, 2025, no CVE):** detailed in the ECS section above — routes around IMDSv2 entirely by using the host's *instance-profile* credentials (obtained via unblocked IMDSv1/v2-optional access, or via any route to 169.254.169.254) to impersonate the ECS agent and harvest every co-located task's credentials over the ACS WebSocket channel. AWS classified this as a design consideration, not a vulnerability; no CVE was assigned — [Sweet Security: ECScape](https://www.sweet.security/blog/ecscape-understanding-iam-privilege-boundaries-in-amazon-ecs)
- **CVE-2026-27127 (Craft CMS, DNS-rebinding SSRF bypass of cloud-metadata protection):** detailed in the DNS-rebinding section above; a generic-cloud-metadata-reaching bypass (fixed Craft CMS 5.8.23/4.16.19), not AWS-IMDSv2-specific but directly demonstrates the rebinding mechanism against metadata-protection filters in the 2026 window — [Vulert](https://vulert.com/vuln-db/CVE-2026-27127)

## HTTP response signatures distinguishing "IMDSv2 enabled and enforced" from "IMDSv2 optional/not enforced" when probed externally via SSRF

### Takeaway
The clearest, most specific signal is the exact combination of status code **401 Unauthorized** plus the response header **`X-aws-ec2-metadata-token-required: true`** on a tokenless GET — this combination only appears when `HttpTokens=required` (IMDSv2 enforced); under `HttpTokens=optional`, the same tokenless GET succeeds (200) exactly as it would under pure IMDSv1.

### Cited Findings
- With `HttpTokens` set to `optional`, both unauthenticated (IMDSv1-style) and token-bearing (IMDSv2-style) requests succeed against the same instance — [multiple corroborating sources via WebSearch synthesis, including Datadog Security Labs and Orca Security cloud-risk pages](https://securitylabs.datadoghq.com/cloud-security-atlas/vulnerabilities/ec2-instance-no-imdsv2-enforced)
- With `HttpTokens` set to `required`, a tokenless request to a metadata path returns **401 Unauthorized** and includes the response header `X-Aws-Ec2-Metadata-Token-Required: true` — this header is described as a more specific/reliable signal than the bare status code alone, since other failures (e.g., disabled IMDS entirely) can also produce non-200 responses — [synthesized from search results; corroborated independently by an Ignition (CoreOS/Fedora) source-code patch comment noting that probing `/latest` under IMDSv2-only returns 401, prompting that tool to instead probe the token URL directly](https://git.almalinux.org/rpms/ignition/raw/commit/07b6f5cc823e04bad67a62b8741119506395a995/internal-providers-aws-probe-the-IMDS-token-URL.patch)
- A non-401 failure mode (e.g., connection refused, or a different error such as 500) is reported as more likely to indicate IMDS is disabled entirely (`enabled=false`) rather than IMDSv2 enforcement specifically — distinguishing "disabled" from "v2-enforced" matters for a detector trying to decide whether any metadata attack surface exists at all — [synthesized from search results, not independently verified against a single primary AWS source in this pass]

### Inferences
- A practical external-probe algorithm for the pentest tool, given an identified SSRF primitive that can at minimum issue an arbitrary GET with arbitrary path (but not necessarily arbitrary headers/method):
  1. GET `/latest/meta-data/` with no special headers.
     - `200` + metadata body → IMDSv1 reachable / IMDSv2 optional (full bypass available immediately, no token needed).
     - `401` + header `X-aws-ec2-metadata-token-required: true` → IMDSv2 is enforced; a tokenless path is dead. Proceed to test whether the SSRF primitive can also set the `X-aws-ec2-metadata-token-ttl-seconds` header and issue a PUT (if yes, the attack chain continues; if the SSRF can only do GET with fixed headers, this specific instance's IMDS is not exploitable via this primitive, though ECS/Lambda adjacent surfaces may still be worth checking per the sections above).
     - Connection error / other non-401 — IMDS likely disabled outright, or the SSRF cannot reach the link-local range at all (worth differentiating in logging, since "disabled" and "blocked by network path" look identical from outside).
  2. In parallel, since this probe is "free" once GET-to-arbitrary-path is established, also probe ECS's `169.254.170.2` and the task-credentials relative URI pattern (if any ECS-style env var disclosure or default-path guessing is feasible) as a token-free alternative, per the ECS section above.

### Gaps
- Could not verify these header/status claims against AWS's own official IMDS documentation page directly within budget (the UserGuide pages fetched in this session covered configuration semantics but not the exact wire-level error response format); recommend a follow-up direct fetch of AWS's "instancedata-data-retrieval" or IMDS troubleshooting doc to confirm the exact header name/casing and status code as an authoritative primary source before hard-coding it into a detector.
